# Context-aware suggestions

The suggestion bar reads the sentence, the person and — when one is live — the
message on screen, instead of reading only the letters under the cursor.

## The problem, measured

`Bar/typing/corpus.json` has held 90 frozen moments mid-typing since it was
written, and nothing had ever run the engine against them. Building that harness
first was the most useful step in this work: it turned "the bar feels wrong" into
a number, **47/76**, and a list of exactly which moments were failing and why.

| Gap | What it looked like |
|---|---|
| No frequency prior anywhere | `helo` → `helot`; `הכתו` → `הכתום` ("the orange") over `הכתובת` ("the address") |
| Next-word was a 26-key table | Every unmatched English sentence answered `I · The · We` |
| Nothing learned from the user | The personal dictionary was hand-typed in Settings and that was all |
| No Hebrew morphology | `לעבו` → two unrelated verbs, never `לעבודה`; `מהג` → `מהגרים` |
| Wrong-layout typing unhandled | `akuo` meaning `שלום` got nothing, from any keyboard on iOS |
| Screen context ignored | `ScreenContextSession` knew the message; the bar never asked |

## Shape

Two tiers that own different things and cannot fight.

```
                    ┌─────────────────────────────────────┐
   every keystroke  │  TIER 1  local, synchronous, ~1ms   │
   ────────────────►│  owns all 3 slots and the BOLD one  │──► bar
                    └─────────────────────────────────────┘
                                      │
                     300ms idle       ▼
                    ┌─────────────────────────────────────┐
                    │  TIER 2  async refine, 200-600ms    │──► slots 1 & 2 only
                    │  never slot 0, never the bold slot  │
                    └─────────────────────────────────────┘
```

**The rule that makes a second tier safe to have at all: it can never change what
the space bar commits.** Autocorrect stays entirely local and deterministic. A
model may improve the *options*; it may never change the *default* while somebody
is looking at the bar deciding whether to press space.

## Tier 1

- **`SeedLanguageModel`** — bundled rank order and bigrams for English and Hebrew,
  from `Resources/LanguageModel.json`, generated by
  `Scripts/generate-language-model.py`. Hand-authored order, disclosed as such in
  the resource itself; the only claim it makes is *rank*. It also serves
  completions (`Wolt`, `Dizengoff`, `Herzliya` — words `UITextChecker` has never
  heard of) and one-edit neighbours.
- **`HebrewMorphology`** — the clitic splitter. One seed entry for `עבודה` serves
  `לעבודה`, `בעבודה`, `מהעבודה`.
- **`LayoutTransposition`** — the word you meant when you typed it on the wrong
  keyboard. Deterministic, gated hard: the result must be a *common* word and what
  was typed must not already be one.
- **`PersonalLanguageModel`** — word counts and word-pair counts, App Group
  backed. Never sentences, never in a credential field, never off the device. Two
  sightings before it ranks, three before it protects.
- **`SuggestionEngine+Candidates`** — provenance-based scoring, replacing the
  append order that used to *be* the ranking.

## Tier 2

- **`TextPrediction`** — its own protocol rather than a fifth `AIAction`, because
  `AIAction` is `CaseIterable` and drives the action row and the layout editor: a
  `.predict` case would draw a Predict button the user can never press.
- **`CloudIntelligence+Prediction`** covers every language including Hebrew;
  **`FoundationModelsEngine+Prediction`** covers the scripts Apple lists, free and
  on-device. No best-effort third branch — three words in the wrong language are
  noise above a keyboard, not a degraded answer.
- **`PredictiveRefiner`** — debounce, bounded cache, and the guards.

## Privacy

Learning is on by default and the Settings row says what is kept in those words.
It is refused in credential fields (`SecureField`, the same question screen
reading asks), refused when the toggle is off, capped and decayed, and clearable
from Settings. Only the real keyboard extension writes to it —
`KeyboardController.personal` is a throwaway everywhere else, which is what stops
the app's onboarding playground and the test suite from filling somebody's
vocabulary with scripted words.

## Latency

`run.sh` reports it, because the design rests on tier one being cheap enough for
every keystroke and the budget people notice is about 20 ms for the whole key
press, drawing included.

Measured over four runs of the 90 entries, warm, on the iOS 26.2 Simulator:
**median 1.1-1.3 ms, worst entry 10-16 ms.** Which entry is slowest changes
between runs of identical code, and one run produced a 27 ms outlier that did not
reproduce — so trust the shape, not the number. The slow ones are always Hebrew
words where the seed has nothing and more than one clitic reading has to be put to
`UITextChecker`. The **first** call in a language is separate and much larger
(~70-280 ms) because Apple builds that language's lexicon then; a user pays it
once per keyboard session.

Two things were fixed after measuring rather than before. The seed list was being
folded on every keystroke — 785 English words, twice each, inside the prefix scan
— and is now folded once at load. And a split Hebrew reading no longer asks
`UITextChecker` when the seed already answered it, which took the worst case down
by roughly a third with no change to the score.

## Result

**73/76**, from 47/76. 26 corpus entries fixed, none broken. 352 unit tests pass.

Three remain, each for a stated reason rather than an unknown one:

- `apos-09` (`were` → `we're`) — `were` has an ordinary reading and is
  deliberately not in the contraction table. Deciding it needs the sentence; that
  is the async tier's job.
- `typo-10`, `typo-11` — the right Hebrew word *is* offered in slot 1 and
  deliberately not committed, because Apple's Hebrew checker reports the typo as a
  real word and this engine does not replace a word two dictionaries accept.

## What is not done

Tier 2 has never been scored, because the corpus is a Tier 1 exam: 90 synchronous
questions with no pauses in them. Its mechanism, guards and swap rules are
unit-tested; the *quality* of its answers is not measured, and saying otherwise
would be the kind of claim this repo's README exists to prevent. Measuring it
needs a second corpus shaped around pauses and live screen context.
