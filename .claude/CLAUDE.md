# AIKeyboard

A mock Hebrew/English iOS keyboard with AI text actions, dictation, and screen-context replies. Built with Swift, SwiftUI, UIKit and a local Swift package; no third-party dependencies.

## Commands

```bash
# Build
xcodebuild build -project AIKeyboard.xcodeproj -scheme AIKeyboard \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

# Test (add TEST_RUNNER_SHOT_DIR=/tmp/shots to keep the screenshots)
xcodebuild test -project AIKeyboard.xcodeproj -scheme AIKeyboard \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

# Format (the PostToolUse hook already does this per edited file)
xcrun swift-format --in-place --recursive \
  AIKeyboard AIKeyboardExtension AIKeyboardBroadcast AIKeyboardUITests AIKeyboardCoreTests Packages
```

No linter is configured.

## Gotchas

- **Most things are mocked on purpose.** `MockSuggestionEngine`, `MockDictation` and `MockScreenContext` are still the swap points; `README.md` carries the mock-to-real table. Do not "fix" a mock by making it real without being asked.
- **The AI text actions are real.** `MockAI` is gone; `RoutedIntelligence` picks between `FoundationModelsEngine` (on-device) and `CloudIntelligence`. The app's cloud transport is `BackendTransport`, which posts to a backend URL read from settings — the app holds no provider credential, because anything in the bundle is extractable. Bar scoring uses a second transport, `Bar/ai-text/harness/VertexTransport.swift`, which calls Vertex AI directly with a gcloud token; it lives outside every target and must stay there. Two things to know before touching it: Apple's on-device model **does not support Hebrew** — `SystemLanguageModel.supportedLanguages` has no `he`, and a session whose *instructions* are in Hebrew is rejected outright with `unsupportedLanguageOrLocale`, even for English input. And every iOS Simulator reports `availability == .available` and then throws `ModelManagerError 1026` on the first call, so on-device answers never appear in a simulator run. Measure against macOS with `Bar/ai-text/harness/run-real.sh`.
- **Reply and Rewrite are vetted before they reach the panel.** `OutputGuard` drops any generated option that names a number, a weekday or a timing promise ("as soon as I can", "בהקדם") the message never contained, and — when the model reports that the message points at something it never names — any reply that agrees without asking what it is. If nothing survives the action fails with `.invented` rather than showing a fabricated commitment in the user's voice. Two consequences when changing this code: the schema field order is load-bearing (`unnamed`/`addressee` before the three replies, `decision`/`specifics` before the three versions — the model fills fields in order, and `VertexTransport` sends `propertyOrdering` to make Vertex do the same), and the word lists are deliberately narrow, checked against all 58 reference answers with no false positives. A broader rule rejects good writing: the reference answer to the corpus's own hallucination probe declines with "it won't be today".
- **Fix is held to the mistakes it names.** `EditScope` is the Fix-side counterpart to `OutputGuard`: Fix generates nothing, so the user's own words are the baseline and every changed word is a claim that the word was wrong. `CloudIntelligence.fix` asks for a `corrections` list *before* the corrected text (field order load-bearing, same as Rewrite's `decision`), and `EditScope.applied` undoes any change that list does not name — a list saying `none` returns the message byte for byte. `FoundationModelsEngine` deliberately does **not** ask: given the same two-field schema, Apple's on-device model got worse at the text it was already good at (it started dropping words — "can you send me the id" came back as "you send me the id") and English Fix fell from 18/24 to 14/24 over the corpus. That path calls `EditScope.repaired` instead, which does only the three things no model gets right: an expanded contraction goes back to a contraction (`dont` is a typo for `don't`, not shorthand for `do not`), a Hebrew word respelled into its other accepted orthography goes back (`והכל`/`והכול` are both correct — this is the change that makes people switch autocorrect off), and a full stop is never *added* to the end of a Hebrew message. That last rule is corpus-derived: all five references that add a terminal full stop are English-only, and not one of the sixteen Hebrew or code-switched references adds one. Punctuation and capitalisation are invisible to the scope check on purpose, because the references make both without ever calling them out. Every rule was checked against all 24 Fix references with no false positives; `EditScopeTests` carries that table.
- **One corpus run is not evidence.** Two runs of *identical* code disagree on ~17 of the 58 entries and swing the total by 1–5 points; `he-en` alone moved 14/17 to 10/17 with nothing changed. Judge and model are both sampled. Compare at least two runs per side before believing a delta, and read per-entry verdicts rather than the total. Several of the "regressions" chased in round 3 turned out to be this.
- **The cloud model thinks, but on a budget.** `VertexTransport` sets `thinkingBudget: 512`. Thinking *off* (`0`) transliterates Latin-script loanwords into Hebrew and destroys the code-switching this product exists for; thinking *unbounded* put the cloud tail at 17–18s, which is too slow to sit inside a keyboard. Capped at 512 the tail is under 4.4s and the corpus score went up, not down. `VERTEX_THINKING_BUDGET=-1` restores dynamic thinking if you want to re-measure.
- **Apple's on-device stack has no Hebrew, in all three places it matters.** Foundation Models does not list it, `SpeechTranscriber` does not list it, and Vision's text recogniser does not list it — 30 languages, identical across `VNRecognizeTextRequest`, the newer Swift `RecognizeTextRequest` and VisionKit Live Text, on both iOS and macOS. Arabic *is* in that list, so none of this is a right-to-left limitation. `VisionLanguageTests` pins the Vision half from the simulator; if it ever fails, that is permission to delete most of `CloudScreenReader`.
- **Screen reading routes without ever naming a script, and that is the point.** The router cannot ask "is this screen Hebrew", because the only component that reads text is the one blind to Hebrew. `VisionScreenReader` compares text regions *found* by `VNDetectTextRectanglesRequest` — which finds text by shape, language-agnostically — against regions actually recognised. Coverage ≥ 0.97 and mean confidence ≥ 0.90 keeps 9 of 12 English screens on device and lets **zero** Hebrew or mixed screens through. Both numbers come from `Bar/screen-context/harness/coverage.swift` over all 30 images; loosening coverage to 0.95 gains one English screen and admits a mixed one, which is the wrong trade. The gate is asymmetric on purpose: a misread Hebrew screen is a confident wrong reply in the user's name, an unnecessary cloud call is five seconds.
- **`VisionScreenReader` reads bubble geometry, so it accepts only two-sided layouts.** Slack, Teams and mail threads print every message against one margin with the author on a label above it, leaving no geometry to say who sent what. Side is read from which *margin* a bubble hugs, never from the line's centre — a long line in a one-sided layout crosses the middle of the screen and a centre test calls it outgoing, which was wrong on every Slack screen measured.
- **Vision is not the same on iOS as on macOS, so never quote a macOS reading of it as the product's number.** Same sources, same pixels, same thresholds: macOS accepts 9 of the 30 bar frames and answers 5, all 5 right. The iOS Simulator accepts 10, answers 7, and **3 of those are wrong** — including `wa-07`, the one frame whose only correct answer is silence, and `sl-05`, which comes back as keyboard key caps. An earlier version of this file claimed "it answers only when it is right"; that was a macOS-only claim reported as the product's. `harness/run-reader.sh` builds with `xcrun -sdk macosx` and is the macOS reading; `ScreenContextBarTests` is the iOS one and is the one that counts. The property the routing rests on survives both: zero Hebrew and zero mixed frames are accepted on device on either platform.
- **On iOS, routing through Vision scores *worse* than asking the cloud.** Measured end to end through `ScreenContextSession.submit`: routed gives sender 26/30, language 28/30, message 16/30 exact and 24/30 within 90%. Cloud alone gives 29 / 29 / 19 / 26. The on-device path is not free accuracy that happens to be private; on this bar it costs 3 points of sender and 3 of exact message. Weigh that against the privacy gain rather than assuming the gain is one-sided.
- **Two refusals, and they are not the same refusal.** `VisionScreenReader.interpret` returns nil for *nothing worth replying to* (a voice note) and throws `.notReadableOnDevice` for *I could not read this layout*. Collapsing both into nil made `RoutedScreenReader` treat "I cannot see" as "nothing is there", so `sl-01` and `sl-03` — plain answerable English the cloud transcribes correctly — silently offered the user nothing. Worth 2 points on every axis.
- **The screen-context prompt's shape is measured, not stylistic.** Same lesson as Rewrite and Fix: `messages` is a *list* the model must finish before naming an answer, because every wrong answer on the bar was a bubble one to four positions above the newest — enumerating took sender from 21/30 to 29/30. `script` and `language` are separate fields because they disagree on exactly the code-switched sentences this product exists for; collapsing them scored 22/30, splitting them 29/30. Flattening the list into a JSON string costs 7 points, which is why `CloudField` carries nested `items`. Two rules that *sound* right measured worse and are deliberately absent — a paragraph on bubble tint and edge, and "a printed name always means incoming"; `CloudScreenReader`'s doc comment lists both so they do not get re-added.
- **ScreenCaptureKit is real on iOS, and still not available here.** It is `iOS 27.0+`, and Apple states plainly that it replaces ReplayKit and that a broadcast extension is no longer necessary. But measured against the installed toolchain (Xcode 26.2), `ScreenCaptureKit.framework` is absent from both `iPhoneOS26.2.sdk` and `iPhoneSimulator26.2.sdk` while present in `MacOSX26.2.sdk`, and `ReplayKit.framework` is present in the iOS SDK as the control. So `import ScreenCaptureKit` does not compile for iOS at all until an Xcode with the iOS 27 SDK is installed. Reading a frame is done and measured; *getting* one is not implemented on either API. `ScreenContextSession.submit(_:appName:appIcon:)` is the seam.
- **The keyboard UI lives in `Packages/AIKeyboardCore/`, not in `AIKeyboardExtension/`.** The extension is a thin host so the companion app can render the same keyboard in onboarding and the playground. New keyboard UI goes in the package, or it stops working in the app.
- **Targets use `PBXFileSystemSynchronizedRootGroup`** (`objectVersion = 77`), so any file dropped into `AIKeyboard/`, `AIKeyboardExtension/` or `AIKeyboardUITests/` is compiled into that target with no `.pbxproj` edit. A file that must *not* compile needs a `membershipExceptions` entry, as `AIKeyboardExtension/Info.plist` has.
- **`swift build` inside `Packages/AIKeyboardCore` fails on macOS.** `Package.swift` declares `platforms: [.iOS(.v17)]` and the sources import UIKit and AudioToolbox, so the package only builds through the Xcode project against an iOS Simulator destination.
- **The App Group is real, and the keyboard needs Full Access to use it.** Both targets carry `com.apple.security.application-groups` for `group.com.nitai.aikeyboard` via `CODE_SIGN_ENTITLEMENTS`. iOS only grants a keyboard extension the shared container when the user allows Full Access, which is why `RequestsOpenAccess` is `true` in `AIKeyboardExtension/Info.plist`. `SharedStore.storage` reports `.appGroup` or `.processLocal` — it never pretends. Prove the round trip with `Scripts/prove-app-group.sh`; `UserDefaults(suiteName:)` being non-nil proves nothing, because it succeeds without the entitlement.
- **On the simulator, entitlements live in the binary, not the signature.** `codesign -d --entitlements` prints an empty dict for a simulator build; read `__TEXT,__entitlements` from the Mach-O instead, as the prove script does.
- **UI tests that drive the keyboard need an uncontended simulator.** Two `xcodebuild test` runs against the same device kill each other's runners, which reports as "crashed with signal kill" rather than a test failure.
