# AIKeyboard

A mock Hebrew/English iOS keyboard with AI text actions, dictation, and screen-context replies. Built with Swift, SwiftUI, UIKit and a local Swift package; no third-party dependencies.

## Commands

```bash
# Build
xcodebuild build -project AIKeyboard.xcodeproj -scheme AIKeyboard \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

# Test (add TEST_RUNNER_SHOT_DIR=/tmp/shots to keep the screenshots)
xcodebuild test -project AIKeyboard.xcodeproj -scheme AIKeyboard \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'

# Format (the PostToolUse hook already does this per edited file)
xcrun swift-format --in-place --recursive \
  AIKeyboard AIKeyboardExtension AIKeyboardBroadcast AIKeyboardUITests AIKeyboardCoreTests Packages
```

No linter is configured.

## Gotchas

- **Two mocks are left, and only one of them is waiting for work.** `MockScreenContext` is the scripted demo the app plays when no broadcast is running, and it yields to a real session the moment one appears. `MockDictation` is blocked on something narrower than it first looks, and getting the distinction wrong wastes a day in either direction. The **keyboard** cannot reach the microphone — Apple's custom-keyboard guidance says so verbatim and Full Access does not lift it. But **Gboard ships voice typing on iOS** by handing off to its own app, so the feature is achievable, and the architecture is the one screen context already uses: record in the containing app, cross the App Group, keyboard reads. The unsettled part is the trigger: `UIApplication` is unavailable to extensions and the responder-chain `openURL` workaround is explicitly disallowed by Apple. The evidence is quoted above `MockDictation` in `MockIntelligence.swift`; read it before trying to fix it, and do not repeat "dictation is impossible in a keyboard" — that was written here once and it is not what the evidence says. `MockSuggestionEngine` is gone, replaced by `SuggestionEngine` over `UITextChecker` and `UILexicon`. `README.md` carries the table.
- **The AI text actions are real.** `MockAI` is gone; `RoutedIntelligence` picks between `FoundationModelsEngine` (on-device) and `CloudIntelligence`. The app's cloud transport is `BackendTransport`, which posts to a backend URL read from settings — the app holds no provider credential, because anything in the bundle is extractable. **`cloudBackendURL` has exactly one editor, and both features that need it point at that one name.** It is `CloudModelView`, reached from `Settings › AI › Cloud model` and from a row on Screen Context; `BackendTransport.settingsPath` is that string, and the four failures that dead-end on a missing backend (`unsupportedLanguage`, `cloudNotConfigured`, `deviceNotSupported`, `ScreenContextEndReason.notConfigured`) all print it. It used to live only on the Screen Context screen under "Where the screen is read", so on a stock install every Hebrew Fix, Rewrite, Tone and Reply failed forever while naming nowhere to go — Hebrew is outside `supportedScripts`, there is no cloud, and the best-effort branch is rejected because its session instructions are Hebrew. Anything that asserts the cloud works has to measure it: `SetupState.cloudConfigured`, not a Full Access tick. Bar scoring uses a second transport, `Bar/ai-text/harness/VertexTransport.swift`, which calls Vertex AI directly with a gcloud token; it lives outside every target and must stay there. Two things to know before touching it: Apple's on-device model **does not support Hebrew** — `SystemLanguageModel.supportedLanguages` has no `he`, and a session whose *instructions* are in Hebrew is rejected outright with `unsupportedLanguageOrLocale`, even for English input. And every iOS Simulator reports `availability == .available` and then throws `ModelManagerError 1026` on the first call, so on-device answers never appear in a simulator run. Measure against macOS with `Bar/ai-text/harness/run-real.sh`.
- **Reply and Rewrite are vetted before they reach the panel.** `OutputGuard` drops any generated option that names a number, a weekday or a timing promise ("as soon as I can", "בהקדם") the message never contained, and — when the model reports that the message points at something it never names — any reply that agrees without asking what it is. If nothing survives the action fails with `.invented` rather than showing a fabricated commitment in the user's voice. Two consequences when changing this code: the schema field order is load-bearing (`unnamed`/`addressee` before the three replies, `decision`/`specifics` before the three versions — the model fills fields in order, and `VertexTransport` sends `propertyOrdering` to make Vertex do the same), and the word lists are deliberately narrow, checked against the 106 primary reference texts with no false positives. Not against every accepted *alternate*, and one of those is a genuine false positive worth knowing about: `tn-mix-01`'s alternate ends `אני אגיע לזה בהקדם`, which the `promises` list rejects, and Tone does run through `OutputGuard.addedSpecifics`. So the guard would drop an answer this corpus accepts. A broader rule rejects more good writing still: the reference answer to the corpus's own hallucination probe declines with "it won't be today".
- **Fix is held to the mistakes it names.** `EditScope` is the Fix-side counterpart to `OutputGuard`: Fix generates nothing, so the user's own words are the baseline and every changed word is a claim that the word was wrong. `CloudIntelligence.fix` asks for a `corrections` list *before* the corrected text (field order load-bearing, same as Rewrite's `decision`), and `EditScope.applied` undoes any change that list does not name — a list saying `none` returns the message byte for byte. `FoundationModelsEngine` deliberately does **not** ask: given the same two-field schema, Apple's on-device model got worse at the text it was already good at (it started dropping words — "can you send me the id" came back as "you send me the id") and Fix fell from 18/24 to 14/24 over the corpus — that denominator is all 24 Fix entries in every language, not the 10 English ones. That path calls `EditScope.repaired` instead, which does only the three things no model gets right: an expanded contraction goes back to a contraction (`dont` is a typo for `don't`, not shorthand for `do not`), a Hebrew word respelled into its other accepted orthography goes back (`והכל`/`והכול` are both correct — this is the change that makes people switch autocorrect off), and a full stop is never *added* to the end of a Hebrew message. That last rule is corpus-derived: all four Fix references that add a terminal full stop are English-only, and not one of the fourteen Hebrew or code-switched Fix references adds one. (`EditScopeTests` says four and is right; this line said five.) Punctuation and capitalisation are invisible to the scope check on purpose, because the references make both without ever calling them out. Every rule was checked against all 24 Fix references with no false positives; `EditScopeTests` carries that table.
- **One corpus run is not evidence.** Two runs of *identical* code disagree on ~17 of the 58 entries and swing the total by 1–5 points; `he-en` alone moved 14/17 to 10/17 with nothing changed. Judge and model are both sampled. Compare at least two runs per side before believing a delta, and read per-entry verdicts rather than the total. Several of the "regressions" chased in round 3 turned out to be this.
- **The cloud model thinks, but on a budget.** `VertexTransport` sets `thinkingBudget: 512`. Thinking *off* (`0`) transliterates Latin-script loanwords into Hebrew and destroys the code-switching this product exists for; thinking *unbounded* put the cloud tail at 17–18s, which is too slow to sit inside a keyboard. Capped at 512 the tail is under 4.4s and the corpus score went up, not down. `VERTEX_THINKING_BUDGET=-1` restores dynamic thinking if you want to re-measure.
- **Apple's on-device stack has no Hebrew in the three places that shaped this design — but it is not a blanket rule, and `UITextChecker` is the counterexample.** The suggestion bar runs on `UITextChecker`, whose `availableLanguages` lists `he_IL` among 42 and which completes `אנ` to `אני` and corrects `שלומ` to `שלום`, pinned end to end by `SuggestionEngineTests`. It is an older API with its own language list, so do not reason from "Apple has no Hebrew" to a fourth API without checking it. The three that do lack it: Foundation Models does not list it, `SpeechTranscriber` does not list it, and Vision's text recogniser does not list it — 30 languages, identical across `VNRecognizeTextRequest`, the newer Swift `RecognizeTextRequest` and VisionKit Live Text, on both iOS and macOS. Arabic *is* in that list, so none of this is a right-to-left limitation. `VisionLanguageTests` pins the Vision half from the simulator — specifically that Hebrew is absent and Arabic is present, which is the load-bearing pair; the count of 30 is prose beside it, not an assertion. If it ever fails, that is permission to delete most of `CloudScreenReader`.
- **Screen reading routes without ever naming a script, and that is the point.** The router cannot ask "is this screen Hebrew", because the only component that reads text is the one blind to Hebrew. `VisionScreenReader` compares text regions *found* by `VNDetectTextRectanglesRequest` — which finds text by shape, language-agnostically — against regions actually recognised. Coverage ≥ 0.97 and mean confidence ≥ 0.90 lets **zero** Hebrew or mixed screens through, and keeps 9 of 12 English screens on device *as macOS reads them* — `coverage.swift` is built with `xcrun -sdk macosx`, and on iOS the same gate accepts 10, because `ml-01`'s mean confidence lands at 0.90 there and 0.896 on macOS. Quote the platform with the number; that distinction has now been got wrong twice in this file. Loosening coverage to 0.95 gains **two** English screens (`sl-02` at 0.9583 and `ml-04` at exactly 0.9500) and admits a mixed one, which is the wrong trade — the trade is what matters here, not the count, and the count was wrong for a year. The gate is asymmetric on purpose: a misread Hebrew screen is a confident wrong reply in the user's name, an unnecessary cloud call is five seconds.
- **`VisionScreenReader` reads bubble geometry, so it accepts only two-sided layouts.** Slack, Teams and mail threads print every message against one margin with the author on a label above it, leaving no geometry to say who sent what. Side is read from which *margin* a bubble hugs, never from the line's centre — a long line in a one-sided layout crosses the middle of the screen and a centre test calls it outgoing, which was wrong on every Slack screen measured.
- **Vision is not the same on iOS as on macOS, so never quote a macOS reading of it as the product's number.** Same sources, same pixels, same thresholds: macOS accepts 9 of the 30 bar frames and answers 5, all 5 right. The iOS Simulator accepts 10, answers 8, and **3 of those are wrong** — including `wa-07`, the one frame whose only correct answer is silence, and `sl-05`, which comes back as keyboard key caps. An earlier version of this file claimed "it answers only when it is right"; that was a macOS-only claim reported as the product's. `harness/run-reader.sh` builds with `xcrun -sdk macosx` and is the macOS reading; `ScreenContextBarTests` is the iOS one and is the one that counts. The property the routing rests on survives both: zero Hebrew and zero mixed frames are accepted on device on either platform.
- **On iOS, routing through Vision scores *worse* than asking the cloud, and the comparison is the durable part while the absolute numbers are not.** Measured end to end through `ScreenContextSession.submit`, both sides replaying the *same* recorded cloud answers: routed gives sender 27/30, language 29/30, message 16/30 exact and 24/30 within 90%; cloud alone gives 30 / 30 / 18 / 25 on that same recording. Apples to apples, so the conclusion holds: the on-device path is not free accuracy that happens to be private, it costs about 3 points of sender on this bar. Weigh that against the privacy gain rather than assuming the gain is one-sided.
- **A frozen corpus is not a frozen bar when the thing being judged is a hosted model behind a moving alias — and there is no dated version to pin to.** `gemini-2.5-flash` is an alias. The obvious fix is to name a version instead, and measured on 2026-08-08 that fix does not exist: `gemini-2.5-flash-001`, `-002`, `-preview-05-20` and `-preview-04-17` all return **404** on this project, and a successful call answers with `modelVersion: "gemini-2.5-flash"` — the alias echoing itself. `VERTEX_MODEL` therefore buys nothing today and is kept only so a dated version can be used the day one appears. What is left is a noise floor, and its *shape* matters more than its size: two full runs of the identical configuration minutes apart disagreed on **2 of 30 frames** and scored 30/30 and 29/30 sender with 30/30 language both times, while an earlier pair taken a day apart disagreed on roughly a third of the corpus. So the drift is day to day, not call to call: a delta measured inside one sitting is close to trustworthy, and any number compared against a recording from another day is not. `cloud_outputs.json` now carries its recording date in every row's `config` and was taken at the configuration the product actually sends (half-size JPEG, not the full PNG every older score used); `cloud_outputs_repeat.json` is the second run, kept so the spread stays a measured number. Do not regenerate either casually: `ScreenContextBarTests` replays the first, so regenerating moves every routed threshold at the same moment as the thing being measured, and the two must be re-taken together and deliberately.
- **Two refusals, and they are not the same refusal.** `VisionScreenReader.interpret` returns nil for *nothing worth replying to* (a voice note) and throws `.notReadableOnDevice` for *I could not read this layout*. Collapsing both into nil made `RoutedScreenReader` treat "I cannot see" as "nothing is there", so `sl-01` and `sl-03` — plain answerable English the cloud transcribes correctly — silently offered the user nothing. Worth 2 points on every axis.
- **The screen-context prompt's shape is measured, not stylistic — and re-measuring it with committed artifacts moved two of the three numbers and killed one outright.** `harness/ablate.py` moves exactly one thing per variant against the same corpus in one sitting and writes each variant's answers to `Bar/screen-context/ablation/`, so these are now checkable rather than remembered. Baseline is `size-encoder/scale2-jpeg.json` from the same sitting: sender 29/30, language 30/30, 18 exact, 7 near, 0 traps.
  - **Enumerating first: confirmed, but smaller than claimed.** Dropping `messages` costs 2 points of sender (29 → 27), 3 of keyboard language, four of the near-misses, and introduces a trap. This file said 21/30 → 29/30; that magnitude does not reproduce. The direction and the reason do — every wrong answer on the bar was a bubble one to four positions above the newest, and a list the model must finish turns "which is newest" from a judgement into an index.
  - **Splitting `script` from `language`: confirmed, and it is the big one.** Collapsing them scores **22/30** keyboard language against 30/30 — the same 22 this file has claimed all along, landing exactly. Eight points, far outside the ±1 noise floor. They disagree on precisely the code-switched sentences this product exists for.
  - **"Flattening the list costs 7 points" is not supported.** The harness baseline *is* the flat string; the nested-array variant scores 28 sender against its 29, so nested is a point *worse*, inside the noise. `CloudField` carries nested `items` and that was the stated reason. Nothing here says nested is wrong — it says the 7 points were never there, so do not treat the nesting as load-bearing the way enumeration and the script/language split demonstrably are.
  - Two rules that *sound* right measured worse and are deliberately absent — a paragraph on bubble tint and edge, and "a printed name always means incoming"; `CloudScreenReader`'s doc comment lists both so they do not get re-added.
- **ScreenCaptureKit is real on iOS, and still not available here.** It is `iOS 27.0+`, and Apple states plainly that it replaces ReplayKit and that a broadcast extension is no longer necessary. But measured against the installed toolchain (Xcode 26.2), `ScreenCaptureKit.framework` is absent from both `iPhoneOS26.2.sdk` and `iPhoneSimulator26.2.sdk` while present in `MacOSX26.2.sdk`, and `ReplayKit.framework` is present in the iOS SDK as the control. So `import ScreenCaptureKit` does not compile for iOS at all until an Xcode with the iOS 27 SDK is installed. The whole ReplayKit loop is now written — capture, fingerprint, channel, the read inside the capture process, and the keyboard consuming it — and **not one line of it has ever executed**, because the simulator runtime ships no `replayd`. Reading a frame is the only half that is *measured*, against `Bar/screen-context/`.
- **The capture channel is two mmap'd pages, and the broadcast extension must never link `AIKeyboardCore`.** `AIKeyboardShared` is the Foundation-only target both ends share (`CaptureStatus`, `CaptureIntent`, `SharedPage`, `FrameFingerprint`, `ScreenReadingRecord`, `CaptureFreshness`) **and the read itself** (`CloudScreenReader` with its measured prompt, `BackendTransport`, `ScreenReadService`, plus the `KeyboardLanguage`, `TextScript`, `AIOutput` and `AIEngineError` those need); `AIKeyboardCore` re-exports it so existing call sites are untouched, and `AIKeyboardBroadcast` links it alone. The prompt is in the shared target rather than copied into the capture process because it is scored against `Bar/screen-context/` and two copies drift. Linking `AIKeyboardCore` there drags SwiftUI and UIKit into a process capped at ~50 MB; `Scripts/prove-capture-channel.sh` check 1 reads the Mach-O and fails if it happens. Four things to know before touching it. The seqlock fences live in a **C target**, `CaptureAtomics`, because Swift 5.9 has no atomics at all — `Synchronization.Atomic` is iOS 18, `<stdatomic.h>` does not import into Swift, and `OSAtomic` has been deprecated since iOS 10 — and plain loads and stores on arm64 are not a seqlock. Every timestamp is `CLOCK_MONOTONIC_RAW`, not a wall clock, because a clock the user can set is a clock that can make a forty-second-old reading look fresh. `FrameIdentity` has `.absent`, not `.none`: `FrameIdentity.none` in an optional position silently resolves to `Optional.none`, which cost a test that asserted against the wrong value. And a flag in a shared page needs a timestamp beside it — `keyboardVisible` outlived the process that wrote it and made the probe publish before anyone was watching.
- **The frame fingerprint's band was wrong twice, and the second time it was our own keyboard.** Crop to the top 14% and everything from the top of *our own UI* downwards, reduce to 32x64 greyscale, SHA-256. Three measured failures, each caught only by an adversarial harness: the original bottom-45% crop removed the newest message and missed **23 of 29** conversation switches; a 64-bit perceptual hash missed **10 of 29** even at the right band; and the shipped band contained about a third of our own keyboard, which animates a shimmer for the whole read, so **30 of 30** frames got a fresh identity from nothing but our loading state — the freshness gate then discarded the reading the user's own tap had just paid a cloud call for. So the keyboard publishes the height it *can* occupy (`CaptureIntent.ownUIHeightPermille`, never the current height, because the strip appearing mid-read would move the band and retire the reading exactly as a real switch does), clamped both ways because one process reads it out of a page another writes. The crop costs no host content: while the keyboard is up, everything below its top edge is ours. `Bar/screen-context/harness/frame-hash.mjs` swept it; `run-fingerprint.sh` holds the *shipping* Swift to the zeros by compiling `FrameFingerprint.swift` itself, and carries a witness that the shimmer still moves the identity over the unfixed band — a harness that cannot fail proves nothing. The 64-bit hash is not deleted, it is confined to `changeScore`, where "uninformative" is the right property.
- **A setting is not a feature until something reads it, and the personal dictionary was written, persisted, reset, counted in Settings and read by nothing.** `SharedStore.personalDictionary` had no consumer outside its own editor, so on a stock install this keyboard's autocorrect destroyed the three names the app ships in that very list: `Nitai` committed as `Nit` on the space bar, `Handi` as `Handing`, `Wispr` as `Wiser`, and both Hebrew entries too — `סאפא` as `ספא`, `בלי־פרופ` as `בלי־פרוף`. The slot was already there and filled with something else: `SuggestionEngine.suggestions(supplementary:)` took `UILexicon` alone. Four things to keep true. The dictionary check is the **first** question `shouldAutocorrect` asks, not a clause on `isKnownWord` at the bottom — the contraction table and the Hebrew final-form rule both `return true` above that line, and the final-form rule is what ate `בלי־פרופ`. The keyboard reads `storedPersonalDictionary`, which goes through `UserDefaults` at the moment of the keystroke, because the editor is in the app and `load()` fills the `@Published` copy once per launch (same reason as `storedDefaultTone`) — and `load()` honours an empty stored list rather than treating it as absent, or the two readers disagree about a list the user emptied while Settings keeps counting six. Matching folds the maqaf U+05BE onto ASCII `-`: Hebrew's own hyphen is what the shipped entry is spelled with and `KeyboardLayout.connectors` gives a Hebrew layout only the ASCII one, so without the fold that entry is unreachable by anything its owner can type. `PersonalDictionaryTests` drives all of it through `KeyboardController`, not through the engine — the engine was never the broken half.
- **And the fourth thing is the one that survived the first fix: a mark after the word.** `currentWordPrefix` runs back to the last *whitespace*, so `Hi Nitai,` reaches the engine as `Nitai,`, which is not `Nitai` — so the list stopped protecting a name the instant a comma touched it, and `Hi Nitai,` still committed as `Hi Nit`, byte for byte what the same input gives with the list emptied. Greeting somebody by name with a comma is the commonest way a name reaches a chat field, so the first fix missed most of the defect. `SuggestionEngine.wordCore` trims edge punctuation (both ends, so an entry like `Ph.D.` reduces the same way whichever side the mark is on) and strips a trailing `'s`, because `'` is punctuation but the `s` after it is not and `Nitai's` came back `Nita's`. The length gate and `isKnownWord` are asked about that trimmed word too — a comma was worth a letter, and `qwt,` reads as four characters and unknown, which pulled a three-letter word onto a six-letter entry. Two traps. `comparable` answers "" for a prefix that is only punctuation, and "" is a prefix of every entry, so both call sites check for it or typing `...` offers two arbitrary names. And a *separate* bug lives next door with no dictionary near it: `replaceCurrentWord` deletes the whole prefix, so every correction ate the mark — `recieve,` committed as `receive `, `helo,` as `help `. `KeyboardController.restoringTrailingMarks` puts it back, and must not when the candidate already carries it, because candidate zero *is* the literal keystrokes.
- **Two brand-tinted buttons sit side by side in the suggestion bar, and both of them were wrong.** The sparkle was disabled by `hasTextToWorkWith || canReply`, which is false on an empty field with no session — the exact state D8's affordance is for, since the broadcast picker lives in the Reply panel and the sparkle is the only route there. It now asks `AIMenuPanel.hasRunnableAction`, so the button and the panel it opens cannot disagree again. Its neighbour runs the default tone and wears that tone's own SF Symbol, which for the shipped default `.clearer` was `sparkle` — the same drawing as `sparkles` at a different count. That is now `eyeglasses`, `ToneIconTests` forbids any tone from wearing a sparkle and checks every icon resolves, and prose names the control instead of drawing it: `SuggestionBar.aiButtonName` is the one spelling, used by the playground and onboarding, next to `ToneSetting.settingsNote`'s "the one-tap rewrite button" for the other.
- **The keyboard UI lives in `Packages/AIKeyboardCore/`, not in `AIKeyboardExtension/`.** The extension is a thin host so the companion app can render the same keyboard in onboarding and the playground. New keyboard UI goes in the package, or it stops working in the app.
- **Every right-to-left keyboard rendered mirrored, and the row data was never the problem.** `UCKeyTranslate` returns letters in *physical key order*, which is already Apple's left-to-right screen order — Hebrew's `"קראטוןםפ"` draws `ק` leftmost exactly as stock iOS does. Reading that as *logical* order and setting `layoutDirection: .rightToLeft` on the row reversed six languages at once. `mirrorsRows` is deleted and every key row is pinned `.leftToRight`; only the suggestion *candidates* follow the language, never the bar's chrome, which used to make the emoji and AI buttons swap sides mid-swipe. Two things were measured off Apple rather than guessed and both were surprises: **Hebrew puts delete at the right end of the *top* row**, not the bottom (hence `LetterLayout.deleteRow`), and iOS's Arabic is 11/11/9 where ours is macOS's 12/10/7. `Bar/layouts/stock-rendered-rows.json` is the committed photograph, `capture-rendered.sh` retakes it, and `AIKeyboardUITests/RenderedRowOrderTests` measures the *rendered* key frames against it — a coverage or row-string test cannot see a reversal, because the string was always right.
- **The in-app playground is not evidence that the keyboard works, and for the whole of development it was believed to be.** The first install on a real phone typed *nothing* — keys drew, animated and clicked, and not one character reached the host app. `KeyboardController.target` was `weak` and `KeyboardViewController` built its `ProxyTextTarget` in argument position, so nothing retained it past `viewDidLoad` and every mutation was `target?.insertText` against nil. The playground was unaffected because `KeyboardPreview` holds its `MockTextTarget` as a `@StateObject`. So: the target is strong (nothing conforming to `TextTarget` references the controller back, so no cycle), the proxy is re-resolved per call through a `weak`-captured input view controller (`textDocumentProxy` is replaced when the host swaps fields, and `unowned` would trap when `KeyView`'s key-repeat `Task` outlives an interrupted gesture), and `AIKeyboardUITests/KeyboardTypesIntoHostTests.swift` presses a key on the real extension over a real `UITextField` and reads the field back. Before that file existed, *nothing* in the repo exercised the extension's own wiring — `AppGroupCrossProcessTests` and `CaptureChannelCrossProcessTests` already stood the extension over that exact field and asserted only that a key *existed*.
- **Three tests in a row passed against the bug they were named after, each for a different reason, and the shape is the lesson.** A `weak` reference held in a method-scoped local stays alive to the end of the method, so a test asserting through it proves nothing — take the reference out of scope first. `SuggestionEngine` returns a hardcoded `["I", "The", "We"]` for an empty prefix, so `XCTAssertFalse(suggestions.isEmpty)` was true of a keyboard whose document was unreadable — and that is exactly what the phone showed, a bar frozen on those three words. And `SuggestionEngine` unconditionally echoes the typed prefix as candidate zero (deliberately: the user must never be trapped in a word they did not type), so `contains { $0.hasPrefix(typed) }` is true even when the dictionary lookup is dead. Assert on something only the *fixed* build produces: a completion that is not the echo. Before writing any assertion here, work out what the broken version returns and check the assertion rejects it.
- **Targets use `PBXFileSystemSynchronizedRootGroup`** (`objectVersion = 77`), so any file dropped into `AIKeyboard/`, `AIKeyboardExtension/`, `AIKeyboardBroadcast/`, `AIKeyboardUITests/` or `AIKeyboardCoreTests/` is compiled into that target with no `.pbxproj` edit — all five are synchronized roots, not the three this line used to name. A file that must *not* compile needs a `membershipExceptions` entry, as both `AIKeyboardExtension/Info.plist` and `AIKeyboardBroadcast/Info.plist` have.
- **`swift build` inside `Packages/AIKeyboardCore` fails on macOS.** `Package.swift` declares `platforms: [.iOS(.v17)]` and the sources import UIKit and AudioToolbox, so the package only builds through the Xcode project against an iOS Simulator destination.
- **The App Group is real, and the keyboard needs Full Access to use it.** Both targets carry `com.apple.security.application-groups` for `group.com.nitai.aikeyboard` via `CODE_SIGN_ENTITLEMENTS`. iOS only grants a keyboard extension the shared container when the user allows Full Access, which is why `RequestsOpenAccess` is `true` in `AIKeyboardExtension/Info.plist`. `SharedStore.storage` reports `.appGroup` or `.processLocal` — it never pretends. Prove the round trip with `Scripts/prove-app-group.sh`; `UserDefaults(suiteName:)` being non-nil proves nothing, because it succeeds without the entitlement.
- **On the simulator, entitlements live in the binary, not the signature.** `codesign -d --entitlements` prints an empty dict for a simulator build; read `__TEXT,__entitlements` from the Mach-O instead, as the prove script does.
- **UI tests that drive the keyboard need an uncontended simulator.** Two `xcodebuild test` runs against the same device kill each other's runners, which reports as "crashed with signal kill" rather than a test failure.
