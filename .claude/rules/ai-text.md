# AI text actions

- **The AI text actions are real.** `MockAI` is gone; `RoutedIntelligence` picks between `FoundationModelsEngine` (on-device) and `CloudIntelligence`. The app's cloud transport is `BackendTransport`, which posts to a backend URL read from settings — the app holds no provider credential, because anything in the bundle is extractable. **A URL is not a credential, and since 2026-08-10 one does ship: `BackendTransport.bundledDefaultURL` is a deployed Cloud Run service (`handi-project`, `europe-west1`, from `Backend/deploy.sh`) that `configured()` falls back to whenever the stored value is absent or empty.** Before that the service existed in `Backend/` and had never been deployed, so `configured()` answered nil on *every* install and the whole product's AI was dead in Hebrew — that was "the AI doesn't work", not a bug in any Swift file. The bearer token still does not ship and is still typed in, so a fresh install 401s until somebody pastes it; a stored value that is not an http(s) URL is now the only route back to nil. **Which makes `configured() != nil` the wrong question for any screen**: it is true from the first launch, so everything that renders a cloud claim asks `BackendTransport.isReady()` — would a call be *accepted* — and `Scripts/prove-cloud-backend.sh` runs the shipping client against the live service. **`cloudBackendURL` has exactly one editor, and both features that need it point at that one name.** It is `CloudModelView`, reached from `Settings › AI › Cloud model` and from a row on Screen Context; `BackendTransport.settingsPath` is that string, and the four failures that dead-end on a missing backend (`unsupportedLanguage`, `cloudNotConfigured`, `deviceNotSupported`, `ScreenContextEndReason.notConfigured`) all print it. It used to live only on the Screen Context screen under "Where the screen is read", so on a stock install every Hebrew Fix, Rewrite, Tone and Reply failed forever while naming nowhere to go — Hebrew is outside `supportedScripts`, there is no cloud, and the best-effort branch is rejected because its session instructions are Hebrew. Anything that asserts the cloud works has to measure it: `SetupState.cloudConfigured` (fed by `isReady()`), not a Full Access tick and not the presence of a URL. Bar scoring uses a second transport, `Bar/ai-text/harness/VertexTransport.swift`, which calls Vertex AI directly with a gcloud token; it lives outside every target and must stay there. Two things to know before touching it: Apple's on-device model **does not support Hebrew** — `SystemLanguageModel.supportedLanguages` has no `he`, and a session whose *instructions* are in Hebrew is rejected outright with `unsupportedLanguageOrLocale`, even for English input. And every iOS Simulator reports `availability == .available` and then throws `ModelManagerError 1026` on the first call, so on-device answers never appear in a simulator run. Measure against macOS with `Bar/ai-text/harness/run-real.sh`.
- **Reply and Rewrite are vetted before they reach the panel.** `OutputGuard` drops any generated option that names a number, a weekday or a timing promise ("as soon as I can", "בהקדם") the message never contained, and — when the model reports that the message points at something it never names — any reply that agrees without asking what it is. If nothing survives the action fails with `.invented` rather than showing a fabricated commitment in the user's voice. Two consequences when changing this code: the schema field order is load-bearing (`unnamed`/`addressee` before the three replies, `decision`/`specifics` before the three versions — the model fills fields in order, and `VertexTransport` sends `propertyOrdering` to make Vertex do the same), and the word lists are deliberately narrow, checked against the 106 primary reference texts with no false positives. Not against every accepted *alternate*, and one of those is a genuine false positive worth knowing about: `tn-mix-01`'s alternate ends `אני אגיע לזה בהקדם`, which the `promises` list rejects, and Tone does run through `OutputGuard.addedSpecifics`. So the guard would drop an answer this corpus accepts. A broader rule rejects more good writing still: the reference answer to the corpus's own hallucination probe declines with "it won't be today".
- **Fix is held to the mistakes it names.** `EditScope` is the Fix-side counterpart to `OutputGuard`: Fix generates nothing, so the user's own words are the baseline and every changed word is a claim that the word was wrong. `CloudIntelligence.fix` asks for a `corrections` list *before* the corrected text (field order load-bearing, same as Rewrite's `decision`), and `EditScope.applied` undoes any change that list does not name — a list saying `none` returns the message byte for byte. `FoundationModelsEngine` deliberately does **not** ask: given the same two-field schema, Apple's on-device model got worse at the text it was already good at (it started dropping words — "can you send me the id" came back as "you send me the id") and Fix fell from 18/24 to 14/24 over the corpus — that denominator is all 24 Fix entries in every language, not the 10 English ones. That path calls `EditScope.repaired` instead, which does only the three things no model gets right: an expanded contraction goes back to a contraction (`dont` is a typo for `don't`, not shorthand for `do not`), a Hebrew word respelled into its other accepted orthography goes back (`והכל`/`והכול` are both correct — this is the change that makes people switch autocorrect off), and a full stop is never *added* to the end of a Hebrew message. That last rule is corpus-derived: all four Fix references that add a terminal full stop are English-only, and not one of the fourteen Hebrew or code-switched Fix references adds one. (`EditScopeTests` says four and is right.) Punctuation and capitalisation are invisible to the scope check on purpose, because the references make both without ever calling them out. Every rule was checked against all 24 Fix references with no false positives; `EditScopeTests` carries that table.
- **App Attest is the whole product's single point of failure, and it failed silently for two days.** The bearer is not typed in any more: `AppAttestation` runs in the containing app, proves the hardware to `/v1/attest`, and stores a ninety-day session token that the keyboard and the capture process read out of the App Group. So when attestation does not happen, *every* cloud action is dead — Fix, Rewrite, Tone, Reply, cloud dictation and screen reading — and the two visible symptoms are different: Reply refuses up front, because `ScreenContextPrompt` asks `isReady()` and gets false, while Fix and Rewrite actually call and come back `.cloudNotConfigured`, because `BackendTransport.mapped` turns the service's 401 into it. Both print "Open AI Keyboard once to reconnect", and on 2026-08-11 opening the app did nothing at all. **Read the Cloud Run request log before touching any Swift**: `gcloud logging read 'resource.labels.service_name="aikeyboard-backend"' --project=handi-project --account=nitai@handi.co.il` separates the three layers in one query, and it said `/v1/challenge` 200 at every app launch, **no `/v1/attest` ever**, and `/v1/text` 401 at every keyboard tap — so the flow was dying inside `DCAppAttestService`, not in the transport, not in the store and not on the server. Everything else checked out and is worth not re-checking: the App ID carries `APP_ATTEST` (App Store Connect API, `/v1/bundleIds/{id}/bundleIdCapabilities`), the Release entitlement is `production` and the service's `ATTEST_ENV` is `production`, and TestFlight ignores the entitlement and uses production anyway. Three rules came out of the fix, all of them Apple's own guidance. `serverUnavailable` is transient and must be retried with **the same key and the same `clientDataHash`** — a fresh key and a fresh challenge is a different request and degrades the device's risk metric — which is why `attestKeyId` is in the shared store rather than in a local, and why it is cleared on success (a key can be attested exactly once) and on `invalidKey` (Apple no longer knows it). `invalidKey` can be permanent on a given device, Apple say so and say not to tell users to reinstall, so a persistently failing install needs a path that is not App Attest or it is simply a dead install. And never swallow the reason: the outcome of every attempt goes to `SharedStore.attestationReport`, to the Cloud model screen under the Try again button, and to the unified log under `com.nitai.aikeyboard:AppAttest`.
- **The cloud is plumbing, and nothing shipped may ask the user to know about it, name it, or repair it.** There is no cloud-model setting in Release: `CloudModelRow` is `#if DEBUG` at all three call sites (Settings › AI, the dictation card, Screen Context), so the server-address field and the Debug token box are unreachable from a shipping build, and the row can never report "Not set up" about a keyboard that connects itself. There is no user-facing recovery either: `setUpRecovery` was an instruction three times over ("Finish setting it up under Settings › AI › Cloud model", then "Open AI Keyboard once to reconnect") and is now a status, "AI Keyboard is reconnecting. Try again in a moment.", because there is nothing behind it a person can do. The phrase "cloud model" is gone from every string a user can reach, and `CloudModelSettingNameTests.testNoDeadEndNamesTheCloudModelAtTheUser` asserts that over the *rendered* messages rather than by reading the source — the leak it exists for was an interpolation, four messages that each looked clean where they were written, and `ScreenReadService.tokenRejected` was a fifth carrying its own hand-copied duplicate of the old sentence. **Making that honest required making it true**: the keyboard cannot attest (different bundle ID, no `UIApplication` to launch the app with), a session token lasts ninety days, and only the containing app can renew one — so an install whose owner onboarded and never came back would go dark with no way back in. `AppAttestation` therefore runs at launch, on every foreground, *and* on a `BGAppRefreshTask` iOS wakes the app for once a day. Both `fetch` and `BGTaskSchedulerPermittedIdentifiers` live in `AIKeyboard/Info.plist`, the partial plist, for the reason the `audio` mode does: `INFOPLIST_KEY_*` build settings for these keys are accepted, echoed by `-showBuildSettings`, and never reach the built plist. A permitted identifier that is never registered traps at launch, so the string is spelled once as `AppAttestation.refreshTaskIdentifier` and read from there by both the `.backgroundTask` scene modifier and the scheduler.
- **`Scripts/prove-cloud-backend.sh` is the only thing in this repo that runs the product's cloud path end to end, and it had quietly stopped compiling.** Check 4 copies the shipping sources into a temp directory and builds them against the macOS SDK, and it did that from a hand-written list of file names. Four of those files had since been split — `AIPrompts.swift` into six, `Models.swift` into three, `EditScope.swift` into two, and `BackendTransport.send` into a file whose name does not start with `CloudTransport` — so the compile failed, the check reported `FAILED`, and nothing anywhere ran it. Every other cloud test in the repo uses a fake transport, which is exactly how the service could be down, mis-deployed or answering the wrong shape for a week with everything green. It copies by *family* now (base file plus every `Name+Part.swift` beside it) and fails loudly on a family that matches nothing, so a future split cannot silently compile a subset. Re-run it after any change to `CloudIntelligence`, `BackendTransport` or the backend: `BACKEND_TOKEN=… Scripts/prove-cloud-backend.sh`, and the token is on the Cloud Run service, not in the repo. Green on 2026-08-12 against the live service, including a real Hebrew correction.
- **The cloud model thinks, but on a budget.** `VertexTransport` sets `thinkingBudget: 512`. Thinking *off* (`0`) transliterates Latin-script loanwords into Hebrew and destroys the code-switching this product exists for; thinking *unbounded* put the cloud tail at 17–18s, which is too slow to sit inside a keyboard. Capped at 512 the tail is under 4.4s and the corpus score went up, not down. `VERTEX_THINKING_BUDGET=-1` restores dynamic thinking if you want to re-measure.

Remember the always-on rule that bites hardest here: **one corpus run is not evidence.** Two runs of identical code disagree on ~17 of the 58 entries.
