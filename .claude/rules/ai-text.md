# AI text actions

- **The AI text actions are real.** `MockAI` is gone; `RoutedIntelligence` picks between `FoundationModelsEngine` (on-device) and `CloudIntelligence`. The app's cloud transport is `BackendTransport`, which posts to a backend URL read from settings — the app holds no provider credential, because anything in the bundle is extractable. **A URL is not a credential, and since 2026-08-10 one does ship: `BackendTransport.bundledDefaultURL` is a deployed Cloud Run service (`handi-project`, `europe-west1`, from `Backend/deploy.sh`) that `configured()` falls back to whenever the stored value is absent or empty.** Before that the service existed in `Backend/` and had never been deployed, so `configured()` answered nil on *every* install and the whole product's AI was dead in Hebrew — that was "the AI doesn't work", not a bug in any Swift file. The bearer token still does not ship and is still typed in, so a fresh install 401s until somebody pastes it; a stored value that is not an http(s) URL is now the only route back to nil. **Which makes `configured() != nil` the wrong question for any screen**: it is true from the first launch, so everything that renders a cloud claim asks `BackendTransport.isReady()` — would a call be *accepted* — and `Scripts/prove-cloud-backend.sh` runs the shipping client against the live service. **There is no cloud-model screen.** `CloudModelView` and its Settings / search / Screen Context rows are deleted. The URL falls back to `BackendTransport.bundledDefaultURL`; `AppAttestation` fills the bearer. `settingsPath` is a leftover string, not a place a person can go. The four failures that dead-end on a missing backend (`unsupportedLanguage`, `cloudNotConfigured`, `deviceNotSupported`, `ScreenContextEndReason.notConfigured`) print `setUpRecovery`, not that path. It used to live only on the Screen Context screen under "Where the screen is read", so on a stock install every Hebrew Fix, Rewrite, Tone and Reply failed forever while naming nowhere to go — Hebrew is outside `supportedScripts`, there is no cloud, and the best-effort branch is rejected because its session instructions are Hebrew. Anything that asserts the cloud works has to measure it: `SetupState.cloudConfigured` (fed by `isReady()`), not a Full Access tick and not the presence of a URL. Bar scoring uses a second transport, `Bar/ai-text/harness/VertexTransport.swift`, which calls Vertex AI directly with a gcloud token; it lives outside every target and must stay there. Two things to know before touching it: Apple's on-device model **does not support Hebrew** — `SystemLanguageModel.supportedLanguages` has no `he`, and a session whose *instructions* are in Hebrew is rejected outright with `unsupportedLanguageOrLocale`, even for English input. And every iOS Simulator reports `availability == .available` and then throws `ModelManagerError 1026` on the first call, so on-device answers never appear in a simulator run. Measure against macOS with `Bar/ai-text/harness/run-real.sh`.
- **Reply and Rewrite are vetted before they reach the panel.** `OutputGuard` drops any generated option that names a number, a weekday or a timing promise ("as soon as I can", "בהקדם") the message never contained, and — when the model reports that the message points at something it never names — any reply that agrees without asking what it is. If nothing survives the action fails with `.invented` rather than showing a fabricated commitment in the user's voice. Two consequences when changing this code: the schema field order is load-bearing (`unnamed`/`addressee` before the three replies, `decision`/`specifics` before the three versions — the model fills fields in order, and `VertexTransport` sends `propertyOrdering` to make Vertex do the same), and the word lists are deliberately narrow, checked against the 106 primary reference texts with no false positives. Not against every accepted *alternate*, and one of those is a genuine false positive worth knowing about: `tn-mix-01`'s alternate ends `אני אגיע לזה בהקדם`, which the `promises` list rejects, and Tone does run through `OutputGuard.addedSpecifics`. So the guard would drop an answer this corpus accepts. A broader rule rejects more good writing still: the reference answer to the corpus's own hallucination probe declines with "it won't be today".
- **Fix is held to the mistakes it names.** `EditScope` is the Fix-side counterpart to `OutputGuard`: Fix generates nothing, so the user's own words are the baseline and every changed word is a claim that the word was wrong. `CloudIntelligence.fix` asks for a `corrections` list *before* the corrected text (field order load-bearing, same as Rewrite's `decision`), and `EditScope.applied` undoes any change that list does not name — a list saying `none` returns the message byte for byte, **except a run of letters that is several words with the spaces missing**. That exception is the WhatsApp case: `מהאופישלומהקורה` is not one already-correct word, the corrections field never called missing spaces a mistake so the model wrote `none`, and `applyDirectly` stayed quiet on the identical string. Spacing is not tidying — the letters did not change — so a split that only inserts whitespace is kept even on `none`, and a list that describes it as "חסרים רווחים" rather than `wrong -> right` is not allowed to glue the token back together. **The model echoing the jammed string is still a no-op after that**, which is why `MissingSpaces` splits on the bundled frequency list at apply time rather than waiting for another sampled call: `therapist` and `לעבודה` stay one word, `יאללה` is left alone because it cannot be covered, and `מהגן` is below the six-letter floor. **The list answers "is this common", not "is this a word", and for English those are different questions — which shipped as Fix rewriting the model.** The list is a top-N, so every ordinary compound below the cut decomposes into two words above it: `standup` is out, `stand` and `up` are in, and Fix's answer `I can't make the standup.` reached the field as `stand up`. That is the one thing `EditScope` exists to stop — a word changed that the corrections list never named — arriving through the single door built to bypass `EditScope`; `checkout`, `workout`, `backend` and `frontend` are the same shape, and `AIDirectEditTests.testFixWritesTheAnswerIntoTheFieldAndLeavesNoStrip` was red on committed main because of it. English now asks `UITextChecker` before splitting, and **Hebrew deliberately does not**: `מהקורה` → `מה קורה` is the measured motivating case and `מהקורה` is *also* a legal Hebrew word-form, so a speller would accept it and retire the feature on the example it was built for. Hebrew's missing boundaries are prefix morphology, which the list plus `pieceRank`'s `ה` rule already models; English's are compounding, which a top-N cannot. The checker is a local instance rather than `SuggestionEngine.sharedChecker`, which is `@MainActor` — pinning `restored` to an actor would cost every caller and every test, for an allocation that happens a few times per Fix behind a model round trip. The field description and both Fix prompts now carry jammed-word examples (`hellothere -> hello there`, `מהקורה -> מה קורה`); Hebrew prefixes stay attached. `FoundationModelsEngine` deliberately does **not** ask for the list: given the same two-field schema, Apple's on-device model got worse at the text it was already good at (it started dropping words — "can you send me the id" came back as "you send me the id") and Fix fell from 18/24 to 14/24 over the corpus — that denominator is all 24 Fix entries in every language, not the 10 English ones. That path calls `EditScope.repaired` instead, which does only the three things no model gets right: an expanded contraction goes back to a contraction (`dont` is a typo for `don't`, not shorthand for `do not`), a Hebrew word respelled into its other accepted orthography goes back (`והכל`/`והכול` are both correct — this is the change that makes people switch autocorrect off), and a full stop is never *added* to the end of a Hebrew message. That last rule is corpus-derived: all four Fix references that add a terminal full stop are English-only, and not one of the fourteen Hebrew or code-switched Fix references adds one. (`EditScopeTests` says four and is right.) Punctuation and capitalisation are invisible to the scope check on purpose, because the references make both without ever calling them out. Every rule was checked against all 24 Fix references with no false positives; `EditScopeTests` carries that table. **A long press on Fix is not a tone.** The popup offers four *passes* (`FixStyle`: proofread, spelling, punctuate, polish) because a `ToneStyle` pointed at Fix would have nothing to do. Punctuate and Polish ask for marks the model will not name as a word mistake, so `applied` on `none` would throw the period away — those two keep a punctuation-only candidate (still through `repaired`, so an added Hebrew full stop goes back). The proofread prompt is the measured base; the other three append a pass rather than replacing it.
- **App Attest is the whole product's single point of failure, and it failed silently for two days.** The bearer is not typed in any more: `AppAttestation` runs in the containing app, proves the hardware to `/v1/attest`, and stores a ninety-day session token that the keyboard and the capture process read out of the App Group. So when attestation does not happen, *every* cloud action is dead — Fix, Rewrite, Tone, Reply, cloud dictation and screen reading — and the two visible symptoms are different: Reply refuses up front, because `ScreenContextPrompt` asks `isReady()` and gets false, while Fix and Rewrite actually call and come back `.cloudNotConfigured`, because `BackendTransport.mapped` turns the service's 401 into it. Both print "Open AI Keyboard once to reconnect", and on 2026-08-11 opening the app did nothing at all. **Read the Cloud Run request log before touching any Swift**: `gcloud logging read 'resource.labels.service_name="aikeyboard-backend"' --project=handi-project --account=nitai@handi.co.il` separates the three layers in one query, and it said `/v1/challenge` 200 at every app launch, **no `/v1/attest` ever**, and `/v1/text` 401 at every keyboard tap — so the flow was dying inside `DCAppAttestService`, not in the transport, not in the store and not on the server. Everything else checked out and is worth not re-checking: the App ID carries `APP_ATTEST` (App Store Connect API, `/v1/bundleIds/{id}/bundleIdCapabilities`), the Release entitlement is `production` and the service's `ATTEST_ENV` is `production`, and TestFlight ignores the entitlement and uses production anyway. Three rules came out of the fix, all of them Apple's own guidance. `serverUnavailable` is transient and must be retried with **the same key and the same `clientDataHash`** — a fresh key and a fresh challenge is a different request and degrades the device's risk metric — which is why `attestKeyId` is in the shared store rather than in a local, and why it is cleared on success (a key can be attested exactly once) and on `invalidKey` (Apple no longer knows it). `invalidKey` can be permanent on a given device, Apple say so and say not to tell users to reinstall, so a persistently failing install needs a path that is not App Attest or it is simply a dead install. And never swallow the reason: the outcome of every attempt goes to `SharedStore.attestationReport` and to the unified log under `com.nitai.aikeyboard:AppAttest`.
- **The cloud is plumbing, and nothing shipped may ask the user to know about it, name it, or repair it.** There is no cloud-model setting in any build. The screen that held the server address and the Debug token box is deleted, so nothing can report "Not set up" about a keyboard that connects itself. There is no user-facing recovery either: `setUpRecovery` was an instruction three times over ("Finish setting it up under Settings › AI › Cloud model", then "Open AI Keyboard once to reconnect") and is now a status, "AI Keyboard is reconnecting. Try again in a moment.", because there is nothing behind it a person can do. The phrase "cloud model" is gone from every string a user can reach, and `CloudModelSettingNameTests.testNoDeadEndNamesTheCloudModelAtTheUser` asserts that over the *rendered* messages rather than by reading the source — the leak it exists for was an interpolation, four messages that each looked clean where they were written, and `ScreenReadService.tokenRejected` was a fifth carrying its own hand-copied duplicate of the old sentence. **Making that honest required making it true**: the keyboard cannot attest (different bundle ID, no `UIApplication` to launch the app with), a session token lasts ninety days, and only the containing app can renew one — so an install whose owner onboarded and never came back would go dark with no way back in. `AppAttestation` therefore runs at launch, on every foreground, *and* on a `BGAppRefreshTask` iOS wakes the app for once a day. Both `fetch` and `BGTaskSchedulerPermittedIdentifiers` live in `AIKeyboard/Info.plist`, the partial plist, for the reason the `audio` mode does: `INFOPLIST_KEY_*` build settings for these keys are accepted, echoed by `-showBuildSettings`, and never reach the built plist. A permitted identifier that is never registered traps at launch, so the string is spelled once as `AppAttestation.refreshTaskIdentifier` and read from there by both the `.backgroundTask` scene modifier and the scheduler.
- **`Scripts/prove-cloud-backend.sh` is the only thing in this repo that runs the product's cloud path end to end, and it had quietly stopped compiling.** Check 4 copies the shipping sources into a temp directory and builds them against the macOS SDK, and it did that from a hand-written list of file names. Four of those files had since been split — `AIPrompts.swift` into six, `Models.swift` into three, `EditScope.swift` into two, and `BackendTransport.send` into a file whose name does not start with `CloudTransport` — so the compile failed, the check reported `FAILED`, and nothing anywhere ran it. Every other cloud test in the repo uses a fake transport, which is exactly how the service could be down, mis-deployed or answering the wrong shape for a week with everything green. It copies by *family* now (base file plus every `Name+Part.swift` beside it) and fails loudly on a family that matches nothing, so a future split cannot silently compile a subset. Re-run it after any change to `CloudIntelligence`, `BackendTransport` or the backend: `BACKEND_TOKEN=… Scripts/prove-cloud-backend.sh`, and the token is on the Cloud Run service, not in the repo. Green on 2026-08-12 against the live service, including a real Hebrew correction.
- **The shipping cloud model is `gemini-3.5-flash-lite` with thinking off.** `Backend/src/vertexClient.js` sends `thinkingBudget: 0`. Measured 2026-08-14 on the 22 Hebrew and mixed Fix/Rewrite entries: Lite at 0 kept Latin loanwords (`sync`, `document`, `API key`), fixed `יבדוק`/`תגדי`/`בבקשא`, and cut Fix from ~2.6s to ~1.2s. `Bar/ai-text/harness/VertexTransport.swift` defaults to the same pair so a bar run measures what ships. On `gemini-2.5-flash`, thinking 0 transliterated `sync` into `סִינְק` — do not put 0 back on 2.5-flash and call it the same config. Unbounded thinking on 2.5-flash put the tail at 17–18s.

- **The scope is the whole field, and the sentence boundary it replaced made Fix get worse the more it was used.** `KeyboardController.aiTargetText` cut at `.!?\n`, so a message Fix had already corrected carried a terminator in the middle of itself and the *second* run saw only what came after it: type `hi mamiwhat?`, Fix to `hi mami what?`, add `up`, Fix again, and the model is handed the single word `up` — there is no answer it could give that reaches `hi mami whats up?`, because it cannot see the question in front of it. That is a report from a real device, and the ordinary case has nothing to do with a previous Fix: two sentences typed into one chat message are one message. So `aiTargetText` is `wholeField` (a selection still wins, because a selection is the user saying which part they mean), and the span helpers are named for the edit rather than for the sentence they used to be. What the field *is* is whatever the host hands over — `documentContextBeforeInput`/`…AfterInput` are the only readers an extension has and iOS truncates both — which is why `TextReplacementTests.checkWindowed` builds its expectation out of `aiTargetText` rather than typing it out. That file is worth reading before touching any of this: an emoji, a flag, a ZWJ sequence, a decomposed accent and Hebrew niqqud each break a different wrong way of counting the delete span, and all five survived the scope change unchanged.
- **An engine that cannot run is not a banner.** On the simulator `FoundationModelsEngine` throws `.modelNotReady` before it ever calls the model (no runtime ships assets, and `respond` blocks rather than failing). The router then tries the cloud. When that 401s, `firstFailure` used to keep the on-device error, so Fix printed "Model not ready / Still downloading" over a keyboard whose real problem was the token. Availability misses (`modelNotReady`, `appleIntelligenceOff`, `deviceNotSupported`, `cloudNotConfigured`) now yield to the later engine's error, and `BannerState.resolve` answers idle for them: the sweep on the key ending is the signal, same as a Fix that named no mistakes. A content failure (`refused`, `invented`, an empty answer) still earns the strip. `testAModelThatCannotRunDoesNotOpenAStrip` is the screenshot: both engines fail, `aiError` is the 401, and `showsActionBanner` is false.
- **All three actions apply themselves and the strip is gone from the running case, which is the state it was up for most.** `ActionBanner` no longer draws for a call in flight: a 69pt row that appeared on the tap and left on the answer relaid out the three candidates and every key row twice per Fix. What says a call is running is a sweep on the key (or tone button) that started it, clipped to the filled brand cap — `KeyActivity.working`. The reserved hairline above the suggestion bar is deleted; `totalHeight` is banner + suggestion + keys, and `FrameReduction.Band.maximumOwnUI` is still `368/874`. Two consequences worth knowing. `BannerState.working` and `.dictating` are **deleted**, not merely unpresented: `resolve` still asks both questions in the same order, because a recording or a call must keep outranking the previous action's leftover `options`, but both answer with the idle state. And `BannerState.activeActionKey` went with them — `KeyboardController.isActionKeyActive` reads `isWorking`, `block` and `dictationKeyState` directly, since the strip it used to ask is not drawn in either of the two states the row most has to report. **Reply moved last and gave up the most**: three answers labelled by intent used to page in the strip, and now the first is written into the field and the other two are reachable only when `applyDirectly` refuses. `applyDirectly` grew an insert mode for it (`aiSourceText` empty means Reply, which replaces nothing and is never stale, because it was written about the *screen*), and `AIEdit.replacedSelection` became `AIEdit.undo` — `.wholeField` or `.spanAtCursor` — because a reply undoes exactly the way a selection edit does and calling that "replaced a selection" would be a name that lies about two thirds of its callers.
- **Fix and Rewrite apply themselves, and the undo is the price.** The answer used to arrive on the 72pt strip behind a Use button, so the corrected sentence was read beside the message and then again inside it; `KeyboardController.applyDirectly` puts it in the field and clears the strip, which is where it was going to be judged anyway. Three things that fall out of it and are not obvious. `UITextDocumentProxy` has no undo of any kind, so the whole of the mitigation is `revertibleEdit` holding both texts and `SuggestionBar` drawing the way back — and it must be cleared by every path that changes the document by hand (`insertCharacter`, `insertSpace`, `deleteBackward`, `insertEmoji`, `apply(_ suggestion:)`, `applyResult`, the dictation transcript sink, and both cursor keys), never from `refreshSuggestions`, which `replaceTargetText` calls itself and which would therefore delete the revert with the edit that created it. **An answer byte-identical to the message is an answer, not a warning** — it is exactly what `EditScope.applied` returns when the model named no mistakes — so it clears the strip rather than re-typing the same characters or announcing "Nothing to change". The sweep on the key ending is the signal. An *empty* answer is left alone so `BannerState.resolve`'s "Nothing came back" still reaches the user. And the tests that used to read `variants`, `runningAction` and `selectedToneIsCustom` after the call now read them **before** it finishes or read the document instead: `applyDirectly` clears the strip, so an assertion made after `settle` is an assertion about `clearBannerState` and is true of every build, including the broken one.
- **Three ways auto-applying destroys a message, and each needs its own guard.** They are worth listing because none of them existed while a Use button stood between the answer and the document, and all three delete text the user typed. **The field moves while the model thinks**: a call takes seconds and people keep typing through them, so tap Fix, type the next word, and an answer written about the earlier sentence replaces the whole field and takes that word with it. `applyDirectly` refuses on `aiTargetText != aiSourceText` — the same staleness test `PredictiveRefiner` makes and for the same reason — and the answer is not thrown away: `aiResultText` and `variants` are already set, so falling through leaves the strip showing it behind the Use button, which is the one state that still needs one. That covers **a selection deselected mid-call** for free, where the scope silently widens from five words to the whole message between the tap and the answer. **And a selection edit undoes differently from a field edit**: the replacement is what consumes the selection, so there is none left by the time Revert runs, and sending it through `replaceTargetText` takes the whole-field branch — `hello there wrold friend`, Fix the selected `wrold`, revert, and the message is the single word `wrold`. `AIEdit.undo` is what picks the path, and `.spanAtCursor` deletes exactly the UTF-16 units it inserted from where it inserted them, guarded on the caret still being immediately after them, because deleting a count from the wrong place is worse than no undo at all. The caret is why both cursor keys clear the revert, and why the *host* moving it is caught by that guard rather than by a callback: a caret move fires `selectionDidChange`, not `textDidChange`, and overriding it is not usable here because this keyboard's own insertions fire it too — the revert would be cleared by the edit that created it, one runloop turn later. The fourth case is not a guard but a clear: **the host emptying the field**, which is Send, and `refreshDocumentState` drops the revert rather than leave it offering to type a sent message back into an empty box.

Remember the always-on rule that bites hardest here: **one corpus run is not evidence.** Two runs of identical code disagree on ~17 of the 58 entries.
