# Dictation

- **Dictation's architecture is forced by one error code, and both halves of that are worth knowing before changing anything.** A keyboard extension calling `AVAudioSession.setActive(true)` to record gets **561145187**, `cannotStartRecording` — Apple's guidance lists "No access to microphone and speaker" under the keyboard sandbox and open access adds Location, Contacts, a shared container, network and iCloud while never mentioning the microphone. So the microphone lives in the app and the transcript crosses the App Group, which is the shape screen context already uses and the one Wispr Flow ships as a "Flow Session". **The same error code is why dictation is a session rather than a button**: an app cannot *begin* recording from the background, but a session that is already active survives an app switch under the `audio` background mode. Nothing in an extension can launch its containing app (`UIApplication` is unavailable there, the responder-chain `openURL` workaround is explicitly disallowed), so with no session running the keyboard explains and names the screen — it must never spin. Do not "simplify" this into recording in the keyboard; `Scripts/prove-dictation.sh` check 1 fails the build if `AIKeyboardExtension` ever links AVFoundation. And **`INFOPLIST_KEY_UIBackgroundModes = audio` does not work**: Xcode accepts it, `-showBuildSettings` echoes it, and the generated Info.plist never contains it, which would have suspended the app at the exact moment dictation is used. It lives in `AIKeyboard/Info.plist`, a partial plist merged into the generated one, with a `membershipExceptions` entry so it is not also copied in as a resource. The prove script reads the built plist, never the build setting.
- **The transcription model cannot be trusted to say it heard nothing, and this is the most dangerous thing in the feature.** Four seconds of digital silence come back as `speech: yes` and *"I'm not sure if I'm going to be able to make it to the meeting."* — reproducibly, in every variant of the first harness shape and in two of four shipping-shape variants, one of which invents the same sentence out of stationary noise. Asking the model harder does not fix it, so `SpeechGate` answers it on the device with arithmetic that cannot hallucinate: speech has gaps between words, a fan or a tone does not, and the quietest-frame-to-peak ratio separates the 36 real clips (0.012–0.21) from the traps (0.91, 0.98) by a factor of four either side of the 0.5 threshold. `SpeechGateTests` re-measures that table from the same WAVs. Its honest limit is that the corpus has true digital silence between words where a real room has tone; the threshold leaves margin, and the error is biased on purpose — a refusal costs a tap, a false accept types an invented sentence in the user's name.
- **The dictation bar is deterministic and the other two are not, so a single-run delta here is evidence.** Two full runs of the identical configuration came back byte for byte identical, which `Bar/ai-text` and `Bar/screen-context` never do. That is a property of `temperature: 0` over a fixed audio file; do not carry it across, and re-check it if the model, temperature or thinking budget moves. What the prompt is worth, all measured in one sitting and committed under `Bar/dictation/ablation/`: the **loanword rule** is the real win (14.3% against a 15.6% baseline, 36/60 entities against 31, and 6 more of the 36 English words kept in Latin letters — the examples are the working part, because `favor` heard through Israeli phonology comes back as `פייבור`), while the **language hint is worth nothing on this corpus and ships anyway**. It earns its place in `Bar/dictation/multilingual/`, 29 languages at one sentence each: without it the Polish clip transcribes as *Portuguese* and the Slovak one drifts to Croatian; with it both are right, and 29/29 come back in the correct writing system. Word error rate on a code-switched sentence is 23.5% against 8-10% for either language alone, so mid-sentence switching is what this is *worst* at — do not put that claim back on the onboarding screen it was removed from.
- **The two-process proof could not pass, and nobody noticed because nobody ran it.** `DictationCrossProcessTests` finished a recording by tapping `dictation-insert`, a button in the deleted `DictationPanel`; the identifier exists nowhere in the repo, so the test waited five seconds for an element nothing draws and then never sent `stopUtterance` at all. `DictationChannelProbe` publishes its transcript only on a stop, so check 4's transcript assertion — the one the whole script is for — could not succeed on any build. The microphone key both starts and finishes a recording now, so the test taps it twice. The lesson is the one this repo keeps relearning: a check that is not run is a check that is not true, and deleting a surface has to include the tests that addressed it. **Streaming is proved through the same seam**: the probe publishes a partial half a second into the utterance, `DictationSession.report()` carries `partial=` in its line beside `transcript=`, and `Scripts/prove-dictation.sh` greps for both. The two strings are deliberately different, because two greps looking for one sentence would both pass on a build that logged the transcript into the partial's slot.
- **Assert the reason by symbol; never pin the sentence it is wrapped in.** `testATapAfterTheSessionDiedRefusesInsteadOfRecordingIntoNothing` asserted the whole of `block.detail` — the ending *and* the remedy prose after it — and went red the day the remedy was rewritten, which is a copy edit and not the defect the test is named for. What the stale-`.ready` build gets wrong is only the first half: with no fresh read there is nothing to explain the ending with, so `dictationRefusalDetail` prints the ordinary no-session sentence and the reason is absent entirely. It asserts `detail.hasPrefix(DictationEndReason.expired.explanation)` now, which still rejects that build — swapping `.expired` for `.interrupted` fails the test, so it is not vacuous — and cannot be broken by rewording the sentence underneath. The neighbouring `testWithNoSessionTheBannerExplainsAndNothingIsDictated` already did it this way (`detail.contains("swipe back")`), and the remedy half belongs there rather than here.
- **Not one line of the recording half has ever run on a phone, and the prove script says so out loud.** `Scripts/prove-dictation.sh` proves what can be proved here: that the extension does not link AVFoundation, that the app declares the background mode, and that a keyboard extension in its own sandbox opens an utterance and receives a transcript a *different* process published. `DictationChannelProbe` replaces the microphone and the transcriber with a fixed sentence, because a UI test cannot speak and a simulator's input is the host Mac's. What no test anywhere covers: that `AVAudioEngine` records, that a session survives jetsam, or that an interruption is handled.
- **`DictationSession.availability` is a cache with one writer, and everything read it whether or not that writer was running — which broke dictation in both directions at once.** `poll()` is the only thing that sets it, and `poll()` only runs while the watch is on. `startDictation` used to check `availability.isLive` *above* the line that starts the watch, so the check read the `.noSession(.notEnded)` a fresh session is initialised with, refused, and returned before `startWatching()` was ever reached: the microphone key answered "No dictation session" over a session that was live in the app, on every device, on every tap, for as long as the keyboard was up. It also emitted not one `dictation-watch` line, because `report()` only runs inside `poll()` — so `Scripts/prove-dictation.sh` was failing at "the keyboard extension process never reported in" rather than at anything to do with audio, and that line is the cheapest way to tell this class of defect from a real channel problem. The same cache failed the other way round: `stopWatching()` left `.ready` behind, so once the transcript sink stopped the watch, `BannerState.resolve` read `dictationIsLive` as true and kept the dictation strip up over a sentence already in the document, and the next tap walked through the guard into a session that could have been dead for an hour — `beginUtterance` answers a number whether or not a recorder exists, so the keyboard showed Listening and waited for a transcript nothing would publish. So: `refresh()` before anything decides, and a `stopWatching()` that forgets what it saw, because not watching means knowing of no session and refusing is the direction whose cost is one tap. **The reason no test caught it is worth more than the fix**: every live-session case in `DictationKeyboardTests` called `session.poll()` by hand immediately before `controller.startDictation()`, which is the one thing the shipping keyboard never does. The three tests that pin this are written without that line.
- **Three defects in the recording half were found by reading it rather than by running it, and all three are invisible to every test here.** An `AVAudioEngine` tap that ends in `Task { @MainActor in append(samples) }` — one unstructured task per buffer — has **no ordering guarantee between tasks**, so a recording longer than a word can be reassembled out of order; the tap now appends under `LiveRecording`'s own lock and the 10 Hz poll reads the level back, so the audio thread touches no actor at all. A route change (earbuds unplugged, Bluetooth out of range) posts `AVAudioEngineConfigurationChange`, after which the engine has stopped and the tap is gone with **nothing thrown** — unwatched, the session heartbeats on and every later utterance is silence. And a transcription outlives the session it was recorded in, so a stop-and-restart inside the two seconds a call takes reopens `publish`'s gate and lands an old sentence in the new session; the session is stamped on the record when the recording closes and compared on the way out. The lesson generalises past dictation: the parts of this repo with no test are the parts where reading the code line by line is the only review there is.
- **The words go into the field while somebody is speaking, and Apple's own dictation model is what puts them there.** `LiveTranscriber` runs `DictationTranscriber` with the `progressiveLongDictation` preset inside the containing app, which already owns the microphone and the audio tap; each reading it emits is published as a `DictationPartialRecord` in `partial.json`, which is the same channel and the same keyboard-side code the cloud partials used. **It is free, local, needs no network and asked for no new permission** — the probe that measured this ran as a bare simulator binary with no Info.plist and no `requestAuthorization` and still produced text. `AssetInventory` downloads the model on the first session (`prepare(locale:)`), reserves it so iOS does not reclaim it, and is bounded by `maximumReservedLocales`, which is **5** — so this is per-language and not something to ask for across all 64. Everything about it is best-effort: a language Apple does not list, a model still downloading, an analyzer that will not start, all fail silently and cost only the streaming, because `CloudDictation` still produces the transcript when the user stops.
- **What replaced it is worth knowing, because the old design was ten times the cost and every part of it looked like an optimisation.** Partials used to be Vertex calls on a cadence, each re-uploading *all* the audio so far. Gemini bills audio at **32 tokens per second** and `thinkingBudget: 512` is paid **per call**, so a 60-second dictation ran ~15 calls for about **$0.035** against $0.0035 for the single final call — and the audio was the *smaller* half of that. It needed a throttle, a no-growth check, a one-in-flight guard, a never-repeating token so a late task could not clear a newer one's slot, and a WAV encode of the whole buffer every couple of seconds under the audio thread's lock. Three defects were found in it by reading: the throttle advanced on *success* rather than on the attempt, so a quiet moment before the first word ran ten full encodes a second; reading the samples out to encode outside the lock left the array multiply-referenced, so the next tap callback paid a copy-on-write duplication of up to 1.9 MB **on the real-time audio thread**; and the late-task slot clobber let two uploads run at once. All of it is deleted. If Apple's model is ever swapped back out, do not restore the shape — send only the *new* audio with the running text as context, and use `flash-lite` with thinking off for drafts.
- **Apple's model is measured, committed, and much worse than the cloud — and it is shipped anyway on purpose.** `Bar/dictation/harness/run-apple.sh` runs it over the same 36 clips and `score.py` grades it with the same scorer, into `apple_live_outputs.json`. Measured 2026-08-12 on an iOS 26.2 simulator: **WER 24.1% Hebrew, 13.9% English, 56.3% code-switched, 31.4% overall**, named entities **8/60**, and **English kept in Latin script 1/36** — against the cloud's 10.7 / 8.5 / 23.5 / 14.2, 38/60 and 25/36. Monolingual it is respectable and on one Hebrew clip it beats the reference on number style (`ב-10:30` where the corpus spells out `בעשר וחצי`, which is what a keyboard wants). Code-switched it collapses: `sync` comes back `סקין`, `roadmap` as `האירוע`, `login` as `לג׳ינס`. That is tolerated because **these words are a draft that the cloud transcript overwrites within a second or two of the user stopping**, and the trade bought is that the live half is free, offline and instant. Anyone reopening this decision should re-run both harnesses rather than re-argue it. And note the general finding underneath: plain word error rate **cannot see** the Latin-script property — the literature had to invent transliterated WER for exactly this — so no vendor's published Hebrew WER answers the question this product actually asks, and none of AssemblyAI, Deepgram, Speechmatics, ElevenLabs or Azure publishes a Hebrew number at all.
- **`SpeechTranscriber` is not the only transcriber in the Speech framework, and reading its locale list as "Apple has no Hebrew" was wrong.** The rule above about Apple's on-device stack ends by warning not to reason from three APIs to a fourth without checking it; `DictationTranscriber` is that fourth. Measured on an iOS 26.2 simulator: `SFSpeechRecognizer` lists 63 locales including `he-IL` (with `supportsOnDeviceRecognition == false`, so it is a network call), **`DictationTranscriber` lists 43 including `he-IL`**, and `SpeechTranscriber` lists **zero** — which is the trap, because a list of zero is not "everything except Hebrew" and the original reading proved nothing either way. `AssetInventory.status` reports `he-IL` as `.supported`, and it downloads and installs. The legacy `SFSpeechRecognizer` path was ruled out separately and for different reasons: one minute of audio per request, ~1,000 requests per device per hour, an undocumented daily quota, `kAFAssistantErrorDomain` 203 reported as common on the server path, a second permission prompt, and audio leaving the device.
- **The keyboard's half of streaming is a record of exactly what it wrote, and that record is the only thing standing between this feature and eating somebody's message.** `KeyboardController.streamedDictation` holds the inserted string character for character, leading space included, because `UITextDocumentProxy` has no undo and no way to address a range — `replaceStreamedDictation` deletes that many UTF-16 units backwards and inserts the new reading. **Only the tail that changed is rewritten, and that is a performance requirement rather than a nicety**: `deleteBackward(utf16Units:)` reads `documentContextBeforeInput` twice per press to find out what the press removed, so retyping a whole utterance every two seconds is about 1,300 proxy round trips on a thirty-second dictation, on the main thread, while somebody is speaking — and the sentence visibly flickers each time. The comparison is `String.commonPrefix`, by `Character`, and the count deleted is UTF-16: pairing them the other way round lands a delete inside a ZWJ emoji or a Hebrew letter carrying niqqud, which is the one way this corrupts text rather than merely misplacing it. **The guard is against the run about to be deleted, not against the whole draft, and that is not a loosening — it is what makes streaming survive a long dictation.** `documentContextBeforeInput` is a *window*: iOS truncates it and there is nothing behind it to reach for, so a draft longer than that window can never be found whole inside it, and a check written against the whole draft abandons itself partway through exactly the long dictations streaming is for — handing the user a duplicated sentence at the end for its trouble. `streamAnchor(replacing:)` answers with the stale run (a word or two, always inside the window) and, when a reading only *extends* the previous one and there is nothing to delete, with the last `streamAnchorCharacters` of the draft, so a stray keystroke at the caret cannot be written over. The safety guarantee is the one that matters and is unchanged: nothing is deleted unless the characters about to be deleted are the ones this recording wrote and are standing at the caret right now — the same test `revertAIEdit`'s span path makes, for the same reason. When that guard fails **nothing is repaired**, and the two callers part company there: a *partial* gives up (`dictationStreamAbandoned` stops this recording streaming at all, so it cannot append a fresh copy of the sentence on this reading and every one after it), while the *final transcript* is inserted anyway, duplicate and all. The first version returned from both, which silently threw the whole sentence away when a host rewrote the field between the last partial and the final call — a draft the user can delete is a worse field, a transcript they never see is a lost message, and only one of those is recoverable. Two consequences worth keeping. Cancelling never deletes what was streamed: `stopDictation(insert: false)` is also what `KeyboardViewController.viewWillDisappear` calls, so a version that tidied up would take text out of a message on the way off screen. And a transcription failure *after* something was streamed does not raise "Nothing to insert" — the sentence is in the field where the user can see it, and a strip saying otherwise over it would be the keyboard disagreeing with itself. `PredictiveRefiner` is also switched off for the length of a recording (`askForRefinement` guards on `isDictating`), because every partial reaches the host's `textDidChange` and a thirty-second dictation would otherwise buy a dozen model calls predicting the next word of a sentence nobody is typing.
- **Nothing edits the field while it is still being spoken into, and that is a rule streaming created.** Fix, Rewrite and Reply are all drawn off for the length of a recording (`isActionKeyDisabled` asks `isDictationActive` before it asks about an empty field), and the guard behind the keys is written **twice, in the two places the routes actually converge**: `run(_:)` for Fix and Reply, and `runTone(_:)` for the whole tone family. That second one is the trap — `press(.quickTone)` calls `runDefaultTone()` and the register popup calls `selectTone(named:)`, and neither goes anywhere near `run(_:)`, so a guard written only there covers two of the three actions while reading as though it covers all of them. Both return silently rather than refusing: the dim key has already made the statement, and a refusal strip opening under somebody mid-sentence would be the banner coming back for the exact case it was taken away for. The sequence it prevents is not cosmetic: Fix over a half-finished message replaces the whole field with a correction of it, `streamedDictation` then points at text that is no longer there, and the transcript landing a second later cannot find its draft and inserts a second copy beside it. Reply is on the list although it is the one action that deliberately needs no text, because it inserts at the caret — exactly where the next reading is about to go. Two consequences. The undo has to go too, and it goes when the utterance *opens* rather than when the first words land (`startDictation`, inside the `if isDictating` branch so a refused tap does not silently take away an undo the user still has) — otherwise it and the pause control share the bar's trailing slot for the second or two before the first reading, and tapping it would replace the whole field underneath a live recording. And "Type something first" stopped being the only reason a key is off, so the words come from `actionKeyDisabledReason` and are passed into `KeyView.disabledHint`: a dim cap says "not now" to somebody who can see it and nothing at all to somebody who cannot, and telling a user to type something while they are dictating is telling them to do the thing they are already doing.
- **A recording is reported on the microphone key, and the action banner is not drawn for one at all.** `DictationKeyState` resolves idle / recording(secondsLeft:) / finishing in one place, and the key's glyph, caption and cap colour all come from it — `KeyView.CapKind.record` is a fifth cap kind rather than a red wash painted over the brand one, so the fill, the glyph colour and the depth recipe cannot disagree. **The microphone is the one key that wears a filled cap at rest**, orange, so that turning red means something: every other control here is neutral until it is doing something, and this one is the way into a feature people do not think to look for. Orange to red is one property changing on a cap the eye already knows. **Idle is `waveform`; recording (`isDictating`) replaces the icon with a live compact waveform in the icon slot; finishing is `pause.fill` and no bars.** There is no ×. A tap while `.finishing` is ignored so it cannot open a second utterance and cannot cancel the insert already on its way. The **countdown** is the key's own caption in the last minute. The waveform is `KeyActivity.recording` drawing `dictationLevels` at the icon-slot height (~20pt), the same drawing the bar copy uses (D8). **The bars hide the moment pause is tapped** (`isDictating`); the key stays red through `.finishing` so it does not flash Record. A build that reads `dictationKeyState.isRecording` for the waveform leaves frozen bars up until the transcript lands. Height is a square root of RMS, neighbouring bars are sined so a held note is a shape rather than a wall, and the history is sampled on every poll (`levelTick`) rather than on every change of loudness — `@Published` on `level` is Equatable and drops a held note. Nothing about a recording is a reserved row any more; `totalHeight` does not grow when the microphone opens. **A silent take does not raise a strip.** "Nothing to insert" was a 69pt row for a second tap; `dictation.$failure` stops the watch and leaves `dictationFailure` empty, same as a cloud failure after words were already streamed, so `BannerState.dictationFailed` is deleted.
- **Pause-the-protocol is gone, end to end, and that was a deletion rather than a hiding.** The keyboard's only dictation control is the microphone key: it starts, it stops, and a tap while the last words are in flight is ignored. What went with the old pause button is the whole cross-process pause protocol — `DictationRequest.pausedRaw`, `DictationPhase.paused`, `DictationSession.Availability.paused`, the reader's `pauseUtterance`/`resumeUtterance`, `LiveRecording.pause`/`resume`, the recorder's paused branch and the suggestion bar's button. **The bytes `pausedRaw` occupied are kept as explicit padding**, because `DictationRequest` is memcpy'd through a fixed-size shared page and its layout is the wire format two processes agree on; leaving the hole where it was means every field after it keeps its offset. The key's own glyph is what promises stop now: a live waveform while recording, a pause bar while the last words are in flight, and tapping it stops.
- **The host emptying the field during a recording or a pending insert is Send.** WhatsApp Send, playground Send, and Return-as-send all arrive as an empty compose box plus `textDidChange` → `refreshSuggestions()` → `stopDictationIfHostSent`. That is `hadText && !documentHasText && deletedWordPrefix == nil`, the same distinction word learning uses, and `stopDictation(insert: false)` so the cloud transcript cannot type a sent message back. It lives there rather than in `refreshDocumentState`, because stream inserts call the latter immediately after `insertText` and the proxy can still look empty. A full stream rewrite is not Send: `isReplacingStreamedDictation` covers the empty window between delete and insert. The pause protocol stays deleted.
- **The transcription language hint is the keyboard's own active layout now, not every language the user has ever enabled, and it is the `storedAutocorrect` trap in a direction that setting has never run in.** `enabledLanguages` used to be passed whole to `CloudDictation`, so a bilingual keyboard sitting on English hinted the transcriber with Hebrew too, for no better reason than the user having Hebrew installed somewhere in Settings. `SharedStore.storedDictationLanguage` is written by the keyboard extension the moment it opens an utterance and read by `DictationService`, running in the containing app — two different processes, so a `@Published` copy would only ever be right in whichever one just wrote it, and the app has usually been running since long before the user last swiped the space bar. `DictationService+Polling.close(utterance:)` reads it fresh off `defaults` at the moment it needs it and falls back to `enabledLanguages` only when nothing has ever been written — a session started and stopped from the app alone, with no keyboard involved at all.
