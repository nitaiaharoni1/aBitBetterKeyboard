# Suggestion bar, autocorrect and the personal dictionary

- **Autocorrect and Predictions are settings the keyboard must re-read, and the default candidate is bold, not a chip.** Space commits the default suggestion only when `storedAutocorrect` is on — the `@Published` copy is filled once at launch, so a toggle flipped in the app while the keyboard is already up is invisible unless the space bar and `refreshSuggestions` go through UserDefaults at the keystroke (same trap as `storedPersonalDictionary`). When the setting is off, `refreshSuggestions` also re-marks slot 0 as default so the bar does not bold a correction space is no longer allowed to commit; a deliberate tap on a candidate still inserts it. Predictions uses `storedPredictions` for the same reason. The default slot is drawn in bold weight with no background fill.
- **A setting is not a feature until something reads it, and the personal dictionary was written, persisted, reset, counted in Settings and read by nothing.** `SharedStore.personalDictionary` had no consumer outside its own editor, so on a stock install this keyboard's autocorrect destroyed the three names the app ships in that very list: `Nitai` committed as `Nit` on the space bar, `Handi` as `Handing`, `Wispr` as `Wiser`, and both Hebrew entries too — `סאפא` as `ספא`, `בלי־פרופ` as `בלי־פרוף`. The slot was already there and filled with something else: `SuggestionEngine.suggestions(supplementary:)` took `UILexicon` alone. Four things to keep true. The dictionary check is the **first** question `shouldAutocorrect` asks, not a clause on `isKnownWord` at the bottom — the contraction table and the Hebrew final-form rule both `return true` above that line, and the final-form rule is what ate `בלי־פרופ`. The keyboard reads `storedPersonalDictionary`, which goes through `UserDefaults` at the moment of the keystroke, because the editor is in the app and `load()` fills the `@Published` copy once per launch (same reason as `storedDefaultTone`) — and `load()` honours an empty stored list rather than treating it as absent, or the two readers disagree about a list the user emptied while Settings keeps counting six. Matching folds the maqaf U+05BE onto ASCII `-`: Hebrew's own hyphen is what the shipped entry is spelled with and `KeyboardLayout.connectors` gives a Hebrew layout only the ASCII one, so without the fold that entry is unreachable by anything its owner can type. `PersonalDictionaryTests` drives all of it through `KeyboardController`, not through the engine — the engine was never the broken half.
- **And the fourth thing is the one that survived the first fix: a mark after the word.** `currentWordPrefix` runs back to the last *whitespace*, so `Hi Nitai,` reaches the engine as `Nitai,`, which is not `Nitai` — so the list stopped protecting a name the instant a comma touched it, and `Hi Nitai,` still committed as `Hi Nit`, byte for byte what the same input gives with the list emptied. Greeting somebody by name with a comma is the commonest way a name reaches a chat field, so the first fix missed most of the defect. `SuggestionEngine.wordCore` trims edge punctuation (both ends, so an entry like `Ph.D.` reduces the same way whichever side the mark is on) and strips a trailing `'s`, because `'` is punctuation but the `s` after it is not and `Nitai's` came back `Nita's`. The length gate and `isKnownWord` are asked about that trimmed word too — a comma was worth a letter, and `qwt,` reads as four characters and unknown, which pulled a three-letter word onto a six-letter entry. Two traps. `comparable` answers "" for a prefix that is only punctuation, and "" is a prefix of every entry, so both call sites check for it or typing `...` offers two arbitrary names. And a *separate* bug lives next door with no dictionary near it: `replaceCurrentWord` deletes the whole prefix, so every correction ate the mark — `recieve,` committed as `receive `, `helo,` as `help `. `KeyboardController.restoringTrailingMarks` puts it back, and must not when the candidate already carries it, because candidate zero *is* the literal keystrokes.
- **The one-tap rewrite key is the only key besides the space bar that commits on lift, and a model call is why.** Long-pressing it opens the registers in `KeyView`'s alternates popup — the same mechanism as a letter's accents, stacked vertically because seven register names is about 1,000 points of width on a 393-point screen. But a letter has *already inserted* its character on finger-down and picking an accent replaces it, whereas this key runs a cloud call: firing on finger-down would spend one on the default tone every time the user held the key to choose a different register, and `beginWork` cancels its predecessor, so the answer being paid for would be thrown away by the register actually wanted. `KeyView.runsOnLift` defers it; a plain tap still runs the default, just on the lift. Three things to keep true. The list is **default-first** (`KeyboardController.toneAlternates`), because `KeyView` treats index 0 as "the long press changed nothing" — a list spelled `ToneStyle.allCases.map(\.title)` looks right and gives every user Clearer when they hold, look and lift without moving. Selection is **by title, not by index**, because the order is built from a stored setting that Settings can change in another process between the key being drawn and the finger lifting. And the popup is a drag, so the registers also hang off the key as `accessibilityActions` — the same rule the layout editor is built on, that every gesture has a non-gesture route. `ToneAlternatesTests` holds all of it. A custom tone that is *written but not selected* is deliberately absent from the list: `ToneSetting` only resolves to `.custom` when `prefersCustomTone` is on, so there would be no instruction to send. `AIResultPanel.toneChips` used to gate its custom chip on exactly the same condition and was the other surface this had to agree with; that panel is deleted, so this popup is the only reader of `customTone` now.
- **Two brand-tinted buttons sit side by side in the suggestion bar, and both of them were wrong.** The sparkle was disabled by `hasTextToWorkWith || canReply`, which is false on an empty field with no session — the exact state D8's affordance is for, since the broadcast picker lived in the Reply panel and the sparkle was the only route there. It was fixed by asking the panel the same question the panel asked itself. **Both the sparkle and that panel are now deleted**: Reply has its own key in the action row and the picker is the banner's trailing chip, so the route no longer depends on a button agreeing with a screen. What survives of the fix is `AIAction.isAvailable` / `.hasRunnableAction`, which `SuggestionBar.anyActionCouldRun` still calls, because the bar holding its own opinion about an empty field is what caused this. Its neighbour runs the default tone, and it used to wear that tone's own SF Symbol — which for the shipped default `.clearer` was `sparkle`, the same drawing as `sparkles` at a different count, so two sparkles sat side by side meaning two different things. Fixing the symbol per tone (`.clearer` became `eyeglasses`) only moved the problem: `figure.wave` for Casual is a waving stick figure in a keyboard, which reads as a profile button and says nothing about rewriting. **So the glyph is now fixed at `SuggestionBar.toneButtonSymbol` — `AIAction.rewrite`'s own icon, because the button is a shortcut through that row — and the tone is printed in words under it.** `ToneStyle.icon` survives for the tone picker and result variants, where a panel header already says what the screen is about; `ToneSetting.icon` had no other reader and is deleted. **The button is a fixed 68pt for every tone, not sized to its label**, because its width is a *setting*: growing it put `Professional` at 67pt against `Casual`'s 44, so changing the default tone on the Settings screen re-laid-out the three candidates the user reads mid-word. 68 is the widest name plus the 5pt insets, so nothing ever truncates or scales. `ToneIconTests` holds all of it: no tone wears a sparkle, every icon resolves, the button's symbol is one no tone wears, every name fits that width measured against `SuggestionBar.toneLabelFont` itself rather than a second spelling of it, and the width still leaves each candidate 64pt on a 375pt screen. Prose names the control instead of drawing it: `SuggestionBar.aiButtonName` is the one spelling, used by the playground and onboarding, next to `ToneSetting.settingsNote`'s "the one-tap rewrite button" for the other.

## The context-aware engine

- **There is a scoring harness now, and the bar had never been scored before it.** `Bar/typing/corpus.json` has held 90 frozen mid-typing moments and a stock-keyboard reference since it was written, and nothing ran the engine against them — so every judgement about the suggestion bar was somebody's opinion. `Bar/typing/harness/run.sh` runs the real `SuggestionEngine` over all 90 and `score.py` grades them against the corpus's own `intended` / `mustNotCorrect` / `acceptable` fields. **Run it before and after any change in this area; a change that is not measured against it is a guess.** Two things about it that are not obvious. It compiles for the **iOS Simulator**, not macOS, because `UITextChecker` is UIKit and macOS would spell-check with `NSSpellChecker` — a different dictionary, a different ranking, and a score of an engine this repo does not ship. And it passes an **empty in-memory `PersonalLanguageModel`**, so a score can never quietly inherit whatever the machine running it has been typing. The measured numbers: **47/76 before this work, 73/76 after, 26 entries fixed and none broken**. The three that remain are `apos-09` (`were` → `we're`, which needs the sentence and is the async tier's job) and `typo-10`/`typo-11`, where the right Hebrew word *is* offered in slot 1 and is deliberately not committed — see the two-dictionary rule below.
- **The ranking is made of provenance, and the old bar's ranking was the order the code happened to be written in.** `SuggestionEngine+Completions` used to append candidates and take the first three, so `helot` beat `hello`, `הכתום` ("the orange") beat `הכתובת` ("the address"), and `Dizeng` completed to `Dizziness`. Every candidate now carries a `Source` and `SuggestionEngine.score` weighs it: **1000 per source tier, +400 if the previous word is known to be followed by it, up to +300 for frequency, −8 per position in its source's own list, −500 per Hebrew clitic stripped.** Four of those numbers were each set by a regression the corpus caught, so none of them is a free parameter. The ordinal term exists because throwing away `UITextChecker`'s own order made the alphabetical tie-break the ranking and `depl` offered `depletion` and `deplorable` while `deploy` fell off the end. `codeSwitch` sits **above both the checker and the seed list** — below either one, `sta` inside a Hebrew sentence offers `station` and `start` and never reaches `standup`, which is the exact failure the list was written for. `neighbour` sits **below** a completion, because a completion agrees with every key that was pressed and a neighbour claims one of them was wrong. And the clitic penalty is half a tier per letter rather than a tie-break, because `ש`+`ל`+`מוכן` = `שלמוכן` is a real Hebrew construction nobody has ever typed and at a small penalty it outranked `שלום`.
- **Hebrew needed morphology, not a bigger dictionary, and that is why its completions were worse than English's.** Hebrew glues ‎ה ב ל מ ו ש כ‎ to the front of a word, so "to work" is one token `לעבודה` and no dictionary lists the glued forms: `UITextChecker` completed `לעבו` to `לעבוד` and `לעבור`, two verbs, and `מהג` to `מהגרים` ("immigrants") when the sentence was about children coming home from kindergarten. `HebrewMorphology.splits` returns *every* reading, unsplit first, and the seed list is asked about each stem — one entry for `עבודה` then serves `לעבודה`, `בעבודה` and `מהעבודה`. **A one-letter stem is included and only the seed list may answer it**: `מהגן` is `מ`+`ה`+`גן`, so reaching it means completing the single letter `ג`, and asking `UITextChecker` that question returns every word in Hebrew starting with gimel.
- **Two dictionaries have to disown a word before it is replaced, and "absent from the seed" is not one of them.** The seed list is a few hundred words per language, so absence proves nothing: `cat` is not in it, `car` is one edit away and *is*, and the first version of the neighbour rule quietly turned one into the other. Asking `UITextChecker` as well fixed it. The cost is measured and accepted: Apple's Hebrew checker reports `תדוה` and `שלמו` as perfectly good words, so those two typos are **offered in slot 1 and not committed on space**. Being conservative there is the deliberate half of the trade — over-correcting is what makes people switch autocorrect off.
- **The four-letter autocorrect gate stays at four, and three-letter typos are covered by a different rule.** Lowering it to three did fix `teh` → `the`, and it also let any three-letter prefix be replaced by a six-letter word starting with it — `qwt` committed as `qwtxyz` the moment that entry was in the personal dictionary, which is what `PersonalDictionaryTests` names. The distinction that matters is not length but kind: a same-length neighbour is a slip, a longer completion is a guess about a word still being typed. `teh` corrects because `the` is a neighbour, not because of its length.
- **A neighbour may never be shorter than what was typed.** Every prefix is a word in progress, so a shorter neighbour proposes deleting a key the user just pressed: `מונ` on the way to `מונית` is one edit from `מון`, `מאו` on the way to `מאוחר` is one edit from `או`. Allowing it turned four correct Hebrew completions into corrections of half-typed words in a single corpus run.
- **`id` came out of the contraction table and `were` never went in.** Membership in `contractions` is what makes a word get replaced on space, and both of those have an ordinary reading — `That's a good id` committed as `That's a good I'd` (corpus `nc-02`). The rest of the table has no such reading, so this is one criterion applied once to the table rather than a per-word rule at runtime; an earlier fix that special-cased `were` with a list of plural subjects was exactly the tailored logic this repo should not carry. `its`, `cant`, `ill` and `thats` are all ordinary English words too and all *stay*, which is why the contraction test is asked **before** the "we never correct a known word" test and not after.
- **Learning is scoped to the real keyboard, and it was not, and the test suite noticed for us.** `PersonalLanguageModel` records committed words and word pairs into the App Group. Every unit test and the app's onboarding playground drive a real `KeyboardController` and press real space bars, so all of them were writing into it: the suite alone had taught it `Handi` ten times and `Nitai` nine, past `protectThreshold`, so `PersonalDictionaryTests` silently stopped being able to prove the personal dictionary does anything — the words it was checking were being defended by a store the tests had filled themselves. `KeyboardController.personal` is `.shared` only when `isSystemKeyboard` is true and a throwaway otherwise. **Nothing from `SharedStore.shippedPersonalDictionary` may go in the seed list either**, for the same reason: two lists defending one word means neither can be shown to work.
- **The async tier may change the options and never the default.** `PredictiveRefiner` waits 300 ms after the last keystroke and may replace slots 1 and 2. It may not touch slot 0 (the literal keystrokes) and `applyRefinement` re-applies `markDefault` at whatever index the local tier chose, so **what the space bar commits is always decided by deterministic local code**. Without that rule every pause in typing is a moment where the word about to be inserted silently becomes a different one. It also refuses to apply at all if the word in progress changed while the call was in flight — and the prefix is handed back through the callback rather than re-read, because the first version compared `currentWordPrefix` against `currentWordPrefix` and was a staleness check that could never fail.
- **The local tier's cost is measured and the harness prints it, because "fast enough for every keystroke" is the assumption the whole two-tier design rests on.** Over four runs of the 90 corpus entries, warm, on the iOS 26.2 Simulator: **median 1.1-1.3 ms, worst entry 10-16 ms**, and *which* entry is slowest changes between runs of identical code — one run also produced a 27 ms outlier that did not reproduce, so the same "one run is not evidence" rule that governs the Bar corpora governs this number too. The shape is stable and is the part to reason about: the slow entries are always Hebrew words where the seed list has nothing and more than one clitic reading has to be put to `UITextChecker`. The **first** call in a language is separate and much larger, ~70-280 ms, because Apple builds that language's lexicon then; a user pays it once per keyboard session and `run.sh` reports it on its own line so it is never averaged into the per-keystroke figure. Two costs were found by measuring rather than by reading: the seed list was being folded on every keystroke (785 English words, *twice* each, inside the prefix scan) and is now folded once at load, and a split Hebrew reading no longer asks `UITextChecker` when the seed already answered that reading — worth about a third of the worst case, with the corpus score unchanged.
