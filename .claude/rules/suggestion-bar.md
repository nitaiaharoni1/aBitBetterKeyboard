# Suggestion bar, autocorrect and the personal dictionary

- **A setting is not a feature until something reads it, and the personal dictionary was written, persisted, reset, counted in Settings and read by nothing.** `SharedStore.personalDictionary` had no consumer outside its own editor, so on a stock install this keyboard's autocorrect destroyed the three names the app ships in that very list: `Nitai` committed as `Nit` on the space bar, `Handi` as `Handing`, `Wispr` as `Wiser`, and both Hebrew entries too — `סאפא` as `ספא`, `בלי־פרופ` as `בלי־פרוף`. The slot was already there and filled with something else: `SuggestionEngine.suggestions(supplementary:)` took `UILexicon` alone. Four things to keep true. The dictionary check is the **first** question `shouldAutocorrect` asks, not a clause on `isKnownWord` at the bottom — the contraction table and the Hebrew final-form rule both `return true` above that line, and the final-form rule is what ate `בלי־פרופ`. The keyboard reads `storedPersonalDictionary`, which goes through `UserDefaults` at the moment of the keystroke, because the editor is in the app and `load()` fills the `@Published` copy once per launch (same reason as `storedDefaultTone`) — and `load()` honours an empty stored list rather than treating it as absent, or the two readers disagree about a list the user emptied while Settings keeps counting six. Matching folds the maqaf U+05BE onto ASCII `-`: Hebrew's own hyphen is what the shipped entry is spelled with and `KeyboardLayout.connectors` gives a Hebrew layout only the ASCII one, so without the fold that entry is unreachable by anything its owner can type. `PersonalDictionaryTests` drives all of it through `KeyboardController`, not through the engine — the engine was never the broken half.
- **And the fourth thing is the one that survived the first fix: a mark after the word.** `currentWordPrefix` runs back to the last *whitespace*, so `Hi Nitai,` reaches the engine as `Nitai,`, which is not `Nitai` — so the list stopped protecting a name the instant a comma touched it, and `Hi Nitai,` still committed as `Hi Nit`, byte for byte what the same input gives with the list emptied. Greeting somebody by name with a comma is the commonest way a name reaches a chat field, so the first fix missed most of the defect. `SuggestionEngine.wordCore` trims edge punctuation (both ends, so an entry like `Ph.D.` reduces the same way whichever side the mark is on) and strips a trailing `'s`, because `'` is punctuation but the `s` after it is not and `Nitai's` came back `Nita's`. The length gate and `isKnownWord` are asked about that trimmed word too — a comma was worth a letter, and `qwt,` reads as four characters and unknown, which pulled a three-letter word onto a six-letter entry. Two traps. `comparable` answers "" for a prefix that is only punctuation, and "" is a prefix of every entry, so both call sites check for it or typing `...` offers two arbitrary names. And a *separate* bug lives next door with no dictionary near it: `replaceCurrentWord` deletes the whole prefix, so every correction ate the mark — `recieve,` committed as `receive `, `helo,` as `help `. `KeyboardController.restoringTrailingMarks` puts it back, and must not when the candidate already carries it, because candidate zero *is* the literal keystrokes.
- **The one-tap rewrite key is the only key besides the space bar that commits on lift, and a model call is why.** Long-pressing it opens the registers in `KeyView`'s alternates popup — the same mechanism as a letter's accents, stacked vertically because seven register names is about 1,000 points of width on a 393-point screen. But a letter has *already inserted* its character on finger-down and picking an accent replaces it, whereas this key runs a cloud call: firing on finger-down would spend one on the default tone every time the user held the key to choose a different register, and `beginWork` cancels its predecessor, so the answer being paid for would be thrown away by the register actually wanted. `KeyView.runsOnLift` defers it; a plain tap still runs the default, just on the lift. Three things to keep true. The list is **default-first** (`KeyboardController.toneAlternates`), because `KeyView` treats index 0 as "the long press changed nothing" — a list spelled `ToneStyle.allCases.map(\.title)` looks right and gives every user Clearer when they hold, look and lift without moving. Selection is **by title, not by index**, because the order is built from a stored setting that Settings can change in another process between the key being drawn and the finger lifting. And the popup is a drag, so the registers also hang off the key as `accessibilityActions` — the same rule the layout editor is built on, that every gesture has a non-gesture route. `ToneAlternatesTests` holds all of it. A custom tone that is *written but not selected* is deliberately absent from the list: `ToneSetting` only resolves to `.custom` when `prefersCustomTone` is on, so there would be no instruction to send, and `AIResultPanel.toneChips` gates its custom chip on exactly the same condition.
- **Two brand-tinted buttons sit side by side in the suggestion bar, and both of them were wrong.** The sparkle was disabled by `hasTextToWorkWith || canReply`, which is false on an empty field with no session — the exact state D8's affordance is for, since the broadcast picker lives in the Reply panel and the sparkle is the only route there. It now asks `AIMenuPanel.hasRunnableAction`, so the button and the panel it opens cannot disagree again. Its neighbour runs the default tone, and it used to wear that tone's own SF Symbol — which for the shipped default `.clearer` was `sparkle`, the same drawing as `sparkles` at a different count, so two sparkles sat side by side meaning two different things. Fixing the symbol per tone (`.clearer` became `eyeglasses`) only moved the problem: `figure.wave` for Casual is a waving stick figure in a keyboard, which reads as a profile button and says nothing about rewriting. **So the glyph is now fixed at `SuggestionBar.toneButtonSymbol` — `AIAction.rewrite`'s own icon, because the button is a shortcut through that row — and the tone is printed in words under it.** `ToneStyle.icon` survives for the tone picker and result variants, where a panel header already says what the screen is about; `ToneSetting.icon` had no other reader and is deleted. **The button is a fixed 68pt for every tone, not sized to its label**, because its width is a *setting*: growing it put `Professional` at 67pt against `Casual`'s 44, so changing the default tone on the Settings screen re-laid-out the three candidates the user reads mid-word. 68 is the widest name plus the 5pt insets, so nothing ever truncates or scales. `ToneIconTests` holds all of it: no tone wears a sparkle, every icon resolves, the button's symbol is one no tone wears, every name fits that width measured against `SuggestionBar.toneLabelFont` itself rather than a second spelling of it, and the width still leaves each candidate 64pt on a 375pt screen. Prose names the control instead of drawing it: `SuggestionBar.aiButtonName` is the one spelling, used by the playground and onboarding, next to `ToneSetting.settingsNote`'s "the one-tap rewrite button" for the other.
