# Suggestion bar, autocorrect and the personal dictionary

- **Current launch rule, which supersedes the older construction note below.** A real system-keyboard controller does not score suggestions during construction. `suggestionWorkIsActive` gates the body of `refreshSuggestions` after cheap document and field bookkeeping, so early UIKit callbacks cannot cold-build the checker, typo lexicon, personal model or refiner before presentation. `viewDidAppear` warms rebuildable caches off-main and then calls `activateSuggestionWorkAfterPresentation()`, whose first refresh keeps refinement off. Non-system controllers remain eager so previews and existing focused tests keep a populated bar at construction.
- **A suggestion is the offer, not a fresh identity.** `Suggestion.id` is a `UUID` minted in the memberwise init so two slots can be told apart, and the synthesised `Equatable` counted it, so every `refreshSuggestions` produced three unequal values even when the offers had not moved. The bar then spent `Theme.Motion.quick` fading them — 180ms behind every letter. Equality is text, language, the bold flag and commit behavior; the candidates snap, while two visually identical offers with different write behavior still republish. `SuggestionEngineTests.testTwoOffersOfTheSameWordAreTheSameOffer` and the commit tests hold both halves.
- **A provably premature Hebrew boundary is a structural, tap-only offer.** `שלו םלכולם` becomes `שלום לכולם`, but the offer carries `Commit.replaceSuffix`, is never bold, and neither Space nor complete-on-pause may apply it. The exact source suffix is recomputed immediately before mutation; a selection, a continuing or unavailable after-caret context, a stale suffix, or an incomplete delete refuses the write. A partial delete is rolled back before the bar refreshes. Whole-text Fix is stricter than a deliberate tap: it refuses an empty remainder, so a legitimate standalone final letter such as `האות ם` is not silently joined, while the bar can still offer `שלו ם` for the user to choose. The structural repair occupies the bar by itself on purpose: ordinary candidates score only the malformed right-hand fragment and compete with the one whole-phrase correction the lexicon can actually prove.
- **Autocorrect, Predictions, Auto-capitalise and the language list are settings the keyboard must re-read, and the default candidate is bold, not a chip.** Space commits the default suggestion only when `storedAutocorrectLevel` is not `.off` — the `@Published` copy is filled once at launch, so a toggle flipped in the app while the keyboard is already up is invisible unless the space bar and `refreshSuggestions` go through UserDefaults at the keystroke (same trap as `storedPersonalDictionary`). When the setting is off, `refreshSuggestions` also re-marks slot 0 as default so the bar does not bold a correction space is no longer allowed to commit; a deliberate tap on a candidate still inserts it. Predictions uses `storedPredictions`, Return and double-space use `storedAutocapitalise`, and the globe / space-bar strip use `storedEnabledLanguages`, for the same reason. `KeyboardViewController.viewWillAppear` also calls `SharedStore.load()` so the published copies the rest of the chrome draws from catch up when the keyboard comes back on screen. The default slot is drawn in bold weight with no background fill.
- **Autocorrect is three positions, the middle one is a floor on a named reason, and every price under it was measured rather than reasoned.** `SuggestionEngine.commitReason` used to answer `Bool`, which threw away *which* of its dozen rules had fired at the last step — and those rules rest on wildly different evidence, from a closed contraction table to "no dictionary has heard of these four letters, take whatever ranked first". It returns a `CommitReason` now, priced in `AutocorrectConfidence.swift`, and `AutocorrectLevel.confidenceFloor` is the only place a price is compared with anything: `.off` answers 101 so nothing reaches it, `.confident` 86, `.full` 0. One comparison covers all three, and a rule added later is priced once and lands on the right side by itself. **Nil is not zero confidence** — `.full` floors at 0, so folding "no reason at all" into a number would commit every word the cascade explicitly refused.
- **The prices came from a probe over `Bar/typing/typos/`, and the first guess at two of them was wrong.** Reasoning from the shape of each rule put `frequency` at a cost of 61–99 *above* the floor ("two explainable slips, still under one wild guess") and the four-letter fallback *below* it. Measured, that band is the worst tier in the file at 1 right and 3 wrong, and the fallback is 5 right and 1 wrong. Per tier, over the 107 corrections: contraction 7/0, Hebrew final form 5/0, frequency at 92 31/1, transposition 9/0, singleEdit 28/2, unknownWord(explainable) 5/0 — then below the floor, frequency at 72 5/6 and unknownWord(unexplainable) 0/1. **Everything above the floor is 93% right or better and everything below it 45% or worse**, so the cut sits in a gap. Two splits do that work, and both reuse machinery already in the file rather than adding a constant: a `frequency` **transposition** is exempt from the cost bound (it rescues `שלמו` → `שלום`, `typo-11`, one of the two entries NIT-153 shipped the corrector to close, at cost 80 = transposition 60 + final form 20), and the four-letter gate now asks `TypoChannel` whether it can price the distance at all — which is what separates `צריכ` → `צריך` from `yjis` → `egos`, three substitutions in a four-letter word. **Neither changes anything at `.full`**, verified: the typo corpus reads 90/7/10 with 21/21 controls before and after, stable over two runs.
- **`.confident` is the shipped default (`AutocorrectLevel.shippedDefault`), and the bill is seven corrections for seven wrong words.** Typos corpus 90 committed / 10 WRONG at `.full` against 85 / 3 at `.confident`, controls 21/21 both; frozen 90 goes 75/76 → 73/76, losing `restaraunt` → `restaurant` (a rotation the channel cannot price inside a ten-letter budget) and `בעוד רבה` → `בעוד רבע` (the sentence-follower override, priced 78 and dropped on purpose). `Bar/typing/harness/run.sh` takes `AUTOCORRECT_LEVEL`; **unset means `shippedDefault`, not `.full`**, so a bare run and `Bar/drift/` measure the product. `SuggestionEngine.suggestions` keeps its own default at `.full`, which means "ask every rule" — the cascade's behaviour, which is what a unit test of the cascade wants. **The old boolean migrates through a new key**: `UserDefaults` reads a stored `Bool` back as the integer 1, which is `.confident`, so reusing `Key.autocorrect` would have landed on the right answer by coercion instead of by decision. An install that had it on gets `shippedDefault`; off stays off.
- **The default is drawn in the middle, and the engine array is not the drawing order.** Mid-word `rank` still pins the typed keystrokes at index 0 so the refiner and `testTheLiteralKeystrokesAreAlwaysSlotZero` can find them. `SuggestionBar.centeredSlots` is the drawing order: default in slot 1, the others on either side, a lone offer centered, an empty prefix (next-word) unfiltered. **The typed echo is drawn when the bar is completing the word and dropped when it is correcting it**, and it takes *two* questions to tell those apart. It used to be dropped unconditionally, on the argument that it is already in the field, and the cost was that **a correctly typed word produced a bar with no bold slot at all**: `centeredSlots` fell through `firstIndex(where: \.isDefault) ?? 0` to a candidate carrying `isDefault == false`, which `candidate(_:)` draws `.light` and gives no `accessibilityHint`, so the row that exists to say what space will do said nothing, and the one word it could have said it about was the only one not on screen. The first question is therefore `isDefault` on index 0, which means nothing is going to replace the word. **The second question exists because being the default is not enough, and a Hebrew typo is why.** Apple's Hebrew checker calls `תדוה` and `טןב` real words, so `commitReason` deliberately declines to commit `תודה` and `טוב` and leaves the default on the keystrokes (the two-dictionary rule below) — and boldening the echo there is a keyboard endorsing a typo it is holding the fix for, and pushing that fix out of the middle to do it. So the bar also asks whether anything on offer **continues** the keystrokes: a completion agrees with every key that was pressed, a correction disagrees with one, and a bar holding corrections alone is saying the word is finished and wrong. **Measured 2026-08-16 over 44 inputs through the real engine**, that line lands on every one: `cat`, `dog`, `בית`, `אני`, `hel`, `hel,` and `אפ` all carry a continuation and keep their own word bold; `מכונ` carries `נכון` **and** `מכונה`, and the completion is what keeps its slot, which is why the test is not "any correction present" — and that completion is candidate *four*, so the evidence keeping the echo on screen is itself pushed off it, which is the right way round, because whether a word is still being typed is something the engine knows and reading it off the drawn slots would be circular; `תדוה`, `טןב` and `qwt` carry nothing but a correction and keep today's bar exactly (the fix centered, unbolded, nothing bold in the row — the honest third state, since space will insert neither). A word with **no** offers keeps its slot, because `כן`, `תודה` and `עכשיו` have no completions in any dictionary here and an empty bar is not an answer. `SuggestionEngine.barSlots + 1` covers every shape — echo plus two offers, or three offers — so the row is full either way. Do not "fix" any of this by reordering `controller.suggestions` itself; `applyRefinement` holds index 0 as the literal, and swapping the array would let the model replace the word the user typed. **No corpus number can move with it**: `Bar/typing/harness/main.swift` records `results.map(\.text)` and `defaultIndex` off the engine and never calls `centeredSlots`, so the frozen 90 and the sweep both grade the array this only changes the drawing of. Four tests hold the corners. `SuggestionEngineTests.testTheTypedWordIsDrawnBoldWhenNothingWillReplaceIt` fails a bar that still throws the echo away; `testTheTypedWordIsNotDrawnWhenACorrectionTakesTheDefault` fails one that draws the typo beside its own correction; `testTheEchoGivesUpItsSlotWhenTheBarIsOnlyOfferingACorrection` and `testACorrectionBesideACompletionStillLeavesTheKeystrokesBold` are the two halves of the continuation question, and **`testANearbyHebrewTypoDrawsTheIntendedWord` is what caught the version that had only the first question** — it went red on `טןב` the moment the echo could take the middle, which is the whole reason that second question exists. `testATrailingMarkStillHidesTheEchoBehindACorrection` asserts the `comparable` match through the correction case: an echo holding the default is drawn whether or not the comparison matched, so only a moved default makes that half load-bearing.
- **The bar has three slots and the engine only ever filled two of them, for the whole life of the feature.** `completions(for:)` asked `rank` for three candidates and the first of those three is the literal keystrokes, which `centeredSlots` then throws away because they are already in the field — so a third of the one row this keyboard has for suggestions was blank on nearly every keystroke. Measured over 234 letter-by-letter moments across 30 Hebrew and 20 English words: **229 of them drew two candidates and a gap**; the frozen corpus shows the same two-entry `slots` on every mid-word entry, which is why no score could see it. Mid-word the engine now returns `SuggestionEngine.barSlots + 1` and the empty-prefix path returns `barSlots`, because next-word has no echo to filter. Three call sites encode that number and all three had to move together — `completions`, `nextWordSuggestions`, and `applyRefinement`, whose `0..<3` was the one path that could shrink the bar back to two the moment the model answered. The **supplementary cap went from 2 to `barSlots` with it**: two was the number of offers that could be shown, so on the *highest* ranked source it meant a third name typed by hand into Settings could never reach the bar. Corpus unmoved at 73/76 over two runs each side. `PersonalDictionaryTests.testTheBarDrawsThreeOffersAndNotTwo` asserts through `centeredSlots` rather than through the engine array, because the engine returning four proves nothing about what reaches the screen.
- **A tap in the host field moves the caret without a key, and `selectionDidChange` is how the keyboard hears about it.** `textDidChange` does not fire for a caret-only move, so without this override the bar keeps scoring the word the caret just left. **Refresh only.** Clearing `revertibleEdit` here would delete the undo on the same turn as the insert that created it, because this keyboard's own insertions move the caret too. `deletedWordPrefix` expires by itself when the word under the caret no longer starts with it.
- **A double tap selects a word and asks what else it could be, and for the whole life of the bar the answer was about a different word.** With a range selected `documentContextBeforeInput` stops at the *start* of it, so `currentWordPrefix` is whatever run sits in front of the selection — for a double-tapped word, nothing at all — and the engine was handed `""`: next-word predictions, in the middle of a sentence the user had just pointed at, with the one word they were asking about the one word the bar could not see. **And they were live.** `replaceCurrentWord` has always had a selection branch, so tapping one of those predictions replaced the selected word with an unrelated guess and added a space after it; the bar was not merely useless over a selection, it was the one state where every slot in it was destructive. `KeyboardController.wordUnderConsideration` is what every reader takes now (`refreshSuggestions` scores it, `SuggestionBar` filters the echo against it), and `selectedWord` is the gate. **Three boundary tests, because part of a word is a different question and any answer to it would be typed over half a word**: one token, nothing joined to the leading end, nothing joined to the trailing end. The leading test is `wordCore(currentWordPrefix).isEmpty` rather than `isEmpty`, so `("recieve")` is still a selected word — the marks are not a word joined to it — and the trailing test is `KeyboardController.staysInsideWord` (dropped its `private` for this), so `don` out of `don't` is refused for the same reason typing an apostrophe does not finish a word. Five consequences, each of which is a defect if it goes the other way. **There is no default at all**, which is a third answer rather than a harder version of Autocorrect-off: space types a space over a range (`insertSpace` already refuses the commit there), so nothing is "inserted when you press space" and nothing may be drawn as if it were. Pinning slot 0, which is what the other two reasons do, does not do that job here: slot 0 *is* the selected word, so under any rule that draws the default it comes back at the user, bold, in the middle slot. **The tap inserts no trailing space**, because the spacing is already in the field and `I recieve it` came back `I receive  it`; scoped to `selectedWord`, so the partial-selection case `CandidateCommitTests.testASelectionIsReplacedAndNothingAroundItIs` pins is untouched. **The word picked is hand-placed**, so `deletedWordPrefix` is taken from the field after the replacement — the caret is left inside a sentence with no space after it, and without that the very next space bar corrects a word the user chose out of the bar (`teh` is the neighbour rule doing exactly that, measured: it commits `the`). **`replaceCurrentWord`'s selection branch restores edge marks**, or a selected `Nitai's` comes back `Nitai` — but only for a whole selected word, because `wordCore` trims the full stop off a selected `hello world.` and would glue it to a one-word candidate. And **the candidate's accessibility hint gains a third sentence** ("Replaces the selected word"), because a bar with no default read out as three bare words: same rule the microphone key is under. The async tier is not asked over a selection: nobody is typing, and `applyRefinement` would drop the answer anyway because the prefix it hands back is not `currentWordPrefix`. **`Bar/typing/harness` and the sweep are structurally blind to this** — `run.sh` compiles `SuggestionEngine*.swift` and the models and no controller or view at all — so the frozen 90 can neither confirm nor regress it, and `SelectedWordSuggestionTests` is the whole of the regression evidence. What the harness *can* do is answer what the engine returns for the strings this feature now hands it, which is how the fixtures were checked rather than guessed (measured 2026-08-16, throwaway corpora): `recieve` → `receive` in slot 1, `שלומ` → `שלום` in slot 1, `recieve,` → `receive` (so the tap restores the comma), and a *correctly spelled* word answers with its own inflections — `receive` offers `received` / `receiver`, `meeting` offers `meetings`, which is the second thing this feature turns out to be good for. **A correctly spelled Hebrew word gives an empty bar** (`שלום` and `עבודה` each come back as one candidate, the echo, which is dropped), and that is the honest answer rather than a bug to fill: the alternative is the next-word list this bullet exists to remove. One assumption is inherited rather than proved here: that the real `UITextDocumentProxy` reports the context either side of a selection and deletes the whole selection on one backspace. `LiveTextViewTarget` is a hand-written model of that, not the proxy — every shipped AI action over a selection already rests on it (`aiTargetText`, `replaceTargetText`), so this feature is not a new bet.
- **The first delete after space undoes the swap, and a later delete does not.** Space that actually replaced the typed word remembers `(original, replacement)` in `pendingAutocorrectUndo`. The next `deleteBackward` that would eat the trailing space restores `original` and drops the space. Offered candidates stay; only the automatic replacement goes. The same spelling is not swapped again this session (`undoneAutocorrectSpellings`, folded, no timestamps). A later letter, a caret that is no longer sitting after `replacement `, Return, a tapped candidate, or a new space clears the pending pair. Do not use `revertibleEdit` for this: that slot is Fix / Rewrite. Autocorrect-off never swapped, so there is nothing to undo. `CandidateCommitTests` holds the cases, each with a control half that *types* the same word, so a build that simply turned autocorrect off fails them.
- **A word the user has backspaced into is never autocorrected, and the delete key undoing itself is why.** Deleting the `ן` off `מאמין` leaves `מאמי`, which no dictionary knows, so `commitReason` read it as a typo and the next space put a different word in the field: the user pressed delete to *change* the word and the keyboard changed it back, which is the single most infuriating thing an autocorrect does. `KeyboardController.deleteBackward` snapshots the word left standing into `deletedWordPrefix` and `isCorrectingWordByHand` is true while the word in the field still starts with it — so typing on from the repair stays protected and any other word does not. Three things about the shape. It is **a prefix snapshot rather than a flag**, because the caret can move without this keyboard hearing about it (a tap elsewhere in the host's field goes through no key at all) and a flag would then suppress autocorrect on a word nobody has touched; it is the same claim-checked-rather-than-trusted shape as `GroupedInput.lastWritten`, and it is still cleared outright wherever a word is finished on purpose — `insertSpace`, `apply`, Return and either cursor key — because the residual case the prefix test cannot see is the *same* word typed again straight afterwards, and a short repaired prefix is a prefix of plenty of other words. The **accents popup lands here too, deliberately**: it picks an alternate by calling `deleteBackward()` and retyping, and `צ׳יפס`, `col·legi` and `café` are exactly the words no dictionary holds and autocorrect destroys. It is checked in **both** `refreshSuggestions` (bold slot back to the literal keystrokes) and `insertSpace` (the commit itself), exactly as `storedAutocorrectLevel` is — slot zero being the literal is a fact about `SuggestionEngine` and the space bar should not break if it stops being one. And only the *automatic* replacement goes: the correction is still offered in the bar and a deliberate tap still commits it. Space on pause is the other automatic path and it **does** fire after backspace: the wait from the deleted letters is armed on a prefix that is gone, so `deleteBackward` starts a new one, `idleTypingMayRun` no longer treats a hand repair as "not typing", and `performIdleTyping` still skips *completing* the word so `hel` → `he` cannot become `hello`. `insertSpace` already skips autocorrect for the same repair. `IdleTypingTests.testIdleSpaceFiresAfterBackspace` is what fails a wait that only starts from letters. `CandidateCommitTests` holds all three, each against a control half reaching the identical word by typing rather than by deleting, so a build that simply switched autocorrect off fails them. The other thing that rewrites text on a backspace is `deleteGroupedStroke`, which is grouped keys re-decoding and is correct: see `.claude/rules/keyboard-layout.md`.
- **A setting is not a feature until something reads it, and the personal dictionary was written, persisted, reset, counted in Settings and read by nothing.** `SharedStore.personalDictionary` had no consumer outside its own editor, so on a stock install this keyboard's autocorrect destroyed the three names the app ships in that very list: `Nitai` committed as `Nit` on the space bar, `Handi` as `Handing`, `Wispr` as `Wiser`, and both Hebrew entries too — `סאפא` as `ספא`, `בלי־פרופ` as `בלי־פרוף`. The slot was already there and filled with something else: `SuggestionEngine.suggestions(supplementary:)` took `UILexicon` alone. Four things to keep true. The dictionary check is the **first** question `commitReason` asks, not a clause on `isKnownWord` at the bottom — the contraction table and the Hebrew final-form rule both `return true` above that line, and the final-form rule is what ate `בלי־פרופ`. The keyboard reads `storedPersonalDictionary`, which goes through `UserDefaults` at the moment of the keystroke, because the editor is in the app and `load()` fills the `@Published` copy once per launch (same reason as `storedDefaultTone`) — and `load()` honours an empty stored list rather than treating it as absent, or the two readers disagree about a list the user emptied while Settings keeps counting six. Matching folds the maqaf U+05BE onto ASCII `-`: Hebrew's own hyphen is what the shipped entry is spelled with and `KeyboardLayout.connectors` gives a Hebrew layout only the ASCII one, so without the fold that entry is unreachable by anything its owner can type. `PersonalDictionaryTests` drives all of it through `KeyboardController`, not through the engine — the engine was never the broken half.
- **And the fourth thing is the one that survived the first fix: a mark after the word.** `currentWordPrefix` runs back to the last *whitespace*, so `Hi Nitai,` reaches the engine as `Nitai,`, which is not `Nitai` — so the list stopped protecting a name the instant a comma touched it, and `Hi Nitai,` still committed as `Hi Nit`, byte for byte what the same input gives with the list emptied. Greeting somebody by name with a comma is the commonest way a name reaches a chat field, so the first fix missed most of the defect. `SuggestionEngine.wordCore` trims edge punctuation (both ends, so an entry like `Ph.D.` reduces the same way whichever side the mark is on) and strips a trailing `'s`, because `'` is punctuation but the `s` after it is not and `Nitai's` came back `Nita's`. The length gate and `isKnownWord` are asked about that trimmed word too — a comma was worth a letter, and `qwt,` reads as four characters and unknown, which pulled a three-letter word onto a six-letter entry. Two traps. `comparable` answers "" for a prefix that is only punctuation, and "" is a prefix of every entry, so both call sites check for it or typing `...` offers two arbitrary names. And a *separate* bug lives next door with no dictionary near it: `replaceCurrentWord` deletes the whole prefix, so every correction ate the mark — `recieve,` committed as `receive `, `helo,` as `help `. `KeyboardController.restoringEdgeMarks` puts it back, and must not when the candidate already carries it, because candidate zero *is* the literal keystrokes.
- **The one-tap rewrite key is the only key besides the space bar that commits on lift, and a model call is why.** Long-pressing it opens the registers in `KeyView`'s alternates popup — the same mechanism as a letter's accents, stacked vertically because six register names is about 1,000 points of width on a 393-point screen. **The stack grows down from the key**, default nearest the finger: index 0 sits just below the action-row button and later names drop over the QWERTY block. `alternatesPopupAlignment` is `.bottom` and the offset is `+(stackHeight + 6)` so the list starts 6 points below the key. `AlternatesPopupTests.testTheFixPopupGrowsDownFromTheKey` is what fails an upward stack. But a letter has *already inserted* its character on finger-down and picking an accent replaces it, whereas this key runs a cloud call: firing on finger-down would spend one on the default tone every time the user held the key to choose a different register, and `beginWork` cancels its predecessor, so the answer being paid for would be thrown away by the register actually wanted. `KeyView.runsOnLift` defers it; a plain tap still runs the default, just on the lift. Three things to keep true. The list is **default-first** (`KeyboardController.toneAlternates`), because `KeyView` treats index 0 as "the long press changed nothing" — a list spelled `ToneStyle.allCases.map(\.title)` looks right and gives every user Clearer when they hold, look and lift without moving. Selection is **by title, not by index**, because the order is built from a stored setting that Settings can change in another process between the key being drawn and the finger lifting. And the popup is a drag, so the registers also hang off the key as `accessibilityActions` — the same rule the layout editor is built on, that every gesture has a non-gesture route. `ToneAlternatesTests` holds all of it. A custom tone that is *written but not selected* is deliberately absent from the list: `ToneSetting` only resolves to `.custom` when `prefersCustomTone` is on, so there would be no instruction to send. `AIResultPanel.toneChips` used to gate its custom chip on exactly the same condition and was the other surface this had to agree with; that panel is deleted, so this popup is the only reader of `customTone` now.
- **Two brand-tinted buttons sit side by side in the suggestion bar, and both of them were wrong.** The sparkle was disabled by `hasTextToWorkWith || canReply`, which is false on an empty field with no session — the exact state D8's affordance is for, since the broadcast picker lived in the Reply panel and the sparkle was the only route there. It was fixed by asking the panel the same question the panel asked itself. **Both the sparkle and that panel are now deleted**: Reply has its own key in the action row and the picker is the banner message, so the route no longer depends on a button agreeing with a screen. What survives of the fix is `AIAction.isAvailable` / `.hasRunnableAction` — the 2026-08-25 cleanup deleted `SuggestionBar.anyActionCouldRun` and `isEnabled` (no view ever read them; the live gate is `KeyboardController.isActionKeyDisabled`), so `AIButtonTests` asserts `AIAction` directly, because the bar holding its own opinion about an empty field is what caused this. Its neighbour runs the default tone, and it used to wear that tone's own SF Symbol — which for the shipped default `.clearer` was `sparkle`, the same drawing as `sparkles` at a different count, so two sparkles sat side by side meaning two different things. Fixing the symbol per tone (`.clearer` became `eyeglasses`) only moved the problem: `figure.wave` for Casual is a waving stick figure in a keyboard, which reads as a profile button and says nothing about rewriting. **So the glyph is now fixed at `SuggestionBar.toneButtonSymbol` — `AIAction.rewrite`'s own icon, because the button is a shortcut through that row — and the tone is printed in words under it.** `ToneStyle.icon` is what Settings' default-tone menu and the Rewrite hold menu draw beside each name. `FixStyle.icon` is the same mark on the Fix hold menu. The one-tap bar button still wears `SuggestionBar.toneButtonSymbol`, not the selected tone's icon. `ToneSetting.customIcon` is only the pencil on "My tone". **The button is a fixed 68pt for every tone, not sized to its label**, because its width is a *setting*: growing it put `Professional` at 67pt against `Casual`'s 44, so changing the default tone on the Settings screen re-laid-out the three candidates the user reads mid-word. 68 is the widest name plus the 5pt insets, so nothing ever truncates or scales. `ToneIconTests` holds all of it: no tone wears a sparkle, every icon resolves, the button's symbol is one no tone wears, every name fits that width measured against `SuggestionBar.toneLabelFont` itself rather than a second spelling of it, and the width still leaves each candidate 64pt on a 375pt screen. Prose names the control instead of drawing it: `SuggestionBar.aiButtonName` is the one spelling, used by the playground and onboarding, next to `ToneSetting.settingsNote`'s "the one-tap rewrite button" for the other.
- **`openWord` is a safety net for a chat Send, and both of its triggers were wrong.** It exists because Send empties the field without pressing space, so `learnWordJustCommitted` sees nothing and the last word of a message would go untaught; `adoptOpenWord` restages it from `currentWordPrefix` on every refresh instead. Two defects, both in that restaging. **It never checked whether the word continues past the caret.** `currentWordPrefix` is only the run *behind* the caret, so tapping back into an already-finished word — `"wor|ld"` — restaged the fragment `wor` as the word to learn, and a Send moments later taught it. The guard is the same one `selectedWord` already asks at its trailing end (`next.isLetter || next.isNumber || KeyboardController.staysInsideWord(next)` against `contextAfter`): refuse to adopt rather than overwrite, and whatever `openWord` already held — the word actually last finished being typed — stays. `learnWordJustCommitted` needed the identical guard for the same reason from the other side: it fires right before a terminator lands, and a terminator pressed with the caret mid-word (Return splitting a line, a mark typed inside a word) reached it with `currentWordPrefix` already cut at the caret too. **And the commit trigger was `currentWordPrefix.isEmpty`, not the document being empty.** That reads true of *any* caret at a word boundary, not only of Send — `"hello| world"` is empty by that test exactly as `""` is — so tapping between two words in an unfinished message taught whatever `openWord` held. `documentHasText` is the fresh answer already sitting on the controller (`refreshDocumentState` sets it one line above `adoptOpenWord`'s call), so the commit is gated on `!documentHasText` instead. `OpenWordLifecycleTests` holds all four shapes: a caret parked mid-word then moved, a caret tapped to a boundary in a non-empty document, `learnWordJustCommitted` asked directly over a mid-word caret, and the control — a host that actually empties the field still teaches the word that was open in it.
- **`openWord` also used to be judged by the wrong field's permission, and the fix is capturing the answer rather than clearing the word.** iOS keeps one controller alive across fields and across host apps, so a word left open in a credential field — never finished with a space or a Return before the keyboard came up over a different, permitting field — was committed with `target?.isSecureTextEntry` re-read at commit time, which by then answered for the *new* field. `openWordPermitted` is `SecureField.permitsRead` captured the instant `adoptOpenWord` adopts the word, while `target` still is the field the letters were typed into, and `recordCommittedWord(_:permittedOverride:)` honours that captured answer instead of re-deriving one whenever a caller is committing `openWord` rather than the word just typed. **This is deliberately not a blanket wipe of `openWord` on every document switch.** A wipe would have been the wrong trade: it protects the credential case for the wrong reason (there is nothing left to leak) and it destroys the ordinary one, where a word typed under a permitting field is switched away from before a terminator and still deserves to be taught on the next natural trigger. `OpenWordLifecycleTests.testAWordAdoptedUnderARefusingFieldIsNotLearnedUnderTheNextFieldsPermission` and its control (`...UnderAPermittingField...StillLearned...`) are the two halves — the second is what a blanket clear would have failed. **A write that is *attempted* and refused still has to drop the word**, or a caller reaching `recordCommittedWord(openWord, ...)` a second time on a stale `openWord` — `learnWordJustCommitted`'s own empty-prefix branch, which never cleared it on refusal the way `adoptOpenWord`'s caller-side clear happened to — could try again later under yet another field. `recordCommittedWord` clears `openWord` unconditionally now, after the write attempt, whether `personal.record` wrote or refused.
- **An email address is the one string this keyboard learns verbatim, and it was never learning it at all.** `PersonalLanguageModel.record()`'s character-class gate — letter, apostrophe or hyphen — refused `@`, every digit and the four marks a word can carry *inside* it without ending: Hebrew's geresh and gershayim, the Catalan interpunct, a standalone Persian zero-width non-joiner (attached to the letter before it the non-joiner already read as part of that letter's `Character` under the old gate — Unicode's own grapheme rule, not this one). The marks are added to the ordinary-word check on both sides of a bigram (`isLearnableOrdinaryWord`, mirrored into the `previous` half). The email shape is a separate, narrower gate — `PersonalLanguageModel.isVerbatimToken`: exactly one `@`, a local part of letters/digits/`.`/`_`/`%`/`+`/`-`, a domain of dot-separated letter/digit/`-` labels ending in a `>=2`-letter alphabetic TLD — so pure digits, a price and a URL carrying a `/` stay refused (none has a lone `@`), and a half-typed `nitai@gmail` stays refused (no dot for a domain to end on). Two things about that shape are decisions, not gaps left in by accident: the local part is the stated character set with no adjacency rule, so consecutive dots pass, because the only job here is telling an address apart from a price or a code rather than validating one a mail server would accept; and a domain or TLD letter is anything `Character.isLetter` calls one, so a Hebrew or accented domain passes too — an IDN reading, chosen because folding non-Latin scripts out of the test would refuse an address this keyboard's own Hebrew typists are exactly the ones who might have. A verbatim token skips the bigram half outright — an address commonly follows a sentence with nothing in common with what usually follows it, so the pair would teach nothing — and every reader (`words(startingWith:)`, `neighbours`, `allWords`) gates it on `protectThreshold`, not `boostThreshold`, so a pasted address seen once or twice stays out of the bar (`readThreshold`). **The trade this makes is real and worth stating plainly: a learned address sits in the App Group JSON in plain text**, the same file every other learned word already lives in, with Full Access still the one precondition for any of it to persist past the keyboard process's own lifetime. `learnedWords()` shows every stored word "including those seen once", so an address is visible under Languages → Personal dictionary → From typing — with its own Forget — from the *first* sighting, well before three sightings ever let it reach the suggestion bar; ranking caution and disk caution are different questions; and `PersonalLanguageModel.clear()` / per-word `forget(_:in:)` are the only ways it leaves the file. Three things had to move alongside the store, and two of them are two doors reading one definition rather than each carrying a copy that can drift. `SuggestionEngine.commitReason` refuses to let space auto-commit any winner carrying a character outside plain letters and the marks `KeyboardController.staysInsideWord` names (`SuggestionEngine.isAutomaticallyInsertable`), checked once on the single winner ahead of every rule that reads it — without that, the four-letter unknown-word gate happily paged an address over an unrelated fragment like `nita`, since it never asked what shape the winner was. **`KeyboardController.idleCompletion` is the second automatic door to the same document, and it read straight past `commitReason` entirely.** `performIdleTyping` goes from a pause straight to `replaceCurrentWord` (or `apply`, the same insert) with no tap in between, so a learned address at three sightings, typed exactly as far as its own local part, ranked `.learned` — the second-highest tier a mid-word candidate reaches — and was exactly what "the first suggestion that is not the typed word" picked: pasted on a pause with nothing to undo, and `recordCommittedWord` on the very next line then counting the paste itself as a fourth sighting, the defect feeding its own evidence. `idleCompletion` now asks `isAutomaticallyInsertable` of every candidate before offering it and falls through to whatever legitimate completion sits behind a refused one, rather than holding the bar hostage to a personal token it has nothing to do with. And `matchCaseUnlessVerbatim` — used by *both* the completion mapping and the neighbour-typo mapping in `checkerCandidates` — skips re-casing a verbatim candidate: the store folds every one to lower case, so a shifted prefix, or a shifted one-substitution typo of a stored address found through the neighbour door, must not capitalise a candidate that was never stored that way. Neither restriction touches a *tap*: `apply` never asks `commitReason`, and a candidate that reaches the bar at all — refused by neither door — still inserts exactly as stored. `VerbatimTokenLearningTests` holds all of it, including the destructive proof that removing either door's guard reproduces the reported leak on the nose.
- **The pair `pendingAutocorrectUndo` remembers was position- and document-blind, and three defects came out of the same root.** The only claim check was `contextBefore.hasSuffix(replacement + " ")`, which asks *whether the text exists somewhere*, not *whether this is the swap that made it*. A caret tapped after any other occurrence of the same replacement word elsewhere in the document satisfied it and the next backspace rewrote that unrelated word — `"hello and helo"`, correct the second into `"hello"`, tap back after the first `"hello "`, backspace, and the *first* one gets eaten and replaced. The fix is `contextAfterSwap`, checked with `==` rather than `hasSuffix` — sound because nothing can legitimately be typed between a swap and its undo (every character key, Return and both cursor keys already clear the pair outright), so there is no "typed since" for an exact match to wrongly refuse, unlike `RevertibleEdit.spanUndo`, which does need that allowance. **A selection was never asked about at all**, so a backspace over a selection sitting right after a fresh swap satisfied the same claim, deleted the selection through `target?.deleteBackward()`, and then ran the resurrection on top of what was left — losing the selected text *and* putting the wrong word back. `selection == nil` is now part of the guard, same as everywhere else on this keyboard a selection changes what a key does. **And the pair survived a document switch**, because nothing retired it when the field changed — `prepareForNewDocument` clears it now, the same seam `discardPendingCharacter` already uses for the analogous "a letter parked for the old field must not type into the new one." This one is *not* solved by the exact-context match: two different documents can read identically at the caret (`PendingAutocorrectClaimTests` builds exactly that case), so only retiring the pair on the switch itself closes it. `PendingAutocorrectClaimTests` holds all three, each with a control half that types the same word live, so a build that simply turned autocorrect off fails both halves.
- **`contextAfterSwap` is built, never re-asked of the proxy, and the first version of this fix got that backwards.** It first read `contextBefore` a second time, right after `target?.insertText(" ")` — which is exactly the read `insertCommittalSpace`'s own doc comment already warns off: "this keyboard's own delete-then-insert can leave the proxy reporting stale context for a moment right after a write it just made." A stale read there only costs a skipped hop; a stale read building this snapshot is worse, because the wrong string becomes the *permanent baseline* every later, honest read is compared against — so on a host whose proxy genuinely echoes asynchronously, the very first backspace after a swap could find the pair already unrecoverable and delete only the space, silently regressing the undo in exactly the window the proxy is known to lie. `insertSpace` already holds the fresh, pre-write `contextBefore` it needs — `contextBeforeSwap`, captured before `original` is touched — so the snapshot is arithmetic on a string the function already has: `contextBeforeSwap` with `original` dropped off the end, plus `replacement`, plus a space. No proxy read happens after the swap or the space land. Every fixture elsewhere in this suite answers every read honestly, which is why this needed its own: `StaleEchoTarget` echoes the pre-write value on the one read immediately following an `insertText` call (deliberately not `deleteBackward`, which `deleteBackward(utf16Units:)` already reads around with its own before/after loop), and `PendingAutocorrectClaimTests.testTheUndoSnapshotSurvivesAProxyThatEchoesStaleContextRightAfterTheWrite` is what fails the post-write-read version — destructively confirmed: reverting to `contextAfterSwap: contextBefore` turns "helo" back into "hello" on the first backspace. Do not "simplify" this back to a second proxy read.
- **A selection has no default, and the guard that draws it ran in the wrong order.** `pinningDefaultToTypedIfNeeded` checked `!prefix.isEmpty` before it checked `selection != nil`, so a selection whose *scoring* prefix is empty — a word selected together with its trailing space, where `selectedWord` refuses on the embedded whitespace and `currentWordPrefix` is also empty because nothing sits in front of the selection — fell through the empty-prefix guard untouched and kept the empty-prefix (next-word) tier's own bold default, hint and all. `SuggestionEngine` always marks a default for an empty prefix (`markDefault(promoteToMiddle(results), at: min(1, results.count - 1))`), so this was not a corner case with nothing in it. The selection strip now runs first, unconditionally: any live selection loses every default no matter what the prefix reads.
- **A next-word request armed by a space can outlive the selection that should have killed it, and `applyRefinement`'s only staleness gate could not tell.** `refreshSuggestions` skips *asking* again once a selection exists, but it used to leave whatever request the previous, selection-free refresh had already armed running — and that request's own staleness check, `prefix == currentWordPrefix`, is blind to a selection because `currentWordPrefix` reads identically with or without one. So a space on an empty prefix could arm a request, a double tap could select a word before the 300ms pause fired, and the model's answer would still land — the guess replacing the selection's own correction candidates with a bold default nothing about a selection may ever have. Two fixes, one on each end: `applyRefinement` now guards `selection == nil` directly, which is what actually stops a stale answer from landing; `refreshSuggestions` also calls `refiner?.cancel()` the moment it sees a selection, which only stops paying for an answer nothing can use any more.
- **The bar could bold a correction the space bar had already agreed never to make again.** `insertSpace` refuses to re-swap a spelling the user already undid this session (`undoneAutocorrectSpellings`), but nothing told `pinningDefaultToTypedIfNeeded`, so retyping the exact word from scratch — past the hand-repair window `isCorrectingWordByHand` protects, which only covers typing on from a backspace — still bolded the correction it would never commit. The fix reuses the mechanism the Autocorrect-off and hand-repair branches already use, `SuggestionEngine.markDefault(results, at: 0)`, gated on the same folded spelling the undo recorded. `performIdleTyping`'s completion path had the identical gap from a different door: `idleCompletion` picks the first offer that is not the literal keystrokes with no idea it is choosing the exact swap `undoAutocorrectIfPending` was just asked to reverse, so it is refused there too now. `UndoneAutocorrectBarTests` holds both, each with a control proving the correction still fires without a prior undo.
- **`KeyboardController.init` used to run a full `refreshSuggestions()`, which starts `PredictiveRefiner`'s clock, before the first frame ever drew (NIT-191).** Over a non-empty document that is a paid model call on every single construction, not every keystroke — and iOS constructs a keyboard extension controller far more often than a user opens one. `refreshSuggestions(schedulingRefinement:)` is the fix: the local tier still scores the document, because the playground, onboarding and most of this suite read `controller.suggestions` straight off a freshly built controller with no refresh of their own, but the async ask is skipped when `schedulingRefinement` is `false` — the one argument `init` passes. Every other caller keeps the default. **This is narrower than turning the call into `refreshDocumentState()`**, which is what the ticket asked for first: dozens of existing unit tests construct a controller and read `suggestions` immediately, with no `isSystemKeyboard: true` and therefore no refiner to begin with, so the actual cost this fixes — the refiner — was never what they depended on, and a `refreshDocumentState()` swap would have emptied the bar under all of them for no safety gained. `RefreshPerformanceTests.testSchedulingRefinementFalseNeverReachesTheRefiner` proves the parameter actually gates the refiner rather than merely compiling; a true black-box "construction never asks" test is not reachable without giving `init` its own refiner-injection seam, which is a larger change than this fix earns.
- **`applyRefinement` republished the bar even when a refiner cache hit reproduced exactly what was already on screen.** `refreshSuggestions` already guards its own publish (`if bar != suggestions`), because `@Published` fires on assignment and never on change and a keystroke runs two or three refreshes; `applyRefinement` skipped that guard, so a cached answer turned each of those refreshes into a full republish — a rebuild of every key — for an array that compared equal under `Suggestion`'s own text-language-bold equality. Guarded the same way now. `RefreshPerformanceTests.testApplyRefinementDoesNotRepublishWhenNothingChanged` asserts zero emissions on `$suggestions` for a merge that reproduces the seeded array; the existing refinement tests that change the bold word (`testRefinementCanChangeTheBoldWord` and its neighbours) are what prove the guard does not swallow a real change.
- **Tapping a suggestion when a space already followed the caret left two of them.** `apply(_:)`'s non-selection branch wrote `insertText(" ")` unconditionally, so `"The teh| quick"` (`|` the caret) committed as `"The the  quick"` rather than hopping the caret over the space already doing that job, the way stock iOS does. `KeyboardController.insertCommittalSpace(after:)` is the fix, called from that branch and from the grouped idle-completion's own space write (`performIdleTyping`'s `grouped.isTyping` branch), which carried the identical defect: read the after-caret text once, and if it begins with a plain space, skip the insert and call `adjustTextPosition(byCharacterOffset: 1)` instead. **The check is a literal U+0020 and nothing `isWhitespace` would also accept**, because a newline is the start of the next line rather than a gap this word is finishing into, and a non-breaking space was placed on purpose by somebody else. **The space bar is deliberately not a caller.** `insertSpace` always writes a literal space, because `pendingAutocorrectUndo` remembers "the replacement plus the space that follows it," and a hop there would leave the first backspace-undo eating a space the user pressed themselves. **The after-caret text has to be read before the replacement runs**, not after, because this keyboard's own delete-then-insert can leave the proxy reporting stale context for a moment right after a write it just made — the same staleness `deleteBackward(utf16Units:)` already reads around — so both call sites capture it ahead of `replaceCurrentWord` / `writeGroupedGuess`. `MockTextTarget` cannot exercise any of this, since its `documentContextAfterInput` is always empty and its `adjustTextPosition` is a no-op; `CommittalSpaceHopTests` drives `CursorTextTarget` and, for the headline case, a real `UITextView`, with controls for the end of the document (a space is still inserted) and a trailing newline (still not hopped). **The hop is scoped to a plain caret.** A range selection that is not a recognised whole word — multi-word or partial — keeps the old unconditional space, even when one already follows it (`say ⟦hello world.⟧ now` tapping `the` is still pinned to `say the  now`), because the multi-word pin encodes "touch nothing outside the selection" and whether that pin should ever move is a design question this fix deliberately leaves closed. One known follow-up is not fixed here either: a caret strictly inside a word still orphans the after-caret tail of that same word (`"The te|h quick"` tapping `the` gives `"The the h quick"`, not `"The the quick"`), which is a separate, recorded change.

## The context-aware engine

- **There is a scoring harness now, and the bar had never been scored before it.** `Bar/typing/corpus.json` has held 90 frozen mid-typing moments and a stock-keyboard reference since it was written, and nothing ran the engine against them — so every judgement about the suggestion bar was somebody's opinion. `Bar/typing/harness/run.sh` runs the real `SuggestionEngine` over all 90 and `score.py` grades them against the corpus's own `intended` / `mustNotCorrect` / `acceptable` fields. **Run it before and after any change in this area; a change that is not measured against it is a guess.** Two things about it that are not obvious. It compiles for the **iOS Simulator**, not macOS, because `UITextChecker` is UIKit and macOS would spell-check with `NSSpellChecker` — a different dictionary, a different ranking, and a score of an engine this repo does not ship. And it passes an **empty in-memory `PersonalLanguageModel`**, so a score can never quietly inherit whatever the machine running it has been typing. The measured numbers: **47/76 before this work, 73/76 after it, 75/76 since `TypoLexicon` gave the commit decision a second dictionary**. One remains: `apos-09` (`were` → `we're`, which needs the sentence and is the async tier's job). `typo-10` and `typo-11` were the other two and were listed here for a long time as deliberate — the right Hebrew word offered in slot 1 and not committed, because Apple's checker calls `תדוה` and `שלמו` words — which was the honest answer while the only second opinion was 353 hand-authored words; see the two-dictionary rule below for what changed. `en-comp-03` commits `response` after `the quick`. `cs-05` commits `screenshot`. That 73/76 is not the async corpus.
- **The commit column was the offered column relabelled for 40 of the 76 judged entries, and that is why a whole class of defect scored as a pass.** `score.py` computed an `acceptable` entry's verdict from whether the right word appeared in *any* slot and then printed it under `commit` — the one number its own docstring calls the only one a user would recognise. So `he-comp-07` committed the non-word `מון` for `מונ` with `מונית` sitting beside it in slot 2, counted as a pass, and the headline did not move. The test now is that the bold slot holds either what was typed or one of the good answers: declining to complete is the conservative half of this engine's trade and is not a failure, while inserting a third word is. An entry with an empty prefix is not asked, because `KeyboardController.insertSpace` commits nothing when no word is in progress. **The headline moved as a result and both numbers are worth keeping straight**: the engine that scored 73/76 under the old scorer scores **71/76** under this one, and the Hebrew final-form fix took it to 72/76. An open `acceptable` list still cannot fail on a miss, but it *can* fail on a commit — `cs-11` was inserting `לף` — so those are printed under their own heading rather than folded into the total.
- **Two runs of identical code disagree on two entries, and the source of it is `UITextChecker` rather than this engine.** `he-comp-04` answers `לעבוד` or `לעבור` in slot 2 and `he-comp-05` answers `העזתי` or `העזיבה`, run to run, with nothing changed: the checker's own completion list for a Hebrew prefix is not stable, and `ordinal` is part of `score`, so a different order out of Apple is a different slot 2. The total tie-break in `rank` fixed the *sorting* half of this and cannot fix the *source* half. It has never moved a `commits` value or the score — 73/76 across the pair of runs after `cs-05` closed — so the headline is the number to trust and a slot-2 diff on those two entries is not a regression to chase. `Bar/typing/engine_outputs.json` is gitignored (`.gitignore:26`), so it is one machine's last run and never a reference: diff two runs you made yourself, the way `score.py before.json after.json` is built to.
- **Nearly half of Hebrew typing was measurably wrong while the corpus said the engine was at its best, because 90 frozen moments are a sample and not a keyboard.** The corpus holds 20 Hebrew entries with a word in progress and exactly 2 of them end in a shape-changing letter, so the rule above could be wrong a fifth of the time and cost at most two entries — both of which were scoring on `offered`. Typing whole words letter by letter through `Bar/typing/harness` with a corpus file of your own is cheap (`run.sh` takes any corpus with the same shape) and it is what found this; the frozen 90 are the regression guard, not the whole examination. The same sweep is what found that a trailing comma turned `תדוה,` into a one-slot bar and that `Nitai’s` was unprotected, neither of which the corpus has an entry for.
- **The ranking is made of provenance, and the old bar's ranking was the order the code happened to be written in.** `SuggestionEngine+Completions` used to append candidates and take the first three, so `helot` beat `hello`, `הכתום` ("the orange") beat `הכתובת` ("the address"), and `Dizeng` completed to `Dizziness`. Every candidate now carries a `Source` and `SuggestionEngine.score` weighs it: **1000 per source tier, +400 if the previous word is known to be followed by it, up to +300 for the seed prior, up to +300 for how often this person has committed the word, −8 per position in its source's own list, −500 per Hebrew clitic stripped.** Personal count is stamped before `rank` and starts at two sightings, the same floor as `words(startingWith:)`. It cannot climb a source tier. Neighbours also search the learned store, so a name you type is offered from a one-key slip the seed has never heard of. Four of the older numbers were each set by a regression the corpus caught, so none of them is a free parameter. The ordinal term exists because throwing away `UITextChecker`'s own order made the alphabetical tie-break the ranking and `depl` offered `depletion` and `deplorable` while `deploy` fell off the end. `codeSwitch` sits **above both the checker and the seed list** — below either one, `sta` inside a Hebrew sentence offers `station` and `start` and never reaches `standup`, which is the exact failure the list was written for. `neighbour` sits **below** a completion, because a completion agrees with every key that was pressed and a neighbour claims one of them was wrong. And the clitic penalty is half a tier per letter rather than a tie-break, because `ש`+`ל`+`מוכן` = `שלמוכן` is a real Hebrew construction nobody has ever typed and at a small penalty it outranked `שלום`.
- **The Hebrew final-form rule may only ever land on a word the seed list knows, and the version that asked nothing at all fired on a fifth of all Hebrew typing.** The rule is right about orthography — a *finished* Hebrew word may not end in the ordinary form of ‎כ מ נ פ צ‎ — and wrong about when it is asked, because a word in progress ends in whatever letter was typed last. 20% of the mid-word keystrokes across the 353-word seed vocabulary land on one of those five, and every one of them fired: the candidate arrives as `.orthography`, which outranks every completion source, and `commitReason` answers on it above the seed check, so it took the bold slot and pushed the word being typed out of the bar. Measured over ten common words typed letter by letter, **17 of 35 keystroke moments bolded a non-word** — `פ` bolded `ף` while `פגישה` sat unbolded beside it, `מכ` bolded `מך`, `נכ` bolded `נך` — and it *committed* on finished input too, because Hebrew writes its loanwords with the ordinary form at the end: `אפ` ("app") went to `אף` ("nose") and `קליפ` to `קליף`. **The gate is `SeedLanguageModel.knows` and it must never be `UITextChecker`**, which is the whole reason the first version was ripped out: `isKnownWord("שלומ")` comes back true on a cold checker and false on a warm one, so a rule gated on it is asleep on the first word of a session. The seed list is a bundled JSON folded once at load and answers the same on keystroke one as on keystroke one thousand; 66 of its words end in a final form, which is the common core this slip happens in — `שלומ` → `שלום`, `צריכ` → `צריך`, `כספ` → `כסף`, `דרכ` → `דרך`. It is the same "only ever land on a common word" gate `SeedLanguageModel.neighbours` and `LayoutTransposition` already carry. After it: 0 of 35, `he-comp-07` commits `מונית` instead of `מון`, and `cs-11` leaves `לפ` alone. `SuggestionEngineTests.testAWordInProgressIsNotCorrectedToItsOwnFinalForm` asserts on the *default*, because the non-word was in the bar either way and only the bold slot rejects the old build.
- **A trailing mark switched the neighbour rule off, and in Hebrew that is the only correction path there is.** `SeedLanguageModel.neighbours` refuses a candidate shorter than what it is given — the "never shorter than what was typed" rule below — so a comma counted as a letter and put every real neighbour under the floor. `teh` corrected to `the` and `teh,` corrected to nothing. English has a second path and mostly survived (`recieve,` still reached `receive` through `UITextChecker.guesses`), but Apple's Hebrew checker reports `תדוה` and `שלמו` as perfectly good words, so there is nothing behind it: `תדוה,` came back holding **one slot**, the typo, with `תודה` never generated at all. **The first repair gave `wordCore` to the neighbour rule alone and that made a second bug**, because a source asked about the word and a source asked about the keystrokes cannot compete: for `(hel` the completions went silent while the neighbours did not, so `hello` and `help` never arrived, `her` had nothing to beat, and a word the user had not typed one letter of took the bold slot — where plain `hel` is correctly left alone. `completions(for:)` trims once now and hands the same string to every source, and `commitReason` asks all of its questions about it, which is what the third bullet above already said was true of the length gate and `isKnownWord` and was true of nothing else. Two consequences worth keeping. The contraction table and the final-form rule are reachable through a mark now (`dont,` → `don't,`, `שלומ,` → `שלום,`). And `KeyboardController.restoringEdgeMarks` restores **both** ends rather than the trailing one, because a leading mark used to hide the word from every lookup except `UITextChecker.guesses`, which reached `receive` from `(recieve` and dropped the bracket on the way. **It restores exactly what `wordCore` removed rather than re-deriving it**, and the difference is not cosmetic: the version that put back the punctuation *runs* at each end looked equivalent and silently deleted the possessive, because `wordCore` also strips `'s` and `'s` is not a run of punctuation — it ends in a letter. `Nitai's` reduced to `Nitai`, was corrected to `Nit`, and committed two characters shorter than what was typed. Locating the core inside the keystrokes keeps the two halves from drifting, which matters because they live in different files. Candidate zero stays the literal keystrokes, marks and all, and neither end is re-added to a candidate that already carries it. Two answers moved and both are the same word agreeing with itself: `sched,` commits `schedule,` where it used to commit `she'd,` (the comma blocked every completion, so a spelling *guess* was all that was left), and `Handi,` is destroyed as `Handing,` rather than `Handy,` — which is exactly what plain `Handi` has always given.
- **`comparable` folded the apostrophe onto itself, and `wordCore` tested the same eight bytes twice.** `replacingOccurrences(of: "'", with: "'")` is ASCII on both sides; the intent was U+2019, which is what `SeedLanguageModel.fold` does correctly two files away. `wordCore`'s `hasSuffix("'s") || hasSuffix("'s")` reads as the two apostrophes and is one of them, so the second branch was dead. The cost was the personal dictionary silently letting go of a word the moment it wore a curly apostrophe: `Nitai's` was protected and **`Nitai’s` committed as `Nita’s`**. That is not an exotic spelling — the apostrophe key's long press offers `’` (`KeyboardLayout+NumbersSymbols`), and a host field with smart quotes on, which is the default everywhere except this suite's own `MockTextTarget`, rewrites a typed `'` to `’` inside the document `currentWordPrefix` reads back. `comparable` is now `SeedLanguageModel.fold(wordCore(word))` rather than a second spelling of it, and the curly form in `wordCore` is written `"\u{2019}s"` so it cannot be normalised back into its twin by an editor.
- **Hebrew needed morphology, not a bigger dictionary, and that is why its completions were worse than English's.** Hebrew glues ‎ה ב ל מ ו ש כ‎ to the front of a word, so "to work" is one token `לעבודה` and no dictionary lists the glued forms: `UITextChecker` completed `לעבו` to `לעבוד` and `לעבור`, two verbs, and `מהג` to `מהגרים` ("immigrants") when the sentence was about children coming home from kindergarten. `HebrewMorphology.splits` returns *every* reading, unsplit first, and the seed list is asked about each stem — one entry for `עבודה` then serves `לעבודה`, `בעבודה` and `מהעבודה`. **A one-letter stem is included and only the seed list may answer it**: `מהגן` is `מ`+`ה`+`גן`, so reaching it means completing the single letter `ג`, and asking `UITextChecker` that question returns every word in Hebrew starting with gimel.
- **A reading is a guess and nothing ever checked it, so a quarter of Hebrew typing was answered with words that do not exist.** The split invents a stem, the seed list is asked what starts with it and answers with the commonest words it has, and the clitic goes back on — `מנ` read as `מ`+`נ` gave `מנכון`, `מנחמד`, `מנפגש`, none of which is a word, all three `.seed`, which outscores every completion `UITextChecker` has, so **all three drawn slots held a non-word and `מנהל` was nowhere**. Measured 2026-08-16 over 121 keystroke moments from 55 common Hebrew words: **17 moments drew a non-word (26 of the 363 slots), and the word being typed was missing from 30.** `בח` gave `בחוזר`/`בחוזרת`/`בחושב`, `שולח` gave `שולחזור`/`שולחכות` while `שולחן` never appeared, `בב` gave `בבבקשה`/`בבסדר`, `מכת` gave `מכתודה`/`מכתבדוק`. The same shape reached a phone as **`מכסהרורי`**, which arrives through the split path's *own* `UITextChecker` call rather than the seed list — Apple completing the invented stem `כסה` to `כסהרורי` — which is why the gate is asked of both sources. `SuggestionEngine.readingIsSpelledOut` is the gate: a candidate with `cliticDepth > 0` must appear in Apple's completion list **for the word as it was actually typed**, so a reading may *re-rank* what the dictionary offers and may not invent anything. An empty list is not a contradiction — Apple answers nothing for plenty of prefixes (`צהרי`) and reading silence as refusal would switch morphology off exactly where nothing else can help. Learned words are exempt and that is the one exception: `לסאפא` is a clitic on a word Apple has never heard of and never will, so the gate's answer there is always no and always uninformative. **The premise this whole layer was built on is no longer true, and that is what makes the gate cheap.** `HebrewMorphology` says no dictionary lists the glued forms; on the iOS 26.2 Simulator `UITextChecker` lists every one of the five controls — `לעבודה` 3rd for `לעבו`, `בעבודה` 1st for `בעבו`, `מהעבודה` 1st for `מהעבו`, `מהעיר` 1st for `מהעי`, `מהגן` 3rd for `מהג`. What morphology still buys is the ranking, since Apple has no frequency model; what it was *also* doing was manufacturing words. **Measured 2026-08-16, two runs per side: the frozen 90 stayed 73/76 with the same three failures, the committed sweep stayed 597 moments / 481 held / 114 on track / 2 diverged, and not one commit value moved on either instrument.** Five frozen entries changed a slot and every one changed a non-word into a word — `הכתודה`/`הכתור` → `הכתוב`/`הכתובות`, `לאת`/`לאני` → `לאחר`/`לאחרונה`, `מאולי` → `מאותו`, and `typo-11`'s `שלמוכן`, which is the `ש`+`ל`+`מוכן` construction `score` names as the reason the clitic penalty is half a tier. `he-comp-09` got *better*: `מהגעתי` left and `מהגן` took slot 1. The split path's `UITextChecker` call is **deleted** rather than gated, because under the gate it can only return something Apple already lists for the typed word, which `checkerCandidates` offers at `cliticDepth` 0 and therefore 500 a letter higher, so `rank` was always going to drop the split copy as a duplicate. That takes a **call count** and not a measured saving, and the difference matters because the comment it replaces defended the path on latency: a Hebrew keystroke now makes exactly one `UITextChecker.completions` call where it could make three, and the harness's own median read 2.28 / 1.62 ms before and 2.28 / 1.77 ms after, with the worst entry swinging between 18 and 94 ms on identical code. The arithmetic is real and this instrument cannot see it. `ContextAwareSuggestionTests.testASplitReadingMayNotInventAWordTheDictionaryDoesNotList` is what fails a build without the gate, and `testCliticSplitReachesAWordNoDictionaryLists` plus `testACliticReadingWithLettersBehindItStillCommits` are what fail one that "fixed" it by dropping the split.
- **`להתרופה` is not in the bar at all any more, and the gate above is what removed it.** `commitTrustsReading` stops the space bar committing a distrusted reading and stays; what it could never do is keep the word out of a slot, and the argument for leaving it there was that no rule could tell it from `מהעבודה` — both `.seed` at depth 2, scoring 2053 and 2068. The dictionary tells them apart without looking at depth at all: `מהעבודה` is Apple's own first completion for `מהעבו` and `להתרופה` is in no list anywhere. `testAStackedCliticReadingDoesNotTakeTheSpaceBar` asserted the candidate was *still offered* for exactly that reason and now asserts the opposite; the control it was providing moved to `testACliticReadingWithLettersBehindItStillCommits`, which fails on a commit rather than on a word being present in a slot and is the stronger place for it.
- **Capping how many split readings may be drawn was tried on the same evidence and rejected, because it took a real word and gave back a worse one.** `מחש` draws `מחשבון`, `מחשוב` and `מחר` while `מחשב` — Apple's first completion, and what almost anybody typing those letters means — is not in the bar, so a one-slot cap on `cliticDepth > 0` looked like the fix. Measured 2026-08-16, two runs per side: **the frozen 90, the committed sweep and the 121-moment sweep all sat exactly where the gate alone left them**, not one commit moved, and the case it was written for went `[מחשבון, מחשוב, מחר]` → `[מחשבון, מחר, ממש]` — a real word swapped for a neighbour, with `מחשב` still absent. The reason is that `מחשב` is not being crowded out by the split at all: `.neighbour` is 2000 and `.seed` 3000 while `.checker` is 1000, so **anything** in a higher tier outranks Apple's whole list, and a cap on one of those tiers just hands the slot to another. Whether a completion Apple ranks first should be able to beat a seed neighbour is a real open question about `score`; it is not a question about morphology, and the cap was answering the wrong one.
- **That open question was then measured and closed, and the answer is to leave `score` alone.** `.checker` is the lowest tier there is, so Apple's own first completion loses to any seed or neighbour word, and the obvious repair is to reserve one of the three drawn slots for it. **The ceiling of that repair was measured before writing it**, which is the cheap order and is what stopped it: over the same 121 Hebrew moments, Apple's top completion is missing from the bar **18 times**, and of the 22 moments where the word being typed is not offered at all, reserving a slot **rescues 2 and spends a slot on some other word 6 times**. English: 2 missing, 0 rescued, 0 spent. So it costs a slot three times as often as it buys one, and `מחש` → `מחשב` — the case that raised the question — is one moment in 121. **The reason no ranking tweak reaches it is that the two cases are indistinguishable from inside the engine**: `לעבו` → `לעבודה` is a split reading beating Apple's first answer and is *right*, `מחש` → `מחשבון` is a split reading beating Apple's first answer and is *wrong*, and in both the winner is `.seed` at depth 1 and Apple's #1 is absent from the seed. Telling them apart needs Hebrew frequency data, which means a longer seed list, not a different formula. Do not re-propose reserving a slot, swapping the `.checker` and `.neighbour` tiers, or bonusing ordinal 0 without new evidence; all three are the same idea and this is the number it has to beat.
- **The Hebrew frequency data was then found, measured, and does not work, so that whole line of repair is closed.** The corpus the previous bullet asks for is already in this repo: `AIKeyboardCore/Resources/GroupedLexicon-{he,en}.txt`, 50,000 word forms a language ranked by frequency in real text, Leipzig Corpora Collection, CC BY 4.0, bundled and attributed for the grouped-keys exploration. **Measured 2026-08-16 with `Bar/typing/sweep/frequency.py`, two runs a side, identical both times: Hebrew gains 4 moments and exposes 48; English gains 0 and exposes 70.** Twelve to one against and unbounded, which is worse than the reserved-slot idea it was supposed to replace, and the English figure says it is neither a Hebrew problem nor a right-to-left one. **It is a domain problem, and the examples are not marginal**: the list is Wikipedia's, so `סליחה` is rank 37,467, `כשאני` 39,651, `מונית` 21,885, and `תודה` sits at 8,904 behind `עוד` at 118. Nobody writes "sorry" or "thanks" in an encyclopedia. `SeedLanguageModel`'s own doc says its 353 words are hand-ranked "against the kind of text this keyboard is typed into" and discloses that they are not measured against a corpus; this is the measurement that says that authored-for-chat property **is** the value, and that a longer list drawn from written text would destroy it. **The frequency term also could not have reached `מחש` → `מחשב` even if the ranks were perfect**, and that is structural rather than a question of budget: read out of the engine, `מחשבון` and `מחשוב` are both `.seed` at depth 1 on 2500 and 2484, `מחר` is `.neighbour` on 2244, and `מחשב` is `.checker` on 1000 — so it needs 1500 points, `Source` says no amount of frequency inside a weaker source may climb over a stronger one, and any term that big would be a second tier system. What is still open is a **longer hand-authored chat list**, which is a person's judgement about their own vocabulary and not something a corpus can supply.
- **`SlotRecord.reachable` is what makes "the bar is missing the target word" an actionable number, and without it that column was noise.** The sweep reported 311 of 664 moments without the target, which sounds enormous and mostly is not: one letter into `להתראות` nothing should offer the whole word, and no ranking can offer a word no source generated. Asking `UITextChecker` whether *its own* completion list holds the target splits them — **81 winnable by re-ranking, 107 that no source has, and 123 that are the last keystroke of a word where the target is what was typed.** 81 is the denominator every future ranking proposal goes against. It is asked in the harness's second pass, after every entry is answered, for the same reason spelling is: Apple's Hebrew answers depend on what that process has already asked it, so a call in the middle of the measurement changes the thing being measured. And it is only asked where the target **continues** what was typed — 24 of the frozen 90 spell `intended` as a correction (`dont` → `don't`), which has no completion relationship with the keystrokes and would otherwise have read as 24 moments no ranking could win.
- **A finished Hebrew word usually cannot be continued at all, and that is the language rather than a defect.** English inflects by *appending*, so a prefix search over a dictionary finishes a finished word for free: measured over 15 common English verbs, **15 of 15 drew a full bar** — `walk` → `walking`, `walked`, `walks`. Hebrew *replaces* the ending, so `רוצה` → `רוצים` is not a prefix extension and no prefix-based completion can ever reach it. That is the same asymmetry `hasDistinctHebrewLexemes` is built on, seen from the other side. Measured over 20 common finished Hebrew words: **7 drew a thin bar, and in every one of those `UITextChecker` itself returned nothing** — `הולך`, `רוצה`, `הודעה`, `פגישה` all come back with an empty completion list, and `מכסה` comes back with exactly one (`מכסהו`), which is why the screenshot that started this had three slots to fill and nothing honest to fill them with. **The verbs Apple does have, it has well**: `כותב` → `כותבים`/`כותבת`/`כותבי`, `דיבר` → `דיברתי`/`דיברנו`/`דיברת`, 13 of 20 full. So the blank slots are Apple's Hebrew lexicon running out, not the gate above, and the thing that would fill them is an **inflection table** — stem the word with `hebrewLexemeStem`, which already knows `ות`, `ים`, `ה`, `ת`, `י`, and offer the *other* endings — rather than anything in the ranking. Next-word prediction is the wrong answer for this: a person who has typed `רוצה` may still be typing `רוצים`.
- **So that table is built, and it is the same rule as `readingIsSpelledOut` pointed the other way.** `SuggestionEngine.hebrewInflections` stems the word with `hebrewLexemeStem`, puts the last letter back into its ordinary shape (`הולך` → `הולכ`, or `הולך`+`ות` is not a word in any sense), hangs the five number-and-gender endings on it, and **keeps only what appears in Apple's completion list for that stem**. The endings say what shape an inflection has; the dictionary says whether that one exists, and neither half works alone — Apple's completions of `רוצ` wholesale include `רוצפה`, and the endings wholesale give `בעבודים`. **`isKnownWord` per candidate is the cheaper test and was measured to be not enough**: Apple's spelling half accepts plenty its completion list would never offer, and over the sweep it passed `בעבודים`, `לעבודים`, `משפחים`, `מסעדים` and `בבקשים` (a masculine plural on a feminine noun), `מכוניה`, `כספה`, and `להתחילה` / `להזמינה`, which hang a gender ending on an infinitive; it also produced `בלי-פרופות` and `בלי-פות` off the hyphenated personal-dictionary entry. The completion list rejects every one of those and needs no rule about hyphens or infinitives to do it. **An empty list refuses here where `readingIsSpelledOut` allows**, and the difference is what silence costs: there it means falling back to the only thing that can reach a glued Hebrew word, here it means the empty slot this rule exists to fill. Three more things hold it down. It only runs on **a word that is already a word**, which also puts the result out of the space bar's reach for free — `commitReason` returns false at `SeedLanguageModel.knows`, or at `!known` in the four-letter gate, for every word this can fire on. The stem must keep **three** letters where `hebrewLexemeStem` stops at two, because that function compares two completions of the same keystrokes and this one invents from a stem: `בית` looks like a `ת` ending, leaves `בי`, and `ביים` has nothing to do with a house (its real plural `בתים` is beyond any ending table, and that is the honest limit of this). And `Source.inflection` is **−1, below every other source**, so it can only ever fill a slot nothing else wanted — which is what makes it safe to measure, since no moment where the bar was already full can move. **Measured 2026-08-16, two runs per side: thin bars over 20 common finished Hebrew words went 7 → 3, English stayed 0 of 15, the frozen 90 stayed 73/76, the sweep stayed 498 held / 114 on track / 2 diverged with 0 non-words, and not one commit moved on either.** 27 sweep moments gained a slot and every one is the last keystroke of a word: `מכסה` → `מכסות`/`מכסים`, `הולך` → `הולכות`/`הולכים`, `צריך` → `צריכה`/`צריכות`/`צריכים`, `נכון` → `נכונה`/`נכונים`/`נכונות`, `שולחן` → `שולחנות`. The three still thin are `עשה` (stem `עש`, refused at the floor) and `הודעה` / `פגישה`, where two endings is all Hebrew has.
- **The plurals no ending can build are a lookup, and the first version of that lookup was invisible because it was ranked like a guess.** `SuggestionEngine.hebrewIrregularPlurals` is 21 pairs — `בית`/`בתים`, `אישה`/`נשים`, `יד`/`ידיים`, `שנה`/`שנים` — read from either end by `hebrewIrregulars`, which is a *separate function* from `hebrewInflections`: that one asks `UITextChecker` whether the word it just built exists and is held down by two length floors, all because it guesses, and a closed table guesses nothing, so it asks nothing and is not subject to floors written for a generator. **Ranked at `Source.inflection` (−1) it fired on 5 of its 21 rows and nobody would ever have seen the other 16.** Measured 2026-08-16: `בית` drew `בית-המשפט`, `ביתי`, `בית-הספר`; `בן` drew three surnames; `שנה` drew `שנהב` ("ivory") while `שנים` — **rank 53 in 50,000 words of real Hebrew** — was nowhere; with the table off, `בית` draws `ביתו`, `ביתי`, `ביתה`, three possessives. All of those are `.checker`, and `UITextChecker` has no frequency model, so a hand-checked table of the commonest words in the language is the better evidence and has to outrank it. The tier is now `Source.irregular`, **above `.neighbour` and below `.seed`**, and getting it there meant renumbering `Source` in tens against a `* 100` multiplier in `score` — every existing value was one apart, so the scale had no way to say "between these two". **No score moved**: a tier is still worth 1000, and the frozen 90 came back 73/76 twice with the same three failures. 26 rather than 25 because a `.seed` reading at one clitic lands on exactly 2500.
- **A word that *looks* irregular usually is not, and 22 rows were kept out of that table by measuring instead of guessing.** The ending rule was run over 45 candidate pairs before a single row was written: it already reaches `מקום` → `מקומות`, `חלון` → `חלונות`, `דרך` → `דרכים`, `מכונית` → `מכוניות`, because `hebrewShapeFolded` puts the final letter back into its ordinary shape before the ending goes on. **A row that duplicates the rule is a row that can disagree with it later**, so none of those 22 is in the table and `testAnIrregularHebrewPluralIsOfferedWhereNoEndingCouldReachIt` asserts `מקום` is absent from it *and* still reached by the rule. Of the 23 that did miss, most are simply too short for the floors — `בן`, `אח`, `יד` fail `word.count >= 3`, and `בית`, `שנה`, `דלת`, `חנות` all leave a two-letter stem once their apparent ending comes off — and the rest reach the dictionary and get the wrong answer, `אישה` being offered `אישות` and `אישים`, real words that are not the plural of "woman". **The spellings are the corpus's, not the author's**: `Resources/GroupedLexicon-he.txt` is 50,000 Hebrew word forms ranked by frequency in real text, and it settles `אמהות` (18,564) over `אימהות` (25,222) and `ידיים`/`עיניים`/`רגליים` over `ידים`/`עינים`/`רגלים`, two of which it does not contain at all. `עם` and `אם` were measured, are correct, and are **left out**: both are two-letter singulars whose commoner reading is a function word ("with", "if") and both plurals sit past rank 6,000 where every kept row is inside 8,200. **Measured two runs per side, 664 sweep moments: 548 held / 114 on track / 2 diverged, 0 non-words offered, and 0 commits moved**, which is the number that matters — every word in the table is a word, so `commitReason` refuses at `SeedLanguageModel.knows` or at `!known` in the four-letter gate for all of them. 16 stable moments gained a slot and every one is the plural taking slot 1. `testEveryIrregularPluralInTheTableIsARealHebrewWord` walks all 21 rows against `UITextChecker`, because a transposed letter in a hand-written Hebrew table ships a non-word with nothing else to catch it and the table deliberately bypasses `readingIsSpelledOut`.
- **Every correction source was one edit deep, so a hand that landed one key over could not be repaired at all — and the second dictionary this file has always asked for was already bundled.** Reported from a phone: `דוגמטןת` for `דוגמאות` ("examples"), `א` keyed as `ט` and `ו` as `ן`, both pairs side by side on the Hebrew top row. `SeedLanguageModel.neighbours` is distance 1 over 353 words and `UITextChecker.guesses` is Apple's own unranked list; between them nothing reaches distance 2, so the bar held **one** offer, `דוגמטית`, which Apple reached in one edit and which appears nowhere in 50,000 words of real Hebrew, while `דוגמאות` is rank 3,643. `TypoLexicon` searches `Resources/GroupedLexicon-{he,en}.txt` — the Leipzig lists already bundled for grouped keys — under `TypoChannel`, a weighted Damerau-Levenshtein that prices a slip by *what kind of slip it is* rather than counting edits: an adjacent key 55, a transposition 60, a Hebrew final form 20, a dropped mater lectionis (`י`, `ו`, `א`) 55, a homophone letter (`א`/`ה`/`ע`, `ח`/`כ`, `ט`/`ת`, `כ`/`ק`, `ב`/`ו`, `ס`/`ש`) 40, anything else 100. The budget is `nil` below four letters, 100 at four or five and 130 at six or more, so **two explainable slips stay in reach and two unrelated ones do not** — 55 + 55 = 110 against 100 + 100 = 200. `Source.frequency` is **5**, above `.correction` and below `.checker`: it must beat an unranked guess and must lose to every completion, which is what structurally keeps it away from a word that is merely half typed. **Measured 2026-08-17, two runs per side: frozen 90 73/76 → 75/76 with `mustNotCorrect` still 12/12; the sweep unmoved at 664 moments, 548 held, the same 2 documented English divergences and 0 non-words; `Bar/typing/typos/` 61 → 90 of 107 committed with its 21 controls all intact and its wrong column flat at 10; median keystroke 1.26 → 1.60 ms.**
- **`isWord` reads all 50,000 forms and `rank` only the window, and conflating them is the defect rather than the shortcut.** `depth` bounds what may be *offered* — a word nobody uses is not worth rewriting keystrokes into — while "is this a word at all" has to see the whole list, because `introductions` is rank 14,999 and a form at 30,000 is still a word. **`depth` is per language and the asymmetry is Hebrew's morphology, not the corpus's**: these are 50,000 word *forms*, and `עבודה`, `לעבודה`, `בעבודה`, `מהעבודה` and `העבודה` are five rows and one word to a reader, so 50,000 English forms is most of the language and 50,000 Hebrew forms is not. At 12,000 the window cut off `משכורת` (15,017), `מסעדה` (15,384), `לפגישה` (15,769), `הפתעה` (16,588), `מהעבודה` (21,876) and `שהילדים` (27,758), and with the right word outside it the corrector reached for the commonest word still inside — `שהילדימ` was "corrected" to `הילדים`, deleting the `ש` rather than fixing the final mem. Hebrew is 30,000; English stays 12,000, measured, because taking it deeper bought nothing and cost a real over-correction (`yjis` committed `iiis`, rank 27,182, Wikipedia's abbreviation noise).
- **The frequency prior is logarithmic, and the linear one it replaced was wrong in both directions at once.** `cost + min(120, rank / 100)` saturated, so past rank 12,000 every word paid the same maximum and frequency stopped discriminating across most of the window; and inside it a rank gap of 12,000 bought 120 points against `cost` quanta differing by as little as 5, so the prior routinely overruled the channel — `הפטעה` was corrected to `הפרעה`, a whole substitution dearer than `הפתעה`, purely on rank. Ranking by which word was meant is minimising `-log P(typed | intended) - log P(intended)`; `cost` is the first term, and word frequencies are Zipfian, so the second is proportional to **log(rank)**. `7 * log2(1 + rank)` sets the scale by one question — being the commonest word in the language rather than the rarest in the window is worth **one ordinary edit and no more** (`7 * log2(30000)` ≈ 104, just over `plainEdit`) — so frequency settles a tie between two equally plausible slips and can never buy a wilder one. No cap, because a logarithm is the shape a cap was faking. The sort carries a total tie-break for the same reason `rank` does: `sorted(by:)` is not stable.
- **A same-length Hebrew substitution is a word in progress only while the keystrokes are still going somewhere, and asking that was worth 13 corrections.** The exclusion was written for `מכונ` → `נכון` — four letters on the way to `מכונית`, measured firing at 2 of 35 keystroke moments — and it was asked about every same-length Hebrew pair, so it also refused every *finished* Hebrew word with one key slipped in it: `בסגר`/`בסדר`, `עכדיו`/`עכשיו`, `פכישה`/`פגישה`, `כתובץ`/`כתובת`, `משםחה`/`משפחה`, `טלפום`/`טלפון`, 13 of 13 in the typo corpus, the right word sitting unbolded in slot 1 every time. That is the largest single class the corpus measures. `TypoLexicon.hasContinuation` separates them: `מכונ` continues to `מכונה`, `מכוניות` and `מכונות`; every one of those slips continues to nothing. It must be asked of that list and not of `SeedLanguageModel.words(startingWith:)`, which is 353 words and would answer "nothing continues this" about most of the language.
- **Three rules were each re-deriving that same-length shape, and two of them turned out to be the identical predicate written twice.** `commitReason` spelled it out in three places — `sameLengthSubstitution` (with `neighbourMatch`), the frequency guard (without it), and the four-letter gate (without the continuation test) — so the differences between them lived in three copies of the same arithmetic and could drift apart without anything noticing. - **Seven of those ten divergences are closed, and the three rules that closed them are all one shape: the winner has to have earned the space bar, not merely won the ranking.** Measured 2026-08-16 at `9c34f5aa`, two harness runs and two sweep runs per side, with every provenance figure read out of the engine by a throwaway probe that calls `completions(for:)` and `commitReason` directly rather than inferred from the slots. **Frozen 90: 73/76 on all four runs, and not one commit value moved across the whole 90** — five entries differ in slot 2 or 3 (`he-comp-01` through `he-comp-05`), which is the `UITextChecker` instability recorded above and cannot be anything else, since none of these rules touches the code that generates or ranks a candidate. **Sweep: 583 shared moments, 9 diverged → 2**, no new divergence, and only two moments moved `ontrack` → `held`.   - **A personal-dictionary entry does not own the common word it extends, and the guard that was there only ever protected an exact match.** `KeyboardKit` took `keyb`, `keybo`, `keyboa` and `keyboar` because `.personal` is the second highest tier there is, so the entry wins the ranking outright and the four-letter gate commits the winner. The line drawn is **what the typed letters can still be**: an entry may finish a word nothing else is competing for (`Zzalph` → `Zzalpha` is the whole point of having a list) and may not when another offered candidate completes the same keystrokes, because then it is winning on its tier rather than on the evidence. `keyboard` was in slot 2 the entire time, which is exactly that evidence. `PersonalDictionaryTests.testAnEntryDoesNotOwnTheCommonWordItExtends` asserts the entry is still *offered* as well as not committed, so a build that dropped `KeyboardKit` from the shipped list fails rather than passes, and `testAnEntryStillFinishesAWordNothingElseIsCompeting` is what fails the simpler rule that no personal completion ever commits.

A wrong-layout typist produces a whole word of gibberish in the plane they are not on — `akuo`, `,usv` and `יקךךם` complete to nothing in the alphabet they were keyed in, and the bar holds the transposition and nothing else — while a code-switcher produces the start of a real word and keeps going, which is `scr` with `screenshot` sitting under it.   - **Two Hebrew words sharing a prefix are `respon` → `respond` / `response` in Hebrew, and the gate is a lexeme test plus the source.** `להתראות` and `להתראיין` agree for five letters and the sweep commits the *other* one whichever is being typed, which is what makes it an ambiguity rather than a bad candidate. **The earlier diagnosis of this moment was wrong about the mechanism and the fix is not `commitTrustsReading`**: the winner is `.checker` at `cliticDepth` 0, score 1000 — Apple completes the glued form itself — so that gate returns true on its first line, and the `ל`+`התרא` reading it does refuse scores 500 lower and never reaches the bar. **`hasDistinctLexemes` cannot be widened to Hebrew and `hasDistinctHebrewLexemes` is why.** English inflects by adding letters, so `hasPrefix` is right for `schedule` / `scheduled`; Hebrew *replaces* the ending, so `hasPrefix` reads `הודעה` / `הודעות` and `בעבודה` / `בעבודות` as two words and stops the correct `בעבו` → `בעבודה` — the objection recorded above, now with a test on it. Two completions are one word when either one starts with the other **or** the same stem is left once the ending comes off (`ות`, `ים`, `ה`, `ת`, `י`, longest first). **The five final forms are deliberately not endings**: `ם` and `ן` are ordinary root letters at the end of a word, and stripping them folds `להתראיין` onto `להתראות` and takes the whole rule with it. The comparison *does* shape-fold, though, because a letter goes back to its ordinary shape the moment anything follows it — `להתראיינה` does not begin with `להתראיין` on the code points, and without that fold the rule refused four keystrokes that were on their way to the right word. **And the source is what keeps the controls**: `בעבודה` arrives `.seed` at 2500 and `מהעבודה` `.seed` at 2400, while `להתראיין` arrives `.checker` at 1000, and `UITextChecker` has no frequency model at all, so "first in Apple's list" is no evidence about which of two real words a person meant. A completion with no prior behind it may offer; it may not finish. Asked only of candidates that *continue* the keystrokes, because a correction disagrees with a key that was pressed and is not one of the readings they are ambiguous between — including them cost `להתראי` and `להתראיי`. The two moments that went `ontrack` → `held` are this rule working: `להתחי` offers `להתחיל`, `להתחייב` and `להתחייבות`, three different words, and `להתרא` after `אוקיי ` was the same ambiguity landing right by luck. `testTwoHebrewWordsSharingAPrefixDoNotTakeTheSpaceBar` replaces `testACheckerCompletionOfASplitStemDoesNotTakeTheSpaceBar`, which was written alongside the `commitTrustsReading` fix, compiled, never run, and asserted behaviour that fix does not produce.
- **Key proximity re-ranks neighbour offers and does not commit them.** `KeyProximity` hardcodes the English QWERTY and `KeyboardLayout.hebrewRows` letter rows (other languages fall back to QWERTY) and marks a same-length neighbour `keyAdjacent` when exactly one index differs and those two keys sit next to each other, including the diagonal, never a transposition. `score` adds **50**, below frequency (300) and context (400), above `ordinal * 8`. Same-length substitutions still take the bold slot only when `SeedLanguageModel.isTransposition` says so. `KeyProximityTests` holds the rows, the adjacency cases, the score order, and the `מכונ` control. The typing harness copies `KeyProximity.swift`; it must not import `KeyboardLayout`.
- **A neighbour may never be shorter than what was typed.** Every prefix is a word in progress, so a shorter neighbour proposes deleting a key the user just pressed: `מונ` on the way to `מונית` is one edit from `מון`, `מאו` on the way to `מאוחר` is one edit from `או`. Allowing it turned four correct Hebrew completions into corrections of half-typed words in a single corpus run.
- **`id` came out of the contraction table and `were` never went in.** Membership in `contractions` is what makes a word get replaced on space, and both of those have an ordinary reading — `That's a good id` committed as `That's a good I'd` (corpus `nc-02`). The rest of the table has no such reading, so this is one criterion applied once to the table rather than a per-word rule at runtime; an earlier fix that special-cased `were` with a list of plural subjects was exactly the tailored logic this repo should not carry. `its`, `cant`, `ill` and `thats` are all ordinary English words too and all *stay*, which is why the contraction test is asked **before** the "we never correct a known word" test and not after.
- **Learning is scoped to the real keyboard, and it was not, and the test suite noticed for us.** `PersonalLanguageModel` records committed words and word pairs into the App Group. Every unit test and the app's onboarding playground drive a real `KeyboardController` and press real space bars, so all of them were writing into it: the suite alone had taught it `Handi` ten times and `Nitai` nine, past `protectThreshold`, so `PersonalDictionaryTests` silently stopped being able to prove the personal dictionary does anything — the words it was checking were being defended by a store the tests had filled themselves. `KeyboardController.personal` is `.shared` only when `isSystemKeyboard` is true and a throwaway otherwise. **Nothing from `SharedStore.shippedPersonalDictionary` may go in the seed list either**, for the same reason: two lists defending one word means neither can be shown to work.
- **Two stores, one screen.** Languages → Personal dictionary lists names the user added (`store.personalDictionary`, never correct) and words inferred from typing (`learnedWords()`, including a single sighting). A name already in Your words is not listed again under From typing. Forget one word or Forget all lives on that screen only, and wipes only the inferred list. Ranking still ignores count below `boostThreshold`; `allWords` stays gated on that floor. The app and the keyboard both `reload()` the App Group file on appear: Forget deletes the file, and a keyboard process that is still alive must drop the old counts. A missing file is empty, not "keep what we had". Do not write learned unigrams into `personalDictionary`. Those are different jobs. **The inferred list is sectioned per language in `KeyboardLanguage.allCases` order, and every section after the first was unreachable**: a bilingual user with 267 English words had to scroll past all 267 to find out whether the keyboard had learned a single Hebrew one, which is the one question that screen answers. Each section is capped at `DictionaryView.collapsedRowCount` with a per-language Show all, and a search is never capped because it has already been narrowed to something somebody asked for. The header count stays the true total. The `groups.count > 1` test is also the only thing that puts a language name in that header, so **"From typing · English" is itself evidence that a second language is remembered** and merely below the fold — worth reading before believing a report that one is missing.
- **Every finished word is learned, not only a candidate tap.** Tapping a suggestion always inserts a space, so that path used to be the only one that reliably reached the store. Typing a word and sending the message — Return, a full stop, an emoji, the keyboard going away, or the host emptying the field — never did. `learnWordJustCommitted` reads the word *under the cursor* (so a trailing space is "already learned") and is called before space, Return and word-ending punctuation land. `refreshDocumentState` keeps the open word and commits it when `textDidChange` reports an empty field, which is how a chat Send finishes a word without a trailing space. An apostrophe or hyphen does not finish the word. Deleting a word does not count it. The same open word is not counted twice if the keyboard comes and goes. `ContextAwareSuggestionTests.testATypedWordIsLearnedWhenItIsFinishedNotOnlyWhenACandidateIsTapped` holds it.
- **The async tier is on-device only, and Hebrew gets none.** `PredictiveRefiner` holds one optional predictor, not a list. `standard()` never takes a cloud engine. Slot 0 stays the typed keystrokes. The first on-device model word that lands becomes the default. The shape matters more than the count: **7 are `mustNotCorrect`, and before NIT-21 there were none at all**, so nothing in it could fail by inventing a change nobody asked for and a refiner that rewrote everything would have scored perfectly. - **Complete on pause and Space on pause are separate, both off by default.** Completing writes the first suggestion that is not the typed word (slot 1 in engine order: the best completion), not the bold slot — mid-word the typed letters stay default unless they are a typo, and Autocorrect-off remakes default to slot 0, so taking `isDefault` made the switch a no-op. Completing leaves no trailing space. Space on pause is the space bar (so Autocorrect still decides whether the bold word comes with it). Both on is that completion plus a space. Neither fires on an empty prefix, a credential field, or while the emoji panel is open. After a complete-only rewrite the pause is cancelled, or the next offer (`hellos` after `hello`) would fire again. **The wait is from the last keyed character, not from a suggestion refresh.** `refreshSuggestions` runs for a caret tap, the keyboard coming on screen, a language switch and the host's `textDidChange`, and starting the pause there inserted a space into a word nobody had just typed. `noteTypedInput` arms it from `insertCharacter` and grouped key presses; a later letter replaces `idleTypedAt` so the first letter's wait cannot fire in the gap between keys; a caret that has moved onto a different word fails the armed-prefix check. The length is `storedIdleDelayMs` (300 ships; 150 / 300 / 500 / 800 / 1200), read at the keystroke with the two toggles, same trap as `storedAutocorrectLevel`. `applyRefinement` also re-pins the bold slot to the typed word when Autocorrect is off, same as `refreshSuggestions`. `IdleTypingTests` holds the cases.
- **The local tier's cost is measured and the harness prints it, because "fast enough for every keystroke" is the assumption the whole two-tier design rests on.** Over four runs of the 90 corpus entries, warm, on the iOS 26.2 Simulator: **median 1.1-1.3 ms, worst entry 10-16 ms**, and *which* entry is slowest changes between runs of identical code — one run also produced a 27 ms outlier that did not reproduce, so the same "one run is not evidence" rule that governs the Bar corpora governs this number too. The **first** call in a language is separate and much larger, ~70-280 ms, because Apple builds that language's lexicon then; a user pays it once per keyboard session and `run.sh` reports it on its own line so it is never averaged into the per-keystroke figure.
