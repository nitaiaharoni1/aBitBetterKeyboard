# Suggestion bar, autocorrect and the personal dictionary

- **A suggestion is the word, not a fresh identity.** `Suggestion.id` is a `UUID` minted in the memberwise init so two slots can be told apart, and the synthesised `Equatable` counted it, so every `refreshSuggestions` produced three unequal values even when the texts had not moved. The bar then spent `Theme.Motion.quick` fading them — 180ms behind every letter. Equality is text, language and the bold flag; the candidates snap. `SuggestionEngineTests.testTwoOffersOfTheSameWordAreTheSameOffer` is what fails the synthesised version.
- **Autocorrect, Predictions, Auto-capitalise and the language list are settings the keyboard must re-read, and the default candidate is bold, not a chip.** Space commits the default suggestion only when `storedAutocorrect` is on — the `@Published` copy is filled once at launch, so a toggle flipped in the app while the keyboard is already up is invisible unless the space bar and `refreshSuggestions` go through UserDefaults at the keystroke (same trap as `storedPersonalDictionary`). When the setting is off, `refreshSuggestions` also re-marks slot 0 as default so the bar does not bold a correction space is no longer allowed to commit; a deliberate tap on a candidate still inserts it. Predictions uses `storedPredictions`, Return and double-space use `storedAutocapitalise`, and the globe / space-bar strip use `storedEnabledLanguages`, for the same reason. `KeyboardViewController.viewWillAppear` also calls `SharedStore.load()` so the published copies the rest of the chrome draws from catch up when the keyboard comes back on screen. The default slot is drawn in bold weight with no background fill.
- **The default is drawn in the middle, and the engine array is not the drawing order.** Mid-word `rank` still pins the typed keystrokes at index 0 so the refiner and `testTheLiteralKeystrokesAreAlwaysSlotZero` can find them. The bar does not draw that echo: it is already in the field, and a slot spent on it hid the completion or correction. `SuggestionBar.centeredSlots` is the drawing order: drop the comparable typed word, default in slot 1, the others on either side, a lone offer centered, an empty prefix (next-word) unfiltered. Do not "fix" this by reordering `controller.suggestions` itself; `applyRefinement` holds index 0 as the literal, and swapping the array would let the model replace the word the user typed. `SuggestionEngineTests.testTheTypedWordIsNotDrawn` is what fails a bar that still draws the echo.
- **The bar has three slots and the engine only ever filled two of them, for the whole life of the feature.** `completions(for:)` asked `rank` for three candidates and the first of those three is the literal keystrokes, which `centeredSlots` then throws away because they are already in the field — so a third of the one row this keyboard has for suggestions was blank on nearly every keystroke. Measured over 234 letter-by-letter moments across 30 Hebrew and 20 English words: **229 of them drew two candidates and a gap**; the frozen corpus shows the same two-entry `slots` on every mid-word entry, which is why no score could see it. Mid-word the engine now returns `SuggestionEngine.barSlots + 1` and the empty-prefix path returns `barSlots`, because next-word has no echo to filter. Three call sites encode that number and all three had to move together — `completions`, `nextWordSuggestions`, and `applyRefinement`, whose `0..<3` was the one path that could shrink the bar back to two the moment the model answered. The **supplementary cap went from 2 to `barSlots` with it**: two was the number of offers that could be shown, so on the *highest* ranked source it meant a third name typed by hand into Settings could never reach the bar. Corpus unmoved at 73/76 over two runs each side. `PersonalDictionaryTests.testTheBarDrawsThreeOffersAndNotTwo` asserts through `centeredSlots` rather than through the engine array, because the engine returning four proves nothing about what reaches the screen.
- **A tap in the host field moves the caret without a key, and `selectionDidChange` is how the keyboard hears about it.** `textDidChange` does not fire for a caret-only move, so without this override the bar keeps scoring the word the caret just left. **Refresh only.** Clearing `revertibleEdit` here would delete the undo on the same turn as the insert that created it, because this keyboard's own insertions move the caret too. `deletedWordPrefix` expires by itself when the word under the caret no longer starts with it.
- **The first delete after space undoes the swap, and a later delete does not.** Space that actually replaced the typed word remembers `(original, replacement)` in `pendingAutocorrectUndo`. The next `deleteBackward` that would eat the trailing space restores `original` and drops the space. Offered candidates stay; only the automatic replacement goes. The same spelling is not swapped again this session (`undoneAutocorrectSpellings`, folded, no timestamps). A later letter, a caret that is no longer sitting after `replacement `, Return, a tapped candidate, or a new space clears the pending pair. Do not use `revertibleEdit` for this: that slot is Fix / Rewrite. Autocorrect-off never swapped, so there is nothing to undo. `CandidateCommitTests` holds the cases, each with a control half that *types* the same word, so a build that simply turned autocorrect off fails them.
- **A word the user has backspaced into is never autocorrected, and the delete key undoing itself is why.** Deleting the `ן` off `מאמין` leaves `מאמי`, which no dictionary knows, so `shouldAutocorrect` read it as a typo and the next space put a different word in the field: the user pressed delete to *change* the word and the keyboard changed it back, which is the single most infuriating thing an autocorrect does. `KeyboardController.deleteBackward` snapshots the word left standing into `deletedWordPrefix` and `isCorrectingWordByHand` is true while the word in the field still starts with it — so typing on from the repair stays protected and any other word does not. Three things about the shape. It is **a prefix snapshot rather than a flag**, because the caret can move without this keyboard hearing about it (a tap elsewhere in the host's field goes through no key at all) and a flag would then suppress autocorrect on a word nobody has touched; it is the same claim-checked-rather-than-trusted shape as `GroupedInput.lastWritten`, and it is still cleared outright wherever a word is finished on purpose — `insertSpace`, `apply`, Return and either cursor key — because the residual case the prefix test cannot see is the *same* word typed again straight afterwards, and a short repaired prefix is a prefix of plenty of other words. The **accents popup lands here too, deliberately**: it picks an alternate by calling `deleteBackward()` and retyping, and `צ׳יפס`, `col·legi` and `café` are exactly the words no dictionary holds and autocorrect destroys. It is checked in **both** `refreshSuggestions` (bold slot back to the literal keystrokes) and `insertSpace` (the commit itself), exactly as `storedAutocorrect` is — slot zero being the literal is a fact about `SuggestionEngine` and the space bar should not break if it stops being one. And only the *automatic* replacement goes: the correction is still offered in the bar and a deliberate tap still commits it. Space on pause is the other automatic path and it **does** fire after backspace: the wait from the deleted letters is armed on a prefix that is gone, so `deleteBackward` starts a new one, `idleTypingMayRun` no longer treats a hand repair as "not typing", and `performIdleTyping` still skips *completing* the word so `hel` → `he` cannot become `hello`. `insertSpace` already skips autocorrect for the same repair. `IdleTypingTests.testIdleSpaceFiresAfterBackspace` is what fails a wait that only starts from letters. `CandidateCommitTests` holds all three, each against a control half reaching the identical word by typing rather than by deleting, so a build that simply switched autocorrect off fails them. The other thing that rewrites text on a backspace is `deleteGroupedStroke`, which is grouped keys re-decoding and is correct: see `.claude/rules/keyboard-layout.md`.
- **A setting is not a feature until something reads it, and the personal dictionary was written, persisted, reset, counted in Settings and read by nothing.** `SharedStore.personalDictionary` had no consumer outside its own editor, so on a stock install this keyboard's autocorrect destroyed the three names the app ships in that very list: `Nitai` committed as `Nit` on the space bar, `Handi` as `Handing`, `Wispr` as `Wiser`, and both Hebrew entries too — `סאפא` as `ספא`, `בלי־פרופ` as `בלי־פרוף`. The slot was already there and filled with something else: `SuggestionEngine.suggestions(supplementary:)` took `UILexicon` alone. Four things to keep true. The dictionary check is the **first** question `shouldAutocorrect` asks, not a clause on `isKnownWord` at the bottom — the contraction table and the Hebrew final-form rule both `return true` above that line, and the final-form rule is what ate `בלי־פרופ`. The keyboard reads `storedPersonalDictionary`, which goes through `UserDefaults` at the moment of the keystroke, because the editor is in the app and `load()` fills the `@Published` copy once per launch (same reason as `storedDefaultTone`) — and `load()` honours an empty stored list rather than treating it as absent, or the two readers disagree about a list the user emptied while Settings keeps counting six. Matching folds the maqaf U+05BE onto ASCII `-`: Hebrew's own hyphen is what the shipped entry is spelled with and `KeyboardLayout.connectors` gives a Hebrew layout only the ASCII one, so without the fold that entry is unreachable by anything its owner can type. `PersonalDictionaryTests` drives all of it through `KeyboardController`, not through the engine — the engine was never the broken half.
- **And the fourth thing is the one that survived the first fix: a mark after the word.** `currentWordPrefix` runs back to the last *whitespace*, so `Hi Nitai,` reaches the engine as `Nitai,`, which is not `Nitai` — so the list stopped protecting a name the instant a comma touched it, and `Hi Nitai,` still committed as `Hi Nit`, byte for byte what the same input gives with the list emptied. Greeting somebody by name with a comma is the commonest way a name reaches a chat field, so the first fix missed most of the defect. `SuggestionEngine.wordCore` trims edge punctuation (both ends, so an entry like `Ph.D.` reduces the same way whichever side the mark is on) and strips a trailing `'s`, because `'` is punctuation but the `s` after it is not and `Nitai's` came back `Nita's`. The length gate and `isKnownWord` are asked about that trimmed word too — a comma was worth a letter, and `qwt,` reads as four characters and unknown, which pulled a three-letter word onto a six-letter entry. Two traps. `comparable` answers "" for a prefix that is only punctuation, and "" is a prefix of every entry, so both call sites check for it or typing `...` offers two arbitrary names. And a *separate* bug lives next door with no dictionary near it: `replaceCurrentWord` deletes the whole prefix, so every correction ate the mark — `recieve,` committed as `receive `, `helo,` as `help `. `KeyboardController.restoringEdgeMarks` puts it back, and must not when the candidate already carries it, because candidate zero *is* the literal keystrokes.
- **The one-tap rewrite key is the only key besides the space bar that commits on lift, and a model call is why.** Long-pressing it opens the registers in `KeyView`'s alternates popup — the same mechanism as a letter's accents, stacked vertically because six register names is about 1,000 points of width on a 393-point screen. **The stack grows down from the key**, default nearest the finger: index 0 sits just below the action-row button and later names drop over the QWERTY block. `alternatesPopupAlignment` is `.bottom` and the offset is `+(stackHeight + 6)` so the list starts 6 points below the key. `AlternatesPopupTests.testTheFixPopupGrowsDownFromTheKey` is what fails an upward stack. But a letter has *already inserted* its character on finger-down and picking an accent replaces it, whereas this key runs a cloud call: firing on finger-down would spend one on the default tone every time the user held the key to choose a different register, and `beginWork` cancels its predecessor, so the answer being paid for would be thrown away by the register actually wanted. `KeyView.runsOnLift` defers it; a plain tap still runs the default, just on the lift. Three things to keep true. The list is **default-first** (`KeyboardController.toneAlternates`), because `KeyView` treats index 0 as "the long press changed nothing" — a list spelled `ToneStyle.allCases.map(\.title)` looks right and gives every user Clearer when they hold, look and lift without moving. Selection is **by title, not by index**, because the order is built from a stored setting that Settings can change in another process between the key being drawn and the finger lifting. And the popup is a drag, so the registers also hang off the key as `accessibilityActions` — the same rule the layout editor is built on, that every gesture has a non-gesture route. `ToneAlternatesTests` holds all of it. A custom tone that is *written but not selected* is deliberately absent from the list: `ToneSetting` only resolves to `.custom` when `prefersCustomTone` is on, so there would be no instruction to send. `AIResultPanel.toneChips` used to gate its custom chip on exactly the same condition and was the other surface this had to agree with; that panel is deleted, so this popup is the only reader of `customTone` now.
- **Two brand-tinted buttons sit side by side in the suggestion bar, and both of them were wrong.** The sparkle was disabled by `hasTextToWorkWith || canReply`, which is false on an empty field with no session — the exact state D8's affordance is for, since the broadcast picker lived in the Reply panel and the sparkle was the only route there. It was fixed by asking the panel the same question the panel asked itself. **Both the sparkle and that panel are now deleted**: Reply has its own key in the action row and the picker is the banner message, so the route no longer depends on a button agreeing with a screen. What survives of the fix is `AIAction.isAvailable` / `.hasRunnableAction`, which `SuggestionBar.anyActionCouldRun` still calls, because the bar holding its own opinion about an empty field is what caused this. Its neighbour runs the default tone, and it used to wear that tone's own SF Symbol — which for the shipped default `.clearer` was `sparkle`, the same drawing as `sparkles` at a different count, so two sparkles sat side by side meaning two different things. Fixing the symbol per tone (`.clearer` became `eyeglasses`) only moved the problem: `figure.wave` for Casual is a waving stick figure in a keyboard, which reads as a profile button and says nothing about rewriting. **So the glyph is now fixed at `SuggestionBar.toneButtonSymbol` — `AIAction.rewrite`'s own icon, because the button is a shortcut through that row — and the tone is printed in words under it.** `ToneStyle.icon` is what Settings' default-tone menu and the Rewrite hold menu draw beside each name. `FixStyle.icon` is the same mark on the Fix hold menu. The one-tap bar button still wears `SuggestionBar.toneButtonSymbol`, not the selected tone's icon. `ToneSetting.customIcon` is only the pencil on "My tone". **The button is a fixed 68pt for every tone, not sized to its label**, because its width is a *setting*: growing it put `Professional` at 67pt against `Casual`'s 44, so changing the default tone on the Settings screen re-laid-out the three candidates the user reads mid-word. 68 is the widest name plus the 5pt insets, so nothing ever truncates or scales. `ToneIconTests` holds all of it: no tone wears a sparkle, every icon resolves, the button's symbol is one no tone wears, every name fits that width measured against `SuggestionBar.toneLabelFont` itself rather than a second spelling of it, and the width still leaves each candidate 64pt on a 375pt screen. Prose names the control instead of drawing it: `SuggestionBar.aiButtonName` is the one spelling, used by the playground and onboarding, next to `ToneSetting.settingsNote`'s "the one-tap rewrite button" for the other.

## The context-aware engine

- **There is a scoring harness now, and the bar had never been scored before it.** `Bar/typing/corpus.json` has held 90 frozen mid-typing moments and a stock-keyboard reference since it was written, and nothing ran the engine against them — so every judgement about the suggestion bar was somebody's opinion. `Bar/typing/harness/run.sh` runs the real `SuggestionEngine` over all 90 and `score.py` grades them against the corpus's own `intended` / `mustNotCorrect` / `acceptable` fields. **Run it before and after any change in this area; a change that is not measured against it is a guess.** Two things about it that are not obvious. It compiles for the **iOS Simulator**, not macOS, because `UITextChecker` is UIKit and macOS would spell-check with `NSSpellChecker` — a different dictionary, a different ranking, and a score of an engine this repo does not ship. And it passes an **empty in-memory `PersonalLanguageModel`**, so a score can never quietly inherit whatever the machine running it has been typing. The measured numbers: **47/76 before this work, 73/76 now**. Three remain on purpose: `apos-09` (`were` → `we're`, which needs the sentence and is the async tier's job) and `typo-10`/`typo-11`, where the right Hebrew word *is* offered in slot 1 and is deliberately not committed — see the two-dictionary rule below. `en-comp-03` commits `response` after `the quick`. `cs-05` commits `screenshot`. That 73/76 is not the async corpus.
- **The commit column was the offered column relabelled for 40 of the 76 judged entries, and that is why a whole class of defect scored as a pass.** `score.py` computed an `acceptable` entry's verdict from whether the right word appeared in *any* slot and then printed it under `commit` — the one number its own docstring calls the only one a user would recognise. So `he-comp-07` committed the non-word `מון` for `מונ` with `מונית` sitting beside it in slot 2, counted as a pass, and the headline did not move. The test now is that the bold slot holds either what was typed or one of the good answers: declining to complete is the conservative half of this engine's trade and is not a failure, while inserting a third word is. An entry with an empty prefix is not asked, because `KeyboardController.insertSpace` commits nothing when no word is in progress. **The headline moved as a result and both numbers are worth keeping straight**: the engine that scored 73/76 under the old scorer scores **71/76** under this one, and the Hebrew final-form fix took it to 72/76. An open `acceptable` list still cannot fail on a miss, but it *can* fail on a commit — `cs-11` was inserting `לף` — so those are printed under their own heading rather than folded into the total.
- **Two runs of identical code disagree on two entries, and the source of it is `UITextChecker` rather than this engine.** `he-comp-04` answers `לעבוד` or `לעבור` in slot 2 and `he-comp-05` answers `העזתי` or `העזיבה`, run to run, with nothing changed: the checker's own completion list for a Hebrew prefix is not stable, and `ordinal` is part of `score`, so a different order out of Apple is a different slot 2. The total tie-break in `rank` fixed the *sorting* half of this and cannot fix the *source* half. It has never moved a `commits` value or the score — 73/76 across the pair of runs after `cs-05` closed — so the headline is the number to trust and a slot-2 diff on those two entries is not a regression to chase. `Bar/typing/engine_outputs.json` is gitignored (`.gitignore:26`), so it is one machine's last run and never a reference: diff two runs you made yourself, the way `score.py before.json after.json` is built to.
- **Nearly half of Hebrew typing was measurably wrong while the corpus said the engine was at its best, because 90 frozen moments are a sample and not a keyboard.** The corpus holds 20 Hebrew entries with a word in progress and exactly 2 of them end in a shape-changing letter, so the rule above could be wrong a fifth of the time and cost at most two entries — both of which were scoring on `offered`. Typing whole words letter by letter through `Bar/typing/harness` with a corpus file of your own is cheap (`run.sh` takes any corpus with the same shape) and it is what found this; the frozen 90 are the regression guard, not the whole examination. The same sweep is what found that a trailing comma turned `תדוה,` into a one-slot bar and that `Nitai’s` was unprotected, neither of which the corpus has an entry for.
- **The ranking is made of provenance, and the old bar's ranking was the order the code happened to be written in.** `SuggestionEngine+Completions` used to append candidates and take the first three, so `helot` beat `hello`, `הכתום` ("the orange") beat `הכתובת` ("the address"), and `Dizeng` completed to `Dizziness`. Every candidate now carries a `Source` and `SuggestionEngine.score` weighs it: **1000 per source tier, +400 if the previous word is known to be followed by it, up to +300 for the seed prior, up to +300 for how often this person has committed the word, −8 per position in its source's own list, −500 per Hebrew clitic stripped.** Personal count is stamped before `rank` and starts at two sightings, the same floor as `words(startingWith:)`. It cannot climb a source tier. Neighbours also search the learned store, so a name you type is offered from a one-key slip the seed has never heard of. Four of the older numbers were each set by a regression the corpus caught, so none of them is a free parameter. The ordinal term exists because throwing away `UITextChecker`'s own order made the alphabetical tie-break the ranking and `depl` offered `depletion` and `deplorable` while `deploy` fell off the end. `codeSwitch` sits **above both the checker and the seed list** — below either one, `sta` inside a Hebrew sentence offers `station` and `start` and never reaches `standup`, which is the exact failure the list was written for. `neighbour` sits **below** a completion, because a completion agrees with every key that was pressed and a neighbour claims one of them was wrong. And the clitic penalty is half a tier per letter rather than a tie-break, because `ש`+`ל`+`מוכן` = `שלמוכן` is a real Hebrew construction nobody has ever typed and at a small penalty it outranked `שלום`.
- **The Hebrew final-form rule may only ever land on a word the seed list knows, and the version that asked nothing at all fired on a fifth of all Hebrew typing.** The rule is right about orthography — a *finished* Hebrew word may not end in the ordinary form of ‎כ מ נ פ צ‎ — and wrong about when it is asked, because a word in progress ends in whatever letter was typed last. 20% of the mid-word keystrokes across the 353-word seed vocabulary land on one of those five, and every one of them fired: the candidate arrives as `.orthography`, which outranks every completion source, and `shouldAutocorrect` answers on it above the seed check, so it took the bold slot and pushed the word being typed out of the bar. Measured over ten common words typed letter by letter, **17 of 35 keystroke moments bolded a non-word** — `פ` bolded `ף` while `פגישה` sat unbolded beside it, `מכ` bolded `מך`, `נכ` bolded `נך` — and it *committed* on finished input too, because Hebrew writes its loanwords with the ordinary form at the end: `אפ` ("app") went to `אף` ("nose") and `קליפ` to `קליף`. **The gate is `SeedLanguageModel.knows` and it must never be `UITextChecker`**, which is the whole reason the first version was ripped out: `isKnownWord("שלומ")` comes back true on a cold checker and false on a warm one, so a rule gated on it is asleep on the first word of a session. The seed list is a bundled JSON folded once at load and answers the same on keystroke one as on keystroke one thousand; 66 of its words end in a final form, which is the common core this slip happens in — `שלומ` → `שלום`, `צריכ` → `צריך`, `כספ` → `כסף`, `דרכ` → `דרך`. It is the same "only ever land on a common word" gate `SeedLanguageModel.neighbours` and `LayoutTransposition` already carry. After it: 0 of 35, `he-comp-07` commits `מונית` instead of `מון`, and `cs-11` leaves `לפ` alone. `SuggestionEngineTests.testAWordInProgressIsNotCorrectedToItsOwnFinalForm` asserts on the *default*, because the non-word was in the bar either way and only the bold slot rejects the old build.
- **A trailing mark switched the neighbour rule off, and in Hebrew that is the only correction path there is.** `SeedLanguageModel.neighbours` refuses a candidate shorter than what it is given — the "never shorter than what was typed" rule below — so a comma counted as a letter and put every real neighbour under the floor. `teh` corrected to `the` and `teh,` corrected to nothing. English has a second path and mostly survived (`recieve,` still reached `receive` through `UITextChecker.guesses`), but Apple's Hebrew checker reports `תדוה` and `שלמו` as perfectly good words, so there is nothing behind it: `תדוה,` came back holding **one slot**, the typo, with `תודה` never generated at all. **The first repair gave `wordCore` to the neighbour rule alone and that made a second bug**, because a source asked about the word and a source asked about the keystrokes cannot compete: for `(hel` the completions went silent while the neighbours did not, so `hello` and `help` never arrived, `her` had nothing to beat, and a word the user had not typed one letter of took the bold slot — where plain `hel` is correctly left alone. `completions(for:)` trims once now and hands the same string to every source, and `shouldAutocorrect` asks all of its questions about it, which is what the third bullet above already said was true of the length gate and `isKnownWord` and was true of nothing else. Two consequences worth keeping. The contraction table and the final-form rule are reachable through a mark now (`dont,` → `don't,`, `שלומ,` → `שלום,`). And `KeyboardController.restoringEdgeMarks` restores **both** ends rather than the trailing one, because a leading mark used to hide the word from every lookup except `UITextChecker.guesses`, which reached `receive` from `(recieve` and dropped the bracket on the way. **It restores exactly what `wordCore` removed rather than re-deriving it**, and the difference is not cosmetic: the version that put back the punctuation *runs* at each end looked equivalent and silently deleted the possessive, because `wordCore` also strips `'s` and `'s` is not a run of punctuation — it ends in a letter. `Nitai's` reduced to `Nitai`, was corrected to `Nit`, and committed two characters shorter than what was typed. Locating the core inside the keystrokes keeps the two halves from drifting, which matters because they live in different files. Candidate zero stays the literal keystrokes, marks and all, and neither end is re-added to a candidate that already carries it. Two answers moved and both are the same word agreeing with itself: `sched,` commits `schedule,` where it used to commit `she'd,` (the comma blocked every completion, so a spelling *guess* was all that was left), and `Handi,` is destroyed as `Handing,` rather than `Handy,` — which is exactly what plain `Handi` has always given.
- **`comparable` folded the apostrophe onto itself, and `wordCore` tested the same eight bytes twice.** `replacingOccurrences(of: "'", with: "'")` is ASCII on both sides; the intent was U+2019, which is what `SeedLanguageModel.fold` does correctly two files away. `wordCore`'s `hasSuffix("'s") || hasSuffix("'s")` reads as the two apostrophes and is one of them, so the second branch was dead. The cost was the personal dictionary silently letting go of a word the moment it wore a curly apostrophe: `Nitai's` was protected and **`Nitai’s` committed as `Nita’s`**. That is not an exotic spelling — the apostrophe key's long press offers `’` (`KeyboardLayout+NumbersSymbols`), and a host field with smart quotes on, which is the default everywhere except this suite's own `MockTextTarget`, rewrites a typed `'` to `’` inside the document `currentWordPrefix` reads back. `comparable` is now `SeedLanguageModel.fold(wordCore(word))` rather than a second spelling of it, and the curly form in `wordCore` is written `"\u{2019}s"` so it cannot be normalised back into its twin by an editor.
- **Hebrew needed morphology, not a bigger dictionary, and that is why its completions were worse than English's.** Hebrew glues ‎ה ב ל מ ו ש כ‎ to the front of a word, so "to work" is one token `לעבודה` and no dictionary lists the glued forms: `UITextChecker` completed `לעבו` to `לעבוד` and `לעבור`, two verbs, and `מהג` to `מהגרים` ("immigrants") when the sentence was about children coming home from kindergarten. `HebrewMorphology.splits` returns *every* reading, unsplit first, and the seed list is asked about each stem — one entry for `עבודה` then serves `לעבודה`, `בעבודה` and `מהעבודה`. **A one-letter stem is included and only the seed list may answer it**: `מהגן` is `מ`+`ה`+`גן`, so reaching it means completing the single letter `ג`, and asking `UITextChecker` that question returns every word in Hebrew starting with gimel.

- **A neighbour may never be shorter than what was typed.** Every prefix is a word in progress, so a shorter neighbour proposes deleting a key the user just pressed: `מונ` on the way to `מונית` is one edit from `מון`, `מאו` on the way to `מאוחר` is one edit from `או`. Allowing it turned four correct Hebrew completions into corrections of half-typed words in a single corpus run.
- **`id` came out of the contraction table and `were` never went in.** Membership in `contractions` is what makes a word get replaced on space, and both of those have an ordinary reading — `That's a good id` committed as `That's a good I'd` (corpus `nc-02`). The rest of the table has no such reading, so this is one criterion applied once to the table rather than a per-word rule at runtime; an earlier fix that special-cased `were` with a list of plural subjects was exactly the tailored logic this repo should not carry. `its`, `cant`, `ill` and `thats` are all ordinary English words too and all *stay*, which is why the contraction test is asked **before** the "we never correct a known word" test and not after.
- **Learning is scoped to the real keyboard, and it was not, and the test suite noticed for us.** `PersonalLanguageModel` records committed words and word pairs into the App Group. Every unit test and the app's onboarding playground drive a real `KeyboardController` and press real space bars, so all of them were writing into it: the suite alone had taught it `Handi` ten times and `Nitai` nine, past `protectThreshold`, so `PersonalDictionaryTests` silently stopped being able to prove the personal dictionary does anything — the words it was checking were being defended by a store the tests had filled themselves. `KeyboardController.personal` is `.shared` only when `isSystemKeyboard` is true and a throwaway otherwise. **Nothing from `SharedStore.shippedPersonalDictionary` may go in the seed list either**, for the same reason: two lists defending one word means neither can be shown to work.
- **Two stores, one screen.** Languages → Personal dictionary lists names the user added (`store.personalDictionary`, never correct) and words inferred from typing (`learnedWords()`, including a single sighting). A name already in Your words is not listed again under From typing. Forget one word or Forget all lives on that screen only, and wipes only the inferred list. Ranking still ignores count below `boostThreshold`; `allWords` stays gated on that floor. The app and the keyboard both `reload()` the App Group file on appear: Forget deletes the file, and a keyboard process that is still alive must drop the old counts. A missing file is empty, not "keep what we had". Do not write learned unigrams into `personalDictionary`. Those are different jobs. **The inferred list is sectioned per language in `KeyboardLanguage.allCases` order, and every section after the first was unreachable**: a bilingual user with 267 English words had to scroll past all 267 to find out whether the keyboard had learned a single Hebrew one, which is the one question that screen answers. Each section is capped at `DictionaryView.collapsedRowCount` with a per-language Show all, and a search is never capped because it has already been narrowed to something somebody asked for. The header count stays the true total. The `groups.count > 1` test is also the only thing that puts a language name in that header, so **"From typing · English" is itself evidence that a second language is remembered** and merely below the fold — worth reading before believing a report that one is missing.
- **Every finished word is learned, not only a candidate tap.** Tapping a suggestion always inserts a space, so that path used to be the only one that reliably reached the store. Typing a word and sending the message — Return, a full stop, an emoji, the keyboard going away, or the host emptying the field — never did. `learnWordJustCommitted` reads the word *under the cursor* (so a trailing space is "already learned") and is called before space, Return and word-ending punctuation land. `refreshDocumentState` keeps the open word and commits it when `textDidChange` reports an empty field, which is how a chat Send finishes a word without a trailing space. An apostrophe or hyphen does not finish the word. Deleting a word does not count it. The same open word is not counted twice if the keyboard comes and goes. `ContextAwareSuggestionTests.testATypedWordIsLearnedWhenItIsFinishedNotOnlyWhenACandidateIsTapped` holds it.
- **The async tier is on-device only, and Hebrew gets none.** `PredictiveRefiner` holds one optional predictor, not a list. `standard()` never takes a cloud engine. Slot 0 stays the typed keystrokes. The first on-device model word that lands becomes the default. Space still only inserts that word when `storedAutocorrect` is on — that switch is how the user keeps control. `shouldRefine` no longer bails on a full mid-word bar; that guard made the remaining corpus misses (`were` → `we're`) unreachable. Stale answers are still dropped: the prefix is handed back through the callback. `testRefinementCanChangeTheBoldWord` is what fails a bar that still pins the local default. `testTheShippingRefinerDoesNotServeHebrew` is what fails a `standard()` that grew a cloud slot again. Do not wire `CloudIntelligence` back into the bar: Fix, Rewrite and Reply are the cloud actions, and three guessed words above the keys are not.
- **The async corpus is a different exam from the local 73/76.** `Bar/typing/async/corpus.json` is **30 paused moments** (it was ~11 until NIT-21), every one carrying a `pauseMs`. The shape matters more than the count: **7 are `mustNotCorrect`, and before NIT-21 there were none at all**, so nothing in it could fail by inventing a change nobody asked for and a refiner that rewrote everything would have scored perfectly. Two of those seven are deliberate contrastive pairs putting the *same* risky word in a context where correction must not fire (`apos-09-control`, `apos-10-control`). The rest is 3 `intended` (including `apos-09`, `were` → `we're`, with `were` staying out of the contraction table), 20 `acceptable`, and 7 Hebrew entries that are expected skips because `PredictiveRefiner.standard()` never carries a Hebrew-capable engine. `Bar/typing/async/validate.py` runs before the simulator does and rejects an entry that does not carry exactly one of `mustNotCorrect` / `intended` / `acceptable`, because `score.py` silently buckets anything else as `unjudged` and it never counts again. `Bar/typing/async/run.sh` runs `AIKeyboardCoreTests/AsyncTypingCorpusTests` and scores with `TYPING_CORPUS` pointed at that file. Two runs on this simulator were **5/6** both times, `engineAvailable: false`, every `asyncRan` false: that is the local tier of those entries, not a model score. Do not fold it into the local 73/76.
- **Complete on pause and Space on pause are separate, both off by default.** Completing writes the first suggestion that is not the typed word (slot 1 in engine order: the best completion), not the bold slot — mid-word the typed letters stay default unless they are a typo, and Autocorrect-off remakes default to slot 0, so taking `isDefault` made the switch a no-op. Completing leaves no trailing space. Space on pause is the space bar (so Autocorrect still decides whether the bold word comes with it). Both on is that completion plus a space. Neither fires on an empty prefix, a credential field, or while the emoji panel is open. After a complete-only rewrite the pause is cancelled, or the next offer (`hellos` after `hello`) would fire again. **The wait is from the last keyed character, not from a suggestion refresh.** `refreshSuggestions` runs for a caret tap, the keyboard coming on screen, a language switch and the host's `textDidChange`, and starting the pause there inserted a space into a word nobody had just typed. `noteTypedInput` arms it from `insertCharacter` and grouped key presses; a later letter replaces `idleTypedAt` so the first letter's wait cannot fire in the gap between keys; a caret that has moved onto a different word fails the armed-prefix check. The length is `storedIdleDelayMs` (300 ships; 150 / 300 / 500 / 800 / 1200), read at the keystroke with the two toggles, same trap as `storedAutocorrect`. `applyRefinement` also re-pins the bold slot to the typed word when Autocorrect is off, same as `refreshSuggestions`. `IdleTypingTests` holds the cases.
- **The local tier's cost is measured and the harness prints it, because "fast enough for every keystroke" is the assumption the whole two-tier design rests on.** Over four runs of the 90 corpus entries, warm, on the iOS 26.2 Simulator: **median 1.1-1.3 ms, worst entry 10-16 ms**, and *which* entry is slowest changes between runs of identical code — one run also produced a 27 ms outlier that did not reproduce, so the same "one run is not evidence" rule that governs the Bar corpora governs this number too. The shape is stable and is the part to reason about: the slow entries are always Hebrew words where the seed list has nothing and more than one clitic reading has to be put to `UITextChecker`. The **first** call in a language is separate and much larger, ~70-280 ms, because Apple builds that language's lexicon then; a user pays it once per keyboard session and `run.sh` reports it on its own line so it is never averaged into the per-keystroke figure. Two costs were found by measuring rather than by reading: the seed list was being folded on every keystroke (785 English words, *twice* each, inside the prefix scan) and is now folded once at load, and a split Hebrew reading no longer asks `UITextChecker` when the seed already answered that reading — worth about a third of the worst case, with the corpus score unchanged.
- **The bar carried a pause button for exactly one build, and then pause was deleted.** A recording reports on the microphone key — orange at rest, record red while listening, a `pause.fill` glyph that *stops* — and the strip that used to hold Pause, Resume and Cancel is not drawn for one at all. Pause briefly moved here, into the slot the undo uses, because there was no height to build it a row of its own. Then it went entirely: the key stops on a second tap, which is all anyone wanted from it, and the whole cross-process pause protocol went with the button (see `.claude/rules/dictation.md`). What survives from that episode is the rule it was written under — a control that renders and answers nothing cannot be told from one that works — and the bar's dictation edge button still wears the same appearances the key does, because two surfaces disagreeing about whether a microphone is on is D8 with the stakes raised.
- **Nothing in the bar redraws on its own any more, and a deletion nearly took the dictation controls with it.** `KeyboardController.dictationAvailability` was a computed property forwarding to `DictationSession`, which worked only because the deleted waveform republished `waveformPhase` twenty times a second and dragged every other dictation reading onto the screen with it. It is a mirrored `@Published` now, subscribed in `init` rather than in `observeDictation()` so a controller that has never opened an utterance still reports what the session can see. `dictationRemainingSeconds` is mirrored **a whole second at a time**, because it feeds a caption that counts in seconds and the session republishes it ten times a second. `dictationLevels` is the deliberate opposite: every tick is kept, because it *is* the waveform the microphone key and its bar copy draw, and throttling it would leave three bars and a pause.
- **The bar carries one control the layout editor cannot configure, and it is an undo.** Fix and Rewrite write their answer straight into the field now (see `.claude/rules/ai-text.md`), so `SuggestionBar` draws a revert button at the trailing end of the three candidates for as long as `KeyboardController.revertibleEdit` is set — which is until the next keystroke. It sits there rather than in `barTrailing` because it is not a control the user chose to have: it appears with an edit they did not ask for twice and has to be where they are already looking when the text changes under them. It costs the three candidates about 53pt (a 44pt button and a 9pt rule) for the one keystroke it lives. It is brand-**tinted** and not brand-filled, which is the opposite of the active action key one row down: a filled cap means "this is happening", and this means "you can take that back".
- **Fix and Rewrite are disabled on an empty field, and that reverses the rule `ToneTap` was written under.** That rule — a control which looks unavailable and swallows the tap teaches the user nothing — came from a button that looked *live*: a fully saturated brand icon over a faded gradient, which read as enabled, did nothing, and said nothing. Answering it with a 72pt refusal and a Dismiss tap was the fix at the time; drawing the key visibly off says the same thing in the place the user is already looking, and `KeyView` carries "Type something first" as the accessibility hint so the words still reach anyone who cannot see it. Three things to keep true. **The key guards its own gesture** (`KeyView.acceptsTouches`, asked in both halves of `pressGesture` and in the repeat and popup starters) rather than trusting `.disabled()` to stop it: `.disabled()` sets `\.isEnabled` in the environment and the built-in controls consult it, but this key is a raw `DragGesture` on a `ZStack` and reads that value nowhere, so whether the gesture is stopped at all is a framework detail that has changed across releases — and being wrong about it gives exactly the dim-key-that-answers-anyway this state exists to remove. `.disabled()` stays on the view as well, because it is what tells VoiceOver and what `EmptyFieldBarTests` can read back off the accessibility tree. **Both halves of the gesture**, because `runsOnLift` makes `onEnded` the only place the one-tap rewrite key ever fires, so a guard on `onChanged` alone would leave it running on every tap. The cap keeps its colour and only the label fades (`KeyView.disabledLabelOpacity`), because fading the whole key punches a hole in a grid whose evenness is most of how it reads. And the key and the bar's own one-tap button must go dim **together** — that is D8's defect, two surfaces disagreeing about what an empty field means — which is why the bar asks `!controller.isActionKeyDisabled(.quickTone)` rather than reading the field for itself. **A second reason to be off arrived and proved that point**: a recording disables all three text actions (see `.claude/rules/dictation.md`), and a bar button that had kept its own copy of the question would have stayed live through it. Both surfaces take their accessibility wording from `actionKeyDisabledReason` for the same reason — "Type something first" printed over a live recording tells the user to do the thing they are already doing — and `KeyView` takes it as `disabledHint` rather than spelling it. The question underneath is still `documentHasText` rather than `hasTextToWorkWith`: they answer the same thing, but only the published one makes a `View` body re-run when the first character lands, and it is filled at the top of `refreshSuggestions` above the Predictions guard, since a user who turned the suggestion bar off still has these two keys. **Every path that changes the document has to reach `refreshDocumentState`, and one did not**: `replaceTargetText`'s insert-only branch — the one a *reply* takes, because `runReply` empties `aiSourceText` on purpose — returned without refreshing, so accepting a reply into an empty field left Fix and Rewrite drawn dim over a field now holding a whole sentence. Reply is the one action that runs on an empty field, so that is the ordinary way this happens rather than an edge. `KeyboardViewController.viewWillAppear` calls it too, since one extension instance is reused across fields and across host apps.
