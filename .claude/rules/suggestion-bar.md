# Suggestion bar, autocorrect and the personal dictionary

- **Autocorrect and Predictions are settings the keyboard must re-read, and the default candidate is bold, not a chip.** Space commits the default suggestion only when `storedAutocorrect` is on — the `@Published` copy is filled once at launch, so a toggle flipped in the app while the keyboard is already up is invisible unless the space bar and `refreshSuggestions` go through UserDefaults at the keystroke (same trap as `storedPersonalDictionary`). When the setting is off, `refreshSuggestions` also re-marks slot 0 as default so the bar does not bold a correction space is no longer allowed to commit; a deliberate tap on a candidate still inserts it. Predictions uses `storedPredictions` for the same reason. The default slot is drawn in bold weight with no background fill.
- **A setting is not a feature until something reads it, and the personal dictionary was written, persisted, reset, counted in Settings and read by nothing.** `SharedStore.personalDictionary` had no consumer outside its own editor, so on a stock install this keyboard's autocorrect destroyed the three names the app ships in that very list: `Nitai` committed as `Nit` on the space bar, `Handi` as `Handing`, `Wispr` as `Wiser`, and both Hebrew entries too — `סאפא` as `ספא`, `בלי־פרופ` as `בלי־פרוף`. The slot was already there and filled with something else: `SuggestionEngine.suggestions(supplementary:)` took `UILexicon` alone. Four things to keep true. The dictionary check is the **first** question `shouldAutocorrect` asks, not a clause on `isKnownWord` at the bottom — the contraction table and the Hebrew final-form rule both `return true` above that line, and the final-form rule is what ate `בלי־פרופ`. The keyboard reads `storedPersonalDictionary`, which goes through `UserDefaults` at the moment of the keystroke, because the editor is in the app and `load()` fills the `@Published` copy once per launch (same reason as `storedDefaultTone`) — and `load()` honours an empty stored list rather than treating it as absent, or the two readers disagree about a list the user emptied while Settings keeps counting six. Matching folds the maqaf U+05BE onto ASCII `-`: Hebrew's own hyphen is what the shipped entry is spelled with and `KeyboardLayout.connectors` gives a Hebrew layout only the ASCII one, so without the fold that entry is unreachable by anything its owner can type. `PersonalDictionaryTests` drives all of it through `KeyboardController`, not through the engine — the engine was never the broken half.
- **And the fourth thing is the one that survived the first fix: a mark after the word.** `currentWordPrefix` runs back to the last *whitespace*, so `Hi Nitai,` reaches the engine as `Nitai,`, which is not `Nitai` — so the list stopped protecting a name the instant a comma touched it, and `Hi Nitai,` still committed as `Hi Nit`, byte for byte what the same input gives with the list emptied. Greeting somebody by name with a comma is the commonest way a name reaches a chat field, so the first fix missed most of the defect. `SuggestionEngine.wordCore` trims edge punctuation (both ends, so an entry like `Ph.D.` reduces the same way whichever side the mark is on) and strips a trailing `'s`, because `'` is punctuation but the `s` after it is not and `Nitai's` came back `Nita's`. The length gate and `isKnownWord` are asked about that trimmed word too — a comma was worth a letter, and `qwt,` reads as four characters and unknown, which pulled a three-letter word onto a six-letter entry. Two traps. `comparable` answers "" for a prefix that is only punctuation, and "" is a prefix of every entry, so both call sites check for it or typing `...` offers two arbitrary names. And a *separate* bug lives next door with no dictionary near it: `replaceCurrentWord` deletes the whole prefix, so every correction ate the mark — `recieve,` committed as `receive `, `helo,` as `help `. `KeyboardController.restoringEdgeMarks` puts it back, and must not when the candidate already carries it, because candidate zero *is* the literal keystrokes.
- **The one-tap rewrite key is the only key besides the space bar that commits on lift, and a model call is why.** Long-pressing it opens the registers in `KeyView`'s alternates popup — the same mechanism as a letter's accents, stacked vertically because seven register names is about 1,000 points of width on a 393-point screen. But a letter has *already inserted* its character on finger-down and picking an accent replaces it, whereas this key runs a cloud call: firing on finger-down would spend one on the default tone every time the user held the key to choose a different register, and `beginWork` cancels its predecessor, so the answer being paid for would be thrown away by the register actually wanted. `KeyView.runsOnLift` defers it; a plain tap still runs the default, just on the lift. Three things to keep true. The list is **default-first** (`KeyboardController.toneAlternates`), because `KeyView` treats index 0 as "the long press changed nothing" — a list spelled `ToneStyle.allCases.map(\.title)` looks right and gives every user Clearer when they hold, look and lift without moving. Selection is **by title, not by index**, because the order is built from a stored setting that Settings can change in another process between the key being drawn and the finger lifting. And the popup is a drag, so the registers also hang off the key as `accessibilityActions` — the same rule the layout editor is built on, that every gesture has a non-gesture route. `ToneAlternatesTests` holds all of it. A custom tone that is *written but not selected* is deliberately absent from the list: `ToneSetting` only resolves to `.custom` when `prefersCustomTone` is on, so there would be no instruction to send. `AIResultPanel.toneChips` used to gate its custom chip on exactly the same condition and was the other surface this had to agree with; that panel is deleted, so this popup is the only reader of `customTone` now.
- **Two brand-tinted buttons sit side by side in the suggestion bar, and both of them were wrong.** The sparkle was disabled by `hasTextToWorkWith || canReply`, which is false on an empty field with no session — the exact state D8's affordance is for, since the broadcast picker lived in the Reply panel and the sparkle was the only route there. It was fixed by asking the panel the same question the panel asked itself. **Both the sparkle and that panel are now deleted**: Reply has its own key in the action row and the picker is the banner's trailing chip, so the route no longer depends on a button agreeing with a screen. What survives of the fix is `AIAction.isAvailable` / `.hasRunnableAction`, which `SuggestionBar.anyActionCouldRun` still calls, because the bar holding its own opinion about an empty field is what caused this. Its neighbour runs the default tone, and it used to wear that tone's own SF Symbol — which for the shipped default `.clearer` was `sparkle`, the same drawing as `sparkles` at a different count, so two sparkles sat side by side meaning two different things. Fixing the symbol per tone (`.clearer` became `eyeglasses`) only moved the problem: `figure.wave` for Casual is a waving stick figure in a keyboard, which reads as a profile button and says nothing about rewriting. **So the glyph is now fixed at `SuggestionBar.toneButtonSymbol` — `AIAction.rewrite`'s own icon, because the button is a shortcut through that row — and the tone is printed in words under it.** `ToneStyle.icon` survives for the tone picker and result variants, where a panel header already says what the screen is about; `ToneSetting.icon` had no other reader and is deleted. **The button is a fixed 68pt for every tone, not sized to its label**, because its width is a *setting*: growing it put `Professional` at 67pt against `Casual`'s 44, so changing the default tone on the Settings screen re-laid-out the three candidates the user reads mid-word. 68 is the widest name plus the 5pt insets, so nothing ever truncates or scales. `ToneIconTests` holds all of it: no tone wears a sparkle, every icon resolves, the button's symbol is one no tone wears, every name fits that width measured against `SuggestionBar.toneLabelFont` itself rather than a second spelling of it, and the width still leaves each candidate 64pt on a 375pt screen. Prose names the control instead of drawing it: `SuggestionBar.aiButtonName` is the one spelling, used by the playground and onboarding, next to `ToneSetting.settingsNote`'s "the one-tap rewrite button" for the other.

## The context-aware engine

- **There is a scoring harness now, and the bar had never been scored before it.** `Bar/typing/corpus.json` has held 90 frozen mid-typing moments and a stock-keyboard reference since it was written, and nothing ran the engine against them — so every judgement about the suggestion bar was somebody's opinion. `Bar/typing/harness/run.sh` runs the real `SuggestionEngine` over all 90 and `score.py` grades them against the corpus's own `intended` / `mustNotCorrect` / `acceptable` fields. **Run it before and after any change in this area; a change that is not measured against it is a guess.** Two things about it that are not obvious. It compiles for the **iOS Simulator**, not macOS, because `UITextChecker` is UIKit and macOS would spell-check with `NSSpellChecker` — a different dictionary, a different ranking, and a score of an engine this repo does not ship. And it passes an **empty in-memory `PersonalLanguageModel`**, so a score can never quietly inherit whatever the machine running it has been typing. The measured numbers: **47/76 before this work, 72/76 now**. The four that remain are `apos-09` (`were` → `we're`, which needs the sentence and is the async tier's job), `typo-10`/`typo-11`, where the right Hebrew word *is* offered in slot 1 and is deliberately not committed — see the two-dictionary rule below — and `en-comp-03`, where `respon` commits `respond` against a closed list of `response`/`responses`, which is the four-letter gate committing a guess about an unfinished word.
- **The commit column was the offered column relabelled for 40 of the 76 judged entries, and that is why a whole class of defect scored as a pass.** `score.py` computed an `acceptable` entry's verdict from whether the right word appeared in *any* slot and then printed it under `commit` — the one number its own docstring calls the only one a user would recognise. So `he-comp-07` committed the non-word `מון` for `מונ` with `מונית` sitting beside it in slot 2, counted as a pass, and the headline did not move. The test now is that the bold slot holds either what was typed or one of the good answers: declining to complete is the conservative half of this engine's trade and is not a failure, while inserting a third word is. An entry with an empty prefix is not asked, because `KeyboardController.insertSpace` commits nothing when no word is in progress. **The headline moved as a result and both numbers are worth keeping straight**: the engine that scored 73/76 under the old scorer scores **71/76** under this one, and the Hebrew final-form fix took it to 72/76. An open `acceptable` list still cannot fail on a miss, but it *can* fail on a commit — `cs-11` was inserting `לף` — so those are printed under their own heading rather than folded into the total.
- **Two runs of identical code disagree on two entries, and the source of it is `UITextChecker` rather than this engine.** `he-comp-04` answers `לעבוד` or `לעבור` in slot 2 and `he-comp-05` answers `העזתי` or `העזיבה`, run to run, with nothing changed: the checker's own completion list for a Hebrew prefix is not stable, and `ordinal` is part of `score`, so a different order out of Apple is a different slot 2. The total tie-break in `rank` fixed the *sorting* half of this and cannot fix the *source* half. It has never moved a `commits` value or the score — 72/76 across every run — so the headline is the number to trust and a slot-2 diff on those two entries is not a regression to chase. `Bar/typing/engine_outputs.json` is gitignored (`.gitignore:26`), so it is one machine's last run and never a reference: diff two runs you made yourself, the way `score.py before.json after.json` is built to.
- **Nearly half of Hebrew typing was measurably wrong while the corpus said the engine was at its best, because 90 frozen moments are a sample and not a keyboard.** The corpus holds 20 Hebrew entries with a word in progress and exactly 2 of them end in a shape-changing letter, so the rule above could be wrong a fifth of the time and cost at most two entries — both of which were scoring on `offered`. Typing whole words letter by letter through `Bar/typing/harness` with a corpus file of your own is cheap (`run.sh` takes any corpus with the same shape) and it is what found this; the frozen 90 are the regression guard, not the whole examination. The same sweep is what found that a trailing comma turned `תדוה,` into a one-slot bar and that `Nitai’s` was unprotected, neither of which the corpus has an entry for.
- **The ranking is made of provenance, and the old bar's ranking was the order the code happened to be written in.** `SuggestionEngine+Completions` used to append candidates and take the first three, so `helot` beat `hello`, `הכתום` ("the orange") beat `הכתובת` ("the address"), and `Dizeng` completed to `Dizziness`. Every candidate now carries a `Source` and `SuggestionEngine.score` weighs it: **1000 per source tier, +400 if the previous word is known to be followed by it, up to +300 for frequency, −8 per position in its source's own list, −500 per Hebrew clitic stripped.** Four of those numbers were each set by a regression the corpus caught, so none of them is a free parameter. The ordinal term exists because throwing away `UITextChecker`'s own order made the alphabetical tie-break the ranking and `depl` offered `depletion` and `deplorable` while `deploy` fell off the end. `codeSwitch` sits **above both the checker and the seed list** — below either one, `sta` inside a Hebrew sentence offers `station` and `start` and never reaches `standup`, which is the exact failure the list was written for. `neighbour` sits **below** a completion, because a completion agrees with every key that was pressed and a neighbour claims one of them was wrong. And the clitic penalty is half a tier per letter rather than a tie-break, because `ש`+`ל`+`מוכן` = `שלמוכן` is a real Hebrew construction nobody has ever typed and at a small penalty it outranked `שלום`.
- **The Hebrew final-form rule may only ever land on a word the seed list knows, and the version that asked nothing at all fired on a fifth of all Hebrew typing.** The rule is right about orthography — a *finished* Hebrew word may not end in the ordinary form of ‎כ מ נ פ צ‎ — and wrong about when it is asked, because a word in progress ends in whatever letter was typed last. 20% of the mid-word keystrokes across the 353-word seed vocabulary land on one of those five, and every one of them fired: the candidate arrives as `.orthography`, which outranks every completion source, and `shouldAutocorrect` answers on it above the seed check, so it took the bold slot and pushed the word being typed out of the bar. Measured over ten common words typed letter by letter, **17 of 35 keystroke moments bolded a non-word** — `פ` bolded `ף` while `פגישה` sat unbolded beside it, `מכ` bolded `מך`, `נכ` bolded `נך` — and it *committed* on finished input too, because Hebrew writes its loanwords with the ordinary form at the end: `אפ` ("app") went to `אף` ("nose") and `קליפ` to `קליף`. **The gate is `SeedLanguageModel.knows` and it must never be `UITextChecker`**, which is the whole reason the first version was ripped out: `isKnownWord("שלומ")` comes back true on a cold checker and false on a warm one, so a rule gated on it is asleep on the first word of a session. The seed list is a bundled JSON folded once at load and answers the same on keystroke one as on keystroke one thousand; 66 of its words end in a final form, which is the common core this slip happens in — `שלומ` → `שלום`, `צריכ` → `צריך`, `כספ` → `כסף`, `דרכ` → `דרך`. It is the same "only ever land on a common word" gate `SeedLanguageModel.neighbours` and `LayoutTransposition` already carry. After it: 0 of 35, `he-comp-07` commits `מונית` instead of `מון`, and `cs-11` leaves `לפ` alone. `SuggestionEngineTests.testAWordInProgressIsNotCorrectedToItsOwnFinalForm` asserts on the *default*, because the non-word was in the bar either way and only the bold slot rejects the old build.
- **A trailing mark switched the neighbour rule off, and in Hebrew that is the only correction path there is.** `SeedLanguageModel.neighbours` refuses a candidate shorter than what it is given — the "never shorter than what was typed" rule below — so a comma counted as a letter and put every real neighbour under the floor. `teh` corrected to `the` and `teh,` corrected to nothing. English has a second path and mostly survived (`recieve,` still reached `receive` through `UITextChecker.guesses`), but Apple's Hebrew checker reports `תדוה` and `שלמו` as perfectly good words, so there is nothing behind it: `תדוה,` came back holding **one slot**, the typo, with `תודה` never generated at all. **The first repair gave `wordCore` to the neighbour rule alone and that made a second bug**, because a source asked about the word and a source asked about the keystrokes cannot compete: for `(hel` the completions went silent while the neighbours did not, so `hello` and `help` never arrived, `her` had nothing to beat, and a word the user had not typed one letter of took the bold slot — where plain `hel` is correctly left alone. `completions(for:)` trims once now and hands the same string to every source, and `shouldAutocorrect` asks all of its questions about it, which is what the third bullet above already said was true of the length gate and `isKnownWord` and was true of nothing else. Two consequences worth keeping. The contraction table and the final-form rule are reachable through a mark now (`dont,` → `don't,`, `שלומ,` → `שלום,`). And `KeyboardController.restoringEdgeMarks` restores **both** ends rather than the trailing one, because a leading mark used to hide the word from every lookup except `UITextChecker.guesses`, which reached `receive` from `(recieve` and dropped the bracket on the way. **It restores exactly what `wordCore` removed rather than re-deriving it**, and the difference is not cosmetic: the version that put back the punctuation *runs* at each end looked equivalent and silently deleted the possessive, because `wordCore` also strips `'s` and `'s` is not a run of punctuation — it ends in a letter. `Nitai's` reduced to `Nitai`, was corrected to `Nit`, and committed two characters shorter than what was typed. Locating the core inside the keystrokes keeps the two halves from drifting, which matters because they live in different files. Candidate zero stays the literal keystrokes, marks and all, and neither end is re-added to a candidate that already carries it. Two answers moved and both are the same word agreeing with itself: `sched,` commits `schedule,` where it used to commit `she'd,` (the comma blocked every completion, so a spelling *guess* was all that was left), and `Handi,` is destroyed as `Handing,` rather than `Handy,` — which is exactly what plain `Handi` has always given.
- **`comparable` folded the apostrophe onto itself, and `wordCore` tested the same eight bytes twice.** `replacingOccurrences(of: "'", with: "'")` is ASCII on both sides; the intent was U+2019, which is what `SeedLanguageModel.fold` does correctly two files away. `wordCore`'s `hasSuffix("'s") || hasSuffix("'s")` reads as the two apostrophes and is one of them, so the second branch was dead. The cost was the personal dictionary silently letting go of a word the moment it wore a curly apostrophe: `Nitai's` was protected and **`Nitai’s` committed as `Nita’s`**. That is not an exotic spelling — the apostrophe key's long press offers `’` (`KeyboardLayout+NumbersSymbols`), and a host field with smart quotes on, which is the default everywhere except this suite's own `MockTextTarget`, rewrites a typed `'` to `’` inside the document `currentWordPrefix` reads back. `comparable` is now `SeedLanguageModel.fold(wordCore(word))` rather than a second spelling of it, and the curly form in `wordCore` is written `"\u{2019}s"` so it cannot be normalised back into its twin by an editor.
- **Hebrew needed morphology, not a bigger dictionary, and that is why its completions were worse than English's.** Hebrew glues ‎ה ב ל מ ו ש כ‎ to the front of a word, so "to work" is one token `לעבודה` and no dictionary lists the glued forms: `UITextChecker` completed `לעבו` to `לעבוד` and `לעבור`, two verbs, and `מהג` to `מהגרים` ("immigrants") when the sentence was about children coming home from kindergarten. `HebrewMorphology.splits` returns *every* reading, unsplit first, and the seed list is asked about each stem — one entry for `עבודה` then serves `לעבודה`, `בעבודה` and `מהעבודה`. **A one-letter stem is included and only the seed list may answer it**: `מהגן` is `מ`+`ה`+`גן`, so reaching it means completing the single letter `ג`, and asking `UITextChecker` that question returns every word in Hebrew starting with gimel.
- **Two dictionaries have to disown a word before it is replaced, and "absent from the seed" is not one of them.** The seed list is a few hundred words per language, so absence proves nothing: `cat` is not in it, `car` is one edit away and *is*, and the first version of the neighbour rule quietly turned one into the other. Asking `UITextChecker` as well fixed it. The cost is measured and accepted: Apple's Hebrew checker reports `תדוה` and `שלמו` as perfectly good words, so those two typos are **offered in slot 1 and not committed on space**. Being conservative there is the deliberate half of the trade — over-correcting is what makes people switch autocorrect off.
- **The four-letter autocorrect gate stays at four, and three-letter typos are covered by a different rule.** Lowering it to three did fix `teh` → `the`, and it also let any three-letter prefix be replaced by a six-letter word starting with it — `qwt` committed as `qwtxyz` the moment that entry was in the personal dictionary, which is what `PersonalDictionaryTests` names. The distinction that matters is not length but kind: a same-length neighbour is a slip, a longer completion is a guess about a word still being typed. `teh` corrects because `the` is a neighbour, not because of its length.
- **A newline closes the thought, and `previousWords` said so in a comment while doing the opposite.** It trimmed the whole context, which takes the line break off the end, and then split on whitespace, which a line break also is — so the boundary was invisible twice over and `See you\n` predicted `tomorrow` exactly as `See you ` does. It reads the last line now. That also stops a space pressed at the head of a fresh line teaching `PersonalLanguageModel` the previous line's last word a second time, which is the same `previousWords` call seen from `learnWordJustCommitted`.
- **Still open: a same-length neighbour can replace a word that is still being typed, and the length floor does not catch it.** `מכונ` on the way to `מכונית` is one substitution from `נכון`, four letters against four, so it clears the floor below and — because the seed knows `נכון` and does not know `מכונית` — it wins the ranking and the bold slot. Measured at **2 of 35** keystroke moments over the same ten Hebrew words (`מכונ` → `נכון`, `מצט` → `מצב`), and 0 of 24 in English. It is older than the final-form fix above, which used to mask it with a different wrong word, and it is not obviously fixable by asking "does the typed word have completions": `helo` → `hello` is the same shape and is the case the rule was written for.
- **A neighbour may never be shorter than what was typed.** Every prefix is a word in progress, so a shorter neighbour proposes deleting a key the user just pressed: `מונ` on the way to `מונית` is one edit from `מון`, `מאו` on the way to `מאוחר` is one edit from `או`. Allowing it turned four correct Hebrew completions into corrections of half-typed words in a single corpus run.
- **`id` came out of the contraction table and `were` never went in.** Membership in `contractions` is what makes a word get replaced on space, and both of those have an ordinary reading — `That's a good id` committed as `That's a good I'd` (corpus `nc-02`). The rest of the table has no such reading, so this is one criterion applied once to the table rather than a per-word rule at runtime; an earlier fix that special-cased `were` with a list of plural subjects was exactly the tailored logic this repo should not carry. `its`, `cant`, `ill` and `thats` are all ordinary English words too and all *stay*, which is why the contraction test is asked **before** the "we never correct a known word" test and not after.
- **Learning is scoped to the real keyboard, and it was not, and the test suite noticed for us.** `PersonalLanguageModel` records committed words and word pairs into the App Group. Every unit test and the app's onboarding playground drive a real `KeyboardController` and press real space bars, so all of them were writing into it: the suite alone had taught it `Handi` ten times and `Nitai` nine, past `protectThreshold`, so `PersonalDictionaryTests` silently stopped being able to prove the personal dictionary does anything — the words it was checking were being defended by a store the tests had filled themselves. `KeyboardController.personal` is `.shared` only when `isSystemKeyboard` is true and a throwaway otherwise. **Nothing from `SharedStore.shippedPersonalDictionary` may go in the seed list either**, for the same reason: two lists defending one word means neither can be shown to work.
- **The async tier may change the options and never the default — and pinning the bold *index* is not pinning the default.** `applyRefinement` re-applied `markDefault` at the local tier's index over a list whose contents the model had already replaced, so the index stood still while the word underneath it became the model's. That is exactly the harm the two-tier split exists to prevent, dressed as the rule against it, and the test named for the rule passed against it: `testRefinementNeverTouchesSlotZeroOrTheDefault` never called `applyRefinement` at all, it built the merged list by hand as `[before[0], Suggestion("REFINED"), before[2]]`, handed that to `markDefault(at: 1)` and asserted the default was still index 1 — which it was, holding `REFINED`. It is reachable wherever the local tier autocorrects with a thin bar: **4 of the 90 corpus entries sit at default index 1 with two slots** (`tomorow` → `tomorrow`), which is the state `shouldRefine` deliberately lets through mid-word (`localSlotCount < 3`), and `refine` serves a cached answer *synchronously*, so not even the 300 ms cushion stands between the keystroke and the swap. The contents of the default slot are held now, and **the pin is scoped to a word in progress**: `insertSpace` leaves an empty prefix alone, so with nothing typed the bold slot is a tap target rather than something space will insert, and refining the likeliest next word is the whole point of the tier. `testRefinementNeverChangesWhatTheSpaceBarWouldCommit` drives the real controller and asserts on the default's text; `testRefinementMayReplaceTheNextWordPrediction` is what stops the fix being "switch the tier off".
- **The async tier may change the options and never the default.** `PredictiveRefiner` waits 300 ms after the last keystroke and may replace slots 1 and 2. It may not touch slot 0 (the literal keystrokes) and `applyRefinement` re-applies `markDefault` at whatever index the local tier chose, so **what the space bar commits is always decided by deterministic local code**. Without that rule every pause in typing is a moment where the word about to be inserted silently becomes a different one. It also refuses to apply at all if the word in progress changed while the call was in flight — and the prefix is handed back through the callback rather than re-read, because the first version compared `currentWordPrefix` against `currentWordPrefix` and was a staleness check that could never fail.
- **The local tier's cost is measured and the harness prints it, because "fast enough for every keystroke" is the assumption the whole two-tier design rests on.** Over four runs of the 90 corpus entries, warm, on the iOS 26.2 Simulator: **median 1.1-1.3 ms, worst entry 10-16 ms**, and *which* entry is slowest changes between runs of identical code — one run also produced a 27 ms outlier that did not reproduce, so the same "one run is not evidence" rule that governs the Bar corpora governs this number too. The shape is stable and is the part to reason about: the slow entries are always Hebrew words where the seed list has nothing and more than one clitic reading has to be put to `UITextChecker`. The **first** call in a language is separate and much larger, ~70-280 ms, because Apple builds that language's lexicon then; a user pays it once per keyboard session and `run.sh` reports it on its own line so it is never averaged into the per-keystroke figure. Two costs were found by measuring rather than by reading: the seed list was being folded on every keystroke (785 English words, *twice* each, inside the prefix scan) and is now folded once at load, and a split Hebrew reading no longer asks `UITextChecker` when the seed already answered that reading — worth about a third of the worst case, with the corpus score unchanged.
- **The bar carried a pause button for exactly one build, and then pause was deleted.** A recording reports on the microphone key — orange at rest, record red while listening, a `pause.fill` glyph that *stops* — and the strip that used to hold Pause, Resume and Cancel is not drawn for one at all. Pause briefly moved here, into the slot the undo uses, because there was no height to build it a row of its own. Then it went entirely: the key stops on a second tap, which is all anyone wanted from it, and the whole cross-process pause protocol went with the button (see `.claude/rules/dictation.md`). What survives from that episode is the rule it was written under — a control that renders and answers nothing cannot be told from one that works — and the bar's dictation edge button still wears the same appearances the key does, because two surfaces disagreeing about whether a microphone is on is D8 with the stakes raised.
- **Nothing in the bar redraws on its own any more, and a deletion nearly took the dictation controls with it.** `KeyboardController.dictationAvailability` was a computed property forwarding to `DictationSession`, which worked only because the deleted waveform republished `waveformPhase` twenty times a second and dragged every other dictation reading onto the screen with it. It is a mirrored `@Published` now, subscribed in `init` rather than in `observeDictation()` so a controller that has never opened an utterance still reports what the session can see. `dictationRemainingSeconds` is mirrored **a whole second at a time**, because it feeds a caption that counts in seconds and the session republishes it ten times a second. `dictationLevels` is the deliberate opposite: every tick is kept, because it *is* the waveform the strip above the candidates draws, and throttling it would leave three bars and a pause.
- **The bar carries one control the layout editor cannot configure, and it is an undo.** Fix and Rewrite write their answer straight into the field now (see `.claude/rules/ai-text.md`), so `SuggestionBar` draws a revert button at the trailing end of the three candidates for as long as `KeyboardController.revertibleEdit` is set — which is until the next keystroke. It sits there rather than in `barTrailing` because it is not a control the user chose to have: it appears with an edit they did not ask for twice and has to be where they are already looking when the text changes under them. It costs the three candidates about 53pt (a 44pt button and a 9pt rule) for the one keystroke it lives. It is brand-**tinted** and not brand-filled, which is the opposite of the active action key one row down: a filled cap means "this is happening", and this means "you can take that back".
- **Fix and Rewrite are disabled on an empty field, and that reverses the rule `ToneTap` was written under.** That rule — a control which looks unavailable and swallows the tap teaches the user nothing — came from a button that looked *live*: a fully saturated brand icon over a faded gradient, which read as enabled, did nothing, and said nothing. Answering it with a 72pt refusal and a Dismiss tap was the fix at the time; drawing the key visibly off says the same thing in the place the user is already looking, and `KeyView` carries "Type something first" as the accessibility hint so the words still reach anyone who cannot see it. Three things to keep true. **The key guards its own gesture** (`KeyView.acceptsTouches`, asked in both halves of `pressGesture` and in the repeat and popup starters) rather than trusting `.disabled()` to stop it: `.disabled()` sets `\.isEnabled` in the environment and the built-in controls consult it, but this key is a raw `DragGesture` on a `ZStack` and reads that value nowhere, so whether the gesture is stopped at all is a framework detail that has changed across releases — and being wrong about it gives exactly the dim-key-that-answers-anyway this state exists to remove. `.disabled()` stays on the view as well, because it is what tells VoiceOver and what `EmptyFieldBarTests` can read back off the accessibility tree. **Both halves of the gesture**, because `runsOnLift` makes `onEnded` the only place the one-tap rewrite key ever fires, so a guard on `onChanged` alone would leave it running on every tap. The cap keeps its colour and only the label fades (`KeyView.disabledLabelOpacity`), because fading the whole key punches a hole in a grid whose evenness is most of how it reads. And the key and the bar's own one-tap button must go dim **together** — that is D8's defect, two surfaces disagreeing about what an empty field means — which is why the bar asks `!controller.isActionKeyDisabled(.quickTone)` rather than reading the field for itself. **A second reason to be off arrived and proved that point**: a recording disables all three text actions (see `.claude/rules/dictation.md`), and a bar button that had kept its own copy of the question would have stayed live through it. Both surfaces take their accessibility wording from `actionKeyDisabledReason` for the same reason — "Type something first" printed over a live recording tells the user to do the thing they are already doing — and `KeyView` takes it as `disabledHint` rather than spelling it. The question underneath is still `documentHasText` rather than `hasTextToWorkWith`: they answer the same thing, but only the published one makes a `View` body re-run when the first character lands, and it is filled at the top of `refreshSuggestions` above the Predictions guard, since a user who turned the suggestion bar off still has these two keys. **Every path that changes the document has to reach `refreshDocumentState`, and one did not**: `replaceTargetText`'s insert-only branch — the one a *reply* takes, because `runReply` empties `aiSourceText` on purpose — returned without refreshing, so accepting a reply into an empty field left Fix and Rewrite drawn dim over a field now holding a whole sentence. Reply is the one action that runs on an empty field, so that is the ordinary way this happens rather than an edge. `KeyboardViewController.viewWillAppear` calls it too, since one extension instance is reused across fields and across host apps.
