# How the extension is wired to the host app

- **The host field's writing direction is `primaryLanguage`, and it is the only thing this process ever tells iOS about its own identity.** The extension Info.plist is `PrimaryLanguage=en-US` and `PrefersRightToLeft=false` because this keyboard is bilingual; those keys are static. `UIInputViewController.primaryLanguage` supersedes them at runtime and is how WhatsApp, Notes and every other host decide whether a Hebrew (Arabic, Persian, …) sentence sits on the right. Leaving it unset is a Hebrew keyboard whose letters land left-aligned in an LTR field — the keys were right, the host never learned the language moved. `KeyboardViewController.publishInputLanguage()` writes `hostLanguage.inputModeTag` on appear and on `$hostLanguage` (synchronously, and from the sink's emitted value: `@Published` fires in `willSet`). `hostLanguage` is the keys except when dictation or Reply insert a language the keys are not on — counting letters to pick that language is the trap `isRightToLeft` already records, so dictation uses the transcriber's reported tags (copied onto `transcriptLanguages` *before* the partial text, or the first insert is counted as Latin) and Reply uses `replyContext.language` on both `applyDirectly` and the Use-button `applyResult` path. Appear calls `prepareForNewDocument()`: an empty field follows the keys, a field that already has Hebrew keeps telling the host that — resetting unconditionally flipped a dismissed WhatsApp draft onto the left. Send, or an empty chat with the keyboard still up, is `refreshDocumentState` giving `hostLanguage` back to the keys only when the field *becomes* empty — a proxy that still looks empty just after `insertText` must not undo the Hebrew we just announced. Apple's Hebrew keyboard reports `he-IL`, not `he`; the tag is the hyphenated spell-checker locale so hosts that match that spelling actually flip. The in-app playground is a `Text`, not a `UITextField`, so it follows `hostLanguage.layoutDirection` on the composer instead. Neither surface catches the other. **Two rules govern the write itself, and both were added after a user reported the stock keyboard arriving mid-swipe.** Mid-session it is written **only when the tag actually changes** — before that guard the same tag was re-announced on every republish of `hostLanguage`, because `@Published` fires on assignment and the sink had no `removeDuplicates`. **An appearance announces it anyway** (`announcingAnyway: true`), and the asymmetry is deliberate: one instance is reused across fields and across host apps, so the tag it is already holding may never have been heard by the app now on the other side, and whether iOS re-reads the property when a host attaches or only reacts to it changing cannot be proved here without a device. Skipping it there would risk the left-aligned Hebrew draft `bbd3c6b7` fixed in order to save a write at the one moment iOS is re-deciding which keyboard serves the field anyway. The write worth removing is the one that changes our identity *under* a host that has already been told, which is the swipe. And **a field that declared it cannot hold another script keeps hearing a Latin tag** even after the user slides the keys to Hebrew: `KeyboardController.announcedInputModeTag(for:)` reads the same `latinFieldTypes` set that `adoptFieldKeyboardType` moves the keys for, so the two halves of that decision cannot drift apart. The reason is the entry below: a space-bar slide is the only thing that changes this keyboard's input-mode identity while it is on screen, and every change is an invitation for iOS to re-decide whether we may serve the field at all. `.webSearch` stays outside the set on both sides — searching in Hebrew is ordinary, and Apple's own Hebrew keyboard stays put on one. `AIKeyboardCoreTests/FieldKeyboardTypeTests.swift` pins all four cases, and the extension logs every real change under the `inputmode` category, because a keyboard that has been replaced leaves nothing else behind.
- **`IsASCIICapable` was `false` for the whole of this keyboard's life, and it is the one reason iOS swapped in its own keyboard that we controlled.** The key defaults to `false` and came in with the initial project scaffold (`8c7cb526`); nothing revisited it. Apple's own words are that it "expresses whether a custom keyboard can insert ASCII strings into a document", and a field asking for `UIKeyboardType.asciiCapable` excludes every keyboard that answers `false` — with ours the only one installed, iOS has nothing left to draw but the system keyboard. This keyboard has typed English QWERTY since day one, so the declaration was simply wrong, and it fired on the ordinary ASCII-hinted fields apps use for usernames, search boxes and codes. It is `true` now. **Three other substitutions are Apple's and are not bugs to chase**: a secure field (`isSecureTextEntry`, which is why `SecureField.swift` says that branch "essentially cannot fire"), a phone pad (`UIKeyboardType.phonePad` / `.namePhonePad`), and a host that opted out of every third-party keyboard through `application:shouldAllowExtensionPointIdentifier:` — banking and health apps do this. In all three iOS resumes our keyboard on the next ordinary field by itself. If a *fourth* pattern shows up, suspect the extension dying rather than the plist: a keyboard extension that is killed for memory or crashes on launch also falls back to the system keyboard. **There is a fifth, and it is the only one this process causes on purpose: writing `primaryLanguage`.** Apple documents it as superseding the plist key and says nothing about a keyboard that is already on screen, and a slide along the space bar is the only thing that changes it mid-session — which is why the swap was first reported as happening *while swiping between languages*. See the entry above for the two rules that now govern the write. It is a hypothesis with a mechanism, not a measurement: nothing here can prove iOS re-resolves the input mode on that write, so the logging under the `inputmode` category is what the next report is read against.
- **The fourth pattern has a shape you can name from the phone: the three above are per-field and deterministic, and a kill is intermittent.** A secure field, a phone pad and an opted-out app give the same answer in the same box every single time; a jetsam kill depends on what the rest of the phone is doing, so the same box gives our keyboard sometimes and Apple's other times. **The ten-second test is the globe key**: after a kill it brings ours straight back and it stays, because the process simply relaunches, where in Apple's three ours is not on offer for that field at all. It is *not* a crash log — jetsam leaves none, no signal and no callback, and iOS just puts the user back on the keyboard they had before.
- **So the keyboard measures itself, because after the kill there is nothing to read.** `MemoryReading` reads `ledger_phys_footprint_peak` — the kernel's own high-water mark on the ledger jetsam kills on — which means no sampling loop and no spike missed between two samples. `KeyboardMemoryPeak` folds that into the App Group container at appear, at disappear and at `didReceiveMemoryWarning`, and Settings shows it; the record is boot-scoped and a peak is never lowered inside a boot, because the excursion is the whole reading. **What it cannot do is catch the killing spike** — that lands between two writes and takes the task's ledger with it — and a launch-versus-clean-exit counter would not help, because iOS tears keyboard extensions down without warning as a matter of course and that counter cannot tell the two apart. The warning count is the signal that is worth most per byte: iOS sends `didReceiveMemoryWarning` ahead of a kill, so a keyboard that has never had one has never been close.
- **The warning is now acted on, and for its whole life it was only recorded.** iOS sends it so a process can give memory back, and answering it by writing one number into a file spends the only notice there is. `KeyboardController.dropRebuildableCaches()` releases the three per-language word lists, which are the largest thing this process holds: `GroupedLexiconResource.cache` (50,000 boxed strings, ~615 KB of Hebrew text), `TypoLexicon.cache` (a compact block plus a `Set` of all 50,000 forms, built at 30,000 deep for Hebrew) and `MissingSpaces.ranks` (a 50,000-entry dictionary). All three are pure functions of a bundled file, so a purge costs time and nothing else — `AIKeyboardCoreTests/RebuildableCachesTests.swift` asserts the answers are identical either side of one, which is the property that makes the release safe rather than the fact that it does not crash. **`MissingSpaces.index` also stopped borrowing the cached list**: it reads each string once to key a dictionary, so it now calls `GroupedLexiconResource.uncachedWords` the way `TypoLexicon.load` already did, and one press of Fix no longer leaves *two* permanent 50,000-entry structures behind in a process with roughly 50 MB to live in. `EmojiCatalog` is deliberately not in the purge: it is a `static let`, so there is nothing to release.
- **A launch counter was rejected once and a launch *timer* is not the same instrument.** `KeyboardMemoryPeak`'s doc rejects counting launches against clean exits, and the objection is right: iOS tears keyboard extensions down without warning as a matter of course, so "started and never finished" counts an ordinary teardown and a jetsam kill identically and separates nothing. `KeyboardLaunchRecord` counts a span that lies entirely **inside one launch** — `viewDidLoad` against the *first* `viewDidAppear` of that instance — and an ordinary teardown happens after a keyboard has appeared, so it lands in both counters and cancels out of the comparison. `loads` above `presentations` is therefore a run that was asked for, began and never reached the screen, which is the shape of "the stock keyboard came up and the second tap gave me ours". **`presentations` counts the first appearance of each instance and not every appearance**, because iOS reuses one instance across fields and host apps and counting them all would put it an order of magnitude above `loads`. Two limits are in the type rather than only in the issue: it cannot see a launch that died before `viewDidLoad` returned, and iOS may build a controller it never presents, so one point of gap is noise and only a persistent ratio is evidence. **The write is dispatched off the main thread and for `.loaded` that is the point rather than a nicety** — a synchronous file write on the launch path would be an instrument measuring itself.
- **The launch path was not lean, an earlier version of this bullet said it was, and the repeated half of it is gone now.** What was always true is the narrow part: `viewWillAppear` calls `refreshDocumentState()` rather than `refreshSuggestions()`, so `UITextChecker` is never reached there and `PredictiveRefiner`'s clock does not start; and the three 50,000-entry lexicons are warmed in `viewDidAppear` off the main thread. From that I concluded there was nothing left to defer, and the audit in NIT-186 said otherwise: on a cold launch, all on the main thread, **three** `containerURL(forSecurityApplicationGroupIdentifier:)` XPC calls and three `UserDefaults(suiteName:)` opens, **two** full reads-and-decodes of `PersonalLanguageModel.json`, **five** decodes of the stored layout, four or five copyclip decodes, and `SharedStore.load()` twice. **Every one of those repeats is now keyed on the bytes rather than on a clock or a first-time flag, and that is the shape to keep.** The obvious repair is "skip the reload when this appearance is the instance's first, since nothing can change in between", and it is unsound: iOS may build a keyboard extension's controller and present it much later, and the user genuinely can go and change a setting inside that window. Four caches were written instead and none of them can be fooled by the length of that gap. `SharedContainer.url` and `.userDefaults` hold a **resolved** container and never a nil or the `.standard` fallback, because `KeyboardViewController.recordPresence()` relies on nil turning into a URL mid-process when the user grants Full Access; the revocation direction is a documented limit and is already `SharedStore`'s behaviour, which probes once in `init` and holds its suite in a `let`. `PersonalLanguageModel.reload()` compares the file's `(modificationDate, size)` and skips the decode when neither moved, and an **absent** file is deliberately not a skip, because Forget deletes it and a live keyboard must drop the counts. **That stamp must come from `FileManager.attributesOfItem(atPath:)` and never from `URL.resourceValues(forKeys:)`, and the difference is the whole feature.** `URL` caches resource values on the `NSURL` behind it, and the URL here is a *stored* property read on every reload, so the first version of this returned one stamp forever: measured on macOS 2026-08-22, a rewrite that changed the file's **length** read back byte-identical through the same stored `URL`. That is a keyboard that never re-reads the file at all — Forget in the app would not reach a live keyboard and a word learned in one process would never reach the other, which is both defects `reload()` exists to prevent, reintroduced by the change meant to make it cheaper. `attributesOfItem` is a fresh `stat` with no cache; building a new `URL` per call was measured and also works. A second measured trap sits in the *test* for it: `setAttributes(_:ofItemAtPath:)` does not round-trip a `Date` read back out of `attributesOfItem`, so forging an unchanged stamp means pinning **both** writes to one explicit constant rather than pushing the second back onto the first's date. `SharedStore.StoredDecode` holds the layout and the copyclip record against the exact `Data` they were decoded from, so five layout decodes become one and a layout the editor saved is different bytes and a real decode. And `KeyboardController.apply` will not republish a `customization` that did not move. **That guard needs *every* id on the path to be stable and there are three, and the first version of it audited two and shipped broken.** `SlotSpec.id` is a `Codable` `UUID` so two decodes of one blob carry the same ids, and `LayoutPreset.all` and `KeyboardCustomization.default` are both `static let` — those two were checked. The third is the globe key `apply` **repairs in two lines above the guard**, which was built with `SlotSpec.init`'s default `id: UUID()`; `SlotSpec`'s `Equatable` is synthesised and includes `id`, so every repaired layout was unequal to every other repaired layout built from identical bytes, and the guard never fired on any phone with a second keyboard installed — that is, on every real install of a product that only exists alongside a system keyboard. It is `KeyboardController.repairedGlobeID` now, a fixed `UUID`, which is safe only because the insert is guarded on `!hasGlobe` so there is never a second globe to collide with. A test that does not set `showsGlobeKey = true` cannot see any of this: `testARepairedGlobeKeyDoesNotMakeTwoIdenticalLayoutsUnequal` is the one that can. Make any of the three a computed `var` and every appearance silently re-keys every `ForEach` in the keyboard again. **`load()` no longer writes back what it read**, which its own doc comment had claimed since the day it was written while `didSet` fired on all twenty-two assignments, two of them full JSON *encodes* re-serialising what had just been deserialised. `isLoading` and `persist(_:forKey:)` suppress the write and **nothing else** — `brandPalette`'s `didSet` also puts the accent into `Theme` and that half has to run — and `persistMigrations(...)` writes the three that are genuine migrations: the pre-three-way autocorrect boolean, the legacy `[Clip]` array, and `decodedLayout`'s globe repair or its unusable-blob fallback. **All three are self-limiting**, which is the property anything added there needs: performing the write is what stops the condition holding next time. A refreshed named **preset** is deliberately not one of them and that is the case almost every install is in — the refresh is re-derived on every read by design, so persisting it stores nothing that is not recomputed, and reporting it would put a full layout encode back on every launch for everybody, forever. **Two of the suppressed writes turn out to have been actively harmful, which is worth knowing before anyone "restores" them.** `enabledLanguages` is assigned from `raw.compactMap(KeyboardLanguage.init(rawValue:))`, which silently drops rawValues the running build does not know, and the old unconditional write-back *persisted the pruned list* — so an older build reading a store a newer one had written permanently deleted the user's other languages. `emojiSkinTone` has the same shape through `EmojiSkinTone.stored`'s `?? .generic`, and that accessor's own doc says the raw `Int` exists precisely so an older build can fall back from a value it does not recognise; falling back was never meant to be destructive. Both are read-only now on the load path. And **a stored copyclip blob that decodes as neither shape counts as a migration** (`decodedCopyclipRecord` returns `(.empty, true)`), matching what `decodedLayout` already did for its twin case: the old write-back cleared corrupt bytes, and reporting `false` would have left them on disk forever and charged every future `load()` two failed JSON decodes of them — which breaks the self-limiting property `persistMigrations` requires of everything it writes.
- **`limit_bytes_remaining` reads 0 on macOS 26 and on the iOS 26 Simulator, so the ceiling is a device-only measurement.** Neither applies a footprint limit to the asking process. That is exactly why the reading is written to a file the phone keeps rather than printed in a test: `MemoryGovernor.ceilingMB` is 50 and its own doc calls it a guess from developer-forum reports, and headroom needs no ceiling at all — it is small precisely when the process is about to die. Zero is reported as nil, never as zero headroom, because a process with no bytes left is already dead.
- **The simulator hands `AIKeyboardCoreTests` a real App Group container even though the target has no entitlement** (measured 2026-08-16). `KeyboardPresenceTests` claimed the opposite in prose for its whole life. So a test that reaches `SharedContainer.url` proves nothing about a device *and* writes into state the app and keyboard both read; take an explicit URL, which is what `record(_:at:)` and `load(from:)` are for. Same family as the standing rule that `UserDefaults(suiteName:)` being non-nil proves nothing.
- **The keyboard opens on the language the user left it on, and for the whole of its life it opened on `enabledLanguages.first`.** iOS rebuilds a `KeyboardViewController` whenever it likes, so for the shipped pair that meant English on every launch and a Hebrew speaker sliding the space bar back by hand several times a day. `SharedStore.storedOpeningLanguage` is the read and `rememberLanguage(_:)` is the write, and **the write has exactly one caller, `KeyboardController.stepLanguage`**, which is where the globe key and a space-bar slide both land. That is the point: the two language writes that are *not* a user's choice must not reach it. `adoptFieldKeyboardType`'s imposed Latin is the sharp one — it is undone when the user leaves the field, so remembering it would outlive the process holding that undo and one email address would leave a Hebrew user in English in every app on the phone, tomorrow. Dictation and Reply write `hostLanguage` rather than `language` and never touch it. The stored value is **validated against `storedEnabledLanguages` rather than trusted**, so a language switched off in the app cannot come back by the side door. Gated on `isSystemKeyboard`, now a stored property, for the reason `personal` already is: the onboarding playground and the layout editor's canvas drive real controllers with real space bars, and a scripted demo must not decide what tomorrow's keyboard opens on. It is deliberately not `storedDictationLanguage`, which holds the same kind of value for a different question — that one is written only at a dictation tap, and it now *falls back* to this when the app has to name one language for a session the keyboard never opened (`DictationService.startLiveTranscription`); the list of transcription *hints* below it deliberately still passes every enabled language, because narrowing a hint on a guess costs a whole transcription when the guess is wrong. **Validating at launch is only half the rule**: iOS keeps one extension instance alive across any number of trips to Settings, so `KeyboardController.settleLanguage()` runs on every appearance and moves the keys off a language the user has since switched off. It moves nothing otherwise, which is the case that matters — it runs on every appearance, so a version that reset to the head of the list would undo every swipe the moment the user changed apps. `AIKeyboardCoreTests/LanguageMemoryTests.swift` holds all of it.
- **The keyboard reads `keyboardType` now, and for the whole of its life nothing did.** iOS substitutes its own keyboard for `.phonePad` and `.namePhonePad` and for *nothing else*, so `.numberPad`, `.decimalPad` and `.asciiCapableNumberPad` — every OTP box, quantity field, price field and PIN entry — came up as the full letter QWERTY, which a user reads as a keyboard that is broken rather than one that is missing a feature. The other half of the same gap is what the `IsASCIICapable` flip above opened: iOS now hands us the ASCII-capable, email and URL fields it used to withhold, so a user whose last keystroke was Hebrew met Hebrew letters in a field that cannot take them, where before the flip they got Apple's ASCII keyboard. `KeyboardController.adoptFieldKeyboardType(force:)` is the whole of it — the numeric types open on `.numbers`, `.asciiCapable` / `.emailAddress` / `.URL` open on `.letters` and on the first *enabled* Latin language, `.default` and nil change nothing. **Reshaping is only half a decision and the other half is putting it back, which the first version did not have.** `plane` is written in three places in the entire project and the only one that restores `.letters` is the `123` key, so a build that reshapes without undoing gives a chat box the digits of the OTP field before it — a different app, no key pressed in between — and the language half is worse, because one extension instance is reused across fields *and* across host apps, so a Hebrew user who touched one email box kept an English keyboard everywhere afterwards and slid the space bar back by hand every time. Entering a field that wants neither digits nor Latin undoes both, and the language is restored **only while the keyboard is still standing on the language this code imposed** (`imposedLatin`), because a user who slid somewhere else inside that field has decided for themselves: the same claim-checked-rather-than-trusted shape as `pendingAutocorrectUndo`. A run of ASCII fields restores what the user had before the *first* of them, not what the fourth left. **`.webSearch` is deliberately not in the Latin set** — Apple documents it as optimised for search terms and URL entry, it takes any script, and Apple's own Hebrew keyboard stays Hebrew on one, so treating a search box as ASCII takes the keyboard away for no reason; `.twitter` is out for the same reason and an address and a URL genuinely are ASCII. **`autocapitalizationType` is now read as its own trait, and the `.emailAddress` / `.URL` shift patch that stood in for it is gone.** That patch existed because `shift` starts `.on`, Return and the double-space full stop re-arm it, nothing reset it per field, and the `IsASCIICapable` flip exposed all of that by handing us email boxes that then typed `Nitai@example.com`. `KeyboardController.adoptFieldAutocapitalization(force:)` is the general fix: `.none` leaves shift off, `.allCharacters` locks it, and `.words`, `.sentences` and nil all defer to the user's own Auto-Capitalise switch. **Nil means `.sentences` rather than "off"**, because nil is a host that never implemented the trait and every field in the app behaved as `.sentences` before this existed, so any other reading would regress fields nobody complained about. `.words` is the only mode that arms shift on an *ordinary* space, which is a call site that never touched shift before. **A locked shift is the one state none of this may overwrite**: `.locked` is produced by `toggleShift()` and by nothing else, so it is the signal that the user decided for themselves, and both the focus decision and the boundary re-arm guard on it. That is the mechanism behind the standing rule that this code decides at focus and does not fight the user mid-field. **The trait is adopted only from `prepareForNewDocument()`**, deliberately not from `refreshSuggestions` the way `keyboardType` is, so a field swapped with no dismissal and no `keyboardType` change is not yet caught; that is known, and it is what `AutocapitalizationTests.testTheModeIsNotReReadWithoutAFreshFocus` pins in place. `AIKeyboardCoreTests/AutocapitalizationTests.swift` holds the trait's own behaviour, and `FieldKeyboardTypeTests` now declares the trait explicitly wherever it asserts on shift. **Five more things are not obvious.** `UITextInputTraits` is `@objc` with optional members, so `keyboardType` reads as `UIKeyboardType?` and the outer nil is a host that never implemented it — `TextTarget` carries it exactly as it carries `isSecureTextEntry`, under the same rule: nothing may answer `.default` to mean "I did not check". **The decision is taken at focus and is never revisited inside that field**, because `refreshSuggestions` runs on every keystroke and every caret move, and re-deciding there is a user who presses ABC on an OTP box and is put back on the digits by their next key. It is undone only on the way *out*, when a different field reports a different trait. What *does* re-decide is the trait **changing**, which is the only news a keyboard extension gets that the host moved focus without dismissing it — `viewWillAppear` does not fire for that, and whether the document callbacks always do on a swap is not something this repo can prove without a device, so the appearance path is still the guaranteed one. **A nil arriving mid-session is a vanished proxy rather than a field**: `ProxyTextTarget` resolves through a `weak` input view controller, so recording that silence as an adoption makes the next callback read the same field as a new one and snap the plane back under a typing finger. **Nobody can be stranded on the numbers plane** — `LayoutValidator.missingPlaneSwitch` makes a layout with no `123` key an error, `apply(_:)` drops an unusable layout back to the default, and `CustomLayoutCompiler.resolvedCap` points that key at `.letters` from every plane that is not `.letters`. And **a Hebrew-only user is never moved to English**, because the Latin language is picked out of `enabledLanguages`: handing somebody a layout the space bar cannot get them off is worse than the wrong keys. Two smaller facts worth not re-deriving: `.alphabet` is deprecated and is the *same raw value* as `.asciiCapable`, so it cannot be given separate behaviour, and `.decimalPad`'s locale-dependent separator is deliberately **not** handled — one numbers plane is shared by all sixty-four languages, so ordering it per locale would move keys under every user, and both `.` and `,` already sit on the plane this opens. `AIKeyboardCoreTests/FieldKeyboardTypeTests.swift` holds all of it.
- **We do not set `hasDictationKey = true`.** Leave `UIInputViewController.hasDictationKey` at Apple's default (`false`). Face ID devices may draw Apple's dictation microphone in the system dock. Do not re-add the suppression.
- **The extension view must not clip, or letter callouts die at the top edge.** Fix and Rewrite now grow down over the letters on purpose. Letter press balloons and accent strips still rise above the key, the way a system key preview does, and they need the room above the keyboard. `UIInputViewController.view` and the `UIHostingController` clip by default. `KeyboardViewController.install` sets `clipsToBounds = false` on both. Do not put it back to hide a shadow: that is this defect.
- **The in-app playground is not evidence that the keyboard works, and for the whole of development it was believed to be.** The first install on a real phone typed *nothing* — keys drew, animated and clicked, and not one character reached the host app. `KeyboardController.target` was `weak` and `KeyboardViewController` built its `ProxyTextTarget` in argument position, so nothing retained it past `viewDidLoad` and every mutation was `target?.insertText` against nil. The playground was unaffected because `KeyboardPreview` holds its `MockTextTarget` as a `@StateObject`. So: the target is strong (nothing conforming to `TextTarget` references the controller back, so no cycle), the proxy is re-resolved per call through a `weak`-captured input view controller (`textDocumentProxy` is replaced when the host swaps fields, and `unowned` would trap when `KeyView`'s key-repeat `Task` outlives an interrupted gesture), and `AIKeyboardUITests/KeyboardTypesIntoHostTests.swift` presses a key on the real extension over a real `UITextField` and reads the field back. Before that file existed, *nothing* in the repo exercised the extension's own wiring — `AppGroupCrossProcessTests` and `CaptureChannelCrossProcessTests` already stood the extension over that exact field and asserted only that a key *existed*.
- **`.toolbar(.hidden, for: .tabBar)` does nothing in this app, and it was believed for as long as it was there.** `MainTabView` is a `ZStack` of four always-mounted pages with `MainTabBar` in a `safeAreaInset(edge: .bottom)` — a deliberate choice, because `TabView`'s crossfade is the flicker — so there is no system tab bar for that modifier to reach. `LayoutView` set it, and the glass capsule went on sitting over the editor's spare-key tray, cutting the last row of keys in half and swallowing every tap that landed on them; the screenshot that finally showed it had been the shipped behaviour for the whole life of the editor. A pushed full-window screen sets `AppChrome.hidesTabBar` instead and `MainTabBar` returns an `EmptyView`, so the inset collapses and the screen gets the 60 pt back — opacity would leave the hole. `AppChrome` is `@Observable` rather than `ObservableObject` for one specific reason: a view that only *writes* it from `onAppear` never reads it in `body`, so it takes no dependency and is not re-rendered, which matters because the one screen that writes it is a `NavigationLink` destination inside a `ScrollView` and is already rebuilt on every Keys tab body evaluation (see below). It lives on `RootView` above the `.id(store.brandPalette)`, so a palette change cannot strand a pushed editor's hidden bar. A UI test that taps a tab straight after leaving such a screen has to `waitForExistence` on the bar rather than assume it.
- **Never hand store-derived state to a pushed `NavigationLink` destination inside a `ScrollView`.** Destinations there are rebuilt on every parent body evaluation, so `LayoutView(layout: store.keyboardLayout)` made the *pushed* editor a function of the store — and its Done button writes the store, so it rebuilt the screen the user was standing on while that screen dismissed itself. The app pinned a core at 100% with an **empty accessibility tree**, which reads as a crash from the outside and leaves no crash report: four UI tests timed out and only the one that never tapped Done passed. The editor takes no parameters and reads `storedKeyboardLayout` once in `.task`. Same file, same class of bug, second instance: anything expensive in a `View.init` runs on every one of those rebuilds, so `LayoutView`'s `KeyboardController` is a `@StateObject` *property initialiser* (an autoclosure, deferred) rather than an assignment to `_canvas` inside `init`, which is not.
