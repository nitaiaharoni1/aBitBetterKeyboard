# Screen context and capture

## Reading the screen

- **Vision has no Hebrew, and `VisionLanguageTests` pins that from the simulator** — specifically that Hebrew is absent and Arabic is present, which is the load-bearing pair; the count of 30 is prose beside it, not an assertion. If it ever fails, that is permission to delete most of `CloudScreenReader`.
- **Screen reading routes without ever naming a script, and that is the point.** The router cannot ask "is this screen Hebrew", because the only component that reads text is the one blind to Hebrew. `VisionScreenReader` compares text regions *found* by `VNDetectTextRectanglesRequest` — which finds text by shape, language-agnostically — against regions actually recognised. Coverage ≥ 0.97 and mean confidence ≥ 0.90 lets **zero** Hebrew or mixed screens through, and keeps 9 of 12 English screens on device *as macOS reads them* — `coverage.swift` is built with `xcrun -sdk macosx`, and on iOS the same gate accepts 10, because `ml-01`'s mean confidence lands at 0.90 there and 0.896 on macOS. Quote the platform with the number; that distinction has now been got wrong twice. Loosening coverage to 0.95 gains **two** English screens (`sl-02` at 0.9583 and `ml-04` at exactly 0.9500) and admits a mixed one, which is the wrong trade — the trade is what matters here, not the count, and the count was wrong for a year. The gate is asymmetric on purpose: a misread Hebrew screen is a confident wrong reply in the user's name, an unnecessary cloud call is five seconds.
- **`VisionScreenReader` reads bubble geometry, so it accepts only two-sided layouts.** Slack, Teams and mail threads print every message against one margin with the author on a label above it, leaving no geometry to say who sent what. Side is read from which *margin* a bubble hugs, never from the line's centre — a long line in a one-sided layout crosses the middle of the screen and a centre test calls it outgoing, which was wrong on every Slack screen measured.
- **Vision is not the same on iOS as on macOS, so never quote a macOS reading of it as the product's number.** Same sources, same pixels, same thresholds: macOS accepts 9 of the 30 bar frames and answers 5, all 5 right. The iOS Simulator accepts 10, answers 8, and **3 of those are wrong** — including `wa-07`, the one frame whose only correct answer is silence, and `sl-05`, which comes back as keyboard key caps. An earlier claim of "it answers only when it is right" was a macOS-only claim reported as the product's. `harness/run-reader.sh` builds with `xcrun -sdk macosx` and is the macOS reading; `ScreenContextBarTests` is the iOS one and is the one that counts. The property the routing rests on survives both: zero Hebrew and zero mixed frames are accepted on device on either platform.
- **On iOS, routing through Vision scores *worse* than asking the cloud, and the comparison is the durable part while the absolute numbers are not.** Measured end to end through `ScreenContextSession.submit`, both sides replaying the *same* recorded cloud answers: routed gives sender 27/30, language 29/30, message 16/30 exact and 24/30 within 90%; cloud alone gives 30 / 30 / 18 / 25 on that same recording. Apples to apples, so the conclusion holds: the on-device path is not free accuracy that happens to be private, it costs about 3 points of sender on this bar. Weigh that against the privacy gain rather than assuming the gain is one-sided.
- **Two refusals, and they are not the same refusal.** `VisionScreenReader.interpret` returns nil for *nothing worth replying to* (a voice note) and throws `.notReadableOnDevice` for *I could not read this layout*. Collapsing both into nil made `RoutedScreenReader` treat "I cannot see" as "nothing is there", so `sl-01` and `sl-03` — plain answerable English the cloud transcribes correctly — silently offered the user nothing. Worth 2 points on every axis.

## The cloud prompt

- **A frozen corpus is not a frozen bar when the thing being judged is a hosted model behind a moving alias — and there is no dated version to pin to.** `gemini-2.5-flash` is an alias. The obvious fix is to name a version instead, and measured on 2026-08-08 that fix does not exist: `gemini-2.5-flash-001`, `-002`, `-preview-05-20` and `-preview-04-17` all return **404** on this project, and a successful call answers with `modelVersion: "gemini-2.5-flash"` — the alias echoing itself. `VERTEX_MODEL` therefore buys nothing today and is kept only so a dated version can be used the day one appears. What is left is a noise floor, and its *shape* matters more than its size: two full runs of the identical configuration minutes apart disagreed on **2 of 30 frames** and scored 30/30 and 29/30 sender with 30/30 language both times, while an earlier pair taken a day apart disagreed on roughly a third of the corpus. So the drift is day to day, not call to call: a delta measured inside one sitting is close to trustworthy, and any number compared against a recording from another day is not. `cloud_outputs.json` now carries its recording date in every row's `config` and was taken at the configuration the product actually sends (half-size JPEG, not the full PNG every older score used); `cloud_outputs_repeat.json` is the second run, kept so the spread stays a measured number. Do not regenerate either casually: `ScreenContextBarTests` replays the first, so regenerating moves every routed threshold at the same moment as the thing being measured, and the two must be re-taken together and deliberately.
- **The screen-context prompt's shape is measured, not stylistic — and re-measuring it with committed artifacts moved two of the three numbers and killed one outright.** `harness/ablate.py` moves exactly one thing per variant against the same corpus in one sitting and writes each variant's answers to `Bar/screen-context/ablation/`, so these are now checkable rather than remembered. Baseline is `size-encoder/scale2-jpeg.json` from the same sitting: sender 29/30, language 30/30, 18 exact, 7 near, 0 traps.
  - **Enumerating first: confirmed, but smaller than claimed.** Dropping `messages` costs 2 points of sender (29 → 27), 3 of keyboard language, four of the near-misses, and introduces a trap. An earlier claim of 21/30 → 29/30 does not reproduce. The direction and the reason do — every wrong answer on the bar was a bubble one to four positions above the newest, and a list the model must finish turns "which is newest" from a judgement into an index.
  - **Splitting `script` from `language`: confirmed, and it is the big one.** Collapsing them scores **22/30** keyboard language against 30/30. Eight points, far outside the ±1 noise floor. They disagree on precisely the code-switched sentences this product exists for.
  - **"Flattening the list costs 7 points" is not supported.** The harness baseline *is* the flat string; the nested-array variant scores 28 sender against its 29, so nested is a point *worse*, inside the noise. `CloudField` carries nested `items` and that was the stated reason. Nothing here says nested is wrong — it says the 7 points were never there, so do not treat the nesting as load-bearing the way enumeration and the script/language split demonstrably are.
  - Two rules that *sound* right measured worse and are deliberately absent — a paragraph on bubble tint and edge, and "a printed name always means incoming"; `CloudScreenReader`'s doc comment lists both so they do not get re-added.

## Capture

- **ScreenCaptureKit is real on iOS, and still not available here.** It is `iOS 27.0+`, and Apple states plainly that it replaces ReplayKit and that a broadcast extension is no longer necessary. But measured against the installed toolchain (Xcode 26.2), `ScreenCaptureKit.framework` is absent from both `iPhoneOS26.2.sdk` and `iPhoneSimulator26.2.sdk` while present in `MacOSX26.2.sdk`, and `ReplayKit.framework` is present in the iOS SDK as the control. So `import ScreenCaptureKit` does not compile for iOS at all until an Xcode with the iOS 27 SDK is installed. The whole ReplayKit loop is now written — capture, fingerprint, channel, the read inside the capture process, and the keyboard consuming it — and **not one line of it has ever executed**, because the simulator runtime ships no `replayd`. Reading a frame is the only half that is *measured*, against `Bar/screen-context/`.
- **The capture channel is two mmap'd pages, and the broadcast extension must never link `AIKeyboardCore`.** `AIKeyboardShared` is the Foundation-only target both ends share (`CaptureStatus`, `CaptureIntent`, `SharedPage`, `FrameFingerprint`, `ScreenReadingRecord`, `CaptureFreshness`) **and the read itself** (`CloudScreenReader` with its measured prompt, `BackendTransport`, `ScreenReadService`, plus the `KeyboardLanguage`, `TextScript`, `AIOutput` and `AIEngineError` those need); `AIKeyboardCore` re-exports it so existing call sites are untouched, and `AIKeyboardBroadcast` links it alone. The prompt is in the shared target rather than copied into the capture process because it is scored against `Bar/screen-context/` and two copies drift. Linking `AIKeyboardCore` there drags SwiftUI and UIKit into a process capped at ~50 MB; `Scripts/prove-capture-channel.sh` check 1 reads the Mach-O and fails if it happens. Four things to know before touching it. The seqlock fences live in a **C target**, `CaptureAtomics`, because Swift 5.9 has no atomics at all — `Synchronization.Atomic` is iOS 18, `<stdatomic.h>` does not import into Swift, and `OSAtomic` has been deprecated since iOS 10 — and plain loads and stores on arm64 are not a seqlock. Every timestamp is `CLOCK_MONOTONIC_RAW`, not a wall clock, because a clock the user can set is a clock that can make a forty-second-old reading look fresh. `FrameIdentity` has `.absent`, not `.none`: `FrameIdentity.none` in an optional position silently resolves to `Optional.none`, which cost a test that asserted against the wrong value. And a flag in a shared page needs a timestamp beside it — `keyboardVisible` outlived the process that wrote it and made the probe publish before anyone was watching.
- **The frame fingerprint's band was wrong twice, and the second time it was our own keyboard.** Crop to the top 14% and everything from the top of *our own UI* downwards, reduce to 32x64 greyscale, SHA-256. Three measured failures, each caught only by an adversarial harness: the original bottom-45% crop removed the newest message and missed **23 of 29** conversation switches; a 64-bit perceptual hash missed **10 of 29** even at the right band; and the shipped band contained about a third of our own keyboard, which animates a shimmer for the whole read, so **30 of 30** frames got a fresh identity from nothing but our loading state — the freshness gate then discarded the reading the user's own tap had just paid a cloud call for. So the keyboard publishes the height it *can* occupy (`CaptureIntent.ownUIHeightPermille`, never the current height, because the strip appearing mid-read would move the band and retire the reading exactly as a real switch does), clamped both ways because one process reads it out of a page another writes. The crop costs no host content: while the keyboard is up, everything below its top edge is ours. `Bar/screen-context/harness/frame-hash.mjs` swept it; `run-fingerprint.sh` holds the *shipping* Swift to the zeros by compiling `FrameFingerprint.swift` itself, and carries a witness that the shimmer still moves the identity over the unfixed band — a harness that cannot fail proves nothing. The 64-bit hash is not deleted, it is confined to `changeScore`, where "uninformative" is the right property.

- **How tall the keyboard is allowed to be is now a measured constraint, and it is the fingerprint that sets it.** `FrameReduction.Band.maximumOwnUI` caps how much of a frame's bottom our own UI may remove. It was 0.40, chosen against a 292 pt keyboard where nothing real ever reached it. The action row and a 56 pt `ActionBanner` would put the keyboard at 372 pt of an iPhone 17 Pro's 874 — 0.4256 — so the clamp started binding and left our own banner *inside* the band, which is the 30-of-30 shimmer failure again. **The obvious fix, raising the ceiling past the cliff, was measured and is wrong.** `run-fingerprint.sh` now takes `OWN_UI_POINTS`, and the sweep over the same 30 scenes with our keyboard on screen is: 292 pt → 0/29 misses, 356 → 0/29, 364 → 0/29, **368 → 0/29**, **370 → 1/29**, 372 → 1/29, 385 → 1/29. The cliff is between 368 and 370 pt and it is sharp — `ml-04`'s two conversations collide the moment the crop passes it, because that much of the bottom takes the newest message with it. It is the near edge of the same cliff `frame-hash.mjs` found at bottom-45%, not a second one. So the banner is 72 pt (three lines of detail fit without an ellipsis), the suggestion bar is 36 pt to pay for it, the tallest form ships at 368 pt, and `maximumOwnUI` is `368/874` — not 0.42, which is 367 and made the layout editor warn on the default. The idle instruction is omitted (`BannerState.isPresented`), so ordinary typing is shorter; the fingerprint crop still publishes the tallest form so a mid-read resize cannot move the band. **Adding a row or growing the total past 368 costs a conversation switch**, which means a stale reading offered as fresh — a reply to the wrong message, in the user's name. The arithmetic said a few points under a message bubble were safe; they were not, and the only reason that was caught is that the harness was run instead of reasoned about.
- **Landscape is over that ceiling on three of the eight shipping widths, and on the narrowest it reproduces the 30-of-30 failure exactly. Measured 2026-08-16, and it is a live defect.** The cap is a *fraction* and `Theme.Metrics` spends *points*, so landscape's margin is a different number on every phone — and every check there was, `LandscapeGeometryTests` included, only ever asked the iPhone 17 Pro. Landscape spends **166 pt** (`totalHeight(for:showsBanner:orientation: .landscape)` = 0 banner at any `showsBanner` + 30 bar + 136 key area, where 136 is `26 × 4 + 8 × 3 + 4 + 4`), and the budget is `0.4210526 × H` where `H` is the landscape screen height, which is the phone's **portrait width**. Break-even is `166 / 0.4210526` = **394.25 pt**, so:

  | landscape height | phones | budget | margin |
  |---|---|---|---|
  | **375** | SE 2/3, XS, 11 Pro, 12 mini, 13 mini | 157.9 | **−8.1** |
  | **390** | 12, 12 Pro, 13, 13 Pro, 14 | 164.2 | **−1.8** |
  | **393** | 14 Pro, 15, 15 Pro, 16, 16e | 165.5 | **−0.5** |
  | 402 | 16 Pro, 17, 17 Pro | 169.3 | +3.3 |
  | 414 | XR, 11, XS Max, 11 Pro Max | 174.3 | +8.3 |
  | 428 | 12 Pro Max, 13 Pro Max, 14 Plus | 180.2 | +14.2 |
  | 430 | 14 Pro Max, 15 Plus, 15 Pro Max, 16 Plus | 181.1 | +15.1 |
  | 440 | 16 Pro Max, 17 Pro Max | 185.3 | +19.3 |

  **NIT-101's "166 against 169, about 3 pt of margin" is the 402 row read as though it were the whole table**, and the earlier claim that landscape was over the cap for its whole life is right for a different reason than the one given: the 6 pt bar bug (`71698717`) made 402 overspend too, and fixing it fixed only 402. Over the cap, `bottomCrop(ownUI:)` clamps, and the rows it then refuses to crop are rows of **our own keyboard** — which is the shimmer failure, arriving in an orientation nobody had swept.

  **`harness/frame-hash-landscape.mjs` is that sweep and `run-fingerprint-landscape.sh` is the shipping Swift over the same renders.** Free — Playwright plus arithmetic, no model call, no simulator. Landscape draws no banner, so the moving part is not the shimmer: it is `ControlSweep` on the Reply chip, 26 pt tall and centred in the 30 pt bar, therefore starting **2 pt** below the top of our keyboard. That 2 pt is the whole threshold, and the sweep lands on it exactly:

  | landscape height | ours | crop | ours left in band | own false |
  |---|---|---|---|---|
  | **375** | 44.27% | 42.11% | **8.1 pt** | **30/30** |
  | 390 | 42.56% | 42.11% | 1.8 pt | 0/30 |
  | 393 | 42.24% | 42.11% | 0.5 pt | 0/30 |
  | 402 | 41.29% | 41.29% | none | 0/30 |
  | 430 | 38.60% | 38.60% | none | 0/30 |
  | 440 | 37.73% | 37.73% | none | 0/30 |

  So **every frame on a 375 pt landscape screen takes a fresh identity from nothing but our own Reply sweep**, and the freshness gate then retires the answer to the tap that paid for it — the identical 30-of-30 defect `FrameReduction` was rewritten to remove, on iPhone SE 2/3, XS, 11 Pro, 12 mini and 13 mini. Two runs and two resamplers agree on that column with no variance at all: Chromium's in the mjs harness, CoreGraphics and the shipping integer box filter in the Swift one. **390 and 393 survive by 0.2 and 1.5 points of chip inset, not by design** — they are over the cap and the overspend simply lands in bar background rather than on the chip. Treat the whole `H < 394.25` set as broken, not just the one that measures broken.

  **Two things this sweep does not establish, said out loud.** Its `miss` and `own miss` columns sit at 0 to 2 and **move between runs of identical code**, always on `ml-*`: landscape shows about three messages, so a Mail thread's newest message sits at the fold and its two renders are sometimes byte-identical and sometimes not. That is the corpus, not the crop — it is not monotone in the crop and the decisive `own false` column has zero variance — so no claim about landscape missing conversation switches rests on it either way. And the renders are the portrait skins relaid on a rotated shell (`renderLandscape`), not photographs of real apps in landscape: bubbles widen because they are percentage-width, which is the shape that matters, but no app's landscape-specific chrome is reproduced and the status bar is collapsed rather than redrawn.

  **The fix is not raising the cap** — that was measured and rejected in portrait. Landscape has to get shorter on the phones that cannot afford it, which means the budget is `min(0.4210526 × H, …)` in points on the narrowest device rather than a constant 166. `LandscapeGeometryTests` asserts the margin only at `referenceLandscapeScreenHeight` (402), which is exactly why this went unseen; any repair needs an assertion at 375.
- **The landscape action strip really is free, and the control beside it is not.** `SuggestionBar.landscapeActions(for:)`'s five chips are drawn inside the same `.frame(height: barHeight)` the bar already had, `chipSize(for: .landscape)` is 44 × 26 against a 30 pt row, and `.quickTone` has an explicit `where orientation == .landscape` branch that swaps the 68 × 40 named `toneButton` for a 26 pt `edgeButton` — so NIT-101's zero-height claim holds, and `Theme.Glyph.font` is `.system(size:)` rather than a Dynamic Type relative size, so no accessibility setting grows a chip out of the row either. **`revertButton` is the one that was missed**: it is a hardcoded `.frame(width: 44, height: 40)`, it is drawn from `candidates` with no orientation guard, and `.frame(height:)` does not clip — so for the one keystroke after a Fix, Rewrite, Reply or CopyClip paste, landscape draws a 40 pt control in a 30 pt row, overhanging 5 pt into the host above and 5 pt onto the 26 pt top key row below. It does not grow the published height, so it is not a fingerprint-cap problem; it is 5 pt of our own UI drawn *above* the height `ownUIHeightFraction` publishes, and a key row it half-covers. `testTheLandscapeActionStripCostsNoHeightAtAll` cannot see it, because that test asks `chipSize` and this control does not go through `chipSize`.
- **The layout editor can exceed that ceiling and that is the user's call, but `ownUIHeightFraction` has to be told which layout.** It read `Theme.Metrics.totalHeight()` — the *default* — which was right while there was only one height. A user who turns on the number row, keeps the action row and picks 52 pt keys covers about 0.55 of the screen while that function goes on publishing 0.42, which leaves ~120 pt of our keyboard in the band rather than 22. It takes a `layout:` now. It still publishes the height the keyboard *can* occupy rather than a live measurement, which keeps the rule that matters: a layout changes only when the user edits it in the app, never mid-read, so it cannot move the band under a reading in flight the way the appearing-and-disappearing context strip did.
