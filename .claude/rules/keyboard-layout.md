# Keyboard layout and right-to-left

- **`KeyboardLayout.rows` and `.columns` are pure functions of their arguments, and the grouping level is passed in rather than read.** The first version of grouped keys read `SharedStore.shared.storedGroupedLevel` inside `letters(for:)` and `columns(for:plane:)`, which quietly made the entire layout engine depend on global mutable state: the dial lives in the App Group, the simulator shares one, and anybody who had tried the feature left it on — at which point `RenderedRowOrderTests` and `LanguageCatalogueTests` measure a *grouped* keyboard and either fail or, worse, pass against one. That is the same shape as the `PersonalLanguageModel` trap in `.claude/rules/suggestion-bar.md`, where the suite taught the store its own vocabulary and then tested against it. Both functions take `grouping: GroupedKeys.Level = .off`, so every existing caller and every test keeps today's keyboard, and **`KeyboardView+Keys` is the only place that asks the controller what the user chose**. `GroupedKeysTests.testTheLayoutIsUngroupedUnlessAskedRegardlessOfTheStore` sets the dial to L1 and then asserts the default argument still draws one letter per cap, so it fails against the version that read the singleton.
- **A grouped key is a block of the keyboard it replaces, and both of its dimensions are load-bearing.** `GroupedKeys.plan` bands the **top two letter rows** into one drawn row of double-height keys and leaves the third — the one carrying shift and delete — grouping sideways as before. A banded key is a *column slice*: `q w` over `a s` is one key, drawn on two lines. Grouping sideways alone was the version that shipped first and it was half the feature and the wrong half — a key that is wider and no taller is a sliver, a thumb misses in both axes, and `q` and `a` sat two keys apart when they are millimetres apart on the glass. **Three invariants hold it together.** `KeyRow.heightUnits` is a multiplier, and the band is two key-heights *plus the row gap it swallowed*, so the keyboard is exactly the height it was and the 368pt screen-context cliff is untouched. A key's `span` is how many of the ungrouped keyboard's positions it covers, so a band adds up to the same ten columns its rows did — which is why `KeyboardLayout.columns` keeps its `max(10, needed)` floor now, where the row-at-a-time version had to skip it. Drawn width is `.slot(of: bandCount)`, not leftover-share or `.unit(span)`: a unit left the band short, leftover-share made third-row buckets ~1.6× a band key, and weighting by span left leftover columns on skinny keys. Grouped letter rows carry no side inset, because a slot is measured against the whole row. And a cap carries a **line break** between the two rows it merged; `GroupedKeys.letters(inCap:)` drops it, `KeySpec.identifier` turns it into a hyphen so a UI test can address the key, and nothing else in the package knows it is there. `GroupedKeys.supports` still **refuses any language whose letters are not single `Character`s**: `press` receives the cap string and nothing else, so the only route back to "which letters is this key" is splitting the cap, and a Devanagari key is a run of combining marks that is one `Character` — the same trap `LetterLayout.init(keys:)` exists for. English and Hebrew are the two this was measured on.
- **Four things about a grouped key are not obvious and each was a defect first.** **A grouped letter key is `.slot(of: bandCount)`, not leftover-share or `.unit(span)`**: a unit is a key width and knows nothing about the spacing beside it, so five two-unit keys came out two units short of the row they replaced and the band drew 27pt narrower than the keys under it, on a feature whose whole purpose is width. Leftover-share (`.share(1)` of what *this row* had after pinned shift/delete) made third-row buckets equal to each other and ~1.6× a band key. A slot is one of N equal parts of the whole row, gutters included, so every grouped letter key is the same width across rows. `span` is kept only so `columns` still adds up to ten. **A leftover one-letter group is folded into a neighbour** rather than drawn: two leftovers join first (`ך` with `ף`), otherwise the letter joins the side that does not put two Hebrew prefixes on one key. **A grouped cap is drawn one `Text` per letter, inside an `.leftToRight` stack, and each letter occupies an equal cell that fills the key**: as a single string, `קר` is one right-to-left run and bidi puts ר to the left of ק while the keys underneath have ק on the left — every Hebrew cap mirrored, in the one place `RenderedRowOrderTests` cannot see it, because the *row* would be right and only the cap reversed. A clustered HStack around intrinsically sized glyphs left `ו` looking like a skinny button beside `קר` on caps `.share(1)` had already made equal, and sizing the font by `width / letterCount` made the one-letter cap's glyph jump larger than its neighbour; hit testing already splits the cap into equal cells, so the drawing has to match. The floor on that divisor is two, so a one-letter line keeps the two-letter cap's font. **`isGroupedCap` is membership in the layout being drawn, not "does this cap hold several letters"**: `SlotAction.text` compiles to `.character(".com")`, so the shape test fed the `.com` key — and `,` `?` `!` `@` on any layout that had moved them — to the decoder as a keystroke. And **`supports` asks whether a letter fuses when doubled**, not whether a key is one `Character`: every InScript key is one, so Devanagari was accepted by a feature that destroys it, and a per-row check would not have been enough either, since a band joins a letter to the one *underneath* it. `KeySpec.groupedLetters` is what carries all of this: only the layout knows a cap is several letters rather than a word, and the drawing, the spelling to VoiceOver and the decoder all need to be told.
- **Banding gained English and cost Hebrew, and the exact opposite was predicted.** The study the design leaned on found the letter-to-key mapping worth under 0.5 points; measured here it moved English +1.8 to +4.4 and Hebrew −1.8 to −7.9, because English's second row is where its rare letters live (a band key is a common letter with ballast under it) while both of Hebrew's top rows are dense with its commonest. **Do not carry an English mapping result into Hebrew.** The numbers in `GroupedKeys.Level.measuredAccuracy` and in Settings are `Bar/grouped/results.json` and have to be re-earned by a sweep whenever the grouping changes; the main sweep assumes the thumb never misses; `Bar/grouped/harness/miss.py` is the measurement that sees the target-size win, and every rate carries a ±2 spread. **Hebrew's grouping is still not plain adjacency**: `GroupedKeys.hebrewClitics` are kept off one another's keys, worth +7.0 points at thirteen keys, because plain grouping puts ב with ה and makes "in X" and "the X" one keystroke. Banding made that constraint *easier* — a band column is atomic, so a column holding two clitics would be unfixable, and Hebrew's band has none (ו over ע; ש, כ and ל each alone) while the other pairing of its rows has כ over ה. It stops being satisfiable below nine keys, where the row that keeps delete holds three clitics and gets two keys. **Hebrew is capped at L1** (`GroupedKeys.Level.hebrewCeiling`): L2 commits the wrong word about three times in ten, the dial is shared, and English keeps the stop the user picked. `KeyboardController.groupingLevel` is what clamps it; Settings says so when the dial is above the ceiling. All of it is measured (`Bar/grouped/`, `.claude/docs/grouped-keys-design.md`), and `Bar/grouped/harness/swift-check.sh` compiles the shipping Swift and requires it to agree with the Python that produced those numbers.

- **Every right-to-left keyboard rendered mirrored, and the row data was never the problem.** `UCKeyTranslate` returns letters in *physical key order*, which is already Apple's left-to-right screen order — Hebrew's `"קראטוןםפ"` draws `ק` leftmost exactly as stock iOS does. Reading that as *logical* order and setting `layoutDirection: .rightToLeft` on the row reversed six languages at once. `mirrorsRows` is deleted and every key row is pinned `.leftToRight`. **Row order does not follow the language now, and the suggestion candidates were the last thing that did.** The bar's chrome was pinned first, after the emoji and AI buttons swapped sides mid-swipe; the three candidate slots kept mirroring for a while longer on the argument that words should read the way the language does, and they are targets a thumb learns, so the same slide that changes language moved the word out from under it. `RenderedRowOrderTests.assertCandidatesRunLeftToRight` measures that on screen, because `controller.suggestions` is in the same order either way and no test that reads it can see a reversal.
- **Two things were measured off Apple rather than guessed and both were surprises.** **Hebrew puts delete at the right end of the *top* row**, not the bottom, and iOS's Arabic is 11/11/9 where ours is macOS's 12/10/7. Delete follows the shape rather than the writing direction: a strictly shortest top row carries it, otherwise the bottom row does. Hebrew's 8/10/9 layout is currently the only top-row case; Arabic keeps delete on its bottom row.
- **Delete and cursor icons follow the script even though the rows do not.** `KeyCap.backspaceSymbol(isRightToLeft:)` / `deleteForwardSymbol` swap `delete.left` and `delete.right` when the language is RTL, because the caret sits on the left of typed text and backspace removes the character to its right. `cursorLeftSymbol` / `cursorRightSymbol` swap `arrow.left` and `arrow.right` the same way, and VoiceOver follows the glyph (`accessibilityLabel(isRightToLeft:)`). Used by `KeyView`, the emoji category-row delete, and cursor keys on the suggestion bar. Offsets stay `-1` / `+1`. Rows stay pinned LTR. Do not set an RTL environment on those Images: `arrow.left` is in Apple's auto-mirroring list and would flip twice.
- **Some alternates are marks rather than letters, and they carry their letter with them.** Hebrew's geresh U+05F3 and gershayim U+05F4 and Catalan's interpunt U+00B7 belong inside a word: `צ׳יפס`, `צה״ל`, `col·legi`. They are `alternates` entries spelled **`צ׳`, `צ״`, `l·` — letter *and* mark** — because picking an alternate deletes the character the key already typed and retypes it, so a bare `׳` would eat the letter in front of it. A bare `·` *key* on the symbols page is a different thing — SwiftKey puts it there, and it is a second tap after `l`, not an alternate of `l`. The geresh still has no key of its own. Two traps in adding more of these. They **must not** go through `KeyboardLayout.alternates(_:)` or `latin(_:)`: both split a value per `Character`, and these marks are spacing punctuation rather than combining, so `"צ׳"` is two `Character`s and the helper turns one alternate into the letter plus a naked mark — the mirror of Devanagari's `"ँः"`, which fuses instead. And `LetterLayouts.hebrewMarks` is generated from `hebrewRows` rather than written out, so a row edit cannot leave a letter without its marks. `LanguageCatalogueTests.testEveryHebrewLetterOffersItsGereshAndGershayimOnALongPress` and `testCatalanCanTypeThePuntVolat` assert the exact list, because a non-empty list is exactly what the split version produces. **Persian's half-space is the one that also needed the view to change**: U+200C has no width and does not join, so `ی` and `ی‌` are the same picture and the popup offered what looked like one glyph twice. `KeyView.displayLabel` draws it as `␣` — نیم‌فاصله means half-space — and inserts the real character; nothing else in any layout is invisible, so that is a substitution rather than a labelling system, and `AlternatesPopupTests.testNoOtherAlternateIsDrawnAsSomethingElse` keeps it that way. **And every popup item needs a non-gesture route**, because the geresh and gershayim are on no plane: `KeyView.accessibilityActions` covers every key with alternates rather than the rewrite key alone, and it replays the press first, since the gesture's handler is delete-then-retype and a rotor action has no finger-down behind it to undo.
- **The sweep that found them, and the two it deliberately left.** `Bar/layouts/apple-layouts.json` drops punctuation on purpose, so asking "which marks can this language's own keyboard type that ours cannot" takes two sources, and both are worth re-running before adding a mark. A `UCKeyTranslate` sweep of every key code on base/shift/option keeping the *non*-letters gives what the macOS layout produces; `UIKeyboardNonstopPunctuationCharacters` in `InputMode_<tag>.plist` inside the simulator runtime gives Apple's own list of the marks that appear *inside* a word, which is the narrower and more useful question. That second key is what settled all three additions: `he` lists exactly `׳` and `״`, `fa` lists U+200C and nothing else, and ten Latin and Cyrillic languages list `’`. **Two gaps are still open on purpose.** Arabic and Persian harakat — the eight on Apple's shift layer — attach to any letter, so they are a plane rather than eight more items on twenty-eight keys, and no `InputMode` file asks for them. Hebrew's maqaf U+05BE and niqqud are on the macOS layout and on neither iOS's own Hebrew keyboard nor its nonstop list. Catalan's interpunt is the one addition *not* backed by an `InputMode` entry; it is there because `l·l` is a distinct sound and CLDR spells it, and it is worth knowing that it rests on a weaker source than the other two.
- **A letter draws a press callout on finger-down even when it has a popup, the popup still waits 200ms, and the popup is centred on the key rather than on its own first item.** Gating the callout on `!hasAlternates` left Hebrew with no tap feedback: every letter carries a geresh, so the thumb covered the glyph and nothing rose above it. `drawsCharacterCallout(popupIsVisible:)` is true for a character key until the strip opens, so a tap previews the letter and a hold replaces that balloon with the strip rather than stacking ח on top of ח beside ח׳. The punctuation key and grouped caps still skip it — the former already wears its marks, the latter is several letters. **The balloon tracks `isTouching`, not `isPressed`, and insertion is identity.** `isPressed` waits on `DragGesture.onChanged`; `@GestureState` updates on the touch itself. `Motion.pop` on this overlay used to sit outside the cap's `animation(nil)`, so SwiftUI's default insertion spent ~350ms scaling from 0.6 and a tap never showed the letter. **`KeyView.alternatesDelay` is never zero** — opening on finger-down puts the popup on screen for the length of every keystroke, which is exactly what showing Hebrew's two-item popup from the press looked like before it was pulled. The centring is a trap that predates all of it: `alternatesWidth` is centred on the key, so the point under a finger that never moved is half the overhang into the strip, which is the 0/1 boundary at two items and the middle of item 4 at nine. Lifting straight up therefore swapped the letter for an alternate nobody aimed at while the highlight said index 0. `KeyView.hasSlid` (6pt, against a 34pt item) is what makes "lifting without moving changes nothing" true, and `AlternatesPopupTests.testTheKeysOwnCentreIsNotTheFirstItemOfItsPopup` asserts `!= 0` rather than a number so no future width can make it quietly pass. **A strip that would draw past the keyboard is shifted by the same amount `alternateIndex` uses.** The period key sits against return, and a centred five- or six-item strip lost its last mark and its rounded corner. The offset is clamped so both ends sit `Theme.Radius.chip` inside the keyboard, and hit-testing subtracts that offset; a visual shift the index function does not know about is how a lift on `.` picks `,`. The period popup is also SwiftKey's order (`! @ # , . ?`, with Arabic `،؟` and Greek `;`) and aligned so the period sits over the key until that clamp has to move it. Resting still keeps `.` because `alternateRestIndex` names the period, not slot 0.
- **A character key types on the lift, and the rollover answer is the *next* finger-down rather than that key's own.** NIT-108: a letter used to insert on finger-down, so holding one wrote a character while the finger was still on it and the accents popup was a delete-then-retype of something already in somebody's message. `KeyView.defersCharacterToLift` parks it instead. **The latency is real and is the price**: the letter now lands one dwell time (roughly 60–120 ms) after the glass is touched, where Apple's own keyboard lands it on contact — the one behaviour on this keyboard that trades feel for correctness, and it is worth re-reading that trade before adding a second. **Three things deliberately did not move with it, and each of them is a defect if it does.** The press balloon and the pressed cap still track `isTouching`, so the key still answers instantly. The click and the thud still play on the finger-down — `KeyboardController.beginCharacterTouch` plays them and tells the deferred press they are spent (`playsFeedback: false`), because a late haptic is *felt* where a late glyph is only seen, and one tap buzzing twice is the Emoji key's defect one bullet up. And **key repeat is untouched because delete does not defer**: `startRepeatIfNeeded` runs from the same finger-down branch the letters left, so a backspace that ever waited for its lift would stop repeating altogether — `KeyViewDeferredCharacterTests.testDeleteStillActsOnTheFingerDownSoItCanStillRepeat` is what fails a deferral widened to every key. **Rollover is settled on arrival, not on lift, and lift order is why.** Two thumbs land in one order and come off in another — press `a`, press `b`, lift `b`, lift `a` is ordinary — so a keyboard waiting for each key's own lift spells that `ba`. `KeyboardController.payOpenTouches(before:)` is the answer and it is the space bar's `interrupted()` line generalised: every key that acts pays the open ones first, so the field already reads `a` while both fingers are still down. A letter landing on an open space bar pays that space on the way in, which is what keeps `sched` + space + `t` from becoming one word — so the two can only ever be open together in *one* order, a letter parked before the space bar was touched, which takes three fingers to reach and is why the character is paid first. **The debt is claimed before either is paid**, because `commitCharacterTouch` goes back through `press`, which pays open touches of its own: settle the space inside that nested call and it lands in front of the letter it is supposed to follow, spelling `a b` as ` ab`. `interrupted()` marking the space spent as it answers is what makes the nested pass find nothing left to do. **`press(_:)` itself stays immediate**, and three callers depend on that: a VoiceOver rotor pick replays it with no lift behind it (`KeyView.commitAlternate`), the accents handler retypes through it, and idle typing inserts through it — a `press` that parked would leave all three holding a character nothing would release. **The base letter is still committed before the popup's pick replaces it**, one line above it in `onEnded`, which looks wasteful and is not: the pick is a delete-then-retype (`KeyboardController.insertAlternate`), so dropping the base letter leaves that delete to eat the character in front of the word — the same failure `KeyView.commitAlternate` replays a press to avoid on the VoiceOver route, and the one `KeyViewDeferredCharacterTests.testAnAlternateReplacesTheLetterRatherThanAppendingToIt` seeds a `c` to tell apart from the appending build. It also keeps a grouped cap's stroke appended before the popup pins a letter out of it. **What that ordering does *not* buy is the protection from autocorrect, and believing it did shipped a bug in build 37.** The popup used to ride on `deleteBackward`'s own snapshot for that, and **that snapshot is the word *left standing*, so it is `""` whenever the mark is on the first letter of the word** — which is where Hebrew's geresh always is, `צ׳יפס` being the word the rule was written about. `isCorrectingWordByHand` refuses an empty prefix, correctly, since it is a prefix of every word and `deletePreviousWord` sets exactly that (`.claude/rules/suggestion-bar.md`). So `insertAlternate` retakes the snapshot from the word the pick actually left in the field — `צ׳` rather than nothing, `café` rather than `caf` — one insert after the delete. **The hole predates NIT-108** and is not a deferral bug: the insert-on-finger-down build deleted from the same empty field and recorded the same `""`. `testTheProtectionSurvivesTypingOnFromAMarkOnTheFirstLetter` asserts through the four letters typed after the mark, because space is what would swap the word and space is four keystrokes later, and it carries a control half — the same word typed without the popup is *not* protected — because a repair that armed on every insert would switch autocorrect off for good. **Every exit a touch has commits, except one, and that one discards on purpose.** `KeyView.endPress` is where the report lives, so a cancelled gesture, a finger that slid off the key and the key leaving the screen mid-press all still type the character the pre-NIT-108 build had already written on the way in — and `wasPressed` is what makes it fire once, since a normal lift reaches `endPress` twice. The exception is the keyboard **coming back up over a new field**: iOS keeps one extension instance alive across fields *and across host apps*, and a teardown mid-press is not promised a SwiftUI disappear callback, so a letter parked in a WhatsApp reply can outlive it and be typed into the Notes field that follows. `KeyboardController.discardPendingCharacter()` is called from `prepareForNewDocument()` — `viewWillAppear`'s path, the same line `refreshDocumentState` is there for — and it is a *discard*, because losing a keystroke the user watched the keyboard swallow is strictly better than putting a character from the last app into this one. That is also the one behaviour difference from the old build that cannot be designed away: insert-on-down had already written it. **A parked character must not reach `documentHasText`**, which is the published value Fix, Rewrite and the bar's one-tap button all read to decide whether they are lit — parking touches the document not at all, so it must touch that not at all, and `KeyViewDeferredCharacterTests.testAHeldCharacterDoesNotMakeAnEmptyFieldLookLikeItHasText` asserts both halves so a build that refreshed on the park fails.
- **Delete is `.pinned`, not leftover share, and the row that holds it has no side inset.** `remainderShare` made English's delete 54pt and Hebrew's 34pt on the same phone, and an inset on Arabic's short bottom row pushed delete 59pt in from the edge. `KeyWidth.pinned` answers a width from the screen (ten reference columns, 1.5 units), `KeyboardView.rowView` draws pinned keys hard against the ends of the row, and the delete row's `sideInsetUnits` is always 0. `LanguageCatalogueTests.testDeleteKeepsTheSameWidthAndTrailingEdgeInEveryLanguageAndOnEveryPlane` rejects a regression. The letters between the pins may shrink on a crowded language.
- **The letter keys slide the way the strip already points, not the way a pager follows a finger.** A right swipe lights the code on the right of the space bar, so the new keys enter from the right (`SpaceSwipe.slideEdges`); content-follows-finger would bring in the left neighbour and fight the affordance. The space row itself does not slide, because the thumb is on it. Reduce Motion keeps the crossfade. `Theme.Motion.swipe` is the beat — the same 80ms `Theme.Motion.duration` as every other change, not a 300ms spring that made the incoming layout a show. The balloon and the sliding highlight on the strip are supporting continuity, not a second show. **The sliding letters live in a ZStack so two languages can overlap, and that ZStack is `fixedSize(vertical:)`.** Without it, GeometryReader leftover height collected between backspace and space, the space row was pushed into the bottom inset and clipped, and `.clipped()` on the same stack sliced the backspace row's shadow off. Do not clip that stack: the swipe is horizontal, and the 12pt row gap is where the key's contact shadow sits.
- **The space row ignores the language's column count.** `123`, punctuation and return are `.unit` multiples so the editor can resize them, but `widths(for:)` resolves that unit against `referenceColumns` (ten) whenever `row.id == RowID.bottom`. Feeding Arabic's twelve-column letter unit into the same row made return shrink and space grow while English kept the stock proportions. Return uses `functionKeyUnits` (1.5), exactly matching Backspace above it — one unit was too narrow, while the old 2.2 units made it the widest key. The space bar stays `.flexible` and absorbs the locked remainder. `LanguageCatalogueTests.testTheSpaceRowWidthsAreIdenticalInEveryLanguage` rejects a regression — it passes each language its own unit and still demands identical widths.
- **The bottom row's full stop is on all three planes, and the row of five marks above it is not a substitute.** It was letters-plane only, on the argument that the numbers plane already carries `. , ? ! '` on its punctuation row. True, and beside the point: the full stop is the one key a thumb finds without looking, so switching to numbers put the return key where it had been. It costs the space bar one unit on two planes. The ids do not collide because `punctuationKey(for:)` passes an explicit `punctuationKeyID` — that key answers to `punctuation` and the one above answers to `char-.` — and that explicit id is the *only* reason this was safe to do; drop it and the plane has two keys with one `ForEach` identity. The same rule lives in two places and both had to move: `KeyboardLayout.bottomRow` and `CustomLayoutCompiler.compile`. Pinning the plane switch and delete on those rows also freed the leftover they used to split, which had made them 94.5pt wide, so the five marks are declared `punctuationRowUnits` (1.5) and the row fills edge to edge instead of floating in the middle.
- **Numbers and symbols are SwiftKey's four rows, and they do not grow the keyboard.** Digits, `[]{}#%^*+=`, then `-/:;()$&@"` on 123 and `_\\|~<>$€£·` on `#+=`, then `#+=` / `123` plus `. , ? ! '` and delete — the same shape on both pages, so switching `#+=` cannot move the punctuation row. ¥ and • ride as long presses of £ and ·. The fourth row is `RowID.extraSymbols` (5), not 3: 3 is the space row and a `ForEach` with two of it is undefined. **Do not raise `rowCount` to pay for it.** That number is the letters plane, and 368 pt is a measured cliff; four rows at the shipped letter height would retire screen context. `Theme.Metrics.fittedKeyHeight` squeezes the extra row into the block three letter rows already occupy. A layout that already turned the number row on has paid for the fourth slot and is left at the shipped key height. `NumbersSymbolsLayoutTests` pins the characters *and* the height; a scan for `[` anywhere on the plane passes the three-row build, because that key already lived on symbols.
- **Emoji covers only the letter area; the action row stays put.** The Emoji key wears the same filled brand cap as the other four while its grid is open, because "this control is currently doing something" is one statement and the row should not draw it four ways and a fifth; the rule that `Theme.Brand` is reserved for the AI moments is about the glyph's tint *at rest*, where emoji is still neutral in both of its label states.  `KeyboardOverlay.emoji` is drawn inside the letter-key `ZStack`, not as a full-key-area panel. One-handed reach pins the emoji panel to the same `gridWidth` as the keys. The grid wears `Keys.background`, the same as the letters it replaced: `Keys.panel` is the warmer lift the banner uses, and painting it here left a cream rectangle inside a grey keyboard. AI and dictation used to cover everything and no longer do — see the rule below.
- **CopyClip is a sibling of emoji, not a new height band.** The action row is four `.fill` keys (copyclip, fix, rewrite, dictation) with a narrow gear in the true middle; Reply ships on `barTrailing`. Emoji is 1.0 units on the bottom row beside 123. The panel replaces the letter keys only. Long-press is the stacked popup of the last five clips, tap is still the panel. Tap inserts and stays open. Swipe deletes one clip. Search is the same swap as emoji: the suggestion bar becomes the box while either CopyClip state is up, tap opens `.copyclipSearch`, the letters come back, and the action row becomes matches. The ✕ while editing returns to the list. **Capture is honest, and it happens at exactly one moment: when CopyClip opens.** Since iOS 16 the first read of the *contents* of a board another app filled raises the system "Allow Paste?" alert, and this keyboard used to snapshot the contents from `viewWillAppear`, from `KeyboardView.onAppear` and from `changedNotification` — so tapping any text field after copying anything in any app put an alert in front of somebody who had not asked for their clipboard, and a session that copied nothing still paid a read. No *read* avoids the alert: `detectPatterns(for:)` answers *what kind* of thing is on the board without prompting but never the value, and `detectValues(for:)` prompts exactly like a plain read. The only lever a read has is *when* it is spent, so `CopyClipRefresh` splits the question in two. **`.passive` calls exactly one accessor, `changeCount`, and then stops** — it syncs the ledger with the shared container and deliberately does *not* advance the cursor, because nothing was read, and leaving the cursor behind is what lets the panel capture that generation later. `hasStrings` is reached only from inside `.userAsked`, where it skips a pointless alert over a copied screenshot: Apple documents `detectPatterns(for:)` as needing no permission and says nothing either way about `hasStrings`, so the silent path is not allowed to depend on it. `.userAsked` is the one path that reads, and `show(_:)` opening `.copyclip` / `.copyclipSearch` is its only caller — **above the `withAnimation`, deliberately**, because the read blocks the main thread until the alert is answered, so the choice is "alert, then a panel that is already right" against "a stale panel, an alert over it, then a row appearing underneath". The `changedNotification` subscription is deleted rather than made passive, because everything it could still do the panel does a moment later anyway. **Three costs are real and all three are the better half of the trade**: two copies between two openings leave only the second in the ledger; the long-press popup no longer holds a string copied since the last capture, and must not try to, because that popup opens 200ms into a hold and a blocking alert under a moving finger is worse than the extra tap the gesture already degrades into; and a generation the user never taps Paste on is never captured at all, silently. **The one genuinely alert-free route is `UIPasteControl`**, iOS 16's system paste button, and it *is* the route now: `refreshCopyClip(.userAsked)` reads no contents, a pending *text* generation leaves the cursor exactly where it is, and `CopyClipPendingCaptureRow` draws the system button for that one generation. It trades one alert per copied item for one tap per capture, and it is system-drawn inside a panel whose cards are on purpose letter keys, so it never disappears into the list the way a `CopyClipCard` does. **Its `target` has to be a `UIResponder`, and both halves of getting that wrong are silent.** The first version handed the control an `NSObject` coordinator carrying a `pasteConfiguration` — which the header's `id<UIPasteConfigurationSupporting>` accepts and the compiler never questions — and the button shipped permanently disabled, drawn at about 45% opacity, with CopyClip's only route from a fresh copy into the ledger dead while the row underneath promised "Paste adds it here. No prompt." iOS asks the target `canPasteItemProviders:` before it enables the control; that requirement is **optional**, and the one default implementation of it — the one that matches the board against `pasteConfiguration` — lives on `UIResponder`. The second half was a name: the Swift spelling is `canPaste(_:)` with *no argument label*, so the coordinator's `canPaste(itemProviders:)` compiled, answered correctly whenever Swift called it, and was exported under a selector of its own that iOS never asks for. Swift says so out loud — "instance method 'canPaste(itemProviders:)' nearly matches optional requirement" — and that warning was the entire bug. `PasteControlHost` is a `UIView` owning the configuration and both methods, with the control added as its subview and pointed at it, which is Apple's own arrangement (`pasteButton.target = textView`, button added to that text view). `CopyClipCaptureStateTests` reaches all of it through `any UIPasteConfigurationSupporting` rather than through the Swift method, because calling the method directly passes against the broken build. Its fill is `Theme.Brand.action`, not `solid`, for the reason every filled surface under `Text.onBrand` is. Same text moves to the front and keeps its id. History is a JSON `CopyclipRecord` (clips plus `lastChangeCount`), written on every mutation, because the extension dies without teardown. The cursor is persisted so Clear cannot be undone by a kill. The open key stays `clipboard.fill` plus the word while the panel is up: `ABC` / `אבג` promises the letters are coming back, and search already hid the action row. Without Full Access the store is process-local and the empty state says so. `isCopyClipOpen` is its own flag: reusing `isEmojiOpen` would flip the wrong key. `isCopyClip` is true for both states, the way `isEmoji` is; draw the panel only on `.copyclip` or search covers the letters it just handed back.
- **A panel that covers the letters has to give back whatever it covered that the user still needs, and CopyClip gave back nothing for the whole of its life.** The emoji grid had already worked this out — `EmojiCategoryRow` pins a real, repeating delete key at the end of its tab row "because this row replaces the letters while it is up, so it *is* the only delete on screen" — and CopyClip has the identical shape with two gaps rather than one. A typo behind the cursor could not be repaired without closing the panel, and **a clip tapped by mistake could not be taken out at all**: one tap puts a whole paragraph in somebody's message, and the only route back was to close CopyClip and hold a delete key the panel had been hiding. `CopyClipControlRow` is the fix, drawn inside the panel and therefore costing the keyboard **no height** — the same free trade the emoji category row makes, nowhere near the 368pt cliff. **It is a toolbar rather than a key row, and the empty middle is the point.** Emoji fills its width with ten category shortcuts; CopyClip has no equivalent, and two keys pushed together in the centre read as a fragment of a keyboard. Splitting them also buys the thing that matters most: one removes a character and the other removes an entire paste, so they are the two controls here that must never be hit for each other. Delete keeps the trailing end it holds on every other row. **Both wear the soft graphite cap, and the undo deliberately does not take the brand tint its twin in the suggestion bar wears** — that is `KeyView.actionTint`'s standing rule (a brand tint on soft graphite is neither readable nor the neutral control the key is), and the bar's revert sits on no cap at all, so only it can afford orange. It also sidesteps a trap: `KeyStyleButton` hardcodes `Theme.Keys.functionPressed` for a pressed cap, which lightens a graphite key correctly and is *the same colour as a resting warm-white one in light mode*, so a `.letter` cap there would have had no visible press at all. **Undo stays on the row when there is nothing to take back and only fades** (`KeyStyleButton.isDisabled`, `KeyView.disabledLabelOpacity`, the gesture guarding itself rather than trusting `.disabled()`). The suggestion bar's revert appears and disappears because there it is competing with three candidate slots for 52pt; here it competes with empty panel, so the cost that bought that behaviour does not exist — and a control nobody can see until they have already made the mistake is one nobody knows is there.
- **Landscape sheds the action row, and that row is the only way out of a panel — so rotating into landscape with one open left a keyboard nothing could type on.** `Theme.Metrics.landscapeLayout(basedOn:)` sets `cursorRow = []`, and the emoji key and the CopyClip key both live in that row; `KeyboardOverlay.emoji` and `.copyclip` both answer `showsLetterKeys == false`. So a phone rotated with either panel open drew a panel, no letters, no space bar, no return and nothing that closed any of it. The escapes all loop: the suggestion bar is the search box, tapping it hands the letters back but they type into the *query*, and the box's ✕ returns to the panel. Nothing resets `overlay` on rotation — and nothing resets it on the way out either, so an extension instance iOS keeps alive can *appear* in landscape already trapped, which is why `KeyboardView` uses `.task(id: orientation)` rather than `.onChange`. `KeyboardController.closeOverlayForLandscape()` closes it, from the view rather than from `KeyboardViewController`, because the view's own `orientation` is what sheds the row and two reads of that question are two things that can disagree. **Closing is the answer rather than keeping the row**: landscape has ≈169pt for the whole keyboard and the row was shed on purpose, so a panel that cannot be *opened* in an orientation should not be standing in it. A user who put CopyClip or Emoji on a bar edge can reopen it there — `SuggestionBar` reads the unmodified customization, so the bar is not shed. Two traps in the fix. It is **silent**: `show(_:)` fires `Feedback.modifierPress()` because a key was pressed, and a rotation is not one, so this goes through `dismissOverlay()` instead. And it is guarded on `overlay != .none` because `dismissOverlay()` also calls `stopDictation(insert: false)` and `clearBannerState()` — dictation runs with *no* overlay, so an unguarded version would cancel a recording every time somebody turned the phone. `LandscapeGeometryTests.testAPanelIsClosedInLandscapeBecauseNothingThereCouldCloseIt` states the premise as its first two assertions rather than the behaviour, so a landscape that ever keeps the action row deletes this workaround instead of adjusting it.
- **The undo behind that key is the *same slot* Fix, Rewrite and Reply use, and a second one would have been a bug with a fuse on it.** `AIEdit` is `RevertibleEdit` now, carrying an `Origin` of `.ai(AIAction)` or `.clip`, because a clip insert is the same event as a Fix seen from the field: text the user did not type, arriving whole, with `UITextDocumentProxy` offering no undo of any kind. Its lifetime is identical too — until the next keystroke — so a second published property beside `revertibleEdit` would have been a second thing to clear from the seventeen places `clearRevertibleEdit()` is already called from, and the first one anybody forgot would delete characters the user had typed. One slot means one implementation of "delete exactly what was put in, from where it was put in", which is the operation that destroys a message when it is wrong. Two consequences fall out. `SuggestionBar.revertButton` draws a clip's way back for free once the letters are handed back, and names it from `Origin.undoLabel` ("Undo paste") rather than learning what a clip is; and `CopyClipControlRow` draws a *Fix's* way back while the panel is up, because it is the only surface that can — the bar is the search box for as long as CopyClip is open. **`RevertibleEdit.standsAtEnd(of:)` is the claim check, and it takes two tests rather than one because `documentContextBeforeInput` is a window and not the field.** A clipboard history is exactly where multi-line text lives, iOS truncates what it hands back, and the old exact-suffix test therefore answered false on a paste that was perfectly intact — a silent no-op on the tap that matters most. The second test is the same claim asked of a truncated window: everything visible behind the cursor is the tail of what the edit wrote, so none of it belongs to the user. An **empty** window is refused, because `""` is a suffix of every string and deleting a count from a field the keyboard cannot see is the one outcome worse than no undo at all. The relaxation applies to the AI span path too, where it only ever turns a silent miss into a working undo. **One gap is left open on purpose**: a clip inserted from the *search* results strip records a way back that nothing on screen draws until the ✕ returns to the list, where it is still live. Closing it would cost a result slot in a strip that shows about five.
- **Nothing the action row does may cover the keys, and the refusals were the half that had not been converted.** Fix, Rewrite and Reply already reported in `ActionBanner` when they *could* run; every path where they could not fell back to a panel over every key row — `AIMenuPanel` for an empty field, `AIResultPanel(.needsScreenContext)` for Reply with no session, `DictationPanel` for a dictation session the app had never opened. Those are the states a new user meets first, so the keyboard hid itself exactly while somebody was learning it, and Fix on an empty field drew nothing at all. All four are `BannerState.blocked` now — a title, a sentence, and a remedy that is either Dismiss or the broadcast picker itself. `KeyboardOverlay` carries only the emoji cases, so `KeyboardView.coversFullKeyArea` and `fullKeyAreaPanel` are deleted rather than reduced, together with `PanelChrome`, `AIActionResultKind`, `ActionBanner.resultPanelIsOpen` and `resolve`'s `resultsShownElsewhere` — each of which existed only to stop a panel and the strip drawing one answer twice. **Three things were given up on purpose.** The broadcast picker is no longer a 42pt trailing chip: that chip's real `UIButton` is inset 5pt by `addBroadcastPickerButton`, so it was a 32pt record-dot that read as already recording, and a tap on "Screen context is off" did nothing. The sentence hosts the picker now (the system button is stretched over it; the glyph is hidden) and trailing is ×. Do not grow the strip to buy a bigger chip — `Theme.Metrics.bannerHeight` is capped by the frame fingerprint. The dictation countdown survived as `12s left` in the tag for the last minute only, and the `עב ⟷ EN` badge did not, because the transcript beside it is already written in its own script. And the best-effort notice is an amber tag plus an accessibility label rather than a sentence. **Two traps in doing it.** `stopDictation`'s third guard clause was `overlay == .dictation`, and that clause was what let a *stopped* session be torn down: `dictation.$failure` clears `isDictating` and `pendingDictationInsert` before setting the reason, so deleting it outright would have made Dismiss on "Nothing to insert" return early and leave the sentence reappearing on every 10 Hz poll. It reads `!dictationFailure.isEmpty`. And `AIMenuPanel.isAvailable` / `.hasRunnableAction` were never panel code — `SuggestionBar` reads them to decide whether its own controls are lit, which is D8 — so they moved to `AIAction` before the panel was deleted. `SlotAction.aiMenu` went with the menu it opened; "Power" and "AI first" carry real Reply keys instead, and `CustomLayoutTests.testEveryPresetReachesEveryAIAction` is what keeps every preset reaching everything.
- **Emoji mode spends no height, because there is none to spend, and every part of its shape is that constraint.** The keyboard's tallest form is 368pt against a cliff between 368 and 370, so a search row of its own would have come out of the grid — three rows of emoji instead of five. Four consequences, and none of them is a preference. The **suggestion bar becomes the search box** while either emoji state is up (`SuggestionBar.body` branches on `overlay.isEmoji`); the three candidates have nothing to say when nobody is typing a word. **`KeyboardOverlay.emojiSearch` is the mirror image of `.emoji`**: the grid goes, the letters come back so there is an alphabet to type with, and the *action row* becomes the results strip — typing a query needs all three of query, keys and results on screen at once, and 368pt has room for exactly the bands that already exist. The grid **scrolls sideways in five fixed rows** rather than vertically per category, so every category is one strip and the tabs are shortcuts rather than steering. And the **category row carries no `אבג`** — the Emoji key in the action row wears the letters-plane label while the grid is open (`KeyView.label`, gated on `isEmojiOpen`), because two keys a thumb's width apart doing one job is what the row had before. `KeyboardOverlay.isEmoji` is what the cap and the bar's tint both read; a bare `== .emoji` makes both revert the moment search opens.
- **A search box does not inherit the document's shift, and the observer rather than the call sites is what makes that true.** An empty field arms shift at focus, so opening emoji search and typing `cat` produced `Cat`, and a shift press from that inherited `.on` went straight to `.locked` — prose rules applied to something that is not prose. Search is case-insensitive (`EmojiSearch.normalise`), so the results were right the whole time and only the box the user reads was wrong, which is why this sat red for a while as a cosmetic problem. **The trap is the other half**: switching shift off on entry and leaving it off loses the capital at the start of the next sentence, which is a real bug traded for a cosmetic one, and four places write `overlay` directly — `show(_:)`, `dismissOverlay()`, `KeyboardController+AI` and `KeyboardController+Dictation` — so a save-and-restore at the call sites is four chances to miss one and strand shift `.off` in the core typing path. It is a `didSet` on `KeyboardController.overlay` calling `adoptSearchShift(from:)`, which a fifth writer that has not been written yet cannot miss. It acts only on a genuine crossing of `KeyboardOverlay.isSearch`, so `.emojiSearch` → `.copyclipSearch` is still one box owning the keys and the parked value is not restored and re-taken; shift pressed *inside* the box belongs to the query and is discarded with it. `EmojiSearchTypingTests.testTheDocumentsShiftIsParkedForSearchAndGivenBack` asserts through `dismissOverlay()` as well as `show(_:)` for exactly that reason, and `testAShiftPressedInsideTheQueryDoesNotLeakIntoTheDocument` is what fails a restore that puts the query's own shift into the message.
- **Emoji search ranking cannot be fixed by reading it, and two principled attempts were measured and thrown away.** Three `EmojiModeTests` are red — `heart` and `לב` answer 🫀 rather than ❤️, and `car` puts 🚗 sixth — and the cause is exact: `EmojiSearch.score`'s exact-keyword branch scores `length` as `shortest(names)`, which is the *shortest across both locales*, so an English query is decided by a Hebrew name. That is the very thing `Match.length`'s own comment says must never happen; the fix was applied to the two name branches and the keyword branch was left behind. **Both repairs make the product worse and the numbers are the reason to believe it.** Scoring the keyword by its own length ties every exact-keyword match and hands the decision to catalogue order, which carries no relevance at all: **51 of 60 queries moved**, `heart` lost ❤️ from the top five entirely and `moon` answered 🥮. Scoring it by the shortest name *in the query's own script* — literally what the failing test is named after — moved **30 of 60**, still put 💏 above ❤️ for `heart` and 🌑 above 🌙 for `moon`. What `shortest(names)` is really carrying is a crude centrality prior (a short CLDR name tends to be the primary emoji for a concept), and removing it costs more than the locale bug does. The missing piece is a frequency signal, the same gap `SeedLanguageModel` exists to fill for words, and there is no `Bar/emoji/` to score one against. **Do not tune this without building that corpus first**, and note that the two `לב` assertions in `EmojiModeTests` contradict each other today (`testHebrewFindsWhatEnglishFinds` wants ❤️, `testRecentsWinACloseCallAndLoseToAName` pins 🫀), so deciding which is right is part of the same job. The ranker is faithfully reproducible outside Swift — a 40-line port over `EmojiCatalog.json` matched the shipping engine byte for byte on `car`, `heart` and `לב` — so the corpus does not need a simulator.
- **Each emoji section is padded to a whole number of columns, and that padding is load-bearing.** `EmojiPanel.sections` fills every category's tail with blank cells so a category boundary is always a column boundary, which lets `category(atOffset:cellWidth:in:)` name a column from the scroll offset. The obvious alternative — a geometry read of a category's *first* cell — goes silent the moment that category is wider than the screen, which most of them are. **A `sectionGap` (`Theme.Space.sm`) sits on the trailing column of every section that has another after it**, so two categories do not run into each other in the strip. It is padding, not a column: a tab still scrolls to the first emoji, and the empty Recent section at the front of a fresh install does not insert a gutter before Smileys. Two traps came out of this. `sections` must **not** be a computed property read from `body`: feeding `@State` from a preference rebuilt 1,870 interpolated ids sixty times a second while a finger moved; it is cached in `@State` and rebuilt only when the recents change, and it is `static` so tests can ask for it without a body evaluation. And a category tab scrolls to **the section's first cell** (`anchorID(forCategory:)`), never to the section: `ForEach(sections, id: \.id)` gives the loop its identity but puts no view on screen carrying the category's id, so `scrollTo("Food")` addressed nothing and every tab was silently dead while the row still drew and the highlight still moved. **The inverse also shipped: the strip moved and Recent stayed orange.** A GeometryReader on the `LazyHGrid` itself sees the viewport, so its offset stays 0 and `category(atOffset:)` keeps answering Recent. The orange tab is `selectedCategory`, set on tap immediately and from the visible cell sitting on the leading edge (`nearerTheLeadingEdge`), and `KeyStyleButton` is recreated when that changes (`.id("\(id)-\(isSelected)")`) because its press `@State` otherwise keeps the first `isSelected` it was given.
- **The Recent tab re-sorted under the finger that tapped it, and the fix is two lists rather than a delayed write.** `insertEmoji` moves the picked emoji to the front of `recentEmoji`, and every view read that array, so tapping the third emoji in Recents slid the two beside it one place across and the next tap in the same spot inserted a different emoji. A Recent tab is muscle memory — that is the whole reason it exists — so a grid that re-sorts while it is open defeats the point of having one. **Writing later is not the alternative**: a keyboard extension is killed without warning and gets no teardown callback, so the record has to go to `SharedStore` at the moment of the pick, exactly as it already did. `KeyboardController.recentEmoji` stays that record and is now read by nothing on screen; `visibleRecentEmoji` is the picture, and `EmojiPanel` and `EmojiResultsStrip` read it. **`settleRecentEmoji()` copies one into the other when the surface becomes visible after not being visible, which is two moments and not one.** `show(_:)` guards on `newOverlay.isEmoji && !overlay.isEmoji` rather than `newOverlay == .emoji`, because the grid and its search box are one visit — search is opened from the grid and backspaced out of it again, and re-settling on either leg is the same shuffle arriving one key later. And `KeyboardViewController.viewWillAppear` calls it too, because nothing resets `overlay` when the keyboard goes away: an instance iOS keeps alive comes back with the grid still open, and without that second call the emoji picked just before the dismissal is missing from Recents until the panel is closed and opened again. Two things deliberately *not* frozen. `setEmojiQuery` still scores against the live `recentEmoji`, so search ranking is unchanged and `testRecentsWinACloseCallAndLoseToAName` is untouched. And an emoji picked this visit is not appended to the visible list either: `sections` pads each category to whole columns, so one more Recent cell can add a column and slide every category after it sideways, which is the same defect one step removed. It also costs less than it did — `EmojiPanel` rebuilds all 1,870 cells whenever the list it watches changes, and that used to be once per emoji picked.
- **The emoji category row is ten shortcuts, not ten keys, and drawing them as keys is what made it unreadable.** `EmojiCategoryRow` gave every tab the full `KeyStyleButton` treatment — warm white card, contact line, ambient lift — at `HStack(spacing: 0)` with no horizontal padding at all, so on a 402pt phone eleven caps butted edge to edge and bled into both edges of the panel. **Spacing is not the fix, and the arithmetic is why**: the row spends 42pt on delete and spent 5 more on a hairline, leaving the ten tabs 35.5pt each, and matching the key rows above (`sideInset` 3, `keySpacing` 5 between twelve items) drops them to 28.3 — a 19pt glyph inside a shadowed 28pt card is more crowded, not less. The chrome goes instead: `KeyStyleButton.drawsCap` is false for a tab, so it is a bare glyph on the panel with 34pt to itself, and the row's only fill is the selected one. **Which then had to stop being a 14% wash, and that is the half of this worth remembering.** Tinting a card 14% works because the card carries the signal and the tint only colours it; take the cards away and the tint is alone, and a `Brand.solid` glyph on a 14% `Brand.solid` wash measures **2.3:1 in orange** (2.58 pink, 2.59 blue) — under the 3:1 non-text floor and *below the 5.18:1 the nine unselected tabs get for free*, so the one tab that has to stand out was the least legible thing in the row. Monochrome is worse than it looks in that table: its selected wash and `pressWash` land 8 units apart in light and invert in dark, so a press read as a selection. The selected tab is `Theme.Brand.action` under `Text.onBrand` now — 3.64 / 5.35 / 5.17, and 13.34 light and 4.80 dark in monochrome — tested *before* the press so re-tapping the current category does not strobe the pill away, with the glyph flip gated on `!isSelected` so it cannot put graphite on orange. This is the same mistake `KeyView.capKind` already records making, in the same words: "a 14% brand wash over whatever cap the key already had ... read as a slightly pink key". One measured caveat so nobody re-derives it: the pill's own edge against `Keys.background` is just under the 3:1 an edge wants in dark for pink and blue — `BrandPalette`'s published 4.46/3.03/3.14 are against `Surface.background`, which is not what this sits on. It is accepted rather than fixed, because the edge is not what picks the tab out: the white glyph inside is the strongest thing in the row by the measure that matters, and every other brand fill on this keyboard already makes the same trade. **Two things fell out.** The hairline between the flags tab and delete is deleted: it existed because the two were the same object with different fills, and with the tabs bare, delete being the row's one keycap says "this one edits your text" without a mark; its 5pt is now `Theme.Space.xs` of air in the same place. And **a capless button cannot answer a press by going pale, but neither of the two named colours that look right works**: a cap lightens from a cap, and a bare glyph has only the keyboard background under it — `Theme.Keys.functionPressed` is 0xFFFEFA against 0xE2E4E8, a pale cap on a pale field, and `Theme.Keys.card` is *the same colour* in light mode, so reaching for it fixes nothing where the problem is and loses contrast in the dark (0x2E3435 on 0x1E2122 is closer than the 0x54595B it would replace). `KeyStyleButton.pressWash` is `secondaryLabel` at 22% instead, the same idiom as `ruleTint`: derived from the label tint, it darkens the light field and lightens the dark one because the label does.
- **The emoji catalogue is generated, and two of the generator's filters are the difference between a grid and a grid full of dotted boxes.** `Scripts/generate-emoji-catalog.py` builds `Resources/EmojiCatalog.json` from Unicode's `emoji-test.txt` and CLDR's `annotations` *and* `annotationsDerived` for `en` and `he`. **`MAX_EMOJI_VERSION` is 15.0 because `Package.swift` floors at iOS 17.0**, which shipped Emoji 15.0; anything newer draws as tofu on a phone that has not been updated, which is a key that looks broken rather than one that is missing. Skin-tone sequences are dropped because the panel offers no tone picker, so they are unreachable and would be five sixths of the grid. CLDR strips U+FE0F from every `cp` attribute while `emoji-test.txt` keeps it, so lookups fold it away — without that, `❤️` finds no annotation and search works in English and dies in Hebrew. `EmojiCatalog.loadFailure` and `EmojiModeTests.testTheCatalogueLoadsOutOfTheResourceBundle` are what stand between a resource that failed to copy and a keyboard whose grid is silently empty.
- **Emoji search ranks rather than filters, and ranking is the whole feature.** Nearly every heart carries the keyword "heart" and nearly every one carries "לב", so a filter answers `heart` with 💘 and `לב` with 🥰. `EmojiSearch.score` is a four-rung ladder and each rung fixed something measured: an **exact keyword ties with a whole word of a name** because CLDR names 🚗 "automobile", so no name rung reaches it for `car` while "police car" and "tram car" do — ranking the keyword below the name buried the actual car under six vehicles; **`Match.coverage`** breaks that tie, since "car" is all of the keyword and 3 of "police car"'s 10 characters; and **the length tiebreak uses the name that matched, never the shortest across locales**, because taking the shortest compared an English query to a Hebrew name and answered `heart` with ♥️ ("קלף לב" is shorter than "לב אדום"). Recents are worth two rungs, bounded so a recent emoji never hijacks a query that names another outright. Measured over 29 English and Hebrew queries: 22 put the obvious answer first, 28 put it in the first five, and the strip shows about nine. **The known gap is Hebrew morphology** — matching is by whole word and prefix, so `בוכה` finds 😭 and `בכי`, the same root in another form, finds nothing; closing it needs a stemmer this package does not have.
- **Every key answers audibly, and both feedback switches are read at the press.** The keyboard played `1104` — iOS's `tock` — for letters, space and return and *nothing at all* for backspace, shift, the plane switch, globe, Settings, the cursor keys, the emoji key and the whole action row, so a held delete clicked once and then ran mute for two hundred characters. iOS ships three sounds and only three (`1104` tock, `1155` delete, `1156` modifier); a fourth means bundling an audio file, and none of them has a volume this keyboard can set. `KeyCap.clickSound` answers for every case and is deliberately **not optional**, so a new cap has to choose a sound rather than inherit silence. `Feedback.keyClick` lives on the two key-event entries: the top of `KeyboardController.press(_:)`, and `deletePreviousWord()` for a held backspace that must not re-enter the one-character path. **Putting the call on the mutation helpers is wrong in both directions.** Too many: the accents popup replaces a letter by calling `deleteBackward()` and then `press(.character:)`, so a click owned by the delete makes one accent pick sound twice. Too few: a repeat that called `deleteBackward()` directly ran silent, and inside emoji search ate the user's message instead of the query. The two insertions with no `KeyCap` behind them, `insertEmoji` and `apply(_:)`, click for themselves. `Feedback.hapticsEnabled` and `soundEnabled` are computed off `SharedStore.storedHaptics`/`storedKeySounds` rather than filled once in `viewDidLoad` — the `storedAutocorrect` trap exactly, and worse here, because both switches live in the app while every press they gate happens in the extension, so an instance iOS kept alive went on clicking after the user turned the sound off. One more that fell out of the audit: the `.emoji` branch fired `Feedback.modifierPress()` and then called `show(_:)`, whose first line is another one, so that key buzzed twice for one tap. **The impact generator has to be bound to the keyboard view.** A style-only `UIImpactFeedbackGenerator` in the extension is a free-floating motor, which is why the first taps of a session were late or missing; `Feedback.attach(to:)` (iOS 17.5+) and `KeyboardView`'s `FeedbackAnchor` are what bind it, and each play prepares the next. `KeyClickTests` and `FeedbackSettingsTests` hold all of it.
- **A held backspace tick calls `deletePreviousWord()`, not `press(.backspace)`.** Tap is still one character. The tick clicks for itself and intercepts emoji search, so sending it back through `press` would be character-repeat. `KeyStyleButton` has a separate `repeatAction` for the same reason. Forward-delete hold stays `press(.deleteForward)` on the letter curve. Word ticks use `KeyRepeater.wordDelete()` (150ms, cap 40): the letter floor is 45ms, which is 22 words a second.
- **The punctuation key skips the single-mark callout.** Its long press *is* the strip of marks, so previewing a lone period for the hold delay looked like a two-step open. Letters keep the callout and open after 200ms (`KeyView.alternatesDelay`); punctuation opens the strip after 50ms (`KeyView.punctuationAlternatesDelay`). 50ms is under a typical tap, so a period tap may flash the strip; that is accepted. A tap on `ח` must not flash Hebrew's geresh strip.
- **`Bar/layouts/stock-rendered-rows.json` is the committed photograph**, `capture-rendered.sh` retakes it, and `AIKeyboardUITests/RenderedRowOrderTests` measures the *rendered* key frames against it — a coverage or row-string test cannot see a reversal, because the string was always right.
- **Key height is three bands, not one number and not one per row, and `keyAreaHeight` is where getting it wrong shows.** `LayoutGeometry.RowBand` is `letters` / `action` / `bottom`: the action row and the space row each answer to their own slider, and the three letter rows *and the optional number row* share one, because a stagger inside the letter grid reads as a rendering fault rather than a preference and because `fittedKeyHeight` — which squeezes the numbers plane's fourth row into the block the letters occupy — has one letter height to divide or it has none. **`rowCount` is the gap count now and is no longer the height multiplier.** `Theme.Metrics.keyAreaHeight(for:)` sums the bands the layout actually draws; the old `keyHeight * rowCount` agrees with the grid on every layout whose bands are equal, which is every preset and every fixture, so a build that kept it would pass the whole suite and be wrong on every keyboard a user builds — the extension would ask the host for a height the grid does not fill, leaving a strip of host app under the keys or clipping the space bar. `CustomLayoutTests.testTheHostHeightMatchesWhatTheGridDraws` carries a fourth `mixed` layout with the action row at the range ceiling and the space row at its floor for exactly that reason; the three equal-band layouts beside it cannot fail. `heightBias` is unaffected: ±3 cancels whatever the bases are. **The two new keys are `decodeIfPresent ?? keyHeight`, and the fallback is the migration.** Every shipped build wrote one `keyHeight` and no row heights; decoding them as required throws and drops a tuned layout back to the default on the next launch, and defaulting them to `Theme.Metrics.keyHeight` silently reshapes a Compact keyboard's action and space rows to 43pt. A missing key means "this row matched the letters", because that is the only keyboard the old model could describe.
- **The space row is three points taller than a letter row, and the numbers row pays for it.** `KeyRow.heightBias` is that pair (`Theme.Metrics.rowHeightBias`): +3 on space, −3 on the digits — the optional number row, and the top row of 123 / `#+=` so tapping those planes cannot leave a gap above the space bar or grow the host. Letter rows stay at `keyHeight`. Growing space alone would cross the 368 pt cliff; shrinking digits alone would collect leftover height between backspace and space, which is the GeometryReader trap below. `CustomLayoutTests.testTheNumbersRowPaysForTheTallerSpaceRow` fails if either side moves by itself.
- **The keyboard's total height is capped by the screen-context fingerprint, not by taste, and the cap binds today.** The shipped layout's *tallest* form sits under the 368 pt cliff on an iPhone 17 Pro (3 pt came back when the reserved progress slot went) and the measured cliff is between 368 and 370, past which the frame fingerprint stops telling two conversations apart. Letter keys at 43 pt and 12 pt row gaps were paid for by shrinking the banner and the top inset, not by growing the total. Before adding a row, growing the banner or raising the default key height, read the swept table in `FrameReduction.Band.maximumOwnUI` and re-run `Bar/screen-context/harness/run-fingerprint.sh` with `OWN_UI_POINTS` set to the new total. A layout the *user* builds may exceed it — that is their choice and costs only their screen context — but the shipped default may not, and **the rail belongs to the build rather than to the user**. `LayoutValidator` used to raise a `costsScreenContext` warning the moment `Theme.Metrics.totalHeight(for:)` passed the ceiling, on the "offered rather than taken" principle the globe refusal is written under; that was wrong here and the warning is deleted. The two are not the same shape: a refusal names something the user can do instead, and "screen context may miss a conversation switch" names nothing they can act on while reporting a choice they made a second earlier on purpose — so the editor carried a permanent amber row above the keyboard for every user who liked tall keys. `LayoutValidator.screenContextHeightLimit` survives as the constant two tests fail the build against (`CustomLayoutTests.testTheShippedLayoutStillFitsUnderTheFingerprintCliff` and `NumbersSymbolsLayoutTests`), read off `FrameReduction.Band.maximumOwnUI` rather than restated so the next sweep moves both together. The same change made `KeyboardGeometry.ownUIHeightFraction` take a `layout:` — it published the *default* height for every keyboard, so a Roomy grid with the number row on covered 0.55 of the screen while claiming 0.43, leaving about 120pt of our own keys inside the band.
- **A key that draws several states has to say several things, and the microphone key said one.** `KeyView`'s accessibility label came from `KeyCap`, which is a value and cannot know a recording is running, so the label read "Record" whether the microphone was idle, live or finishing — the whole distinction `DictationKeyState` exists to draw was a red cap, a glyph and a caption, all of them silent. The label now comes from `DictationKeyState.accessibilityLabel` ("Record", "Pause recording") and the state from `accessibilityValue` ("Recording", "Recording, 12 seconds left"), which is the right split: a button's label is what a tap does, and a countdown is not that. The bar's copy of the control takes the same two strings through `edgeButton`'s `spokenLabel`/`value`, keeping its `bar-dictation` identifier fixed — two surfaces describing one control differently is D8 with a live microphone as the stake. The general rule this is the second instance of: **when a control gains states, its accessibility surface has to gain them too**, and `KeyView.disabledHint` exists because "Type something first" was being read out over a live recording.
- **The two states the banner was up for most no longer draw it, and they no longer reserve a row either.** A model call is a sweep on the control that started it (`KeyActivity.working`). A recording is a compact waveform on the microphone (`KeyActivity.recording`), only while `isDictating`. `totalHeight` is banner (when shown) + suggestion + keys; deleting the reserved slot shrinks banner-on by 3 pt and banner-off by 24 pt. `bannerHeight` is **58**, paid down from 69 so the letter keys could grow. Title plus two lines of detail still fit. `FrameReduction.Band.maximumOwnUI` is `368/874` and 368 is a measured cliff, so a row that is added has to be paid for by a row that shrinks. Do not grow keys to spend the reclaimed space. What is left presenting is a live reading, a refusal, a failure and an answer nothing could apply. `KeyView.CapKind` gained a fifth case, `.record`, rather than `background` painting red over the brand cap — the same rule the enum was written under, that fill, glyph colour and depth recipe come from one answer. And the countdown that used to read `12s left` in the banner's tag survives as the microphone key's own caption (`DictationKeyState.recording(secondsLeft:)`), because a session that closes itself with no warning stops a recording mid-sentence.
- **`ActionBanner` is omitted while idle, and the host height follows it; the fingerprint crop does not.** The default "Type, or pick an action below" instruction is gone — the action row is the affordance — so `BannerState.isPresented` is false for `.hint` and true for a live reading, a refusal, a failure or an answer nothing could apply. A model call and a recording do not present it. `KeyboardViewController` asks the host for `totalHeight(for:showsBanner:)`. `KeyboardGeometry.ownUIHeightFraction` still reports the tallest form (`showsBanner: true`), which is the rule the old appearing-and-disappearing context strip broke: a band that moves mid-read retires the answer. The active action key in the row paints a **filled** brand cap from `BannerState.activeActionKey` so the user can see which of Reply / Fix / Rewrite / Dictate is live without reading the strip. It was a 14% brand wash, and on the warm-white AI caps that is a key which looks very slightly pink — a photograph of a live recording from a real device shows a microphone key indistinguishable at a glance from the four beside it. `KeyView.capKind` answers `.action` for an active key rather than `background` painting a tint over it, which is what keeps the file's own rule true: the fill, the glyph colour and the depth recipe all come from one switch, so an orange cap can never end up with a white cap's shadow or a white cap's graphite glyph. Two things moved with it. The pressed fill is chosen by `capKind` rather than by `spec.cap` — the two agreed for every shipped key until an active key started wearing orange, at which point a press on it would have darkened it like a letter instead of lightening it like the return key it now matches. And the microphone key is the one control this feature has: `press(.dictation)` is `toggleDictation()`, so it starts and stops — a tap while the last words are in flight is ignored, not a cancel. It is also the one key wearing a filled cap **at rest** — orange, so that turning red while recording means something — with `record.circle.fill` as its resting glyph and `pause.fill` while it runs. The cross-process pause protocol is deleted; a key that could start something it could not end would be a trap, and a key with an × as well as pause is a third mode nobody asked for. One cost is known and taken: `Theme.Brand.action` is 3.64:1 against `Text.onBrand`, which clears WCAG's large-text floor and not the 4.5:1 for body, and the caption under the glyph is 9pt — so on the one key that is lit at a time the *word* is below AA while the glyph, the fill and the position all still say which action it is. Darkening the cap far enough to clear 4.5 leaves a brown that is no longer this product's orange; if that trade is ever revisited, it is `Theme.Brand.action` that moves, and it moves for the return key and every primary button at the same time.
- **The action row is `KeyboardCustomization.cursorRow`, not a row of its own.** CopyClip, Fix, one-tap Rewrite and dictation ship in it as `.fill`, with a narrow gear in the true middle. Reply ships on `barTrailing`. Emoji is 1.0 units on the bottom row beside 123. **Emoji and the gear have traded seats twice**, and both times the cap colours went with the seats rather than the keys — `KeyView.capKind` answers `.letter` for whichever one holds the action row's centre and `.soft` for whichever sits beside `123`, so that centre is always warm white between two AI caps and the bottom-row key is always soft graphite. Both seats are 1.0 unit, `SlotWidth.minimumUnits`, the narrowest the model can describe, so neither key changes size when they trade. **Moving Emoji out of the action row takes away the only way out of its own grid, and nothing in the build says so.** `Overlay.showsLetterKeys` is false under an open panel; it used to hide the letter *and bottom* rows, while `showsActionRow` kept the action row. So while Emoji sat in the action row it was the exit — `KeyView.label` turns it into `ABC` / `אבג` while the grid is up — and `EmojiCategoryRow`'s own `אבג` key had been deleted as a duplicate of it. The trade put Emoji in a row the grid covered, stranding the user inside the grid with no key that closes it, in both orientations. `LayoutValidator` cannot see this (it looks for a repeat inside one row, not for a key that is present but covered), and neither can the landscape strip tests. **The fix is that a panel may no longer cover the bottom row at all**: `KeyboardView.panelCovers(rowID:)` is the one rule, it answers false for `RowID.bottom`, and `KeyboardView+Keys` draws that row outside the panel's stack. So an open grid sits above `123 | אבג | space | . | return`, which is the iOS arrangement, and no second `אבג` is needed anywhere. `EmojiModeTests.testAnOpenEmojiGridAlwaysHasAWayBack` holds it, and asserts on `panelCovers` rather than on `showsLetterKeys`, which is identical in the broken build.

- **The emoji grid's row count follows the height, and it was a constant that only suited one.** The panel lost the bottom row's 55pt when it stopped covering it, so the grid under the category strip is 110pt in portrait and **60pt in landscape** — five rows of a 60pt grid is a 12pt cell holding a 9pt emoji, and landscape was already the worst case at 18pt. `EmojiPanel.rowCount(forGridHeight:)` holds the *cell* steady instead, at a `minimumCellHeight` of 26pt clamped to `rowCountRange` 2...5: portrait takes 4, landscape 2, a number row or a tall `keyHeight` takes 5 back. Everything else in the panel is counted in multiples of that number — the blanks padding a section to a whole column, `leadsSection`, `trailsSection`, and the column count `category(atOffset:)` derives the tab highlight from — so `sections(recent:rowCount:)` has to be rebuilt when it changes (`.task(id: rows)`), and the grid draws at `sectionRowCount`, the count the cells in hand were actually built for, never the freshly measured one. `EmojiModeTests` asks every count in the range rather than one, because a build that is right at 4 and wrong at 2 is right in portrait and broken sideways. **The presets are where a seating change actually breaks**, because "Power" writes its own `cursorRow` and "AI first" its own `bottomRow` and neither inherits the default's: the same trade left Power with Emoji in both rows and AI first with the gear in both. `CustomLayoutTests.testNoActionAppearsInTwoRowsOfAnyPreset` and `testEveryPresetKeepsBothTradedKeys` ask all five. `barLeading` ships empty. There is deliberately no second row concept and no second height path: `rowCount` counts it, `Theme.Metrics.keyAreaHeight(for:)` measures it, and `KeyboardViewController` republishes the height from banner presence and `controller.$customization`. **`KeyboardView` draws it above the letter block**, even though the compiler still appends it last: the array order is what `[RowID.bottom]` lookups depend on, and the view is what the thumb sees. Dictation is *not* also in the bottom row, and `LayoutValidator` would not have caught it if it were — it warns about a duplicate action within a row, and those would have been in two. `KeyView` draws a caption under the glyph at 56 pt or wider and the glyph alone below, so the same action reads correctly in the six-way row and as a 1-unit key.
- **Whether a key draws its name is three answers folded into one, and `KeySpec.showsActionCaption(inRow:width:)` is where they meet.** The user's own switch (`SlotSpec.showsLabel`) first, then the position — the shipped action row keeps Emoji and Dictate as bare glyphs, because those two names are already known and CopyClip's clipboard mark is not — then `KeyView.captionMinimumWidth`, 56 pt, below which a word truncates to two letters. **Three things about it were each a defect first.** The width floor used to live inside `KeyView.actionLabel`, at the moment of drawing, which made an explicit "show label" on a one-unit key a switch that silently did nothing; it is a *default*, so it is applied in the resolution and an explicit yes clears it — the same principle the `costsScreenContext` warning was deleted under, that a choice made a second ago on purpose is not a thing to report back as a problem. **Rewrite, Reply and Fix never read the flag at all**, calling `actionLabel` without the argument and leaning on the floor alone, which stayed invisible for exactly as long as the only row that disagreed was one nobody could edit — all six read it now, or the editor's switch would work on half the row. And **the editor's own tray carried a hand-copied second version of the position rule**, which is why the resolution is asked of the `KeySpec` rather than written at the call site. `SlotSpec.showsLabel` is `Bool?` for the reason `LayoutGeometry`'s two row heights are `decodeIfPresent`: nil is "whatever this key would do where it stands", which is the only keyboard the model before the switch could describe, and an untouched layout re-encodes without the key at all. The switch is a `Toggle` inside the inspector's ellipsis menu rather than a second control beside Fill, and that is arithmetic rather than taste — the shelf band is one fixed-height row, and on a 375 pt phone Fill, the menu, Remove and Close already claim about 310 of the 327 points inside the card. `LayoutEditorModel.drawsLabel(_:drawnWidth:)` takes the width the *canvas measured* rather than the slot's unit count, because whether units clear the floor depends on the phone and the language, and a switch reading "on" over a key with no word on it is the thing it exists to avoid.
- **A permanent `zIndex(1)` on the action row hid every top-row callout.** The balloon on `y` grows up into Reply / Fix / Rewrite, and that row was raised so a Fix / Rewrite / CopyClip stack could cover QWERTY. `KeyPopupLayer` keeps the letters above the resting action row (`2 > 1`) and climbs the action row only while Fix, Rewrite or CopyClip is held (`3 > 2`). The climb is `KeyView.onPopupLayerChange` on finger-down, not a preference: a preference was a frame late (the menu drew under QWERTY) and a letter press could raise the wrong block. `KeyView.zIndex(10)` still only orders neighbours in the same `HStack`; it cannot climb out of the letter block. The middle block of a pinned row is `zIndex(1)` so `m` sits above trailing delete. An active action key uses the same per-key raise so Reply's orange cap is not sliced by Fix. `AlternatesPopupTests.testALetterCalloutSitsAboveTheActionRow` is what fails the permanent raise.
- **The layout editor does not jiggle the editable rows.** `LayoutJiggle` rotated every key on the action row and the space row ±1.2° on a 140ms forever loop while `isEditingLayout` was true. Those are the only two rows the user can rearrange, so the page looked like those rows were flying. A rotation on a tight key grid overlaps the row above it (the space row onto ZXCVBNM). The red ✕ already marks what can move. Do not bring the home-screen wiggle back.
- **The keyboard's shape is a setting now, and the letters are deliberately not part of it.** `KeyboardCustomization` describes the suggestion bar's two ends, an optional number row, the whole bottom row, an optional extra row and the grid's geometry; the three letter rows stay exactly as `letterLayouts` has them, because they are extracted from Apple's own data for 64 languages and held to `Bar/layouts/` by `LayoutProvenanceTests` and `RenderedRowOrderTests`. That is also what makes *one* stored layout correct for all 64: the editable surface is the part that does not vary by language. Four things to keep true. **Customization is a source of `KeyRow`s, not a second rendering path** — `KeyboardLayout.rows(for:plane:showsGlobe:customization:)` compiles it into the same `KeySpec`/`KeyRow` the measured rows produce, so the width solver, `KeyView` and the left-to-right pinning never learn this feature exists, and `CustomLayoutTests.testTheDefaultCompilesToTodaysRows` is what holds the shipped default to rendering byte for byte what it did before. A compiled key's id is **two parts** — `char-,#a1b2c3d4` — because the prefix is what a test and VoiceOver address and the suffix is what stops two commas on one row being one `ForEach` identity; compare through `KeySpec.addressableID`, which is the bug that silently stopped the punctuation key drawing its long-press marks. The **globe is repaired in `KeyboardController.apply(_:)` and nowhere else**, because `needsInputModeSwitchKey` is a property of the device and the store cannot know it — a layout saved on a one-keyboard phone is missing nothing, and would otherwise become a trap the day a second is installed. **"Nowhere else" had to be made true twice, and the second time was a rail that fired at the wrong person.** `LayoutValidator` also carried a `missingGlobe` error, written when every preset placed the key. Commit `fd321e97` gave that slot to `.settings` in the default and in all four presets — deliberately, with a `SharedStore.replacingInternalGlobe` migration for layouts already stored — and left the rule behind. It could never fire where it was aimed, because `apply(_:)` inserts the key *before* it validates; the one surface that did see it was the layout editor, which from that commit refused Done on the shipped default for every user with two keyboards installed. The rule, the `LayoutIssue.missingGlobe` case, the refusal string and the now-unused `showsGlobe:` parameter on `issues`/`isUsable`/`canRemove` are all deleted: the compiler drops a globe slot the device does not need (`CustomLayoutCompiler`) and `apply` adds one it does, so no validator is in that path at all. It took eleven tests down with it and **crashed the unit bundle three times** — three fixtures force-unwrapped `.globe` out of `KeyboardCustomization.default`, and a nil `!` in a test kills the runner rather than failing (see `.claude/docs/testing.md`). One of the eleven, `testGlobeCannotBeRemovedWhenIOSRequiresIt`, *passed* throughout: it removed a globe that was not there and then asserted the error it had not caused. And `Theme.Metrics.keyAreaHeight` used to hardcode four rows; it is now a function of the layout, and the extension republishes its height on `controller.$customization` as well as on the context strip. `LayoutValidator` is the counterpart to `OutputGuard` and `EditScope`: errors block Done, warnings do not, and a "this row is crowded" warning was written and deleted because a whole-key minimum width makes any row of more than twelve keys already over budget — it could never fire while reading like a rail.
