# Keyboard layout and right-to-left

- **`KeyboardLayout.rows` and `.columns` are pure functions of their arguments, and the grouping level is passed in rather than read.** The first version of grouped keys read `SharedStore.shared.storedGroupedLevel` inside `letters(for:)` and `columns(for:plane:)`, which quietly made the entire layout engine depend on global mutable state: the dial lives in the App Group, the simulator shares one, and anybody who had tried the feature left it on — at which point `RenderedRowOrderTests` and `LanguageCatalogueTests` measure a *grouped* keyboard and either fail or, worse, pass against one. That is the same shape as the `PersonalLanguageModel` trap in `.claude/rules/suggestion-bar.md`, where the suite taught the store its own vocabulary and then tested against it. Both functions take `grouping: GroupedKeys.Level = .off`, so every existing caller and every test keeps today's keyboard, and **`KeyboardView+Keys` is the only place that asks the controller what the user chose**. `GroupedKeysTests.testTheLayoutIsUngroupedUnlessAskedRegardlessOfTheStore` sets the dial to L1 and then asserts the default argument still draws one letter per cap, so it fails against the version that read the singleton.
- **A grouped key is a block of the keyboard it replaces, and both of its dimensions are load-bearing.** `GroupedKeys.plan` bands the **top two letter rows** into one drawn row of double-height keys and leaves the third — the one carrying shift and delete — grouping sideways as before. A banded key is a *column slice*: `q w` over `a s` is one key, drawn on two lines. Grouping sideways alone was the version that shipped first and it was half the feature and the wrong half — a key that is wider and no taller is a sliver, a thumb misses in both axes, and `q` and `a` sat two keys apart when they are millimetres apart on the glass. **Three invariants hold it together.** `KeyRow.heightUnits` is a multiplier, and the band is two key-heights *plus the row gap it swallowed*, so the keyboard is exactly the height it was and the 368pt screen-context cliff is untouched. A key's `span` is how many of the ungrouped keyboard's positions it covers, so a band adds up to the same ten columns its rows did — which is why `KeyboardLayout.columns` keeps its `max(10, needed)` floor now, where the row-at-a-time version had to skip it. Drawn width is `.share(1)`, not `.unit(span)`: a unit left the band short, and weighting the share by span left leftover columns on skinny keys. And a cap carries a **line break** between the two rows it merged; `GroupedKeys.letters(inCap:)` drops it, `KeySpec.identifier` turns it into a hyphen so a UI test can address the key, and nothing else in the package knows it is there. `GroupedKeys.supports` still **refuses any language whose letters are not single `Character`s**: `press` receives the cap string and nothing else, so the only route back to "which letters is this key" is splitting the cap, and a Devanagari key is a run of combining marks that is one `Character` — the same trap `LetterLayout.init(keys:)` exists for. English and Hebrew are the two this was measured on.
- **Four things about a grouped key are not obvious and each was a defect first.** **A grouped letter key is `.share(1)`, not `.share(span)` or `.unit(span)`**: a unit is a key width and knows nothing about the spacing beside it, so five two-unit keys came out two units short of the row they replaced and the band drew 27pt narrower than the keys under it, on a feature whose whole purpose is width. A share takes its proportion *of what the row actually has*, so the gutters land inside the keys. Weighting that share by `span` then left leftover columns — English `p`, Hebrew `ף` — on a skinny button beside a fat one; equal shares fill the row as equal buttons, and `span` is kept only so `columns` still adds up to ten. **A leftover one-letter group is folded into a neighbour** rather than drawn: two leftovers join first (`ך` with `ף`), otherwise the letter joins the side that does not put two Hebrew prefixes on one key. **A grouped cap is drawn one `Text` per letter, inside an `.leftToRight` stack**: as a single string, `קר` is one right-to-left run and bidi puts ר to the left of ק while the keys underneath have ק on the left — every Hebrew cap mirrored, in the one place `RenderedRowOrderTests` cannot see it, because the *row* would be right and only the cap reversed. **`isGroupedCap` is membership in the layout being drawn, not "does this cap hold several letters"**: `SlotAction.text` compiles to `.character(".com")`, so the shape test fed the `.com` key — and `,` `?` `!` `@` on any layout that had moved them — to the decoder as a keystroke. And **`supports` asks whether a letter fuses when doubled**, not whether a key is one `Character`: every InScript key is one, so Devanagari was accepted by a feature that destroys it, and a per-row check would not have been enough either, since a band joins a letter to the one *underneath* it. `KeySpec.groupedLetters` is what carries all of this: only the layout knows a cap is several letters rather than a word, and the drawing, the spelling to VoiceOver and the decoder all need to be told.
- **Banding gained English and cost Hebrew, and the exact opposite was predicted.** The study the design leaned on found the letter-to-key mapping worth under 0.5 points; measured here it moved English +1.8 to +4.4 and Hebrew −1.8 to −7.9, because English's second row is where its rare letters live (a band key is a common letter with ballast under it) while both of Hebrew's top rows are dense with its commonest. **Do not carry an English mapping result into Hebrew.** The numbers in `GroupedKeys.Level.measuredAccuracy` and in Settings are `Bar/grouped/results.json` and have to be re-earned by a sweep whenever the grouping changes; the harness measures the decoder assuming the thumb never misses, so it cannot see the target-size win that is the entire point, and every rate carries a ±2 spread. **Hebrew's grouping is still not plain adjacency**: `GroupedKeys.hebrewClitics` are kept off one another's keys, worth +7.0 points at thirteen keys, because plain grouping puts ב with ה and makes "in X" and "the X" one keystroke. Banding made that constraint *easier* — a band column is atomic, so a column holding two clitics would be unfixable, and Hebrew's band has none (ו over ע; ש, כ and ל each alone) while the other pairing of its rows has כ over ה. It stops being satisfiable below nine keys, where the row that keeps delete holds three clitics and gets two keys. **Hebrew is capped at L1** (`GroupedKeys.Level.hebrewCeiling`): L2 commits the wrong word about three times in ten, the dial is shared, and English keeps the stop the user picked. `KeyboardController.groupingLevel` is what clamps it; Settings says so when the dial is above the ceiling. All of it is measured (`Bar/grouped/`, `.claude/docs/grouped-keys-design.md`), and `Bar/grouped/harness/swift-check.sh` compiles the shipping Swift and requires it to agree with the Python that produced those numbers.

- **Every right-to-left keyboard rendered mirrored, and the row data was never the problem.** `UCKeyTranslate` returns letters in *physical key order*, which is already Apple's left-to-right screen order — Hebrew's `"קראטוןםפ"` draws `ק` leftmost exactly as stock iOS does. Reading that as *logical* order and setting `layoutDirection: .rightToLeft` on the row reversed six languages at once. `mirrorsRows` is deleted and every key row is pinned `.leftToRight`. **Nothing follows the language now, and the suggestion candidates were the last thing that did.** The bar's chrome was pinned first, after the emoji and AI buttons swapped sides mid-swipe; the three candidate slots kept mirroring for a while longer on the argument that words should read the way the language does, and they are targets a thumb learns, so the same slide that changes language moved the word out from under it. `RenderedRowOrderTests.assertCandidatesRunLeftToRight` measures that on screen, because `controller.suggestions` is in the same order either way and no test that reads it can see a reversal.
- **Two things were measured off Apple rather than guessed and both were surprises.** **Hebrew puts delete at the right end of the *top* row**, not the bottom, and iOS's Arabic is 11/11/9 where ours is macOS's 12/10/7. Delete follows the shape rather than the writing direction: a strictly shortest top row carries it, otherwise the bottom row does. Hebrew's 8/10/9 layout is currently the only top-row case; Arabic keeps delete on its bottom row.
- **Some alternates are marks rather than letters, and they carry their letter with them.** Hebrew's geresh U+05F3 and gershayim U+05F4 and Catalan's interpunt U+00B7 are not on any of the three planes and cannot be, because they belong inside a word: `צ׳יפס`, `צה״ל`, `col·legi`. They are `alternates` entries spelled **`צ׳`, `צ״`, `l·` — letter *and* mark** — because picking an alternate deletes the character the key already typed and retypes it, so a bare `׳` would eat the letter in front of it. Two traps in adding more of these. They **must not** go through `KeyboardLayout.alternates(_:)` or `latin(_:)`: both split a value per `Character`, and these marks are spacing punctuation rather than combining, so `"צ׳"` is two `Character`s and the helper turns one alternate into the letter plus a naked mark — the mirror of Devanagari's `"ँः"`, which fuses instead. And `LetterLayouts.hebrewMarks` is generated from `hebrewRows` rather than written out, so a row edit cannot leave a letter without its marks. `LanguageCatalogueTests.testEveryHebrewLetterOffersItsGereshAndGershayimOnALongPress` and `testCatalanCanTypeThePuntVolat` assert the exact list, because a non-empty list is exactly what the split version produces. **Persian's half-space is the one that also needed the view to change**: U+200C has no width and does not join, so `ی` and `ی‌` are the same picture and the popup offered what looked like one glyph twice. `KeyView.displayLabel` draws it as `␣` — نیم‌فاصله means half-space — and inserts the real character; nothing else in any layout is invisible, so that is a substitution rather than a labelling system, and `AlternatesPopupTests.testNoOtherAlternateIsDrawnAsSomethingElse` keeps it that way. **And every popup item needs a non-gesture route**, because these marks are on no plane: `KeyView.accessibilityActions` covers every key with alternates rather than the rewrite key alone, and it replays the press first, since the gesture's handler is delete-then-retype and a rotor action has no finger-down behind it to undo.
- **The sweep that found them, and the two it deliberately left.** `Bar/layouts/apple-layouts.json` drops punctuation on purpose, so asking "which marks can this language's own keyboard type that ours cannot" takes two sources, and both are worth re-running before adding a mark. A `UCKeyTranslate` sweep of every key code on base/shift/option keeping the *non*-letters gives what the macOS layout produces; `UIKeyboardNonstopPunctuationCharacters` in `InputMode_<tag>.plist` inside the simulator runtime gives Apple's own list of the marks that appear *inside* a word, which is the narrower and more useful question. That second key is what settled all three additions: `he` lists exactly `׳` and `״`, `fa` lists U+200C and nothing else, and ten Latin and Cyrillic languages list `’`. **Two gaps are still open on purpose.** Arabic and Persian harakat — the eight on Apple's shift layer — attach to any letter, so they are a plane rather than eight more items on twenty-eight keys, and no `InputMode` file asks for them. Hebrew's maqaf U+05BE and niqqud are on the macOS layout and on neither iOS's own Hebrew keyboard nor its nonstop list. Catalan's interpunt is the one addition *not* backed by an `InputMode` entry; it is there because `l·l` is a distinct sound and CLDR spells it, and it is worth knowing that it rests on a weaker source than the other two.
- **The popup is the only balloon a key with alternates draws, it waits 200ms, and it is centred on the key rather than on its own first item.** The press callout and the popup are two balloons in the same place drawing the same glyph, so a hold played as ח, a beat, then ח beside ח׳ — in Hebrew that was every letter, since every one carries a geresh. `showsCharacterCallout` is now `!hasAlternates`, so a key with a popup shows nothing until the popup, and a key without one keeps the callout as its only press feedback. That is why the wait collapsed from three numbers to one: 450ms was paid for by the callout filling it, and against a blank space above the key a long hold reads as a keyboard that has not noticed. **`KeyView.alternatesDelay` is never zero** — opening on finger-down puts the popup on screen for the length of every keystroke, which is exactly what showing Hebrew's two-item popup from the press looked like before it was pulled. The centring is a trap that predates all of it: `alternatesWidth` is centred on the key, so the point under a finger that never moved is half the overhang into the strip, which is the 0/1 boundary at two items and the middle of item 4 at nine. Lifting straight up therefore swapped the letter for an alternate nobody aimed at while the highlight said index 0. `KeyView.hasSlid` (6pt, against a 34pt item) is what makes "lifting without moving changes nothing" true, and `AlternatesPopupTests.testTheKeysOwnCentreIsNotTheFirstItemOfItsPopup` asserts `!= 0` rather than a number so no future width can make it quietly pass.
- **Delete is `.pinned`, not leftover share, and the row that holds it has no side inset.** `remainderShare` made English's delete 54pt and Hebrew's 34pt on the same phone, and an inset on Arabic's short bottom row pushed delete 59pt in from the edge. `KeyWidth.pinned` answers a width from the screen (ten reference columns, 1.5 units), `KeyboardView.rowView` draws pinned keys hard against the ends of the row, and the delete row's `sideInsetUnits` is always 0. `LanguageCatalogueTests.testDeleteKeepsTheSameWidthAndTrailingEdgeInEveryLanguageAndOnEveryPlane` rejects a regression. The letters between the pins may shrink on a crowded language.
- **The letter keys slide the way the strip already points, not the way a pager follows a finger.** A right swipe lights the code on the right of the space bar, so the new keys enter from the right (`SpaceSwipe.slideEdges`); content-follows-finger would bring in the left neighbour and fight the affordance. The space row itself does not slide, because the thumb is on it. Reduce Motion keeps the crossfade. `Theme.Motion.swipe` is the beat; the balloon and the sliding highlight on the strip are supporting continuity, not a second show. **The sliding letters live in a ZStack so two languages can overlap, and that ZStack is `fixedSize(vertical:)`.** Without it, GeometryReader leftover height collected between backspace and space, the space row was pushed into the bottom inset and clipped, and `.clipped()` on the same stack sliced the backspace row's shadow off. Do not clip that stack: the swipe is horizontal, and the 12pt row gap is where the key's contact shadow sits.
- **The space row ignores the language's column count.** `123`, punctuation and return are `.unit` multiples so the editor can resize them, but `widths(for:)` resolves that unit against `referenceColumns` (ten) whenever `row.id == RowID.bottom`. Feeding Arabic's twelve-column letter unit into the same row made return shrink and space grow while English kept the stock proportions. Return uses `functionKeyUnits` (1.5), exactly matching Backspace above it — one unit was too narrow, while the old 2.2 units made it the widest key. The space bar stays `.flexible` and absorbs the locked remainder. `LanguageCatalogueTests.testTheSpaceRowWidthsAreIdenticalInEveryLanguage` rejects a regression — it passes each language its own unit and still demands identical widths.
- **The bottom row's full stop is on all three planes, and the row of five marks above it is not a substitute.** It was letters-plane only, on the argument that the numbers plane already carries `. , ? ! '` on its punctuation row. True, and beside the point: the full stop is the one key a thumb finds without looking, so switching to numbers put the return key where it had been. It costs the space bar one unit on two planes. The ids do not collide because `punctuationKey(for:)` passes an explicit `punctuationKeyID` — that key answers to `punctuation` and the one above answers to `char-.` — and that explicit id is the *only* reason this was safe to do; drop it and the plane has two keys with one `ForEach` identity. The same rule lives in two places and both had to move: `KeyboardLayout.bottomRow` and `CustomLayoutCompiler.compile`. Pinning the plane switch and delete on those rows also freed the leftover they used to split, which had made them 94.5pt wide, so the five marks are declared `punctuationRowUnits` (1.5) and the row fills edge to edge instead of floating in the middle.
- **Emoji covers only the letter area; the action row stays put.** The Emoji key wears the same filled brand cap as the other four while its grid is open, because "this control is currently doing something" is one statement and the row should not draw it four ways and a fifth; the rule that `Theme.Brand` is reserved for the AI moments is about the glyph's tint *at rest*, where emoji is still neutral in both of its label states.  `KeyboardOverlay.emoji` is drawn inside the letter-key `ZStack`, not as a full-key-area panel. One-handed reach pins the emoji panel to the same `gridWidth` as the keys. The grid wears `Keys.background`, the same as the letters it replaced: `Keys.panel` is the warmer lift the banner uses, and painting it here left a cream rectangle inside a grey keyboard. AI and dictation used to cover everything and no longer do — see the rule below.
- **Nothing the action row does may cover the keys, and the refusals were the half that had not been converted.** Fix, Rewrite and Reply already reported in `ActionBanner` when they *could* run; every path where they could not fell back to a panel over every key row — `AIMenuPanel` for an empty field, `AIResultPanel(.needsScreenContext)` for Reply with no session, `DictationPanel` for a dictation session the app had never opened. Those are the states a new user meets first, so the keyboard hid itself exactly while somebody was learning it, and Fix on an empty field drew nothing at all. All four are `BannerState.blocked` now — a title, a sentence, and a remedy that is either Dismiss or the broadcast picker itself. `KeyboardOverlay` carries only the emoji cases, so `KeyboardView.coversFullKeyArea` and `fullKeyAreaPanel` are deleted rather than reduced, together with `PanelChrome`, `AIActionResultKind`, `ActionBanner.resultPanelIsOpen` and `resolve`'s `resultsShownElsewhere` — each of which existed only to stop a panel and the strip drawing one answer twice. **Three things were given up on purpose.** The broadcast picker's tap target went from 42pt to 32: `-[RPSystemBroadcastPickerView addBroadcastPickerButton]` insets its real `UIButton` 5pt on every edge, so the 42×42 chip a 48pt strip can afford leaves 32, against 52×52 in the panel — and the strip cannot grow to buy it back, because `Theme.Metrics.bannerHeight` is capped by the frame fingerprint. The dictation countdown survived as `12s left` in the tag for the last minute only, and the `עב ⟷ EN` badge did not, because the transcript beside it is already written in its own script. And the best-effort notice is an amber tag plus an accessibility label rather than a sentence. **Two traps in doing it.** `stopDictation`'s third guard clause was `overlay == .dictation`, and that clause was what let a *stopped* session be torn down: `dictation.$failure` clears `isDictating` and `pendingDictationInsert` before setting the reason, so deleting it outright would have made Dismiss on "Nothing to insert" return early and leave the sentence reappearing on every 10 Hz poll. It reads `!dictationFailure.isEmpty`. And `AIMenuPanel.isAvailable` / `.hasRunnableAction` were never panel code — `SuggestionBar` reads them to decide whether its own controls are lit, which is D8 — so they moved to `AIAction` before the panel was deleted. `SlotAction.aiMenu` went with the menu it opened; "Power" and "AI first" carry real Reply keys instead, and `CustomLayoutTests.testEveryPresetReachesEveryAIAction` is what keeps every preset reaching everything.
- **Emoji mode spends no height, because there is none to spend, and every part of its shape is that constraint.** The keyboard's tallest form is 368pt against a cliff between 368 and 370, so a search row of its own would have come out of the grid — three rows of emoji instead of five. Four consequences, and none of them is a preference. The **suggestion bar becomes the search box** while either emoji state is up (`SuggestionBar.body` branches on `overlay.isEmoji`); the three candidates have nothing to say when nobody is typing a word. **`KeyboardOverlay.emojiSearch` is the mirror image of `.emoji`**: the grid goes, the letters come back so there is an alphabet to type with, and the *action row* becomes the results strip — typing a query needs all three of query, keys and results on screen at once, and 368pt has room for exactly the bands that already exist. The grid **scrolls sideways in five fixed rows** rather than vertically per category, so every category is one strip and the tabs are shortcuts rather than steering. And the **category row carries no `אבג`** — the Emoji key in the action row wears the letters-plane label while the grid is open (`KeyView.label`, gated on `isEmojiOpen`), because two keys a thumb's width apart doing one job is what the row had before. `KeyboardOverlay.isEmoji` is what the cap and the bar's tint both read; a bare `== .emoji` makes both revert the moment search opens.
- **Each emoji section is padded to a whole number of columns, and that padding is load-bearing.** `EmojiPanel.sections` fills every category's tail with blank cells so a category boundary is always a column boundary, which lets `category(atOffset:cellWidth:in:)` name a column from the scroll offset. The obvious alternative — a geometry read of a category's *first* cell — goes silent the moment that category is wider than the screen, which most of them are. **A `sectionGap` (`Theme.Space.sm`) sits on the trailing column of every section that has another after it**, so two categories do not run into each other in the strip. It is padding, not a column: a tab still scrolls to the first emoji, and the empty Recent section at the front of a fresh install does not insert a gutter before Smileys. Two traps came out of this. `sections` must **not** be a computed property read from `body`: feeding `@State` from a preference rebuilt 1,870 interpolated ids sixty times a second while a finger moved; it is cached in `@State` and rebuilt only when the recents change, and it is `static` so tests can ask for it without a body evaluation. And a category tab scrolls to **the section's first cell** (`anchorID(forCategory:)`), never to the section: `ForEach(sections, id: \.id)` gives the loop its identity but puts no view on screen carrying the category's id, so `scrollTo("Food")` addressed nothing and every tab was silently dead while the row still drew and the highlight still moved. **The inverse also shipped: the strip moved and Recent stayed orange.** A GeometryReader on the `LazyHGrid` itself sees the viewport, so its offset stays 0 and `category(atOffset:)` keeps answering Recent. The orange tab is `selectedCategory`, set on tap immediately and from the visible cell sitting on the leading edge (`nearerTheLeadingEdge`), and `KeyStyleButton` is recreated when that changes (`.id("\(id)-\(isSelected)")`) because its press `@State` otherwise keeps the first `isSelected` it was given.
- **The emoji category row is ten shortcuts, not ten keys, and drawing them as keys is what made it unreadable.** `EmojiCategoryRow` gave every tab the full `KeyStyleButton` treatment — warm white card, contact line, ambient lift — at `HStack(spacing: 0)` with no horizontal padding at all, so on a 402pt phone eleven caps butted edge to edge and bled into both edges of the panel. **Spacing is not the fix, and the arithmetic is why**: the row spends 42pt on delete and spent 5 more on a hairline, leaving the ten tabs 35.5pt each, and matching the key rows above (`sideInset` 3, `keySpacing` 6 between twelve items) drops them to 28.3 — a 19pt glyph inside a shadowed 28pt card is more crowded, not less. The chrome goes instead: `KeyStyleButton.drawsCap` is false for a tab, so it is a bare glyph on the panel with 34pt to itself, and the row's only fill is the selected one. **Which then had to stop being a 14% wash, and that is the half of this worth remembering.** Tinting a card 14% works because the card carries the signal and the tint only colours it; take the cards away and the tint is alone, and a `Brand.solid` glyph on a 14% `Brand.solid` wash measures **2.3:1 in orange** (2.58 pink, 2.59 blue) — under the 3:1 non-text floor and *below the 5.18:1 the nine unselected tabs get for free*, so the one tab that has to stand out was the least legible thing in the row. Monochrome is worse than it looks in that table: its selected wash and `pressWash` land 8 units apart in light and invert in dark, so a press read as a selection. The selected tab is `Theme.Brand.action` under `Text.onBrand` now — 3.64 / 5.35 / 5.17, and 13.34 light and 4.80 dark in monochrome — tested *before* the press so re-tapping the current category does not strobe the pill away, with the glyph flip gated on `!isSelected` so it cannot put graphite on orange. This is the same mistake `KeyView.capKind` already records making, in the same words: "a 14% brand wash over whatever cap the key already had ... read as a slightly pink key". One measured caveat so nobody re-derives it: the pill's own edge against `Keys.background` is just under the 3:1 an edge wants in dark for pink and blue — `BrandPalette`'s published 4.46/3.03/3.14 are against `Surface.background`, which is not what this sits on. It is accepted rather than fixed, because the edge is not what picks the tab out: the white glyph inside is the strongest thing in the row by the measure that matters, and every other brand fill on this keyboard already makes the same trade. **Two things fell out.** The hairline between the flags tab and delete is deleted: it existed because the two were the same object with different fills, and with the tabs bare, delete being the row's one keycap says "this one edits your text" without a mark; its 5pt is now `Theme.Space.xs` of air in the same place. And **a capless button cannot answer a press by going pale, but neither of the two named colours that look right works**: a cap lightens from a cap, and a bare glyph has only the keyboard background under it — `Theme.Keys.functionPressed` is 0xFFFEFA against 0xE2E4E8, a pale cap on a pale field, and `Theme.Keys.card` is *the same colour* in light mode, so reaching for it fixes nothing where the problem is and loses contrast in the dark (0x2E3435 on 0x1E2122 is closer than the 0x54595B it would replace). `KeyStyleButton.pressWash` is `secondaryLabel` at 22% instead, the same idiom as `ruleTint`: derived from the label tint, it darkens the light field and lightens the dark one because the label does.
- **The emoji catalogue is generated, and two of the generator's filters are the difference between a grid and a grid full of dotted boxes.** `Scripts/generate-emoji-catalog.py` builds `Resources/EmojiCatalog.json` from Unicode's `emoji-test.txt` and CLDR's `annotations` *and* `annotationsDerived` for `en` and `he`. **`MAX_EMOJI_VERSION` is 15.0 because `Package.swift` floors at iOS 17.0**, which shipped Emoji 15.0; anything newer draws as tofu on a phone that has not been updated, which is a key that looks broken rather than one that is missing. Skin-tone sequences are dropped because the panel offers no tone picker, so they are unreachable and would be five sixths of the grid. CLDR strips U+FE0F from every `cp` attribute while `emoji-test.txt` keeps it, so lookups fold it away — without that, `❤️` finds no annotation and search works in English and dies in Hebrew. `EmojiCatalog.loadFailure` and `EmojiModeTests.testTheCatalogueLoadsOutOfTheResourceBundle` are what stand between a resource that failed to copy and a keyboard whose grid is silently empty.
- **Emoji search ranks rather than filters, and ranking is the whole feature.** Nearly every heart carries the keyword "heart" and nearly every one carries "לב", so a filter answers `heart` with 💘 and `לב` with 🥰. `EmojiSearch.score` is a four-rung ladder and each rung fixed something measured: an **exact keyword ties with a whole word of a name** because CLDR names 🚗 "automobile", so no name rung reaches it for `car` while "police car" and "tram car" do — ranking the keyword below the name buried the actual car under six vehicles; **`Match.coverage`** breaks that tie, since "car" is all of the keyword and 3 of "police car"'s 10 characters; and **the length tiebreak uses the name that matched, never the shortest across locales**, because taking the shortest compared an English query to a Hebrew name and answered `heart` with ♥️ ("קלף לב" is shorter than "לב אדום"). Recents are worth two rungs, bounded so a recent emoji never hijacks a query that names another outright. Measured over 29 English and Hebrew queries: 22 put the obvious answer first, 28 put it in the first five, and the strip shows about nine. **The known gap is Hebrew morphology** — matching is by whole word and prefix, so `בוכה` finds 😭 and `בכי`, the same root in another form, finds nothing; closing it needs a stemmer this package does not have.
- **Every key answers audibly, one line plays the sound, and both feedback switches are read at the press.** The keyboard played `1104` — iOS's `tock` — for letters, space and return and *nothing at all* for backspace, shift, the plane switch, globe, Settings, the cursor keys, the emoji key and the whole action row, so a held delete clicked once and then ran mute for two hundred characters. iOS ships three sounds and only three (`1104` tock, `1155` delete, `1156` modifier); a fourth means bundling an audio file, and none of them has a volume this keyboard can set. `KeyCap.clickSound` answers for every case and is deliberately **not optional**, so a new cap has to choose a sound rather than inherit silence, and `Feedback.keyClick` is called from exactly one line: the top of `KeyboardController.press(_:)`, above the emoji-search branch, because a key typing into that box is still a key. **Putting the call on the actions instead is wrong in both directions.** Too many: the accents popup replaces a letter by calling `deleteBackward()` and then `press(.character:)`, so a click owned by the delete makes one accent pick sound twice. Too few: the two paths that reach a key *without* `press` — the held-delete repeat in `KeyboardView+Keys` and the emoji panel's own delete button — called `deleteBackward()` directly and were silent. Both go through `press(.backspace)` now, which also fixed a delete repeat inside emoji search eating the user's message instead of the query, since `consumeForEmojiSearch` is reached from `press` alone. The two insertions with no `KeyCap` behind them, `insertEmoji` and `apply(_:)`, click for themselves. `Feedback.hapticsEnabled` and `soundEnabled` are computed off `SharedStore.storedHaptics`/`storedKeySounds` rather than filled once in `viewDidLoad` — the `storedAutocorrect` trap exactly, and worse here, because both switches live in the app while every press they gate happens in the extension, so an instance iOS kept alive went on clicking after the user turned the sound off. One more that fell out of the audit: the `.emoji` branch fired `Feedback.modifierPress()` and then called `show(_:)`, whose first line is another one, so that key buzzed twice for one tap. `KeyClickTests` and `FeedbackSettingsTests` hold all of it.
- **The punctuation key skips the single-mark callout.** Its long press *is* the strip of marks, so previewing a lone period for the hold delay looked like a two-step open. Letters keep the callout; punctuation opens the strip after a shorter 250ms threshold.
- **`Bar/layouts/stock-rendered-rows.json` is the committed photograph**, `capture-rendered.sh` retakes it, and `AIKeyboardUITests/RenderedRowOrderTests` measures the *rendered* key frames against it — a coverage or row-string test cannot see a reversal, because the string was always right.
- **The keyboard's total height is capped by the screen-context fingerprint, not by taste, and the cap binds today.** The shipped layout's *tallest* form is 368 pt on an iPhone 17 Pro and the measured cliff is between 368 and 370, past which the frame fingerprint stops telling two conversations apart. `Theme.Metrics.bannerHeight` is 72 so a refusal can show three lines without an ellipsis, paid for by a 36 pt suggestion bar and 40 pt keys, so the total stays at that cliff. Before adding a row, growing the banner or raising the default key height, read the swept table in `FrameReduction.Band.maximumOwnUI` and re-run `Bar/screen-context/harness/run-fingerprint.sh` with `OWN_UI_POINTS` set to the new total. A layout the *user* builds may exceed it — that is their choice and costs only their screen context — but the shipped default may not, and the choice is **offered rather than taken**: `LayoutValidator` raises a `costsScreenContext` warning the moment `Theme.Metrics.totalHeight(for:)` passes the ceiling, so the Problems list on the editor says so where the slider is. It reads the threshold off `FrameReduction.Band.maximumOwnUI` rather than restating it, so the next sweep moves both together. The same change made `KeyboardGeometry.ownUIHeightFraction` take a `layout:` — it published the *default* height for every keyboard, so a Roomy grid with the number row on covered 0.55 of the screen while claiming 0.43, leaving about 120pt of our own keys inside the band.
- **A key that draws several states has to say several things, and the microphone key said one.** `KeyView`'s accessibility label came from `KeyCap`, which is a value and cannot know a recording is running, so the label read "Record" whether the microphone was idle, live or finishing — the whole distinction `DictationKeyState` exists to draw was a red cap, a glyph and a caption, all of them silent. The label now comes from `DictationKeyState.accessibilityLabel` ("Record", "Pause recording") and the state from `accessibilityValue` ("Recording", "Recording, 12 seconds left"), which is the right split: a button's label is what a tap does, and a countdown is not that. The bar's copy of the control takes the same two strings through `edgeButton`'s `spokenLabel`/`value`, keeping its `bar-dictation` identifier fixed — two surfaces describing one control differently is D8 with a live microphone as the stake. The general rule this is the second instance of: **when a control gains states, its accessibility surface has to gain them too**, and `KeyView.disabledHint` exists because "Type something first" was being read out over a live recording.
- **The two states the banner was up for most no longer draw it, and the three points that replaced them came out of the banner rather than out of the total.** A model call is `WorkingProgressBar` — `Theme.Metrics.progressBarHeight` is 3, reserved in every state, so a call starting cannot move the three candidate slots under a thumb — and a live recording is the microphone key in record red. `bannerHeight` is therefore **69, not 72**: `FrameReduction.Band.maximumOwnUI` is `368/874` and 368 is a measured cliff, so a row that is added has to be paid for by a row that shrinks. The banner still fits a title and three lines of detail at 69. What is left presenting is a live reading, a refusal, a failure and an answer nothing could apply. `KeyView.CapKind` gained a fifth case, `.record`, rather than `background` painting red over the brand cap — the same rule the enum was written under, that fill, glyph colour and depth recipe come from one answer. And the countdown that used to read `12s left` in the banner's tag survives as the microphone key's own caption (`DictationKeyState.recording(secondsLeft:)`), because a session that closes itself with no warning stops a recording mid-sentence.
- **`ActionBanner` is omitted while idle, and the host height follows it; the fingerprint crop does not.** The default "Type, or pick an action below" instruction is gone — the action row is the affordance — so `BannerState.isPresented` is false for `.hint` and true for a live reading, a model call, a refusal or a recording. `KeyboardViewController` asks the host for `totalHeight(for:showsBanner:)`. `KeyboardGeometry.ownUIHeightFraction` still reports the tallest form (`showsBanner: true`), which is the rule the old appearing-and-disappearing context strip broke: a band that moves mid-read retires the answer. The active action key in the row paints a **filled** brand cap from `BannerState.activeActionKey` so the user can see which of Reply / Fix / Rewrite / Dictate is live without reading the strip. It was a 14% brand wash, and on the warm-white AI caps that is a key which looks very slightly pink — a photograph of a live recording from a real device shows a microphone key indistinguishable at a glance from the four beside it. `KeyView.capKind` answers `.action` for an active key rather than `background` painting a tint over it, which is what keeps the file's own rule true: the fill, the glyph colour and the depth recipe all come from one switch, so an orange cap can never end up with a white cap's shadow or a white cap's graphite glyph. Two things moved with it. The pressed fill is chosen by `capKind` rather than by `spec.cap` — the two agreed for every shipped key until an active key started wearing orange, at which point a press on it would have darkened it like a letter instead of lightening it like the return key it now matches. And the microphone key is the one control this feature has: `press(.dictation)` is `toggleDictation()`, so it starts and stops — a tap while the last words are in flight is ignored, not a cancel. It is also the one key wearing a filled cap **at rest** — orange, so that turning red while recording means something — with `record.circle.fill` as its resting glyph and `pause.fill` while it runs. The cross-process pause protocol is deleted; a key that could start something it could not end would be a trap, and a key with an × as well as pause is a third mode nobody asked for. One cost is known and taken: `Theme.Brand.action` is 3.64:1 against `Text.onBrand`, which clears WCAG's large-text floor and not the 4.5:1 for body, and the caption under the glyph is 9pt — so on the one key that is lit at a time the *word* is below AA while the glyph, the fill and the position all still say which action it is. Darkening the cap far enough to clear 4.5 leaves a brown that is no longer this product's orange; if that trade is ever revisited, it is `Theme.Brand.action` that moves, and it moves for the return key and every primary button at the same time.
- **The action row is `KeyboardCustomization.cursorRow`, not a row of its own.** Emoji, Reply, Fix, one-tap Rewrite and dictation ship in it, all `.fill`, and `barLeading`/`barTrailing` ship empty. There is deliberately no second row concept and no second height path: `rowCount` counts it, `Theme.Metrics.keyAreaHeight(for:)` measures it, and `KeyboardViewController` republishes the height from banner presence and `controller.$customization`. **`KeyboardView` draws it above the letter block**, even though the compiler still appends it last: the array order is what `[RowID.bottom]` lookups depend on, and the view is what the thumb sees. Dictation is *not* also in the bottom row, and `LayoutValidator` would not have caught it if it were — it warns about a duplicate action within a row, and those would have been in two. `KeyView` draws a caption under the glyph at 56 pt or wider and the glyph alone below, so the same action reads correctly in the five-way row and as a 1-unit key.
- **The keyboard's shape is a setting now, and the letters are deliberately not part of it.** `KeyboardCustomization` describes the suggestion bar's two ends, an optional number row, the whole bottom row, an optional extra row and the grid's geometry; the three letter rows stay exactly as `letterLayouts` has them, because they are extracted from Apple's own data for 64 languages and held to `Bar/layouts/` by `LayoutProvenanceTests` and `RenderedRowOrderTests`. That is also what makes *one* stored layout correct for all 64: the editable surface is the part that does not vary by language. Four things to keep true. **Customization is a source of `KeyRow`s, not a second rendering path** — `KeyboardLayout.rows(for:plane:showsGlobe:customization:)` compiles it into the same `KeySpec`/`KeyRow` the measured rows produce, so the width solver, `KeyView` and the left-to-right pinning never learn this feature exists, and `CustomLayoutTests.testTheDefaultCompilesToTodaysRows` is what holds the shipped default to rendering byte for byte what it did before. A compiled key's id is **two parts** — `char-,#a1b2c3d4` — because the prefix is what a test and VoiceOver address and the suffix is what stops two commas on one row being one `ForEach` identity; compare through `KeySpec.addressableID`, which is the bug that silently stopped the punctuation key drawing its long-press marks. The **globe is repaired in `KeyboardController.apply(_:)` and nowhere else**, because `needsInputModeSwitchKey` is a property of the device and the store cannot know it — a layout saved on a one-keyboard phone is missing nothing, and would otherwise become a trap the day a second is installed. **"Nowhere else" had to be made true twice, and the second time was a rail that fired at the wrong person.** `LayoutValidator` also carried a `missingGlobe` error, written when every preset placed the key. Commit `fd321e97` gave that slot to `.settings` in the default and in all four presets — deliberately, with a `SharedStore.replacingInternalGlobe` migration for layouts already stored — and left the rule behind. It could never fire where it was aimed, because `apply(_:)` inserts the key *before* it validates; the one surface that did see it was the layout editor, which from that commit refused Done on the shipped default for every user with two keyboards installed. The rule, the `LayoutIssue.missingGlobe` case, the refusal string and the now-unused `showsGlobe:` parameter on `issues`/`isUsable`/`canRemove` are all deleted: the compiler drops a globe slot the device does not need (`CustomLayoutCompiler`) and `apply` adds one it does, so no validator is in that path at all. It took eleven tests down with it and **crashed the unit bundle three times** — three fixtures force-unwrapped `.globe` out of `KeyboardCustomization.default`, and a nil `!` in a test kills the runner rather than failing (see `.claude/docs/testing.md`). One of the eleven, `testGlobeCannotBeRemovedWhenIOSRequiresIt`, *passed* throughout: it removed a globe that was not there and then asserted the error it had not caused. And `Theme.Metrics.keyAreaHeight` used to hardcode four rows; it is now a function of the layout, and the extension republishes its height on `controller.$customization` as well as on the context strip. `LayoutValidator` is the counterpart to `OutputGuard` and `EditScope`: errors block Done, warnings do not, and a "this row is crowded" warning was written and deleted because a whole-key minimum width makes any row of more than twelve keys already over budget — it could never fire while reading like a rail.
